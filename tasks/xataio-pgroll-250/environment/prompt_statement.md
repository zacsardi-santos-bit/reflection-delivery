I've noticed that when I use the column-alteration migration operation to modify a column that already has a unique constraint, the uniqueness enforcement silently disappears. For example, if I change the type of a column that was previously unique, or if I add a check constraint, a foreign key, or a not-null requirement to a unique column, the resulting column no longer rejects duplicate values. This means data integrity is broken after the migration — rows that should have been rejected as duplicates are accepted instead. I'd expect the unique constraint to be carried forward and remain in effect both during the migration transition period (when both old and new schema versions coexist) and after the migration is fully complete.
