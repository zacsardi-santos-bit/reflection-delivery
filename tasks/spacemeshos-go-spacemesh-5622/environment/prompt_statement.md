I'm working on refactoring the peer-to-peer networking layer in a blockchain node codebase. Right now, making a request to another node requires passing in two callback functions — one for success and one for failure — which gets called asynchronously. This makes the code hard to follow and error propagation nearly impossible to get right. I want to simplify this so that sending a request to a peer is just a regular synchronous call that returns the response data and any error directly, like a normal Go function.

As part of this, the functions that fetch data from peers (things like getting the list of known malicious nodes, fetching layer data, and getting layer opinions) currently accept a whole list of peers and use callbacks internally. I want to change these so each one operates on a single peer and returns the result directly. The callers can then loop over peers themselves, which makes it much easier to handle partial failures — if one peer fails but others succeed, that's fine; if all peers fail, the error should be surfaced.

There's also a related issue with error handling in higher-level sync operations: when a downstream fetch fails (like fetching malfeasance proofs or ballot data), the error is currently swallowed and ignored. These failures should be returned to the caller so they can be handled properly.

On the activation transaction side, I'd also like the internal processing function to directly return a malfeasance proof when it detects a node submitting duplicate transactions for the same epoch, rather than only side-effecting. The outer handlers can then decide whether to broadcast the proof (when receiving via gossip) or just store it (when syncing), making the distinction between sync and gossip modes explicit and clean.
