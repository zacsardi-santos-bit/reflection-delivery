I'm working on the IoTeX blockchain codebase and running into an inconsistency with how legacy accounts handle nonces. When an account was created under the old protocol and has only ever received funds — never sent a transaction — the system internally reports its pending nonce as 1 rather than 0. This is because legacy accounts add 1 to the stored nonce, so a stored nonce of 0 becomes pending nonce 1. But under the newer account type, a fresh account legitimately starts with pending nonce 0.

I need the account type to gain a few new capabilities. First, it should be possible to identify whether an account is a "legacy fresh" account — one that is legacy type with a stored nonce of zero, meaning it has only ever received and never sent. Second, there should be a way to retrieve the nonce for such an account that treats it as if it were the newer zero-nonce type (returning 0 instead of 1). Third, there should be a method to actually convert such an account to the new zero-nonce type, which should only succeed when called with the adjusted nonce value of 0, and return whether the conversion took place.

Once these account-level primitives are in place, the block processing logic needs to use them so that legacy fresh accounts are automatically upgraded to the new type when a block is committed at or beyond the protocol upgrade height. The gas price validation in the action pool also needs updating to account for the new nonce semantics when the feature is active.

The end result should be that a legacy fresh account, after the protocol upgrade height, behaves identically to a brand-new account — it can send its first transaction with nonce 0, and its state is consistent whether stored in memory or on disk.
