I've noticed that when I create a table in the database, the response says 1 row was affected. That doesn't seem right — creating a table is a schema-level operation, not a data operation, so it shouldn't affect any rows. I'd expect the affected-rows count to be 0 for table creation, whether the request comes in via SQL or through the gRPC interface.

While looking into this, I also found a few related things that should be cleaned up. The function that translates an alter-table expression into a concrete request currently returns an optional result, treating a missing operation kind as a valid "no-op." It would be cleaner for it to return an error in that case and always produce the request directly, simplifying callers. Similarly, the function that prepares an insert request for a table currently requires a full schema reference to look up column types, even though that type information is already embedded in the incoming request itself — that dependency should be removed. Finally, the table alteration API would benefit from a way to pass extra context data through the call without modifying the fixed request structure, so that implementations can access, for example, the original expression that triggered the alter.

The test infrastructure for distributed instances also needs some attention: it should properly keep temporary directories alive for the full duration of tests and return a single structure that provides access to both the frontend and the individual datanodes.
