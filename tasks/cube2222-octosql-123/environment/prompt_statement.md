I'm working on the query optimizer's filter pushdown logic and I've found a bug: it's merging filter predicates into data source scans even when one side of the predicate is a complex expression — like a function call — over a column from that data source. Data sources can only filter on direct column references, so pushing down a predicate that wraps a column in a function call produces an incorrect query plan.

For example, if I have a predicate that applies a function to a local column and compares the result against a column from another source, the optimizer should leave that predicate as a separate filter, not push it down. Similarly, if both sides reference the same data source but one side goes through a function call, the predicate should stay in the filter layer. On the other hand, if a function's inputs come entirely from external sources and the other side of the predicate is a plain direct column from the data source, that should still be considered pushdown-able.

The fix needs to be applied in the part of the optimizer that checks whether a predicate can be moved into a data source, and also in the part that actually performs the move. The key insight is that only plain direct column references — not expressions derived from columns — should qualify as the data-source-local side of a comparison when deciding whether a predicate can be pushed down.
