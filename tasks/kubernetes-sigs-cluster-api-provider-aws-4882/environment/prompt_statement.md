I'm working on adding support for AWS edge infrastructure locations (like Local Zones) to our Kubernetes cluster provider. Right now, when a user includes subnets from both standard availability zones and edge locations in their cluster's network configuration, the system doesn't know how to treat them differently — it tries to use edge-zone subnets for core infrastructure resources that don't support them, and routing for private edge-zone subnets doesn't work correctly because they can't have their own NAT gateways.

I need the system to look up each subnet's zone type from AWS and record that information on the subnet objects. Based on that zone type, subnets in edge locations should be excluded from the results when selecting subnets for core infrastructure like load balancers, NAT gateways, and control plane nodes. There should also be a way to get all subnet IDs across all zone types when you do need to include edge subnets.

For routing, private subnets in edge zones should route traffic through the NAT gateway in their parent availability zone (or fall back to the first NAT gateway available). Public and private IPv4 subnets in edge locations should get routes to the internet and NAT gateways respectively, but IPv6 in edge zones is not supported and should produce a clear error.

When creating subnets in a managed VPC, edge-zone subnets should not get load balancer role tags, and attempting to create an IPv6 subnet in an edge zone should fail with an informative error. If zone type information cannot be retrieved for a subnet, the reconciliation should fail with an appropriate error message.
