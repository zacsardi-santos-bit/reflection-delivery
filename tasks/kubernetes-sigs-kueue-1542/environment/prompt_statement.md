I'm working with Kueue's wait-for-pods-ready feature. When a workload gets evicted because its pods didn't become ready within the timeout, it gets re-queued — but it's sorted in the scheduling queue using the time of eviction rather than when it was originally submitted. This means a workload that was running and got evicted can end up behind newer workloads that were submitted while it was running, even if those newer workloads arrived much later.

I'd like to add a configurable option within the pods-ready settings that lets operators choose which timestamp to use for ordering re-queued workloads: either the eviction timestamp (the current default behavior, where the workload is treated as if it arrived at the time of eviction) or the original creation timestamp (where the workload keeps its original priority position and is not penalized for having been evicted). The eviction-timestamp mode should remain the default so existing behavior is preserved.

When the creation-timestamp mode is active, a workload that was submitted earlier than a competing workload should be re-admitted first after eviction, even if the competing workload has been waiting in the queue since before the eviction occurred. This should work consistently in both the blocking and non-blocking pods-ready admission modes.
