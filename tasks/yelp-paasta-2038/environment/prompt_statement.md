I'm working on adding support for shared secrets in our service platform. Right now, all secrets are tied to a specific service, but we need a way to define secrets that can be referenced by any service without duplicating them. I want to introduce a "shared secret" concept with a distinct reference format so the system can tell them apart from regular service-scoped secrets.

Here's what I need: the secret reference detection and name extraction logic should work for both the existing format and the new shared format. When retrieving the hash of a shared secret, the lookup should use the shared service storage location rather than the individual service directory.

For managing secrets through the CLI, I'd like a new option that lets users create or update a shared secret without specifying a service name. The cluster list should still be required when working with shared secrets — if it's missing, the command should exit with an error. The confirmation output after adding a shared secret should reflect the correct reference format so users know how to use it in their service configuration.

For local development runs, the code that decrypts secret environment variables should handle the two types separately: service-specific secrets get decrypted using the service context, and shared secrets get decrypted using the shared service context. The results should be combined and returned together. I'd like the decryption logic for a single service to live in its own helper function so it can be reused cleanly for both cases. Any failure during decryption should still cause an early exit.
