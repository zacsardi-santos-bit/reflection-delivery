I'm running into an issue where users who log in via a browser session can't create scheduled tasks through our API. When the request comes from a session-authenticated user rather than a token-authenticated one, task creation either fails or produces a task with no authorization token attached — which means the task can never actually run. The task engine needs a token to execute jobs unattended, but we don't currently generate one when the request comes from a session.

To fix this properly, I also need the system to be able to look at a query script and figure out exactly what permissions it needs before running — so we can create a token with precisely the right access. For example, a query that writes data to a named bucket should result in a write permission scoped to that specific bucket (resolved by name to its actual ID and owning organization). Once we can compute required permissions from a query, we can automatically provision a correctly scoped authorization token at task creation time and persist it so it's retrievable later.

The end result should be that a session-authenticated POST to the task creation endpoint succeeds with a 201 response, the underlying task record has a valid token attached, and that token can be looked up by value via the authorization service.
