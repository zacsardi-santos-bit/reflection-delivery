I'm working on a network tracing tool and I'd like to add NAT detection to the per-hop data. When a probe is sent and an intermediate router sends back a time-exceeded error, that error message echoes back part of the original probe's transport layer, including the checksum. If a NAT device is on the path, it may rewrite that checksum — so what gets echoed back will differ from what was originally sent.

I want the tool to compare the expected checksum (what we calculated when building the probe) against the actual checksum that was echoed back in the router's error reply. Based on this comparison, each hop should be assigned a NAT detection status. For the first hop that responds, the comparison is straightforward: if the expected and actual checksums match, no NAT was detected; if they differ, NAT was detected. For hops beyond the first, rather than comparing against the probe's expected checksum, the comparison should be against the checksum echoed by the previous responding hop — this handles the case where a NATted checksum "carries forward" and becomes the new baseline for downstream hops.

Hops that receive no responses at all should be marked as not applicable for NAT detection. The status should only ever reflect the most recently received probe for that hop.

The NAT detection status for each hop should be tracked as part of the hop's state and be accessible through the hop data structure. There should be three possible states: NAT not detected, NAT detected, and not applicable (no response received). The logic for computing the NAT status from a given expected checksum, actual checksum, and optional previous-hop checksum should be encapsulated in a dedicated function.
