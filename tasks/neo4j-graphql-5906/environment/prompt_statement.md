I'm hitting a bug in the GraphQL-to-database query translation layer. When my schema has a relationship that points to an interface type (for example, a type with a field that can be one of several concrete node types), filtering on properties of that related interface-implementing node doesn't work correctly. The query comes back empty even when matching nodes clearly exist in the database, or it returns wrong results.

After some investigation, the problem seems to be that the code generating database queries reuses the same internal variable name for optional match count variables across different parts of the query, causing conflicts. When two or more parts of the query try to assign a value to the same named variable, the result is undefined or incorrect behavior.

The fix should make the generated queries use unique variable names across all optional match patterns, rather than deriving the name from the relationship name (which can repeat). As a result, filtering on a relationship to an interface type should correctly return nodes whose related entities match — whether they're of the first concrete type or the second — and return empty results when nothing matches. This also needs to work for list-type interface relationships with quantifiers.
