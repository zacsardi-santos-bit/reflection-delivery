I'm working on the multi-store commitment layer in our blockchain SDK and I've run into a problem with how proofs are structured. Right now, when someone queries a value with proof enabled, we only return a single-level proof that ties the key to its store's tree root. But that's not enough — light clients and relayers need a full proof chain that goes all the way from the individual key up to the overall multi-store commit hash. There's no way to verify the complete path with what we currently expose.

On top of that, the commitment store doesn't persist any metadata about which store hashes were committed at each version. This means if we restart or need to produce a historical proof, we can't look up the commit info for a past version — the information is simply gone.

I need to update the system so that queries with proof return two chained proof operations: one proving the key within its store's Merkle tree, and a second proving that store's root within the overall multi-store commitment. Each proof operation should be independently runnable, where feeding the output of the first into the second eventually yields the overall commit hash.

To support this, the commit store needs to persist commit metadata (version and per-store hashes) to a database on every commit, and it needs to expose a way to retrieve that metadata by version number. The commit store constructor should accept a database for this purpose. The per-tree commit operation should also return the committed version number alongside the hash. Commit metadata must be sorted consistently by store key to ensure deterministic hashing.
