## Description

When a federated GraphQL mutation fails on an upstream subgraph — with the upstream returning null for data along with one or more error objects — the federation gateway currently returns two errors to the client instead of one. The first error is a spurious internal message about a "missing required field," and the second is the actual upstream error. Only the second error is meaningful; the first is internal noise generated by the gateway's own schema validation when it encounters the null data.

## Expected Behavior

- When an upstream subgraph returns null data along with a non-empty errors list for a mutation, the gateway should forward only the upstream error(s) to the client.
- The internally-generated "missing required field" error should be suppressed when proper upstream errors are already present.
- The response data should remain absent (null) in the final response.

## Current Behavior

The gateway emits both:
1. An internal "missing required field" error (with a path pointing to the mutation field)
2. The actual upstream error message

This double error response is confusing and incorrect — it makes it look like there are two distinct problems when really the upstream service simply reported a single failure.

## Why This Matters

Developers debugging failed mutations get misleading error responses with duplicate or spurious errors. The fix should ensure that when an upstream subgraph explicitly signals failure via its errors array alongside null data, only those upstream errors are surfaced — not additional internal validation artifacts.
