I'm working on the SQL parser in our database system and I've noticed that pattern-matching expressions — the kind that use keyword-based pattern matching and regular-expression-style matching — are being stored in the AST as generic binary operators. This causes a problem because there's no way to represent the optional escape character that these expressions can carry. If someone writes a query with an escape clause in a pattern-matching expression, that information is just lost when the SQL is parsed.

There's also an issue with the PostgreSQL-specific operator symbols for pattern matching. Right now, when we parse these operator-style variants and then format the AST back to SQL, they come out as their keyword equivalents instead of preserving the original operator syntax. So the SQL doesn't round-trip cleanly.

I'd like to introduce dedicated AST node types for these pattern-matching expressions (the keyword-based ones for both case-sensitive and case-insensitive matching, as well as the regular-expression similarity operator). Each dedicated node should carry the left-hand expression, a flag indicating whether the match is negated, the pattern, and an optional escape character. The PostgreSQL-specific operator symbols should remain as distinct variants that preserve their original form during formatting. There's also a place in the SQL generator that creates binary operations from expression types — that mapping will need to be updated to use the new operator symbol variant rather than the old keyword-based one.
