I'm working on the managed ledger module and I've run into a problem with size-bounded reads on read-only cursors. When a consumer tries to do an asynchronous read that limits both the number of entries and the total byte size, it crashes with an unexpected runtime exception if the cursor is read-only. The crash happens because the size estimation code tries to access the currently active write ledger, which simply doesn't exist in a read-only context.

Beyond the crash, the estimation logic itself is hard to verify because it's buried inside the cursor implementation and can only be exercised through a full integration test with a real managed ledger. I'd like to extract it into a standalone utility class that can be tested directly with just a ledger metadata map, without spinning up a full managed ledger. The utility needs to handle several edge cases correctly: "earliest" and "latest" special positions, a missing active ledger ID (the read-only scenario), empty ledgers that should be skipped, tiny byte budgets that must still return at least one entry, an explicit cap on the maximum number of entries, and an immediate return of the cap when the byte budget is effectively unlimited. There's also a default entry size constant that needs to be made accessible for the fallback case when no entry size information is available.

Once the utility is in place, the read-only cursor's size-bounded async read should complete successfully, returning the correct number of requested entries.
