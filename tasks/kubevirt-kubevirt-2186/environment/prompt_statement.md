I'm working on KubeVirt's live migration support and I've found a couple of gaps I need to fix.

First, the migration eligibility check currently only looks at traditional persistent volume claim volumes — it completely ignores data volume sources. So if a virtual machine instance is using a data volume backed by non-shared storage, the system doesn't catch that during the validation phase, and migration attempts may appear to succeed initially but fail later. I need the validation to cover data volume sources the same way it covers persistent volume claims, so that VMs with non-shared data volume storage are immediately and clearly rejected as non-migratable.

Second, there's no way to override the hypervisor-level migration safety checks for situations where an administrator knows the environment is safe. For example, if a VM has a shared iSCSI filesystem volume, the hypervisor will refuse to migrate it because filesystem volumes can be unsafe for concurrent access — but there are valid scenarios where this should be allowed. I need a cluster-level configuration flag that, when set, will pass the appropriate "unsafe" flag to the hypervisor during migration, bypassing its safety checks.

As part of this work, the test utilities that create iSCSI persistent volumes and data volumes need to be updated. The iSCSI PV/PVC creation helpers should accept an explicit volume mode parameter (block or filesystem) instead of hardcoding block mode. Similarly, the data volume creation helper should accept an explicit access mode parameter. A new helper function is also needed to create an iSCSI persistent volume without an associated PVC, and a new container disk type representing an empty disk (formatted as a filesystem) needs to be supported in the iSCSI target pod setup.
