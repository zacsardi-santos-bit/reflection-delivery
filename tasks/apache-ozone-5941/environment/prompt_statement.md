We're seeing correctness problems with prefix access control operations in Ozone's high-availability setup. When an access control entry is added to a prefix that already has that entry, or when the same set of access controls is applied again via a "set" operation, the in-memory prefix tree doesn't get updated and the transaction log index stays stale. In HA mode this means followers replaying the log end up with a different state from the leader — the update ID doesn't match what the leader committed.

We also found that when the last access control entry is removed from a prefix, the prefix entry isn't always cleaned up from the metadata table and the in-memory prefix tree. The entry lingers even though there are no access controls left. Related to this, trying to remove an access control from a prefix that doesn't exist at all doesn't consistently return a "not found" response.

On top of that, the path validation isn't catching malformed prefix paths early enough. A prefix path without a trailing path delimiter should be rejected with a "prefix not found" status, and a path with an invalid structure (like consecutive delimiters) should be rejected with an "invalid path" status. Currently these cases slip through validation and cause failures further down.

The fix needs to ensure all three prefix ACL operations — add, remove, and set — always update the in-memory state and persist the correct transaction ID regardless of whether the ACL content changed. Removing the last ACL should delete the prefix entry entirely. The persistence layer also needs to correctly round-trip the object ID and update ID fields so that a prefix read back from storage is considered equal to what was originally written.
