I'm working on the Horizontal Pod Autoscaler controller and I need to improve how it handles and reports replica count normalization. Right now, when the autoscaler calculates that it needs more pods than the configured maximum allows, it isn't clearly distinguishing between two different limiting factors: the configured maximum replicas ceiling versus the built-in scale-up rate limiter. Both can cap the final count, but they mean different things operationally and should be reported with different reasons.

I'd like to extract the replica normalization logic into a standalone function that applies a clear set of rules and returns both the normalized count and the specific reason for any adjustment. The rules should handle these cases: the desired count is already within the acceptable range (no adjustment); the desired count is too low and needs to be raised to the minimum; the desired count is zero or below even when the minimum is configured as zero (in which case the absolute floor of one should apply); the desired count exceeds the configured maximum replicas and the maximum is the binding constraint; and the desired count exceeds the scale-up rate limit but the configured maximum is higher (so the rate limit is the binding constraint).

Additionally, when the system's metric-calculated desired count would naturally push above the configured maximum replicas, the controller should cap at that maximum and explicitly report the reason as the configured maximum being exceeded — not simply let it silently fall into a generic limiting case.
