I'm working with Apache Hudi and have a table whose schema uses standard Avro logical types — things like decimal numbers with precision and scale, calendar dates, times of day, UTC timestamps, local timestamps without timezone, fixed-size duration values, and UUIDs. When I try to write JSON records to this table, the converter either throws an unhelpful exception or silently produces incorrect Avro data.

I need the JSON-to-Avro converter to correctly handle all of these logical types. For each type it should accept the natural input formats — formatted strings like an ISO date or a time string, plain numeric values, or in some cases raw byte representations — and produce the proper Avro encoding. It should also validate inputs against the schema constraints: for example, a decimal value that exceeds the configured precision should be rejected with a clear error rather than silently truncated or misrepresented. Similarly, a timestamp string that includes a timezone marker when the field expects a local (timezone-free) time should be rejected, and a duration value supplied as a list with the wrong number of elements should also fail cleanly.

The error raised for invalid inputs should be a specific, named exception type so that callers can handle conversion failures explicitly rather than catching a generic runtime exception.
