I'm working on the Kubernetes operator for a security platform and I've run into a problem with secret lifecycle management. When the main custom resource is deleted, Kubernetes automatically garbage-collects all secrets that have an owner reference pointing to it. This is the correct behavior for most secrets, but it's causing issues for the database password secret — if that secret gets deleted along with the custom resource, operators can't re-attach the existing database when recreating the instance.

I need to introduce a flexible ownership tracking mechanism for the secret reconciliator. Specifically, it should support two strategies: one that sets owner references on secrets (current behavior, causing cascading deletion), and one that only sets a managed-by label without adding an owner reference (allowing secrets to survive resource deletion). The decision of which strategy to use should be made when creating the reconciliator.

The ownership determination logic should work as follows: a secret is considered "managed" if it either has an owner reference to the Central resource OR has the correct managed-by label. A secret with neither should be left untouched. An owner reference should be treated as a stronger signal of managed status than the label — so if a secret has an owner reference but no label, it should still be considered managed regardless of strategy.

The database password secret specifically needs to use the label-only strategy so it persists after the custom resource is deleted, while other secrets (TLS certs, admin password, scanner database passwords) should continue using the owner-reference strategy.
