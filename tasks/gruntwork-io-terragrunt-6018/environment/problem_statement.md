## Description

When generating autoinclude configuration for infrastructure stacks, there is currently no distinction between the output filename used for individual units and the output filename used for composite stacks. Both types of component write their autogenerated dependency configuration to the same filename. This creates a correctness problem: a stack-level autoinclude file placed alongside a plain unit config is mistakenly picked up and merged into the unit's own configuration, even though that file was intended only for the stack component.

## Expected Behavior

- Autoinclude files generated for individual units should use one filename (the existing unit-level autoinclude filename).
- Autoinclude files generated for composite stacks should use a distinct filename (a new stack-level autoinclude filename).
- A function should be available to look up the correct filename given a component's kind ("unit" or "stack"). Calling it with any other value should produce a clear panic explaining which kinds are valid.
- When a unit's configuration is parsed, stack-level autoinclude files found in the same directory must be ignored and must not be merged into the unit's config.

## Why This Matters

Without this separation, stack dependency configuration can accidentally bleed into plain unit configs, causing incorrect inputs to be applied and breaking the isolation that the two-filename scheme is designed to guarantee. Adding a separate filename for stack autoincludes and enforcing that the unit merge path only considers the unit-level filename ensures each component type processes only the configuration intended for it.
