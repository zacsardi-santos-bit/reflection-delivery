I'm working on the distributed store component of our system that processes replicated schema commands — things like adding or deleting collections, managing tenants, updating shard status, and adding properties. There are two things I need to address.

First, the interface the store uses to communicate with the underlying persistence layer has a generic name that no longer fits its actual role. It handles physical index operations, so I'd like to rename it to something that clearly conveys it's an indexer rather than just a generic database handle. Every place in the codebase that references the old name needs to be updated to the new one.

Second, the command processor that handles all of these replicated operations needs to have clearly defined, predictable behavior for all error and success paths. Specifically: adding a collection should fail gracefully when the command is malformed or when the collection already exists; updating tenants should fail when the collection or tenant can't be found; deleting a collection should always succeed and remove it from the in-memory schema; and similar for all the other command types. The processor should also panic for unknown command types (to signal that an application upgrade is needed) and panic when it receives log data it can't decode. For non-schema log entries, it should return an empty structured response rather than a nil value. All errors should be wrapped with appropriate sentinel values so callers can distinguish bad-request failures from schema-conflict failures using standard error-checking patterns.
