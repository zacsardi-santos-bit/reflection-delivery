I'm hitting a bug in the linter rules that sort Python collection definitions. When I apply the auto-fix on a collection that has a trailing comma in an unusual position — like the comma sitting right before the closing bracket on the same line, or the comma sitting on its own line separated by blank lines or comments — the resulting fixed code is invalid Python. I end up with two consecutive commas after the last element, which breaks parsing.

This happens for both the rule that sorts module-level export lists and the one that sorts class slot declarations. It looks like the fixer isn't checking whether the text that comes after the sorted items already starts with a comma before deciding whether to append its own trailing comma. I'd like to see these trailing-comma edge cases handled correctly so that the auto-fix always produces valid, parseable output.
