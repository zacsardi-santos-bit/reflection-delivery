I'm working on refactoring the Profile Settings page in the Linode Manager. Right now, all user preferences — theme selection, email notifications, sensitive data masking, and type-to-confirm — are all handled together in one big component. I'd like to split these into four separate, self-contained components, each living in the Profile Settings folder and responsible for its own data fetching and rendering.

Each component should show a heading for its setting and a control (checkbox or radio buttons) that reflects the current preference from the backend. For example, the mask sensitive data section should show whether data is currently masked or visible, and the theme section should show which theme is selected (defaulting to the system theme if none is stored). The type-to-confirm setting should default to enabled when no preference has been set yet.

At the same time, wherever the full preferences object is being passed around just so a component can extract one field from it, I'd like to update those usages so only the specific preference value is passed or selected — not the whole object. This applies to both the sensitive data masking component and the sort order preference used in list components.
