I'd like to add a convenient way to race any future against a cancellation token using a fluent extension method, similar to how timeout adapters work on futures. Right now, whenever I want a future to respect cancellation I have to manually write the select-style racing logic inline, which is repetitive and clutters the code.

What I'm looking for is an extension trait on futures that adds two methods: one that takes a borrowed cancellation token, and one that takes an owned cancellation token. Both should return a new future whose output is an optional value — producing the inner value on normal completion, or a "cancelled" indicator when the token fires. The wrapper should have a specific fairness property: if both the inner future finishes and the token is cancelled at the same time, the inner future's result should win. Additionally, when the token is already cancelled before the future is first polled, it should resolve immediately without spurious wakeups; and when the token is cancelled while the future is pending, the runtime waker should be notified exactly once.
