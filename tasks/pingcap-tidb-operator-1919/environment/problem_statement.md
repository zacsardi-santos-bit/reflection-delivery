## Description

The Prometheus configuration generated by the operator for cluster monitoring has two related issues with how it resolves scrape targets and handles secure connections.

**Address resolution via pod DNS:** The current configuration uses a generic approach to extract the host from a pod's IP address and port annotation. This is unreliable when pods should be reached through their headless service DNS names rather than direct IP addresses. For the three core components, the scrape target address should instead be constructed using the pod name and cluster instance name to form a stable DNS address following the peer service naming convention, combining the pod name, cluster name, component type, and port into a DNS-resolvable hostname via the component's peer service.

**TLS scheme configuration:** When cluster-level TLS is enabled, Prometheus must scrape the relevant components over HTTPS with proper TLS certificates. Previously the scheme setting was not reliably reflected in the rendered config output. Now, when TLS is enabled:
- Two of the three components should be scraped with HTTPS and full certificate verification using the cluster client TLS certificate paths.
- The third component should remain on HTTP with certificate verification skipped, because it does not yet support HTTPS scraping.

When TLS is not enabled, all components should explicitly use HTTP.

## Expected Behavior

- All scrape job configurations for the three core components always include an explicit scheme (http or https).
- Address relabeling constructs targets using pod name and cluster instance label, producing a DNS-based address via the peer service for each component.
- With TLS enabled, two of the three components use HTTPS with proper CA, certificate, and key files and strict certificate verification; the third remains HTTP with certificate verification skipped.
- With TLS disabled, all three components use HTTP.

## Why This Matters

Without stable DNS-based target addresses, Prometheus may fail to reach components after IP changes. Without correct TLS scheme handling, encrypted clusters may be scraped over the wrong protocol, causing scrape failures or silent insecure connections.
