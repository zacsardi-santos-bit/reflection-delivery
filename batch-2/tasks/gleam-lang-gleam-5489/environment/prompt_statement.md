I'm chasing a codegen bug in the Gleam compiler's JavaScript backend around how pipelines get compiled. When a pipeline expression is used as a statement in a function body, meaning it isn't the final return value, the intermediate steps are being emitted as bare JS expressions with no trailing semicolon. That's fine until the next line in the function starts with a curly brace, at which point JavaScript's parser gets confused and treats the block as a continuation of the previous expression (like an argument to a call) instead of a fresh independent statement. So the compiled program silently does the wrong thing at runtime even though everything compiled clean, which is exactly the kind of bug that's miserable to track down.

What I want is for the JS emitter to terminate each intermediate pipeline step that's rendered as a statement with a semicolon, so the output is always syntactically unambiguous no matter what statement follows the pipeline. That includes the case where a debug-print keyword shows up as an intermediate pipeline step, oh and the generated call for that needs to end with a semicolon too. The relevant logic lives in the JavaScript expression generation code under `@compiler-core/src/javascript/expression.rs`. Basically if a pipeline is followed by a block expression on the next line, the two should read as separate statements rather than the block being swallowed into the pipeline. Just the intermediate steps need the semicolons; the final tail value keeps behaving as it does now.
