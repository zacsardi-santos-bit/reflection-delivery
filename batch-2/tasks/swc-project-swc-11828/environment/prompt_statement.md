I'm running into two related TypeScript annotation issues, one in the parser and one in the fast type-stripping tool, and they're both biting me in binary expression contexts.

First the parser. We've got the two keywords for annotating an expression's type, the one that widens a type (`as`) and the one that does satisfaction checking (`satisfies`), and they really should bind at the same operator precedence when parsing binary expressions. Right now they don't, the satisfaction keyword is getting parsed at a different binding strength than the widening one. So if I write something with addition, then multiplication, then a `satisfies` annotation, then a division, it should parse the same way as the equivalent `as` version, with the annotation grabbing the preceding subexpression and the trailing division applying to the whole annotated result. Works for `as`, broken for `satisfies`. I want them identical in all binary contexts.

Second, the fast-strip mode, the one that removes type annotations by deleting tokens from the source text instead of re-parsing. There's a silent correctness hazard here. If a type assertion annotates an expression that contains a lower-precedence binary operator than the operator that follows the annotation, deleting the annotation text re-groups the remaining operators and you get JavaScript with different runtime semantics. Neither the widening variant nor the satisfaction variant catches this today, they just emit broken code silently. Instead I want it to detect when removing an assertion would change binary operator grouping (precedence differences or right-associativity) and emit an unsupported-syntax error saying the annotation can't be safely removed in strip-only mode. This should cover both keywords. And the cases that are actually safe to strip should keep working with no errors, meaning same operator on both sides, a lower-precedence next operator, and equal-tier cross-operator when the annotated subexpression is already parenthesized. Without this fix, satisfaction-annotated code parses wrong and some strip cases produce semantically different output, both nasty to trace at runtime.
