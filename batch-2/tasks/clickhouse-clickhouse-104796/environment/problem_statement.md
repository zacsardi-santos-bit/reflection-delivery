I'm hitting a crash in ClickHouse whenever I use a dictionary "get or default" lookup and the key ends up nullable. Easiest repro is concatenating a nullable string column into the lookup key, which makes the whole key expression nullable, and then boom, undefined behavior. When I run with UBSan it flags a null pointer dereference inside the short-circuit evaluation path of the conditional function that merges the dictionary result with the supplied default value.

Digging in, the root cause is a type mismatch. When the key is nullable, the overall result type of the function becomes nullable too, but the dictionary attribute itself isn't nullable. During short-circuit evaluation the code uses that overall result type (the nullable variant) instead of the actual dictionary attribute type when it prepares the default values column. So it hands a non-nullable column to logic that treats it as nullable, and that's what triggers the null pointer access inside the conditional evaluation.

I want the fix so dictGetOrDefault style lookups handle nullable keys without crashing. The short-circuit path preparing defaults should use the dictionary attribute's own type, not the potentially-nullable result type. After that, these lookups should work correctly whether or not the key is nullable, and the default value computation shouldn't produce undefined behavior either way. This matters because it's easy to accidentally produce a nullable key and the crash is silent UB that's a pain to track down.
