I'm working on our command sandboxing layer and hit a real gap. Right now the policy only does an allowlist, so I can grant access to paths beyond the workspace, but I've got no way to explicitly deny a path even when it sits inside the workspace that's otherwise wide open. That's a security hole, credential files or secrets living in the project dir can't be protected from sandboxed commands. I want to add forbidden paths to the sandbox policy so callers can list paths that are always blocked for both reads and writes no matter what else the policy says.

A few things that matter here. If a path shows up in both the allowed list and the forbidden list, forbidden wins, always. Forbidden directories need to block recursively, so every nested file and subdir under them is off limits too. If a forbidden path doesn't exist yet, setup shouldn't blow up, it should degrade gracefully, and on platforms that support it we should also stop that path from being created in the first place. And when a forbidden path is a symlink, block both the symlink path and its resolved real target. This all has to behave the same on Linux, macOS, and Windows.

Oh and while I'm in here, the platform-specific code has synchronous path-resolution logic scattered around that I want to replace with one shared async utility for resolving real paths. The tricky part is missing files, so it should walk up the directory tree until it finds a real ancestor, resolve that, then reconstruct the full path back down. That way non-existent forbidden paths still resolve to something sensible for blocking. Wire the platform backends through this shared resolver so they all handle symlinks and missing paths consistently.
