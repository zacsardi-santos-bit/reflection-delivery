I'm working on the OpenLineage integration in Apache Airflow and I want to extend how hook-level SQL lineage gets tracked. Right now we only track asset-level lineage (which tables got read or written) at the task level, but when a SQL hook runs a bunch of individual queries during a task there's no way to see what actually ran. Some operators are basically a black box running arbitrary code, so hook-level tracking is the only visibility we get. What I want: for each individual SQL query a hook executes, emit a separate pair of lineage events (a start event plus a completion or failure one, where a successful task state gives completion events and a failed state gives failure events), linked back to the parent task as child jobs. Each event carries the SQL text, an external query ID if we've got one, and the data source namespace.

A few behaviors I care about. Extras with neither SQL text nor a job ID should just be silently skipped, no processing. Job names for the per-query events get numbered sequentially by how many processable queries there are, so skipped extras don't bump the counter. If SQL parsing fails for a query, fall back gracefully to an event with just the raw SQL text as a facet. If event emission itself fails, log a warning and keep going instead of raising. Per-query events should include a standard job type facet marking them as batch SQL queries running via Airflow, and an external query facet when both a query ID and a source namespace are present. Oh and when the hook collection yields SQL extras but no asset-based inputs or outputs, still emit the per-query events but don't return any asset-based lineage result from the hook extraction step.

I also need the lineage data container to support a merge operation so when both an operator extractor and hook-level collection produce results for the same task we can combine them, concatenating inputs and outputs and merging metadata facets with the current object's values winning on conflicts. And the function that parses SQL into lineage needs an option to skip acquiring a live database connection, since when we're processing hook-collected SQL after the fact we may not want or be able to open a new one.
