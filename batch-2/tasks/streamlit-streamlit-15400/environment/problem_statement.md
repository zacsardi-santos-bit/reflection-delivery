I'm trying to fix how our Streamlit server picks its bind address at startup. Right now `@lib/streamlit/web/server/server.py` always binds to the IPv4-only wildcard by default, even on machines that have IPv6, and that breaks dual-stack setups where a client tries the IPv6 loopback or otherwise connects over v6 and just can't reach the app unless someone manually reconfigures the address. Most modern OSes will happily listen on both families through one dual-stack socket, so I want us to take advantage of that automatically.

Here's the behavior I'm after. When the user hasn't explicitly set a bind address and the host reports IPv6 support, prefer the IPv6 wildcard address (which typically accepts both v4 and v6 connections). But if the system claims IPv6 support and the actual IPv6 bind blows up at runtime because the address family isn't really available, quietly fall back to the IPv4 wildcard instead of crashing. Important: a port conflict (address already in use) must not trigger that fallback, it should keep behaving like today (retry or exit depending on config). And if the user did explicitly configure the bind address, use it exactly as given, no auto-upgrades or rewrites.

Oh and there's a gap I keep hitting, if the underlying server fails to fully start, the process should actually detect that and exit with a specific error code rather than silently continuing along. Also I want the app-mode launch path to be updated to go through this new socket-binding logic directly instead of delegating the whole thing off to an external function call. This matters because folks running in Linux containers or cloud environments that default to IPv6 see their apps looking like they started fine but being totally unreachable, and doing the dual-family bind where it's supported just makes that class of problem disappear without any manual config.
