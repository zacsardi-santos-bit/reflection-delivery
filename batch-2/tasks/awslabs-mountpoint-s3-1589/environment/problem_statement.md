I'm cleaning up our filesystem integration tests, the ones that spin up a mock HTTP server to fake out S3 API responses so we can check that the filesystem layer handles and propagates errors correctly. Stuff like throttling and weird HTTP status codes. The annoying part is the mock server lib we use right now is synchronous, which sticks out like a sore thumb in an otherwise async codebase. Server startup is sync, registering mock responses is sync, but every actual S3 client op in these tests is async, so there's this constant friction and I worry about subtle test ordering issues too.

I want to swap that sync dependency out for a mock HTTP server library that's async-first from the ground up, so both starting the server and mounting mocks can use await. The new one should let me define request matchers (HTTP method, path, query params) and a response template in a fluent builder style, then mount those mocks onto the server asynchronously. I also need to be able to grab the server endpoint as a full URI string.

Mostly this is a straightforward dependency swap plus reworking the test helper that creates the mock server so it becomes async. The key thing is all the existing scenarios keep passing: throttling responses coming back as HTTP 503, unexpected error codes during lookup surfacing as HTTP 409, and unexpected error codes during reads showing up as HTTP 418. Those tests verify error propagation from S3 up through the filesystem, which is kind of critical for reliability, so I don't want to break any of them, just make the infra consistent with the async style everything else uses.
