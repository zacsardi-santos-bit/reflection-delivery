I'm hitting some rough edges on the file reload path in marimo and want to fix them together. Right now when a notebook file gets reloaded from disk, the reload swaps the entire internal app object for a freshly loaded one, so any code holding a reference to the cell manager, the notebook document, or the compiled cells before the reload ends up pointing at stale abandoned instances. That breaks anything that captured those references, like a session that grabbed the document before calling reload. I want reload to work in-place instead, so after a reload the cell manager is the same Python object it was before, the document is the same object, and the internal compiled cells dictionary is the same object updated in place, contents changing but identity staying stable. Oh and the document's version counter should advance monotonically after each reload, consistent with how normal edit-based version bumps work.

The other thing is reload currently returns just a set of changed cell IDs, which forces callers who need to broadcast a diff to connected consumers to reconstruct that diff from a snapshot taken before the reload, which is awkward and race-prone. I'd rather reload return both the transaction describing what changed and the set of changed cell IDs together as a single tuple, so callers get everything in one call without snapshotting beforehand.

Also the helper that builds the reload transaction should move into the file manager module (over in `@marimo/_server/file_manager.py` rather than the file change handler module), and it should take two cell managers, the previous state and the new state, as keyword arguments, returning the transaction and changed cell IDs together. Then the file change coordination layer should just use that return value directly instead of calling a separate diff function. Net result, anything holding a reference to the document before a reload finds that same object still valid and updated once reload finishes.
