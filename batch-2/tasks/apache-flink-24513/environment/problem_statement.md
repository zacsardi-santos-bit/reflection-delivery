I'm deep in the file-merging checkpointing code in Flink and hit two things that really need to go together. First, some of the state handle classes that the file-merging checkpoint system relies on are sitting in a checkpoint-internal package, but they're actually general state management concepts and belong alongside the other state handle types in the broader state management package hierarchy. Can you move them there and fix up every import reference across the codebase so nothing breaks?

The bigger one though: when an operator has no user state and file-merging is on, the snapshot currently returns an empty result, which is just wrong. Even stateless operators get managed checkpoint directories created for them, and if those directories never make it into the shared state registry they're invisible to the lifecycle and can get deleted way too early, before the checkpoint is even retired. So instead of nothing, I want an empty snapshot to still hand back a file-merging-aware state handle that acts as a placeholder and registers the operator's managed directories with the shared state registry. That means both the exclusive task-owned directory and the shared per-subtask directory. Those dirs should stick around on the filesystem as long as the checkpoint referencing them is active, and only get deleted once no retained/active checkpoint points at them anymore.

To make this work, the snapshot manager needs a way to expose directory state handles (not just the raw directory paths) per subtask and per scope, and the checkpoint storage location used for file-merging needs to be able to pass those handles down to the snapshot strategy so it can build the placeholder handle. Basically the goal is that stateless operators actually participate in the shared state registry lifecycle so their managed directories get cleaned up correctly when their checkpoint is discarded, instead of leaving directory management in an inconsistent state or wiping things prematurely.
