I'm adding support for Python's new PEP 751 standardized lock file format to Trivy, we already handle pip, Pipenv, Poetry, and uv but this cross-tool lock spec is new and nothing scans it yet, so anyone using it gets zero vuln coverage on their deps. I want a new analyzer that detects these lock files, parses them, and reports packages with correct direct vs indirect relationships.

On naming, the analyzer should match both the plain default lock filename and a variant with an optional single-segment identifier appended before the extension (think an environment- or platform-specific name). Anything with multiple identifier segments, or an empty identifier, must not match, so be careful the detection rejects those. Also recognize the companion `pyproject.toml` project config so it can sit alongside the lock file and tell us which packages are direct deps vs transitive ones.

For classification: packages listed as direct dependencies in `pyproject.toml` should come back as direct, and that includes ones defined in optional dependency groups (extras), oh and right now our existing pyproject.toml parsing doesn't pick up those optional groups at all so that needs fixing. Everything else is indirect (transitive). If the project itself shows up in the lock file, treat it as the root package. So when the lock file is parseable the analyzer returns the full package list: the root (if present), directs, and indirects, and scanning a repo containing one of these should surface vulns in its packages.

When the lock file is broken or unparseable, don't error out, just return an empty result. Also the lock file parser should accept a context parameter so it's consistent with the other parsers in the codebase.
