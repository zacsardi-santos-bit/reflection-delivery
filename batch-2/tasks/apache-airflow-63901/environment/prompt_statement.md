We use a CLI tool called Breeze to drive our CI builds and every time a job blows up in GitHub Actions someone has to reverse-engineer how to reproduce it locally, like which commit to check out, which image to build (Python version and platform), and the exact command plus flags that ran. It's tedious and people get it wrong.

I want to add a utility module that prints a "how to reproduce locally" block at the end of every Breeze CLI command run. It should show the exact git commands to fetch and check out the same code, handling both pull-request refs (with a friendly note mentioning the PR number in the fetch command) and plain commit SHAs, and then the full Breeze CLI invocation with all the options that were actually active.

The tricky part is which options to include. Anything explicitly set, whether from the command line or from an environment variable, should show up in the reproduction command, but options still sitting at their default value should be omitted so the output stays clean. Oh, and options set via env var should always be included even when they happen to equal the default. Also there's a small set of internal, side-effect-only params that should always be excluded no matter what, stuff used for debug resource tracking and similar operational options that don't change the actual build behavior.

The CLI group class should automatically trigger this output after each command finishes. And it should only fire when we're genuinely inside GitHub Actions, meaning both the CI indicator and the GitHub Actions indicator env vars confirm a CI context, not during local dev. Wire this so contributors debugging a failure can just copy the sequence straight out of the CI log.
