I'm cleaning up the graph vertex code in our flow execution engine and the base vertex class is doing way too much. All the logic for reading and converting template params (resolving file paths through a storage service, evaluating code fields, merging dict fields, converting ints and floats, turning table fields into dataframes, handling booleans, skipping hidden fields) is crammed inline into one long method, which makes it basically impossible to unit test any single piece.

I want all that parameter-processing logic pulled out into a dedicated standalone class living alongside the vertex module (accessible from the vertex base module in `@src/backend/base/langflow/graph/vertex/base.py`), constructable with just a vertex and a storage service. It should expose individual methods for each concern so I can test them in isolation, so things like processing edge-connected params, processing an individual file field, deciding whether a field should be skipped (hidden ones), processing non-list edge params, handling optional fields with defaults, and one method that processes all the template field params at once. That full-processing method needs to return both the parameter dict and a list of fields that need loading from the database.

Error handling matters here too, so unknown field types should raise a clear descriptive error, invalid table field values should raise a clear descriptive error, and if code field evaluation blows up it should fall back gracefully to the original value instead of crashing.

Oh and separately, one of the model component modules needs renaming to better reflect what it actually does, and every place that imports from the old name has to be updated to point at the new one. The renamed module should still export the same component class as before so nothing downstream breaks.

The whole point is making it easy to write targeted unit tests for each bit of parameter handling and leaving the vertex base class simpler to reason about.
