I'm cleaning up the Cassandra storage backend in Jaeger and there's this annoying intermediate hop I want gone. Right now when we convert between OTel traces and Cassandra-stored spans, the code bounces through Jaeger's protobuf model as a middleman, but the real storage target is Cassandra's own native schema, not protobuf. So the conversion layer ends up depending on a data model built for network transmission instead of the one we actually persist with, which is just extra complexity and an impedance mismatch. I want the conversion functions rewritten so they operate directly on the Cassandra-native data model types without routing through the protobuf representation first.

Part of this: the timestamp field in Cassandra log entries should be an integer type (epoch microseconds) rather than a time struct, since that's literally what Cassandra stores, and the conversion needs to correctly translate those integer microsecond timestamps into the nanosecond-based timestamps OTel span events use, both directions.

Also, over in the Cassandra data model package, a bunch of constants that identify value types (string, bool, 64-bit integer, 64-bit float, binary) plus the span reference types are currently unexported, so other packages in the storage layer can't reference them and end up duplicating the raw string values. I want those made publicly accessible so the rest of the storage layer can use them instead of repeating magic strings.

Oh and two edge cases while converting: when I turn OTel resource attributes into a Cassandra process record and there's no service name anywhere, use a defined default placeholder for the process service name rather than leaving it empty. And going the other way, converting tags from Cassandra back to OTel, if a tag has some unrecognized value type it shouldn't get silently dropped, produce a human-readable fallback string attribute instead.
