I'm hitting a gap in our stateful API testing tool, the part that infers dependencies between operations by looking at field names in request bodies and responses. It's solid at spotting foreign key relationships when fields are underscore-separated, so a field like `customer_id` gets correctly linked to the Customer resource, but it totally whiffs on camelCase, which is everywhere in JSON/REST APIs. So if a request body has something like `locationId`, the tool doesn't see the dependency and skips generating a stateful flow for it, and the same problem hits nested fields, a camelCase id buried inside a nested object gets ignored too.

What I want is for the FK field name inference to also recognize camelCase names that follow the convention of a resource name joined directly with an identifier-type suffix (think `locationId` mapping to Location, `id` being the suffix), extracting the resource name and figuring out whether it's a single or an array relationship. Plural variants where the name ends in the plural form of that identifier suffix (like `locationIds`) should be treated as array foreign keys.

Keep the false-positive avoidance we already have for snake_case, so plain identifier fields with no resource prefix, short words that just happen to end in an id-like suffix, and common English words should still produce no FK inference. And the existing underscore-separated support has to keep working exactly as it does now. When these FK fields show up inside nested objects in a request body, make sure the right input slot gets created linking the nested field to the target resource. This lives in the dependency inference engine that analyzes field names, and the win is consistent coverage so camelCase APIs get the same stateful test flows snake_case ones already get.
