I'm working on the Nx release config system and there's a gap I keep running into. Right now there's no explicit way to control whether we push git changes to a remote after versioning or changelog generation. The behavior is kind of opaque, sometimes it pushes and sometimes it doesn't depending on context, and users can't opt out through the schema. I want to add a push option (boolean) to the release git configuration that controls whether the release process pushes commits and tags to the remote.

It should default to off, but here's the nuance: it needs to automatically default to on when a hosting-platform release like a GitHub Release is configured, since creating that kind of release requires the commits and tags to already be on the remote. So push is a prerequisite there.

Also I need a validation step. If someone explicitly disables push while also having hosting-platform release creation enabled, the config resolution should fail early with a clear error code that flags the conflict between the disabled push and the enabled hosting release, rather than crashing or silently failing at runtime. And this conflict needs to be caught no matter which git config scope the push-disabled setting lives in, whether it's top-level (global), on the version step, or on the changelog step. All three scopes.

Two smaller things while I'm in here. When we log that we're pushing to a git remote, the message should include the actual remote name in quotes so it's obvious where changes are going. And the "matched projects" info message (the one that lists which projects matched a given filter) should only show once at the top of a release run instead of being repeated at each sub-step. Easiest way is to have the filtering function return the filter data rather than printing it directly inside itself, so the caller decides when and whether to display it. That's the whole ask, btw the motivation is folks who manage their own push in CI or want a dry-run-ish release without pushing need a supported way to turn it off.
