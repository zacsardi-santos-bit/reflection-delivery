I'm adding data catalog safety checks to our R2 CLI write commands and want your help wiring it up. Context: R2 buckets can have a data catalog feature turned on that tracks metadata about bucket contents, and certain writes (uploading objects, deleting objects, bulk uploads, and lifecycle rule changes) can leave that catalog in an inconsistent state if run blindly. Right now we don't warn anyone, so people can silently corrupt their catalog metadata, which is a pain to detect and recover from. I want the CLI to surface the risk before the op finishes.

Here's the flow I'm after. For single-object ops (upload and delete) and lifecycle rule add and set, the CLI should send a special catalog check header on the initial request to the API. If the API comes back signaling a conflict (meaning the bucket has data catalog enabled and the op could corrupt it), we prompt the user asking if they want to proceed anyway knowing the catalog might end up invalid. If yes, retry the same operation without the check header. If no, cancel it and print a clear message that it was cancelled.

For bulk uploads it's different since per-object checks across potentially thousands of objects isn't practical, so do the check once upfront before any work starts. If the user confirms, all the uploads run without sending the check header; if they decline, cancel the whole bulk operation. And in non-interactive environments like CI, the bulk upload should auto-proceed using a fallback "yes" answer so pipelines don't hang.

Also there's a force flag people can pass to skip all of this, it stops the check header from being sent and bypasses any prompting entirely, handy for automated pipelines where they already know what they're doing. Oh and lifecycle rule removal should not trigger any catalog check at all since removing rules can't corrupt the catalog, so leave those alone.
