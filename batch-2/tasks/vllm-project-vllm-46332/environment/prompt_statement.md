I'm hitting a nasty early-release bug in our KV cache transfer path for disaggregated prefill/decode inference, where the prefill side and decode side can run different numbers of tensor-parallel workers. When decode has more workers than prefill (say 4 prefill GPUs and 8 decode GPUs), each decode worker independently sends a "done" signal for the same cached blocks, but right now we mark the transfer complete after the very first signal lands and free the blocks while other decode workers are still reading them. That's causing memory corruption and silent data races, so I want the prefill side to actually count how many completion signals to expect (based on the decode-to-prefill worker ratio) and only mark a transfer done once all of them arrive. Duplicate signals after a transfer's already complete should be silently ignored, not retrigger another completion event, and signals for transfers that aren't live anymore should be ignored too.

On the consumer (decode) side, the completion notification needs to carry the consumer's worker count so the producer knows how many acknowledgments to expect, and that count has to be serialized into the actual sent payload, not just set locally. Also I need utility functions to compute the mapping between local and remote worker ranks when the two sides have different parallelism degrees, figuring out which remote rank corresponds to each local rank, and raising an error when the counts aren't integer multiples of each other. And I want a validation function that rejects KV head configurations that can't be split in a supported way across heterogeneous worker counts, with a clear error, while still allowing multi-head latent attention (MLA) configs regardless of any worker count mismatch. Net goal is making heterogeneous TP prefill/decode disaggregation safe to actually deploy.
