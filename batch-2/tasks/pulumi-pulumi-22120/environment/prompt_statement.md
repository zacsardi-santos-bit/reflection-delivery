I'm hitting a bug in how Pulumi serializes resource state into a snapshot (the checkpoint file). When an output value gets written out during serialization, it's always stored as a computed/unknown placeholder no matter what, so even outputs that have actually resolved to a real known value are getting flattened into that placeholder. That means the snapshot loses the real value, which is clearly wrong, the state file stops reflecting the actual shape of the resource data and downstream the engine ends up treating known values as unknown on later operations.

What I want is for the serialization path to actually distinguish the cases. If an output is truly unknown (not resolved yet) it should keep being stored as the computed placeholder since there's nothing meaningful to record. But if the output is known and has a resolved value, its actual inner value needs to be preserved in the snapshot instead of being dropped and replaced. And if a known output is also marked secret, it should be stored as an encrypted secret wrapping that inner value, not just discarded.

Oh and the round-trip has to hold: if I serialize a property value containing these output values and then deserialize it back, the result should match the expected inner shape, so unknown outputs come back as computed placeholders, known outputs come back as their resolved inner values, and known secret outputs come back as encrypted secrets. Please make the serialize and deserialize logic consistent so that round-trip works cleanly.
