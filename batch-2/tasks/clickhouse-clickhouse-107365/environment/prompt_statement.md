I'm hitting a bug with the sorting-prefix fill feature in ClickHouse. When I sort a query by a string column using a case-insensitive collation and layer range filling on a numeric column, strings that are equal under the collation (think 'a' and 'A' under a case-insensitive locale) get treated as separate fill groups instead of one. So the fill range gets applied independently to each distinct spelling and I get way more rows than I should.

Concrete repro: a table with four rows, two that are different letter-case spellings of the same letter (collation-equal, say lowercase 'a' with numeric value 1 and uppercase 'A' with numeric value 2), plus two rows using a distinct letter with values 1 and 3. Order by the string column with a case-insensitive collation and fill the numeric column from 1 to 4. I expect 6 rows out (one group for the collation-equal spellings, one group for 'b'), but I'm getting 9 because each spelling gets the full fill range applied on its own.

What I want is for strings that compare equal under the specified collation to form a single fill group. This has to hold for both small and large datasets, since the code takes different paths depending on row count (the boundary between the two internally changes the algorithm used to find group boundaries), and it needs to survive processing across multiple data blocks so no spurious fill rows show up when collation-equal values span chunk boundaries. Oh and the fix should work for both ascending and descending collated orderings. Right now the output row count isn't predictable and intermediate fill values end up duplicated for each distinct byte representation of what's logically one value under the collation, so that's the core thing to fix.
