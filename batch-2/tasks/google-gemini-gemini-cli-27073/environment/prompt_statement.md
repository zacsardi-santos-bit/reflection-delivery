I'm digging into the a2a-server package and hit two things that are tangled together, one security and one correctness, and I want them fixed as a pair.

First problem is that workspace settings get loaded and merged unconditionally. There's no check for whether the workspace directory is actually trusted before its settings get applied, which is bad because a malicious or untrusted workspace could craft a settings file that overrides sensitive policy-related paths (think admin policy paths, user policy paths, that kind of thing) and quietly change how the tool policy system behaves. I want to reuse the existing trust-checking utility from the core package to verify the workspace is trusted before merging anything in, and if it's not trusted the workspace settings should just be silently skipped. Also, even when a workspace is trusted, those sensitive path-related policy fields still shouldn't be overridable at the workspace level at all, they need to stay protected regardless.

Second, when we build the policy engine config for the a2a-server it's constructed inline right now and I'd rather it call the dedicated policy configuration builder function from the core package instead. That builder should get a unified settings object that merges the legacy tool allowlist format with the newer format, and when both are present the legacy format takes priority for the allowed tools list. Oh and in the default non-unrestricted (non-YOLO) mode the resulting config currently starts with an empty ruleset, which means no baseline access controls apply at all, so instead it should include a set of default rules loaded from the default policy files. In YOLO mode that doesn't matter but default mode really needs those baseline protections. Anyone opening a project shouldn't be able to silently rewrite the tool access policy, and default mode users deserve a real baseline.
