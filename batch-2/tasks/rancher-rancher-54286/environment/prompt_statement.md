I'm cleaning up the handler that syncs the system-upgrade-controller status condition on control plane objects in Rancher and I've got two things bugging me. First, the way it figures out whether the downstream cluster is reachable is fragile. Right now it does this indirect lookup through a separate provisioning cluster cache and reads a connectivity condition off that object, which can error out entirely if the cache lookup fails instead of just skipping, and honestly it's redundant since the connection state is already sitting right there on the control plane status object. I want to switch to reading that directly available agent connection flag on the control plane status and drop the dependency on the provisioning cluster cache completely.

Second thing, the handler fires a downstream API call on every single reconcile with zero rate-limiting, so during high reconcile churn it can flood downstream clusters. I want a per-object throttle so those downstream API calls happen at most once every 30 seconds per control plane object. When the window's still active, don't call the API, just schedule one delayed re-enqueue instead, and if a delayed re-enqueue is already pending for that object then skip scheduling another so we don't stack up redundant retries. When the window's expired, proceed normally and record the time of the new call. Oh and on a transient error, clear the throttle state so the next retry isn't artificially delayed. Also when a control plane object is being deleted, clean up its throttle state too.
