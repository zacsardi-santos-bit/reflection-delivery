I'm running into a nasty bug in the governance module's end-of-block proposal processing. After a chain upgrade removes a previously registered message type, any proposals that contained that type become undecodable, and when the block processor hits one of those stale proposals in either the active or inactive voting queue it does the wrong thing. Right now it either panics outright or just leaves the queue entry sitting there, which means the same broken proposal gets replayed on every single block and the chain effectively wedges. Not great.

The active queue case looks like it's trying to remove the entry using a field pulled off the undecodable proposal itself (which may well be nil since we couldn't decode it), instead of using the key that the queue iterator already handed back. And the inactive queue case seems to be missing the removal step entirely, so nothing ever gets cleaned up there.

What I want is for the end-of-block logic to handle undecodable proposals gracefully in both queues. For the active queue, mark the proposal as failed, remove it from the active queue using the iterator's returned key, and keep going without panicking or returning an error. For the inactive queue, remove the entry and continue without error too. Once an undecodable entry is cleaned up, the next block processing run should find nothing left in that queue position and complete normally, so a chain that's gone through one of these message-type-removing upgrades can just keep running and auto-clean whatever unprocessable proposals it stumbles across.
