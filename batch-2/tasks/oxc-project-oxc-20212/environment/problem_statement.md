I'm hitting a spot in our JS minifier where side-effect analysis is way too conservative around built-in globals. Right now if code reads from something like the math utility, an array or other built-in constructor, or a data serialization helper (JSON and friends), the minifier assumes it might have side effects, so it won't drop unused expressions and won't inline variables that only touch those globals. I want accessing any well-known built-in global identifier treated as fully side-effect-free, and reading a recognized property off one of those globals should be safe too, but unknown properties on them still need to be flagged as possibly side-effecting. It should go a couple levels deep as well, so a three-level chain on the base prototype object (Object.prototype.<well-known method>) counts as safe for the known prototype methods, while other three-level chains on random globals don't get that special pass.

Environment-specific stuff is different though. Browser APIs, debug utilities, other host-provided objects, those should only count as side-effect-free when the user has explicitly declared them as known globals, and anything genuinely unknown stays side-effecting even if it was declared. Basically match how the popular JS bundlers classify these same global identifiers.

While I'm in here, a few inlining follow-ups I'd expect to see. The built-in unique-symbol constructor (Symbol) should be treated as a pure call so it can get inlined. When a loop that copies function arguments into an array gets rewritten to spread syntax, the leftover intermediate variable should also be eliminated if it's only used once. And a conditional branch where both sides call the same function but pick a different argument should collapse to one call using logical OR. Without accurate classification the output stays bigger than it needs to be and doesn't line up with what people expect from modern tooling, so it's worth getting right.
