I've got a ClickHouse table with a JSON-typed column and a min/max skip index on it, and the index is basically doing nothing. When I run comparison queries filtering on that JSON column (greater-than, equal-to, or less-than), the EXPLAIN shows every granule being scanned instead of just the ones that could match, so the skip index is useless for JSON columns.

Digging into the JSON column type implementation, I found the method that's supposed to compute the min and max values over a range of rows just ignores the start and end row parameters. It always returns the first row's value for both min and max (or an empty value when the column is empty), so the per-granule min/max statistics recorded for the index come out wrong, which is why pruning never happens.

What I want is for the JSON column type to actually walk the given row range and compute the true minimum and maximum JSON values within it, respecting those start/end boundaries. Once that's fixed, a comparison query on a JSON column backed by a min/max skip index should only read the granules that could possibly hold matching rows. Concretely, if I've got a table with one row per granule and three distinct JSON values, then a greater-than, equal-to, or less-than filter against the middle value should read only 1 of the 3 granules, and the results still need to be correct, meaning only the rows that genuinely satisfy the filter come back. So this is both a correctness thing and a performance thing, since right now the index gives no benefit and could even hand back wrong data if it's trusted.
