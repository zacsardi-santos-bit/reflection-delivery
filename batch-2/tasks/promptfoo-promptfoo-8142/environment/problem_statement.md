I'm adding argument-level checks to our trajectory-based agent evals and right now we can confirm which tools got called but we've got no way to see what arguments went into them, which is a real gap because an agent can call the right tool with totally wrong params and we'd never catch it. I want a new assertion type that lets me say a specific tool was called with expected argument values. It should default to partial matching where the tool call's args just need to contain at least the key-value pairs I specify, and also support an exact mode where all args have to match precisely, oh and an inverse mode so I can assert a tool was NOT called with certain args. Tool names should match either by exact name or by glob-style pattern. A few edge cases matter: if the tool's found but no argument data was captured, the assertion should fail gracefully rather than blow up, and if I forget to include the argument data in the assertion value it should raise an informative error, and only valid matching modes should be accepted so an invalid mode gives a clear error too.

For any of this to work the trajectory step extraction has to start including the parsed arguments for each tool call pulled from the trace span. Args might live in span attributes a few different ways, as a JSON string in one attribute, as a plain object in another, or from MCP-specific attributes, so the extraction needs to handle all of those.

Also on the tracing side, when MCP tool calls get recorded into trace spans, the tool input should be serialized and stored as a trace attribute, but that input can carry sensitive stuff like passwords, API keys, or email addresses so those fields need to be automatically redacted before storage. And if the input is just a plain string that doesn't represent structured arguments, redact the whole value.
