I'm poking at the redundant dictionary key check rule and it handles plain string keys fine but falls over on f-string keys. You know the pattern it catches, where you write something like `if key in d and d[key]:`, testing membership and then indexing with the same key in one boolean expression. Works great when the key is a simple literal string, but when the key is an f-string it either misses the pattern completely or gets the fix safety wrong, and I want it fixed.

Here's the behavior I'm after. When the f-string key interpolates a non-literal expression (a variable, an object reference, anything whose string conversion could run side effects or return something different on a second evaluation), the rule should still flag it as redundant but mark the automatic fix as unsafe, since evaluating the f-string again might trigger a custom `__str__` or `__format__` and change the result. When the f-string only interpolates literal stuff like a numeric constant, flag it and keep the fix safe. And a plain f-string with no interpolation at all is safe too.

Oh and there's a nasty edge case: walrus operator expressions used as keys. Those carry an inline assignment, so any auto-fix would silently drop that assignment and change what the program does, so the rule just shouldn't fire at all when the key involves a walrus. No diagnostic, nothing.

This matters because f-strings are everywhere in Python and people build dict keys out of them constantly, so without this the linter either quietly misses real redundant checks or, worse, hands out an unsafe fix that suppresses side effects and subtly breaks things. I want accurate detection plus correct safe/unsafe classification.
