I'm adding response caching to a GraphQL gateway that fires outgoing requests over three protocols (plain HTTP, GraphQL, and gRPC), and right now there's no standard way to compute a unique id for a given request from its runtime parameters, so the cache can't tell when two requests are identical versus when they actually differ. I want a shared trait that all three request template types implement so the caching layer can call one method to get a cache key without caring which specific request type it's holding. The key needs to be a 64-bit unsigned integer (u64) derived deterministically from the rendered request parameters, and it should fold in everything that identifies a request: the target URL, any request headers (both the ones baked into the template and the ones coming from the request context), and the body content.

The core rule is that two requests that differ in any meaningful way (different URLs, different header values, or different body content) have to produce different keys, and two identical requests always land on the same key. For body-based keys specifically, the key should depend on the rendered value, not the template string itself, so if two different templates happen to render to the same output they map to the same key. Oh and each of the three implementations needs to be collision-resistant on similar-looking but distinct inputs, like if I swap a key name and its value inside a body object that should still come out as a different key. Concretely, HTTP templates give distinct keys when URL, headers, or body differ, GraphQL templates give distinct keys when the rendered query differs, and gRPC templates give distinct keys when the rendered body or URL differs. Getting this collision-free behavior right is the whole point since it's what makes it safe to serve a stored result when requests match and do a fresh network call when they don't.
