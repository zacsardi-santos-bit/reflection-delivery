I'm cleaning up Hudi's ZooKeeper-based distributed locking and it's driving me a little nuts. Right now if you want ZK locking you have to hand-configure a ZooKeeper path and a lock key even though that stuff is completely derivable from the table's base path and name, which you've already set up as part of standard Hudi config. It's redundant, error-prone, and couples the ZK setup to table knowledge the system should just handle on its own.

So I want a new lock provider that auto-derives the ZooKeeper coordination path from the table's base path plus table name, no explicit ZooKeeper-specific config needed. If someone's already got the table base path and table name set, this provider should just work, initialize fine, and let them acquire and release locks. But if the required table identity props are missing, I want it to fail fast right at construction with a clear argument validation error, not silently and not later during a lock operation.

Meanwhile the existing provider that takes an explicit ZooKeeper path and lock key should stick around for folks who want direct control, and it should keep working, but it also needs to throw a validation error at construction time when its required config is absent (same fail-fast behavior). Oh and both providers should share a common base type so lock management code can treat them interchangeably.

One more thing, the existing explicit-path provider currently accepts an external ZooKeeper client instance directly and I want to drop that. It should only need the standard configuration plus a storage configuration (which is allowed to be null), no passing in a client anymore.
