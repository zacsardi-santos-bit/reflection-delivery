I want to add a new lint rule to our JS analyzer that pushes people toward explicit comparisons when they're checking the length or size of a collection. Right now folks lean on JavaScript's truthiness coercion, so they write a bare truthy check on some array's `.length` to mean "non-empty," or a negated check on a map's `.size` to mean "empty," and it works but it hides what's actually being tested. I'd rather the linter flag these and steer toward a greater-than-zero comparison for the non-empty case and a strict equality to zero (`=== 0`) for the empty case. Way easier to read, no need to have JS truthiness rules memorized.

It shouldn't just catch the simple direct case though. I want it to also recognize double-negation patterns (`!!foo.length`), explicit boolean conversion wrapper calls where length or size is the sole argument (think `Boolean(foo.length)`), reversed zero comparisons where the literal comes first, and the "greater than or equal to 1" idiom, all of which should simplify down to the explicit form. And it needs to work for both `.length` and `.size`.

Every violation should come with an automatic fix. One gotcha: when the fix drops a negated expression right after a keyword with no separator, I need it to insert a space so the output stays syntactically valid, otherwise you get garbage like `return0`. Also don't flag the stuff that's already fine, so code that already uses an explicit comparison, uses the property in a non-boolean context, or has a number literal on the right-hand side of a logical OR (nullish/`||` fallback style) should be left alone.

Wire this into the JavaScript analyzer's lint rules alongside the other correctness-ish rules so it picks up length and size property reads used as implicit booleans.
