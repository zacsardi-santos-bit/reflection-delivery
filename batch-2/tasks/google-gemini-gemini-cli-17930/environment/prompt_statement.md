I'm reworking the hooks display in our CLI and the current setup bugs me, when someone runs the hooks command (or its panel subcommand) it just pushes a static message item into the main UI message feed, which tightly couples the hooks list to the message queue and gives no interactive or scrollable experience. I want the command action to instead return a dialog-style result that gets rendered separately from the conversation/message stream, more polished and self-contained like our other informational panels.

The dialog should show all configured hooks grouped by the event they're triggered on, and each entry needs to say whether it's enabled or disabled plus display the hook's source file, a security warning, and any relevant metadata like match conditions, execution order, and timeout settings. Oh and if a hook has no explicit name configured, fall back to using its command string as the display name.

It's gotta be keyboard-friendly too, Escape closes it and up/down arrows scroll through the list. When the list is longer than what fits in the visible area, show a scroll indicator at the bottom to signal there's more content below, and once the user scrolls down show one at the top as well, and hide each indicator when the user hits the corresponding boundary. Also the dialog should accept a configurable limit for how many entries are visible before scrolling kicks in. Users with lots of hooks need a readable navigable view, embedding it in the message stream just makes it awkward to review.
