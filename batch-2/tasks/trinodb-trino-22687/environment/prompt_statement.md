I'm pulling the Trino client's connection URI handling off Java's JDBC driver infrastructure and it's turning into a mess for anyone using the client outside a JDBC context. Right now when you parse or validate a connection URI it throws checked SQL/database-driver exceptions, which is dumb when you have nothing to do with drivers, so I want those to become plain unchecked runtime exceptions instead. No more try/catch boilerplate for exceptions that carry no meaning here.

Also the validation bails on the first bad property and throws immediately, so if someone has two misconfigured properties they only ever see one at a time and have to keep retrying. I want validation to collect all the errors and report them together in one aggregated message, a descriptive header line followed by each individual error on its own line.

On top of that I want a real builder API for constructing connection URIs programmatically. It needs a generic setter that takes any connection property descriptor plus a value, and named setter methods for each known connection property. And each connection property should be able to encode a typed value to its string form and decode a string back to the typed value, and that round-trip has to work for every property type.

Give me a static method on the connection properties registry that returns all known properties as a set so callers can enumerate them. Oh and the CLI query runner constructor should drop the network logging level parameter since that config lives in the connection properties system now. The CLI options class (the non-CLI-specific fields) should each be annotated with which connection property it maps to, and that mapping needs to be exhaustive and verifiable at runtime. Port 443 should still default to enabling SSL, but fix the SSL validation so it accounts for that default, SSL-related config should only be rejected when SSL is explicitly disabled, not when it's on via the port 443 implicit default. And when a property shows up both in the URL and in the properties argument, the error message should say clearly that it was provided in both places.
