I'm working on the Opik Python SDK and need to add a proper way to record pass/fail assertions coming out of automated test suites. Right now everything in the eval pipeline gets shoved through the generic feedback-scores endpoint as a numeric score, but suite assertions (stuff like "must mention Paris" or "must be polite") aren't floating-point quality metrics, they're binary checks, and they deserve their own path so they're queryable independently.

So first I want a new method on the main client that takes a batch of assertion results. Each entry carries at least a trace id, an assertion name, and a pass/fail status, plus optional fields for a failure reason and a per-item project name override. It should silently skip any entry whose status is invalid or missing, skip entries with an empty trace id, and if nothing valid is left over it shouldn't send anything at all.

Also the eval pipeline's result-logging function needs updating so score results tagged as suite assertions get auto-routed to this new method instead of the feedback-scores endpoint, while everything else (the normal numeric scores) keeps going through the existing path. Oh and anything that failed during the scoring step itself should be excluded from both paths entirely.

On the message-processing side I need a dedicated processor class that posts these assertion results to a new backend endpoint. The tricky bit is backward compat with older self-hosted backends: if that endpoint comes back 404 or 405 (server's too old to know about it), the processor should transparently fall back to the legacy feedback-scores path, converting each assertion into a score of 1.0 for pass or 0.0 for fail, and then it needs to remember that fallback choice for the rest of the session so it doesn't keep hammering the unsupported endpoint. For any other API error (server errors, etc.) it should just propagate the exception normally instead of swallowing it. This keeps things working against both new and old deployments.
