I'm hitting a nasty reliability bug running browser automation agents against remote cloud browsers. The WebSocket stays alive at the TCP level (keepalive fine) but the browser silently stops replying to commands, and the agent just freezes forever. Individual CDP requests wait on responses that never come, action handlers never return, and the agent stops emitting steps, so I get empty history traces with zero useful error info. No timeout, no error, nothing.

I want two layers of timeout protection. First, browser protocol commands sent to a remote browser need a per-request timeout so a silent server gets caught fast and raises a clear error saying which command timed out and how long we waited. Second, each tool action the agent runs needs a max runtime, and if the handler takes too long the system should return an error result naming the action that timed out instead of blocking.

Both timeouts should be configurable via environment variables with a sensible built-in fallback, and please handle bad config gracefully. Invalid values (empty strings, non-numeric input, zero, negative numbers, infinity, not-a-number) should silently fall back to the safe default rather than crashing on startup or silently disabling the protection. Oh and the default per-action timeout needs to be high enough that legitimately slow stuff like content extraction (can take up to 120 seconds) doesn't get prematurely killed, so pick a default with headroom above that.

Also the browser session layer needs updating so it actually uses the new timeout-protected browser protocol client when it makes CDP connections to remote browsers, otherwise the protection isn't live in production. The whole point is that a single unresponsive remote browser shouldn't stall the entire agent indefinitely with operators none the wiser, failures should surface quickly with informative errors and the agent can move on to the next step.
