I'm hitting two related bugs with the RTSP static source reader in MediaMTX (the code that pulls streams from a remote RTSP server). First problem: when I set a source URL that uses HTTP tunneling or WebSocket tunneling, the connection to the remote server isn't actually established with that transport, the remote server never sees the tunneling I asked for. This matters a lot because tons of real-world cameras and servers are only reachable through HTTP or WebSocket tunneling since firewalls block the standard RTSP ports, so right now I just can't ingest those streams. Second problem: even for totally plain, unencrypted RTSP, the reader seems to be applying security/encryption (TLS) settings when it shouldn't, which breaks those connections too, so even people with a working plain setup can hit surprise failures.

What I want is for the source to look at the URL scheme alone and set up the connection to match. If the scheme signals HTTP tunneling, use HTTP tunneling; if it signals WebSocket tunneling, use WebSocket tunneling; if it signals encryption (a secure variant), then the outgoing requests should use the secure scheme and TLS gets configured with the provided fingerprint; and if it's a plain non-secure variant, don't apply any TLS at all regardless of other settings. The whole set of variants should work off the scheme: plain, secure, HTTP-tunneled, secure HTTP-tunneled, WebSocket-tunneled, and secure WebSocket-tunneled. And the existing plain UDP and TCP transports need to keep working like before, don't regress those. Basically I shouldn't need any extra config beyond picking the right scheme in the URL.
