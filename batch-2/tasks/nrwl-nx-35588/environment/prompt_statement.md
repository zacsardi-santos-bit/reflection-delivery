We're finally killing off two ancient deprecated options in our Jest integration and I need two migration scripts so existing workspaces upgrade cleanly instead of breaking silently, since neither the generator nor the executor reads these anymore after the change.

First option is a generator flag that let people skip generating a test setup file. It's been superseded by an equivalent value in the modern setup-file selection option, so it shouldn't live in the generator schema anymore. I want the first migration to rewrite that old skip-setup default to its new equivalent when it was turned on, and just drop it entirely when it was off. It has to walk both the workspace config file and per-project config files, handle the flat and nested forms of generator defaults, keep unrelated generator entries intact, and clean up any empty objects left behind after the removal.

Second option is an executor-level property pointing at a test setup file by path. That info belongs inside the Jest config file itself now, under the standard Jest-native setup files array, not in the project executor options. So the second migration, for each project using the Jest executor with that deprecated option, reads the matching Jest config file and inserts the setup path into that array, expressed relative to Jest's rootDir. This one's fiddly, it needs to handle both CommonJS and ESM config formats, append to existing arrays without duplicating (recognizing when two paths are actually equivalent), deal with object spread operators including multiple spreads where last-wins, respect literal vs dynamic rootDir resolution, handle setup files inherited from workspace-level defaults, handle project configs that override the Jest config file, and the case where two targets share the same config. Oh and when things are too ambiguous or risky to automate safely, it should still strip the deprecated option off the project config but leave the Jest config file untouched, and return a follow-up callback so we can surface a warning to the user afterward.
