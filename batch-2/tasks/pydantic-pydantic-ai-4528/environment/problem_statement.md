I keep hitting a nasty bug with the OpenRouter gateway in our AI model client. Every so often, especially when routing to certain downstream providers, instead of a real completion or a clean error I get this confusing internal validation crash that tells me nothing about what actually went wrong. I dug into the raw responses causing it and there are two distinct shapes tripping us up (this is all tracked in issue #3994, shows up in real production traffic when providers time out or error out through OpenRouter).

First pattern: all the top-level standard fields come back null, so the list of generated choices, the model name, the response id, all null, and the actual completion data is tucked inside the provider metadata field as a nested dict. Right now that blows up with an unhandled validation failure. What I want is for the client to detect that the real response data lives inside the provider metadata, unwrap it, and treat it like a normal response. Oh and if the provider name inside that nested structure is null or missing, fall back to "unknown" instead of failing. But if there's a provider dict that just can't be read as a valid completion (no choices in it), then keeping the existing validation error is totally fine.

Second pattern: the response carries an error object with a numeric status code and a message, but again everything else is null. Instead of crashing with an internal validation error, I want the client to recognize that error object and raise a properly typed HTTP error carrying the numeric status code and the message text. Any extra fields hanging off the error object (like provider metadata) should just be ignored silently. And if the error field isn't even a dict (totally malformed), it's fine to keep the existing unexpected-model-behavior error path.

The OpenRouter handling lives in the gateway client code, so that's where these two checks need to go before the normal validation runs.
