I'm hitting a nasty data-loss bug in how Pulumi handles map properties with certain special keys. When a resource property map has nested map values whose keys start with our internal-use prefix, those keys get silently stripped out by the infra layer. The stripping is intentional at the outermost level of a resource's properties (that's where we filter internal bookkeeping keys), but it absolutely shouldn't happen inside nested maps. Providers and programs can have totally valid map entries whose keys just happen to start with that prefix, or even an empty string key, and right now those entries silently vanish during the resource lifecycle, so I'm getting subtle corruption.

What I want is for the internal-prefix filtering to be restricted to only the top level of a resource property map. Nested maps, meaning any map value that sits inside a top-level property, need to pass through completely intact with every key preserved regardless of prefix.

Same deal on the Go SDK side, the map-value unmarshaling path drops internal-prefix keys even when they show up in nested positions, so the round-trip loses data. Fix that too so nested keys and their values survive the round-trip losslessly.

Also I'd like a conformance test that validates this end to end across a real program, covering resource creation, invocations, and stack outputs, using a map that includes adversarial keys like empty strings, keys starting with the internal prefix, and keys containing special escape sequences. That way all the language SDKs get held to the same contract, since providers and programs may legitimately use maps whose keys look like internal keys and we can't keep silently dropping them.
