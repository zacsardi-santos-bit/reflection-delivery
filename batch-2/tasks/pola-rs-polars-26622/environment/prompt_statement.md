I'm hitting a type-propagation bug in Polars' SQL interface around array literals. When I write a query that builds an array out of typed elements, the resulting list column doesn't carry the element type I'd expect. Concretely, if I make an array of date literals the column comes back without the date type, and the same thing happens with time and timestamp literals, and with numeric values that have an explicit cast applied. The schema ends up wrong or the whole query just fails.

What I want is for array literals in SQL to correctly propagate the types of their elements into the resulting list column. That should cover the standard typed-literal syntax for dates, times, and timestamps (so a DATE '...' inside an array yields a list with a Date element type, TIME gives Time, and TIMESTAMP gives the corresponding datetime type). It also needs to handle casts, both the shorthand inline-cast form and the explicit keyword-based CAST(... AS ...) form, so the list element type matches the cast target's Polars type. Nested arrays with typed elements should work too, preserving element types through each level of nesting.

Oh and one more thing, if I accidentally mix incompatible types in a single array literal (say a date and a time together), I'd rather get an informative error that actually explains the type inconsistency than a silent failure or a wrongly-typed result. The fix lives in the SQL array literal handling code, wherever Polars turns those array constructor expressions into list literals. This matters because analytical queries often need inline lists of temporal or numeric values, like comparing against a set of known dates or building a reference list, and right now those queries either blow up or produce columns with wrong types that break things downstream. Getting this right brings the SQL behavior in line with what people expect from standard SQL.
