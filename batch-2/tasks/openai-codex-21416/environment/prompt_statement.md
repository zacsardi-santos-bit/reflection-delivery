I've got tool spec factories, the functions that tell the language model each tool's name, JSON schema, description, and parameters, all sitting off in a separate utilities crate while the actual handler impls live in the core crate, so every time I want to understand a tool I'm bouncing between two crates. I want to consolidate by moving those spec factories into the core crate as spec modules that live right alongside the existing handler modules in the handlers directory. So I need a shell spec module, an apply-patch spec module, an MCP resource spec module, and a test-sync spec module, each holding the factory functions that produce the correct tool spec structures for those tools. Oh and I also need brand-new spec modules for code-execution-mode tools since nothing like that exists in core yet, one for the execute operation which should use a grammar-based freeform tool definition constrained by a formal grammar, and a separate one for the wait operation which is a function-call tool with parameters for the cell identifier, yield time, max tokens, and a terminate flag. Then there's a hosted-tools spec module covering image generation, which takes an output format string and produces an image-generation spec carrying that format, plus web search. Each spec module should contain the factory functions that build the right structures, and the existing tests from the utilities crate need to move over (or get recreated) in the new core-crate locations so they run as part of core's test suite. The point is co-locating spec and handler so each tool's a cohesive unit, less cross-crate coupling, easier to add or tweak tools without jumping around, and it fills the gaps where code-execution and hosted tools had no spec factories in core before.
