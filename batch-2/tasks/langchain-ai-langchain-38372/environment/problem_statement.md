I'm hitting a wall with multi-turn conversations when I run the model API in stateless mode, meaning responses aren't stored server-side between turns. My flow replays the whole conversation history on each subsequent turn, but the API chokes because that history carries references to reasoning steps and generated images that only live in server-side storage, which just isn't there in stateless mode. So the replayed history points at IDs the server can't resolve and the request fails.

What I want is for the conversation history builder to know whether stateless mode is active and adjust what it emits. In stateless mode it should drop reasoning entries that are just references with no self-contained encrypted context, omit assistant message IDs the server can't look up, and skip bare image generation call references that have no actual image data attached. Items that do carry their own data should still go through, so reasoning that includes encrypted context and image generation results that carry the actual image stay in, but without the positional index metadata that isn't needed for replay. Tool call items need to be left completely intact, IDs and all, since those IDs are how tool responses get correlated back.

And in the default stateful mode everything keeps working exactly like it does today, so message IDs and reasoning blocks are preserved as before, nothing changes there. Basically I just need both modes handled correctly so stateless multi-turn stops being unreliable.
