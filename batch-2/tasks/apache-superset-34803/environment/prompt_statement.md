I'm cleaning up how Superset reacts when a dataset or metric ships a SQL template with busted syntax, like someone typing a natural language phrase inside a Jinja expression instead of real syntax. Right now that path returns a generic HTTP 400 and it just feels wrong since the request isn't structurally malformed, the input just can't be processed, so I want a 422 Unprocessable Entity instead for these template errors.

While I'm in there I want way better error detail. For user-caused problems (invalid syntax, references to variables that aren't defined, or security policy violations) the error should clearly say what kind of error it is, include the exception type name right in the message, and carry a snippet of the original template so the caller knows which one blew up. Server-side failures though, think out-of-memory or other resource exhaustion, should stay separate and surface as an internal server error (HTTP 500) with its own distinct message format, don't lump those in with the user errors.

Also I want a new standalone utility that validates template syntax without actually executing anything. It should take raw template strings and raise a descriptive error when the syntax is wrong. It should also handle a JSON blob that might have embedded template expressions inside SQL filter entries, so invalid JSON raises one kind of validation error and valid JSON that happens to contain a syntactically broken template raises a different validation error making clear it's the template that's the problem, not the JSON. Oh and passing nothing or an empty string should just be treated as valid, no error raised. This lets callers reject bad input early with actionable messages before execution ever happens.
