I've been chasing a nasty data-corruption bug in our record store's handling of uncommitted versionstamp data during bulk deletes. Here's the deal: when we save records inside a transaction, the system writes uncommitted versionstamp placeholders into a transaction-local buffer that only get resolved at commit time. That's fine on its own, but when a bulk deletion happens in the same transaction, whether that's deleting all records, deleting records matching a filter prefix, wiping out an entire store, disabling a version index, or dropping a version index entirely, those pending uncommitted mutations aren't being cancelled. So they still get committed to the database as if the records exist, leaving stale version-tracking data behind even though the records themselves are gone.

I want the fix so any of these bulk deletion paths also cancels the buffered uncommitted versionstamp writes for the affected key ranges. After deleting all records there should be no version info left for any record key, both committed and uncommitted. Deleting by a prefix filter should drop version data (including the pending mutations) for matching records while leaving other groups intact. Deleting an entire store should clear all its version data without touching other stores in the same transaction. Disabling or removing a version index needs to cancel any pending uncommitted mutations for that index so the underlying storage range comes back empty, while version data for records is still reachable through other means. Oh and aggregate version indexes, like the ones tracking the max version per group, have to get cleaned up for deleted groups too.

The behavior needs to hold both within the same transaction before commit and after commit, so looking up the version of a deleted record returns nothing and scanning any version index for the deleted range returns empty. Other records and stores not touched by the deletion must stay completely unaffected. Part of this is giving us a way to clear keys or key ranges from the transaction that also handles cancelling these buffered mutations, rather than only clearing from the underlying database transaction directly.
