I'm hitting a bug in our linter's rule that spots redundant duplicate type-checking, you know the pattern where you check whether some object is one type in one "or" branch and another type in a separate "or" branch, and the rule offers to auto-fix by merging both checks into a single call. The auto-fix works most of the time but it's corrupting certain expressions and I need it fixed.

The core problem is that the fix re-renders the checked expression through the internal AST representation instead of just keeping the original source text. So when the value being type-checked is an interpolated string (f-string) that uses escape sequences inside a format specifier, the fix mangles those escapes, and when the f-string embeds a lambda in its interpolation, the fix reformats or breaks the lambda entirely. Either way I end up with syntactically broken or semantically different code, which kills my trust in the whole thing. What I want is for the auto-fix to always preserve the original source text of the checked expression verbatim, no round-tripping through the representation.

Also there are two type-argument cases that misbehave. When the type argument is a tuple that uses starred unpacking (like spreading a variable that holds several types), the rule doesn't flatten those elements into the merged call correctly, so I get a wrong suggestion. And when one of the two calls passes an empty tuple as its type argument, the rule doesn't handle it gracefully and can produce invalid output. I want starred unpacking flattened properly into the merged result, and empty tuples handled so the fix stays valid.

Oh and parenthesized forms need to work too, whether it's the outer expression wrapped in parens or one of the individual operands, both should still be detected and fixed correctly.
