I'm building out an API client and I keep hitting a wall with response decoding, right now it only knows JSON, plain text, and binary blobs and I need a plugin system so devs can register their own decoders for other MIME types like proprietary binary serialization formats. The idea is a plugin declares which MIME types it handles and provides a decode function, so when the client gets a response it checks whether any registered plugin can handle that content type and if so hands decoding off to that plugin and returns its output as the response data. MIME matching needs to be case-insensitive and support wildcard patterns, so a pattern like "application/vnd.*+json" should match "application/vnd.api+json", and when multiple plugins could match the first registered one wins. Plugins that don't have a response body handler should just get skipped gracefully rather than blowing up.

There's also this related bug where a server returns a response with no content-type header at all and the client behaves unpredictably, so I want it to default to treating those as plain text, both for resolving which plugin decoder to use and for parsing the MIME type used in the response display. To make this work the buffer decoding function needs to become async and accept an optional plugin handler, and the request-sending (execution) function needs to accept and forward the list of active plugins when it dispatches requests. Also I need a couple new utility helpers, one for resolving the content type with that plain-text fallback baked in, and one for finding the right plugin handler given a MIME type. The whole point is that folks working with APIs that return binary or custom-encoded data shouldn't have to decode stuff themselves outside the client and lose the integrated pipeline, and the missing content-type case shouldn't silently fail anymore.
