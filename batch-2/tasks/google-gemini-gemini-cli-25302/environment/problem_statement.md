I'm building out a system that runs locally-defined subagents and I've hit a gap in the protocol layer, there's currently no way to run a local subagent and watch its progress (thinking steps, tool calls, lifecycle boundaries) through the same streaming event interface every other agent type uses. So locally-defined subagents can't compose with the rest of the infra or get monitored in a uniform way, and I want to fix that.

What I need is a session class that wraps a local executor and translates its activity callbacks into structured typed agent events. It should let callers subscribe to an event stream, send input, grab the final result, and cancel mid-flight. Input can come two ways: as config updates that get buffered until a message is sent, or as a direct message. Multiple config updates should accumulate and merge with the next message, and that merged config must not carry forward into later interactions. Also if a message has no text content, don't include a query field in what gets passed to the executor.

For the translation, map the executor's raw activity types onto standard events: thoughts become message events carrying thought content, tool call starts become tool request events, tool call ends become tool response events, and errors become non-fatal error events with an internal status. Unknown activity types should produce nothing. The executor's terminate/stream-termination modes map to standard end reasons on the final lifecycle event: successful completion to "completed", timeout to a time-exceeded reason, turn limit to a turn-exceeded reason, abort to "aborted", and error conditions to "failed". Each stream gets a distinct identifier and every event in that stream (start, activities, end) shares it, with start and end emitted exactly once per stream even under errors. Sequential interactions after a stream completes should each spin up a fresh stream with its own lifecycle and id.

Couple more things: there's an optional raw activity callback provided at construction time that fires with the unprocessed activity data before translation so callers can inspect or forward original events. Abort should resolve the result promise (not reject) with an empty outcome. Calling the result accessor before any input is sent should throw a descriptive error, and trying to send a new message while a stream's still running should throw rather than silently queue. Oh and multiple subscribers should be able to watch the same stream at once and each unsubscribe independently. The result accessor otherwise gives back the raw executor output once execution completes and rejects appropriately when the executor fails.
