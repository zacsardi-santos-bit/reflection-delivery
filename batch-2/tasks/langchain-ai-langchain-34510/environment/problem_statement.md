I'm hardening the deserialization path for cloud AI model configs against SSRF, since right now if someone hands us a serialized payload for a cloud model that carries a custom endpoint or base URL param, it just gets passed straight through when the config loads and the model client happily fires requests at whatever URL was baked in, including internal cloud metadata endpoints that leak credentials. So what I want is a built-in class-specific validation layer in the load system that runs automatically during deserialization, before we ever try to import or instantiate the target class. It's gotta cover all the known class paths and legacy aliases for the affected integrations, both the original serialized IDs and the resolved import path variants, because an attacker could reach for either form to sneak past the check. The really important bit: this protection has to fire even when the caller passes no general-purpose validator at all, it can't be something you opt out of just by omitting a validator. When a payload contains one of these dangerous URL-override params, I want the deserialization rejected outright with an error that names the offending parameter(s) and calls out the SSRF risk clearly so whoever's debugging knows what happened. Also I need the existing general validator callback to keep working right alongside the new class-specific validators, so when both are present both should actually run, don't let one shadow the other. And obviously safe payloads, the ones with no URL-override params, should still deserialize normally like nothing changed. The point here is closing this attack surface at the framework level so every caller doesn't have to reinvent their own security checks, since an untrusted config could otherwise silently redirect all the cloud model API calls to an internal metadata service.
