I'm building out the OpenLineage provider for Apache Airflow and right now there's no stable public way for developers to emit lineage from their own task code. Everything's buried in internal listeners tied to the task lifecycle, so operators that manage their own connections or run queries outside Airflow's built-in SQL operators can't contribute lineage without copying internal guts. I want to fix that with a proper public API module.

I need a couple high-level functions. One declares dataset-level lineage, associating a task with its input and output datasets, and one emits lineage for individual SQL queries run during a task. Both should work inside a running task and auto-pull the standard metadata (parent run IDs, job type, ownership, tags, timing) straight from the execution context so callers assemble nothing. If no task instance is passed explicitly they resolve it from the current running context. Errors during emission should get swallowed and logged as warnings by default so a lineage failure never breaks task execution, but there's a raise_on_error option for callers wanting strict behavior. I also want a small function to check whether OpenLineage is currently active (enabled and configured) plus one to emit a raw event to the configured backend.

On utilities, please pull the logic for assembling run facets and job facets out of the listener internals into standalone helpers that can be reused and tested on their own. There should also be a utility managing a per-task counter for numbering individual queries within a task run, incrementing each call within the same execution context, resetting for a new context, and falling back to a random identifier when called outside a running task.

The dataset lineage function should validate (when raise_on_error is on) that at least one input or output is provided and that each item passed is actually a dataset. The SQL query lineage function should emit a start event followed by a completion or failure event, optionally accepting the query text for SQL parsing, explicit start/end timestamps, and extra custom facets, and it should number queries within the run and attach query identity metadata plus optionally parse the SQL to extract dataset-level lineage. Custom facets from the caller get merged into the event but must not override internally computed facets like the parent run reference or job type.
