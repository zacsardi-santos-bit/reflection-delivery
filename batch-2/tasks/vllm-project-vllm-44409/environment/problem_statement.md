I'm chasing a nasty memory-safety bug in the KV cache manager for hybrid attention models, the ones that split layers across multiple KV cache groups like a mix of full-attention and sliding-window layers. When a request hits the local prefix cache in one group but also needs externally-fetched computed blocks in another group, the allocator ends up handing out the same physical block twice, one group claims it as a cache hit while another treats it as freshly allocated. So I get duplicate block IDs across groups and the reference counts on those blocks get corrupted. Root cause is ordering: external block allocation runs before the locally-cached blocks in other groups have been registered and protected, so the external allocator can evict a block another group is about to use and re-issue it.

I want a two-phase fix at the coordinator level: register and protect all locally-cached blocks across every group first, then let any group claim new external blocks. That way no external allocation can evict a block that's already spoken for. To make that clean, the internal method that registers locally-cached blocks should be renamed so it reflects its narrowed job (it shouldn't also do external allocation anymore), and a new separate method should handle just the external allocation step. Local registration always completes for all groups before external allocation begins.

After this, every physical block ID assigned to a request needs to be unique across all groups, and every block the request references must have a refcount of at least 1 (nothing evicted should show up in an allocation). This has to hold for both 2-group and 3-group hybrid configs. Also handle preempt-then-reallocate: when a request is freed and later rescheduled with the same ID, treat it as a brand new request so the two-phase ordering runs fresh and there's no double allocation on the second attempt. And after freeing a request, querying its blocks should come back empty for all groups.
