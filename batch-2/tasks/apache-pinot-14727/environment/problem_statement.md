I'm hitting two group-by aggregation problems in Pinot and want both sorted out. First one's a straight-up crash: when I run a group-by query with a limit on the number of groups and that limit ends up smaller than the actual count of distinct groups in the data, the thing throws an array index out-of-bounds instead of just handing me back the allowed number. It happens on both single-key and multi-key group-by when dictionary-based group key generation is in play, so it's not some edge case with only compound keys. What I actually want is for it to trim the result down to the configured limit and return that quietly, no exception. Being able to set a small group limit is how I bound resource usage, so the crash defeats the whole point.

Second thing's more of a gap in the multi-stage query engine. At the final aggregation stage there's currently no way for me to say how many groups the aggregation operator should keep in its output, and I'd like a trim size I can configure via a query option, plus a per-query hint on the aggregation that overrides that option when both are present (hint wins). If neither the option nor the hint is set, trimming should just be disabled by default, no limit applied. Oh and I want to read the trim size back off the operator itself so I can inspect what it landed on. This helps me tune memory and control result sizes on multi-stage queries.
