I've been cleaning up our DuckDB test infrastructure and there are two things I want to fix together. First, running the suite today means passing two paths on the command line, where the Python helper script lives and where the compiled test binary lives, and everybody hates hardcoding both in CI. I want a wrapper module that lands in the build output directory as a single self-contained entry point that just knows where its sibling binary is. It should check that the compiled binary actually exists next to itself before doing anything, and if it's missing, print a clear error to stderr explaining that. When the binary's there it invokes the existing test runner from the repo root and returns the same exit code it got back, no separate binary path argument needed. Oh and I want the CI workflow definitions that call the runner directly updated to use this new single-path wrapper instead of the old two-argument approach.

Second thing is failure output readability. Right now a result mismatch crams the expected value, actual value, and diagnostic message all into one line, which is awful to scan. I want expected and actual shown in clearly labeled separate sections. For crashes and signal failures give me a human-readable description of what signal came back instead of nothing, but if sanitizer output is present that should win over the generic crash description. Also the code snippets we print on failure carry a bunch of shared leading indentation, strip that common whitespace so they read cleanly. And skipped test counts should only show up in the final aggregated summary, not mixed into individual failure detail blocks. These output changes need to apply consistently whether the failure's a query result mismatch, a C++ assertion, a crash, or a query diagnostic combined with an assertion failure.
