I'm working on the Kafka config CLI and I want to fix two related things in how it applies config changes. Right now when I alter a config property on a topic, a specific broker, or the broker defaults, the tool does an extra read of the existing config first before applying anything. That preliminary read is wasteful network overhead and I'd rather skip it entirely and just apply the incremental config change directly, no fetch-then-diff round trip.

The bigger problem is delete. If I try to delete a config key that isn't currently set on the resource, it throws an error instead of just succeeding. That makes delete non-idempotent, so say I want to strip a config property off every topic in a cluster but not all of them actually have it set, the command blows up on any topic missing that key. What I want instead is for deleting a non-existent config key to be a plain no-op that succeeds regardless of whether the key was there. "Delete this key if it exists" is a totally natural pattern, especially for scripted automation where I don't want to pre-check what's set on each entity before removing anything.

Oh and this needs to behave the same way across all the entity types, topics, individual brokers, and broker defaults alike, so delete is consistent and safe to run in automation without prior existence checks. So basically two changes: drop the preliminary config read on alter, and make delete idempotent everywhere.
