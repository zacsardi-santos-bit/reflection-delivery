I'm poking at the new union type declaration feature in the C# compiler (the Roslyn source generation / binding layer around union decls) and I've hit a real gap: the compiler happily accepts union bodies that contain members it shouldn't, because unions synthesize their own storage and their own one-parameter conversion constructors, and those impose hard constraints on what members can live in the body. Right now none of that is enforced, so invalid declarations just compile clean and blow up or misbehave later. I want three categories of restrictions checked at compile time, each producing its own distinct descriptive diagnostic reported at the location of the offending member so devs know exactly what and where.

First, instance storage members have to be rejected inside a union body: instance fields, auto-properties, properties that implicitly back their value in a compiler-managed backing field, field-like events (events declared without explicit add/remove accessor bodies), and explicit interface implementations of auto-properties should all error. Static versions of all of these stay allowed and keep compiling fine, same for non-field-backed instance properties and explicitly-accessored events.

Second, explicitly declaring a public constructor that takes exactly one parameter is an error since it conflicts with the synthesized conversion constructors; zero-param or two-plus-param constructors are fine.

Third, every explicitly declared instance constructor must chain to another constructor via a this-initializer with arguments, so one with no this-initializer, or one chaining to the parameterless default ctor, should be rejected. Static constructors are exempt from this chaining rule. Valid ctors with proper this-initializers keep compiling.
