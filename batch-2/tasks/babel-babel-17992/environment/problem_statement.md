I'm running into a Babel source map bug when I transform bundled JS that already ships with its own external source map. That input map tracks certain variable names in its names table, but when I run a plugin that renames scope bindings the output source map drops the original name attribution instead of carrying it through.

It's clearest when a variable that's tracked in the input source map gets renamed, especially when there's a naming conflict between scopes so the inner variable ends up with a different renamed form than the outer one (one keeps the base name, the other gets a disambiguating suffix). In that case I'd expect both renamed identifiers to still trace back to their shared original name from the input map, but the name attribution just vanishes.

What I want is for Babel's source map generation to check, when it's emitting an identifier token, whether the input source map already has a name recorded at that source position, and if so use that original name in the output source map. So the output map should include those original names and correctly map all the renamed output identifiers back to them, keeping the full chain intact: output identifier back to renamed identifier back to the original identifier in the pre-bundled source.

This matters because when Babel consumes bundled output as input (common in a lot of toolchain setups), losing the original variable names breaks the end-to-end source map chain and makes it impossible to reliably debug or trace transformed identifiers back to the original symbols. So please fix it so the name chain survives even through renames and cross-scope conflicts.
