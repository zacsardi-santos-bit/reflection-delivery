I've been poking around the search tools and there's this naming mismatch that keeps tripping me up. The parameter that excludes files from a search already has a nice descriptive name ending in `_pattern`, but the one that includes only specific files uses a shorter name without that suffix. So the two complementary filters don't match, which makes the whole thing harder to predict, and honestly it's the kind of inconsistency that leads to silent failures where someone sets the filter with what they assume is the right field name and it just gets ignored because the implementation is looking for something else.

What I want is to rename the inclusion filter param so it picks up the same `_pattern` suffix the exclusion filter uses, so both read the same way and the API self-documents. Once it's renamed I need the tool to actually honor the filter under the new name, so a search restricted to a given glob (say only files of one extension, or files matching a couple of extension types) really does narrow the results to just those files.

Oh and the human-readable description the tool generates for a search should reflect the file filter when the inclusion pattern's set, showing the search query alongside the glob being applied. And if someone passes both an inclusion pattern and a directory path, both of those should show up in that generated description too.
