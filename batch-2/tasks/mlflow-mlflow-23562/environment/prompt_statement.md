I'm building out the MLflow TypeScript tracing SDK and hit a gap: right now traces only land in MLflow experiments, but for our Databricks agents in prod we really need to route trace data straight into Unity Catalog tables so it lives in the same governed, queryable layer as everything else. There's currently no way to configure a UC destination when tracing starts, and no client plumbing for the new Databricks trace management endpoint or for pushing spans into UC-hosted tables.

So I want a new trace location type representing a UC table-prefix destination (catalog name, schema name, table prefix), plus helpers to construct these, check whether a given location is UC-based, derive a display string, and resolve the OTLP spans table name. I also need a new trace ID format that encodes the UC storage location, with utilities to build and parse those IDs (and the existing format should still parse fine too). On the client side, add a method that creates trace metadata via the new Databricks trace management API, and another that exports OpenTelemetry spans to a UC table over OTLP with the right auth header, and when there are no spans it should just return gracefully without any network call.

Then I need a span processor and exporter pair covering the full lifecycle: assign the new UC trace ID when a span starts, persist trace metadata (including any tags set during execution) to the new backend endpoint on span end, and upload the spans to whatever table the backend hands back. The tracing init function should take an optional Unity Catalog destination config and, when it's present, wire up this processor automatically. Oh and I want a utility that derives the UC destination from experiment-level tags, returning null when the tags are missing or malformed (a path that isn't three segments, or has empty segments). Also trace info serialization/deserialization needs to handle the new location variant correctly, converting between camelCase in memory and snake_case on the wire.
