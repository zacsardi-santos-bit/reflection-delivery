I'm cleaning up error handling for remote agent operations and it's kind of a mess right now. When a remote agent fails to load, whether the URL doesn't resolve, the server bounces us with an auth error, or the network is just down, the user gets a raw or generically-prefixed string that tells them nothing about whether to fix a URL, add credentials, or go poke at their firewall. Same deal when a remote agent call dies mid-stream. I want structured error types that categorize the failure modes: not found, authentication failure, authorization failure, missing auth configuration, and a generic connection error fallback. Each one should carry a friendly message that names the agent, says what went wrong, and points at the exact config field to fix (like referencing which URL entry to update on a not-found, or pointing at the auth config with the HTTP status included on auth/authz failures).

The tricky part is classification has to walk the full cause chain, including nested causes and plain-object causes that carry status codes, since the HTTP client tends to wrap things. Oh and network-level stuff like DNS failures needs to land as a connection error, definitely not misclassified as "not found." When an agent's card loads fine but its security requirements aren't matched by the current config, I want a warning that names the agent and spells out what's missing, but we still register the agent so folks can fall back to default credentials. On the invocation side, if a call fails I want the surfaced message to use the structured one when it's there, otherwise a consistent generic format, and if output was already streaming when it broke, keep that partial output alongside the error. Also errors going through the message streaming layer shouldn't get re-wrapped with extra prefixes anymore, just let the original propagate as-is.
