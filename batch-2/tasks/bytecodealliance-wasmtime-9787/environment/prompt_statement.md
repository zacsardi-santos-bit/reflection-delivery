I'm hacking on the Winch baseline compiler backend for AArch64 in Wasmtime and hit two related problems around int/float stuff that I need sorted out.

First, the AArch64 backend just doesn't do integer-to-float conversions at all. Wasm has instructions for converting both signed and unsigned integers into floats across every size combo (i32 and i64 sources going to both f32 and f64 destinations), and right now none of those are wired up, so any module doing numeric conversions between ints and floats either fails to compile or produces garbage on AArch64. I want the backend to emit the right native conversion instructions for each of those cases: signed i32->f32, i32->f64, i64->f32, i64->f64, and the same four again for unsigned. So eight conversions total, all working.

Second issue, the reinterpret ops are broken. These are supposed to be pure bit-level reinterpretations, treating the raw bits of an integer as a float or the raw bits of a float as an integer with zero numeric transformation, but the current code emits arithmetic conversion instructions instead, which actually changes the numeric value. That's semantically wrong and silently corrupts results in low-level numeric code. Both directions (int-to-float reinterpret and float-to-int reinterpret) have this bug, they need to use a bit-preserving move (fmov style) that keeps the bit pattern exact rather than a conversion.

Oh and all of this needs to behave correctly no matter where the operand comes from, whether it's a compile-time constant, a local variable, a function parameter, or a value that's been spilled to the stack. The relevant code lives in the Winch AArch64 masm/backend under `@winch/codegen/src/isa/aarch64`, so that's where the emit logic for these conversions and reinterprets should go.
