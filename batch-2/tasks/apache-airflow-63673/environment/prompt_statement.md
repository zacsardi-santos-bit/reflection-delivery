I'm hitting an encoding crash when reading pod logs asynchronously from Kubernetes. Whenever a container emits bytes that aren't valid UTF-8, like binary data, mixed or non-UTF-8 encodings, or truncated multi-byte sequences, the async log read blows up with a Unicode decode error and aborts the whole thing, so operators end up with zero usable log output for that task. That's rough because we've got real workloads where I have no control over what encoding the container writes, and one bad byte shouldn't kill visibility into everything else.

What I want is for the async pod log reading to just tolerate undecodable bytes instead of throwing. When decoding the container stream, any invalid or undecodable bytes should get silently swapped for the standard Unicode replacement character (the usual "replace" error handling) rather than raising. The read should still complete successfully and return a list of strings, one per line, containing all the decodable content with the problematic bytes substituted out.

Oh and this needs to behave the same way in both the base Kubernetes async hook and the Google Kubernetes Engine async hook, so wherever the async log-fetching logic lives for those two, make sure the decode path handles errors by replacement consistently across both.
