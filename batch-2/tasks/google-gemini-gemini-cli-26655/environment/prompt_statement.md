I'm reworking the context memory in our agent so it stops throwing away everything on each compression cycle. Right now when we compress old conversation history it just spits out a prose blob that gets rebuilt from scratch next time, so file paths, error codes, and user instructions silently vanish. I want a structured, machine-readable snapshot instead that can be incrementally updated: separate lists for active tasks (each with a unique ID and a description), discovered facts (empirical strings), user constraints and preferences, and a rolling chronological summary of recent events.

The flow I'm after is calling the model in a structured way asking it for a delta patch describing only what changed (new facts, resolved/removed tasks by ID, obsolete facts by index, etc.), then merging that patch into existing state rather than replacing it. Facts can be appended or removed by index, tasks added or removed by ID, and the summary should behave as a rolling window. Important: if the model call fails or returns malformed/garbage data, I want the existing state returned untouched, no data loss whatsoever.

Also needs a configurable token budget enforcement step: when the serialized state exceeds the limit, prune in priority order, oldest facts first, then oldest constraints, then oldest narrative summaries, then tasks only as a last resort.

Oh and I need a utility that formats conversation nodes into a clean text transcript for the model. Each node labeled with its role, type, and a relative turn index where most recent is 0 and earlier ones go negative. Tool responses need semantic labels (shell command execution labeled differently from file content reads) and should get truncated with a clear marker if they're too big so they don't blow out the context window.

Last thing, both the sync and async memory processors need a "global lookback" feature: on start they should scan current context for the most recent existing snapshot node and use it as the baseline even when the normal inbox or coordination channel is empty, so memory stays cumulative. And when a new snapshot consumes an old baseline snapshot, the old snapshot's ID has to end up in the new snapshot's list of absorbed/consumed node IDs so it gets garbage collected properly.
