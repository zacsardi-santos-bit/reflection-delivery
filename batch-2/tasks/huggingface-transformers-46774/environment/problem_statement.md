I'm building out a CI automation helper for a big open-source repo and I need a brand new script dropped into the `utils/` directory that posts and updates CI run summaries right on the GitHub PRs. Right now when a run finishes there's no automated way to shove a structured overview into the PR description, so people have to go dig through the CI system to see how many tests ran, how many failed, how long it took, what the overall conclusion was. I want to fix that.

Here's the flow I'm after. After a CI run completes the PR body gets a status badge at the very top linking to a monitoring dashboard, plus a detailed recap section at the bottom summarizing the run, the overall result, job count, test count, failure count, and duration. It should pull those metrics from a Prometheus-compatible monitoring backend, and when metrics aren't available yet it falls back gracefully to info from the workflow run itself. Oh and if a code quality check job failed, the recap needs a prominent warning about that. On later runs the badge and recap blocks get updated in-place (think delimited blocks I can inject or replace without disturbing the surrounding PR text) rather than duplicated, and old-format dashboard comments left behind by earlier versions of the script should get cleaned up automatically, which means issuing delete requests for those stale comments.

I need some utility functions in there too. Number formatting with thousands separators and human-readable durations, so "1,234" for a test count and things like "1h 1m" for a long run or "9m 59s" for a shorter one. A helper to query the Prometheus-compatible backend for run-level stats, and one to safely escape strings before they go into monitoring queries. The GitHub side has to paginate through API responses correctly to find PRs, jobs, and comments, find the open PR tied to a given commit SHA, and check job conclusions. All of this should be well covered by unit tests and behave correctly with mocked external dependencies. Contributors lean on PR checks to know whether they broke anything, so having results embedded straight in the description cuts down context-switching and makes it obvious at a glance whether the run passed and whether any quality checks tripped.
