I'm hitting a dependency resolution bug in how we figure out npm deps for libraries whose build target uses the generic command runner (nx:run-commands style executor) to invoke tsc. When the build command runs the TypeScript compiler with a project-specific config file passed via a build flag (like `--project` or `-p tsconfig.lib.json`), the resolver that decides which npm packages get bundled into the published package is reading the workspace root tsconfig instead of the project-level one to figure out whether the TypeScript helper library (tslib) needs to be a dependency.

This breaks two ways. If my project's own config turns on helper imports (importHelpers) but the root workspace config doesn't, tslib gets left out of the published deps entirely, so consumers hit runtime failures. And the flip side, if the root config enables helper imports but my project-level config doesn't, tslib ends up wrongly included as a dep, which is just bloat.

What I want is for the resolver to pull the config file referenced in the build command and resolve it relative to the working directory specified in the target options (`cwd`), or fall back to the project root if no cwd is set, then read that project-level config to decide whether helpers are needed. It should include tslib in the output deps if and only if that resolved project config enables helper imports. The project-level config needs to take precedence over the workspace root config whenever a specific project config is identifiable from the command. If no such config is discernible from the command, falling back to root behavior is fine, but when it is discernible, use it.
