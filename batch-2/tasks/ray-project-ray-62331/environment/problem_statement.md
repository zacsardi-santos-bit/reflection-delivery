I'm chasing down a nasty autoscaling bug in Ray Serve where our scale-up and scale-down delays don't actually respect the wall-clock time operators configure. The way it works now, the delay logic in the autoscaling policy just counts how many control loop iterations have gone by and compares that to a precomputed iteration count derived from the configured delay, which quietly assumes every iteration takes exactly the standard control loop interval. That assumption falls apart under load. On a busy cluster a single iteration can take several times the baseline interval, so a configured 100-second upscale delay can silently stretch to 600 seconds or more, and deployments react to traffic way later than intended.

I want to rip out the iteration-counting approach and instead track actual elapsed wall-clock time from the moment a consistent scaling direction (up or down) was first detected. The scaling decision should fire once that real elapsed time meets or exceeds the configured delay, no matter how many iterations have passed or how long each one took. So a delay of N seconds fires after roughly N seconds of real time, and importantly the overshoot should be bounded to at most one additional iteration duration beyond the configured delay, not some multiple of it.

Also, to make this testable without actually sleeping, the delay function needs an optional parameter to inject a specific timestamp so I can drive the wall-clock behavior precisely in tests. When no timestamp is passed in, it should grab the current time through an injectable time source so tests can swap in a fake clock. This matters because operators lean on these delay settings to tune responsiveness, and if the delays aren't honored in real time you get queued requests, latency spikes, and unpredictable scaling behavior under exactly the load conditions where it matters most.
