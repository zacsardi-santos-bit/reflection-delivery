I'm adding support for a new kind of hook that fires right before a user's prompt gets submitted to the AI. These user prompt submit hooks can peek at the input, throw warnings, or block the submission outright, and right now the chat interface only knows how to render hooks that fire during tool use so this whole category is invisible. I need the app-server protocol to gain a new hook event type for user prompt submission, plus new output entry categories covering warning and stop outcomes that these hooks produce. On the rendering side, when one of these hooks starts, the chat UI should show an inline notification that the hook is running and what it's checking, and when it completes (whether it produced warnings, blocked the prompt, or both) the UI should display the hook's final status along with each output entry, warning or stop, with its message.

Two more things. When a session gets refreshed or rebased, hook notifications are getting dropped, which means people lose visibility into which hooks ran. I want both started and completed hook notifications preserved through rebase, same way request events survive, so the logic deciding which events make it through a refresh needs to keep both.

Also the conversion from app-server protocol hook types to core protocol hook types currently goes through an intermediate step that silently drops notifications for any hook type that can't be losslessly converted across both layers, so my new user prompt submit type and the warning/stop entries won't render at all unless I fix it. Rewrite that conversion to do direct field mapping with proper variant conversion instead, so new variants and fields don't just vanish.
