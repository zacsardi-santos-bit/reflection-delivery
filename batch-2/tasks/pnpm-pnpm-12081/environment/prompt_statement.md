I'm hitting a peer dependency resolution bug in pnpm around a diamond-shaped peer graph and it's producing a busted lockfile. Here's the setup: I've got a plugin that peer-depends on both a parser and a shared runtime library, and that parser itself also peer-depends on that same shared runtime. My root workspace resolves a newer version of the runtime, but one of my packages nests the plugin under a context that uses an older runtime internally. When pnpm resolves peers, it wrongly pairs my plugin with the top-level parser instance (the one resolved against the newer runtime) instead of the locally consistent parser that was resolved against the older version. So I end up with a lockfile where the plugin's own runtime peer points at one version while its parser's runtime peer points at another, which is exactly the mismatch I don't want.

What I'd expect is for the resolver to always keep the plugin and its parser agreeing on shared peer versions. If the plugin's the three of them (plugin, parser, shared runtime) all need to line up on the same runtime version. When the top-level project has the newer runtime but the plugin sits under an older-version context, the plugin's parser should be the one from that older context, not the hoisted top-level parser. And the lockfile should end up with exactly one snapshot for the plugin showing consistent peer resolution across all its shared deps, no duplicate or contradictory entries.

The real-world shape here is a TypeScript toolchain, btw, a linting plugin peer-depending on both a TS parser and TypeScript itself, with the parser also peer-depending on TypeScript. If root uses TypeScript 2 and an inner package uses TypeScript 1, the plugin should always pair with the TypeScript-1 parser, but pnpm was reusing the hoisted TypeScript-2 parser for it and causing the mismatch, which wires deps wrong and can blow up at runtime in projects juggling multiple TypeScript versions. Fix the peer resolution logic so this diamond case stays consistent.
