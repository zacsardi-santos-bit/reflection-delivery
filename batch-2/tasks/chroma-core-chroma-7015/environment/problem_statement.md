I'm working on a system where async functions get attached to data collections and run in the background as data gets ingested, and I've hit a gap in the coordinator layer around safely finalizing those async invocations. Right now there's no way to atomically record that one of these functions finished its work while also checking whether the collection's underlying data log has advanced past the function's completion point. I need a finalize operation that compares the collection's current log position against the requested new completion offset, and if the log is ahead of that offset it should tell the caller a repair is needed and hand back the current log position so they know what to reconcile to, but if the log is at or behind the new completion offset it just reports success and returns the updated completion offset. Oh and there's a hard invariant here, completion offsets only move forward, so if something tries to set the completion offset to a value lower than what's already stored the operation has to fail with an error instead of silently letting it regress backward.

On top of that I want a separate operation that finalizes the repair process itself, so once reconciliation is done it clears the pending repair flag and the function is fully settled. Both of these need to be idempotent since we're in a distributed setting and calls get retried, so calling either one multiple times with the same args has to land on the same outcome every time without producing inconsistent state. Please wire this into the existing transaction mechanism and the database interfaces we already have for attached functions and collections rather than inventing a new path. The whole point is that async functions processing data from a collection currently have no safe way to record progress or handle the case where ingestion races ahead of processing, which leaves us with state that's really painful to recover from, so the repair signaling plus idempotency is what makes this reliable.
