I'm hitting a fusion gap when I optimize Qwen3 models with ONNX Runtime's transformer optimizer. Qwen3 computes rotary positional embeddings on the fly at runtime instead of reading a precomputed table, so during export you get this multi-node subgraph where learned inverse frequencies get multiplied with position IDs through a matmul, then the result is transposed, concatenated with itself to double the frequency dimension, run through cosine and sine, scaled, and finally unsqueezed to tack on a head dimension. Problem is after I run the optimizer all those individual ops are still sitting there as separate nodes, it just doesn't recognize the pattern and fuse it into the specialized fused rotary embedding operator that other models already use. I want the Qwen3 optimizer to detect this and swap it out for fused nodes, one for the query path and one for the key path, so a single decoder layer ends up with exactly 2 fused rotary embedding nodes.

Oh and there's a variant where the inverse frequencies get explicitly expanded out to the batch size using a conditional selection (Where-style) op before the matmul, that one should get fused too and also land at 2 nodes. One edge case I really care about: when the inverse freq values can't be pinned down at graph-optimization time because they come in as a runtime graph input rather than a constant, the fusion should skip gracefully instead of crashing, leaving 0 fused nodes.

After a successful fusion I'd expect precomputed cosine and sine cache tables stored as initializers, and their values need to match the standard formula, cosine and sine of each position index times the inverse frequencies, then scaled by the attention scaling factor, verified to numerical precision across a wide range of sequence positions so it's actually useful in practice. Without this we're leaving real inference perf on the table since the on-the-fly path stays as a pile of nodes instead of one optimized kernel, which just burns memory bandwidth and latency.
