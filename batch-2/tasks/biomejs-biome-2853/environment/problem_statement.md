I'm working on the JavaScript side of our analyzer and I want to add a new lint rule that catches yoda-style comparisons, you know the ones where a constant sits on the LEFT of the operator and the actual variable you're testing is on the right, like `"red" === color` instead of `color === "red"`. Most style guides want the variable first since it reads more naturally, so I'd like to flag these and enforce the conventional order.

When the rule fires it should offer a safe automatic fix that flips the operands around. The tricky part is ordering operators need to be inverted so the logic doesn't change, so a less-than becomes a greater-than, greater-than-or-equal becomes less-than-or-equal, that kind of thing. Equality and strict equality operators just stay the same after the flip.

There are cases I definitely don't want flagged. If both sides are constants there's no conventional order so skip it, and range-check patterns where two comparisons are combined to test whether a value falls between a lower and upper bound should be left alone since those are idiomatic and readable even with a literal on the left. Also don't touch non-comparison operators like bitwise ones.

Oh and the fix has to hold up with gnarlier operands too, parenthesized expressions, inline comments that need to move with their operand, negated/unary values, yield expressions, await expressions, and assignment expressions used as operands. One more thing, a template literal with dynamic interpolation inside it shouldn't count as a plain constant when it's on the left, so treat those as non-literals. The whole point here is consistent comparison ordering is a common style guideline and having automated detection plus a reliable auto-fix means folks can clean up every instance across the codebase without manual review.
