I'm deep in the Zigbee2MQTT integration and hit a few gaps I need sorted. First up, adapters: I want to add a new protocol type alongside the existing ones because a bunch of popular USB dongles that used to only run the legacy "ezsp" mode can now use the newer "ember" driver, which we should prefer. Those dual-capable dongles need to show up in the adapter selection list twice, once for the new ember mode and once for the legacy mode labeled accordingly. And instead of plain strings, the list should return structured objects carrying both the display name and the protocol type identifier.

Next, the function that configures the container shouldn't just hand back a boolean anymore. I want an object that tells me whether the overall config changed and separately whether the adapter type changed, because if only the config content changed I can just restart, but if the adapter type flipped I need to stop, remove, and recreate the container entirely for it to take cleanly.

Then I need a new function that reads the container's log output after startup to catch errors. It should stream the logs, strip the Docker stream prefix bytes and ANSI color codes off each line, then match known patterns. The one I care about is firmware being incompatible with the expected protocol version, when a line signals that firmware-host protocol incompatibility it gets recorded as a structured error with a recognized protocol version mismatch error code and no message, and the stream closes. For other unrecognized stuff, any line starting with an error marker (matched case-insensitively) becomes the error message, keeping only the last such line, and known error codes win over generic error lines. No error found means the error state is absent. Oh and it has to handle a stream that never ends, so resolve after 30 seconds, and if log reading fails outright the error state stays absent and startup just continues.

To back that, we already have something that pulls a Docker container as a stream, I need a sibling for fetching container logs with sensible defaults for output channels, a line limit, and streaming mode, with custom options able to override those defaults.

Lastly, when a message comes in from the running bridge reporting coordinator details with firmware metadata, store the firmware type and version fields and fold them into the status we broadcast to the front end, and that status payload should always include the container error state too.
