I've been digging into ClickHouse's Arrow IPC format reader and it's got a nasty heap out-of-bounds read problem. Someone can hand it a crafted (or just corrupt) Arrow IPC file that declares thousands of rows in the metadata while the actual data buffer only holds a handful of bytes, and the reader trusts that declared row count and does bulk copies or per-element reads way past the end of memory it owns. Sanitizers catch it and it's exploitable in prod, so I want the reader to validate every buffer against the declared metadata before it touches any raw memory, and any mismatch should come back as a clean data integrity error.

This is basically everywhere in the column reader so I need it covered across the board: fixed-width numeric reads, dates, timestamps, intervals, booleans, decimals, string and binary, the view-based string types, JSON and geo readers, dictionary-encoded columns, IPv4/IPv6, and the fixed-size binary paths used for UUIDs, fixed strings, and 128/256-bit ints. Also all the nested paths, lists, large lists, fixed-size lists, maps, and structs.

A few tricky edges I keep hitting: arithmetic overflow where a row count near 2^62 makes size times count wrap around to zero and sneak past checks, validity bitmaps that are too small for the declared row count (validate before any null-check), negative declared lengths that underflow the size math, non-monotonic or out-of-bounds list offsets, view struct sizes, and child arrays whose lengths are inconsistent with their parent, plus struct fields shorter than the parent and sliced structs with zero-length child fields (after a flatten or slice a child bitmap can end up shorter than the parent expects). Oh and one big thing, this validation has to run before any column memory reservation, because right now an inflated declared length makes the reader attempt a giant allocation and fail with a memory error instead of a data error, which is wrong. So any malformed file, whether the corruption is in the top-level row count, a child length, an offsets buffer, a view struct size, a validity bitmap, or a buffer-size arithmetic overflow, needs to be rejected with a data integrity error before any unsafe op happens.
