I'm hitting a parsing bug when I try to wire up external function callbacks in my provider config on Windows. When I point at a Windows-style drive-letter path (like `C:` followed by the rest of the path and then a colon and a function name), the parser splits on the drive-letter colon instead of the colon right before the function name, so the file never loads and I get a cryptic not-found error. I need the parser to correctly pull the function name off the end of a drive-letter path rather than choking on that first colon.

There's also the standard local-file URL format that Windows tools spit out, the one with three slashes after the protocol prefix. On Windows that leaves a spurious leading slash in front of the drive letter which makes the path invalid, so I want that extra slash stripped on Windows. But on Linux or Mac the same triple-slash URL should keep the leading slash as part of the path since there's no drive letter to strip, so the behavior has to be platform-aware.

Also, if a file or directory name legitimately has a colon in it (happens on some filesystems), the current logic wrongly treats it as a separator and tries to extract a function name that isn't there. A colon should only count as a function name separator when the path before it actually resolves to a JavaScript or Python file, otherwise treat the colon as part of the path. And oh, right now only JS files support the colon-based named-function syntax, so I'd like Python script files supported the same way so specifying a named function out of a `.py` file works just like it does for `.js`. Fixing this should make callbacks work reliably across all platforms.
