I'm cleaning up the error reporting on our S3 filesystem mount and it's being way too eager about failing at open time instead of at read/write time. Right now if a file is already being written to by some other process, or has already been written, or lives in a low-priority retrieval class like Glacier that needs restoration, or is a locally-created file that hasn't committed yet, the open call itself just fails. That's not how POSIX-style filesystems behave, opening generally succeeds and you only find out about problems when you actually try to move data. I want opening to succeed in all those cases and push the error down to the actual read or write attempt with the right error code at that point. So a file in a restricted storage class should open fine but error on read, a mid-write file should open fine but error when another handle tries to read it, and trying to overwrite an already-written file without explicit truncation should fail at write time, not open time.

Also I want a new config option, off by default, that when enabled allows overwriting existing files. With it on, an existing file can be opened for writing but only if the caller explicitly asks to truncate first, and opening with that truncation flag should immediately clear the file's contents even if no write follows. Without the truncate request, writes still get rejected.

Oh and a few related edge cases while I'm in here: reading from a write-only handle should fail, reading from a file mid-write even through the same read-write handle should fail, and reading a file being written by another handle should fail, all reported at the point the op is attempted rather than at open. The whole point is the mount should feel predictable and match standard filesystem semantics where open succeeds unless the file truly doesn't exist or can't be accessed at all.
