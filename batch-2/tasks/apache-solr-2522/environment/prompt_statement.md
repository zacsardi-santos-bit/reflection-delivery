I'm cleaning up the rate limiting layer in our search platform and the slot-acquisition API has a design smell I keep tripping over. Right now when code tries to grab a rate-limiting slot it always gets back an object, even when no slot was actually granted, so to know whether you really hold one you have to poke at a "releasable" flag on that object. It's unintuitive and super easy to misuse, and there's no clean way to auto-release a slot when a block finishes so people are stuck making explicit release calls they forget half the time.

What I want is to refactor this so a failed acquisition returns nothing (callers just do a simple absence check instead of interrogating a flag), and a successful acquisition hands back a closeable resource that releases the slot automatically when the block exits. That kills the "releasable" flag entirely and lines us up with normal resource-management idioms.

The timeout behavior has to be correct too. When all slots are occupied, an acquire attempt should block for the configured timeout and only then give up and return nothing, not bail immediately. But when a slot is available it should be granted quickly, well within that timeout. And under concurrent load the invariants really matter: the number of slots held at once must never exceed the configured total allowed, the number of borrowed slots must never exceed the borrow quota (total allowed minus guaranteed), and guaranteed slots have to stay available for their native request type even when the borrow quota's fully consumed by another type. Oh and after everything's released the limiter should report it's empty. This is all so rate limiting actually protects the system under real load instead of forcing boilerplate flag-checking everywhere.
