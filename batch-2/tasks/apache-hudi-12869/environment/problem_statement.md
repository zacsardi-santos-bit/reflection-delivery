I'm poking at the V1 archived timeline in Apache Hudi (over in `@hudi-common/src/main/java/org/apache/hudi/common/table/timeline`) and I keep hitting a few gaps when I load historical commit data out of the archive log files. Right now I can only give it a start timestamp when I build the archived timeline, there's no way to also pass an end timestamp, so I want a constructor that takes both start and end and uses a closed range with both endpoints inclusive to decide which instants get loaded.

Also I need to filter by lifecycle state when loading archived instants. Sometimes I only want requested instants, sometimes only completed ones, sometimes all of them at once, so let me pass an optional state param (requested, in-flight, completed, or all) alongside the time range. And separately I want to target specific archive log files by path instead of always scanning everything, so when I hand it a set of file paths only those files should be read.

The big one though: the current code tracks only one payload per commit timestamp, so if the same commit has a requested record, an in-flight record, and a completed record in the archive, loading them all means the earlier ones get clobbered. I need state-specific details retrievable independently, so querying for the requested state of a commit returns the requested-state bytes, not the completed ones. Basically the detail lookup has to be keyed on both the timestamp and the lifecycle state, not just the timestamp. This matters because tools auditing historical states (like inspecting the original compaction plan for a now-completed compaction) can't work if that state-specific metadata gets lost.

One nuance to get right: clean and rollback action types only store completed metadata in archived log entries, so asking for their requested or in-flight state should return nothing. And replace-commit actions don't store in-flight metadata, but they do keep a separate record for the requested state.
