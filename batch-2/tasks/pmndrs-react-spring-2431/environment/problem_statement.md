I've been running our animation library inside a project with React strict mode turned on, and I keep hitting weird animation behavior that only shows up in development. Strict mode intentionally simulates an unmount then remount on the initial mount to smoke out side-effect bugs, and it looks like our animation context component doesn't survive that cycle right.

The core thing I traced it to is spring stopping. When a spring gets stopped during that simulated unmount, it incorrectly records a goal target even if the spring was never started, basically setting a target off the current value instead of just leaving the state alone. That corrupts the spring's internal state so on remount the animation context doesn't replay the right sequence of updates. What I want on mount in strict mode is the full sequence coming through: first the user-configured animation target and its callback, then a default property broadcast, then the user-configured update again. Right now something goes sideways during the stop/restart and those updates don't all fire, so I end up with animations starting from wrong positions, missing lifecycle callbacks, and just generally behaving differently between strict-mode dev and production.

Can you fix the stopping behavior so it only establishes a goal target when one already exists? If no target was ever set, stopping the spring should leave it in its original unstarted state, untouched. And make sure the animation context replays all its updates correctly after the simulated remount. Oh and while you're in there, the spring animation hooks all need to be fine with strict mode's double-invocation, meaning props functions get called twice per render pass without breaking anything. The whole point is React pushes strict mode hard in dev and tons of projects have it on by default, so if we behave inconsistently there we're effectively broken for a big chunk of users, and I just want animations consistent across dev and prod.
