I'm poking at the XDS override host LB policy in gRPC and it's just not doing the right thing when the host you're pinning to isn't READY. Like when a pick comes in asking for a specific override host and that host's subchannel is mid-connect, the policy kind of shrugs and does nothing sensible, no queueing, no connection kickoff, so traffic gets misrouted or the override silently vanishes. That's bad for session stickiness and host-pinning during rolling deploys, connectivity blips, or backend restarts.

What I want is for the policy to actually branch on the subchannel's connectivity state. If the override target is connecting, hold the pick in a queue until it comes up. If it's idle, proactively start a new connection to it and queue the pick while we wait. And if it's in a permanent failure state, abandon the override entirely and let the pick fall through to the remaining healthy subchannels in the pool rather than sitting there doing nothing.

Also, whenever one of these tracked override host subchannels drops to idle or slides into a failed state, I want the policy to trigger name re-resolution so we can pull fresh endpoint info from the resolver. Oh and one more thing, the policy should keep reporting itself as READY to the parent as long as there are some subchannels available, no matter what state the override-targeted subchannel happens to be in.
