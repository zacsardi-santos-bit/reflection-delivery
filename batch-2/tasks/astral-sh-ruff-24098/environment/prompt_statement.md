I'm running into a false positive in the duplicate union member lint rule when f-strings use the self-documenting debug format (the `f"{x=}"` "show the variable name" syntax) inside type annotations. Two f-string literals that are visually different, say they differ in the whitespace around the expression name in the debug specifier, or they use different numeric notations for the same value like hex vs octal, are getting flagged as redundant duplicates in a union type. They shouldn't be. Those are genuinely distinct literal type members because the runtime output actually differs depending on how they were written, so treating them as the same thing is wrong, and it's worse than just noise because the lint may auto-fix by removing one of the union members and quietly change the type semantics.

While digging into this I also noticed the parser's AST for debug f-string expressions is incomplete. Right now the node records the leading and trailing text on either side of the expression but not the expression's own source text, so any tool trying to compare, format, or reconstruct these debug f-strings from the AST alone can't do it accurately. I want that fixed too: the debug f-string AST node should store the expression source text as its own field, sitting alongside the existing leading and trailing fields.

So two things. First, the AST node needs that expression source text field added. Second, the duplicate union member check should use the full source text, including the expression portion, when deciding whether two f-string literals are really equal. Actual duplicates with identical source text should still get detected and flagged like before, I just don't want the false positives on the ones that only look similar.
