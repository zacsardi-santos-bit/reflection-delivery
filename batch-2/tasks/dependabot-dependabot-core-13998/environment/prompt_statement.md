I'm working on Dependabot's Maven support and I keep hitting a problem with plugins that follow Jenkins' continuous delivery release conventions, the ones that embed a git commit hash right in the version string, like a build number followed by a dot (or hyphen) and then a hex string that pins the exact source revision. When Dependabot compares my current version against a newer candidate that uses the same pattern, it sees the hashes differ and decides the suffixes are incompatible, so it filters the upgrade out. That's wrong, and it leaves projects stuck on outdated plugins even when newer ones exist.

What I want is for the version type comparison logic to recognize this pattern and treat both versions as the same type when either or both contain an embedded git hash. A valid git hash here is 7 to 40 hexadecimal characters (a-f, 0-9), may optionally start with the letter "v", may contain underscores (Jenkins encodes certain uppercase hex letters that way), and must include at least one non-numeric hex letter. So if both current and candidate have embedded hashes, that's a compatible upgrade, and if only one of them does, still compatible. But strings that only look like SHAs but are too short, too long, all-numeric, or contain non-hex characters should not count as git hashes, they should fall back to the normal suffix comparison.

Oh and there's a related bug, a version string that starts with the word "RELEASE" followed by digits is being handled wrong. I need it recognized as a stable release so Dependabot won't suggest bumping it to some pre-release version. This all lives in the Maven version type comparison code under `@maven`, so that's where the fix goes.
