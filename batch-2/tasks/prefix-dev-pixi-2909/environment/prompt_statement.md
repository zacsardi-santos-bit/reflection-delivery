I'm bumping the conda typing library deps (the whole family we use for package specs and package records) to their newer releases and now the project won't build. The new versions added an "extras" concept, basically optional feature groups you can select when depending on a package, as a field on the match spec type, plus a field on package records for extra-specific dependencies, and both of those ripple through our code.

In our package spec module the compile breaks because we construct match spec structs without giving a value for that new optional-feature-groups field, so every place that builds a match spec needs to pass something for it. Also some of the enum variants that hold detailed package specs inline are now too big and need to move to heap-allocated wrappers (box them) to cut stack size. When a detailed version spec gets converted into a nameless match spec, make sure all the fields come across correctly including the new optional feature groups one.

Oh and the breakage isn't only in the spec module, it's downstream too, our auth middleware and other utilities that call into the updated networking APIs also fail to compile, so everything in the dependency chain of the package spec module has to build cleanly against the new versions.

What I actually want green: the package spec module compiles and its tests pass, specifically the ones checking whether a spec is correctly identified as binary, whether a detailed spec converts properly to a nameless match spec, and whether TOML-based specs round-trip (parse and serialize back) correctly. Also the integration test helpers that build package records need to initialize the new extra-specific dependencies field so those don't blow up either. Boxing the big variants is a nice stack-pressure win on its own, but the real blocker is that without this bump nothing in that module even compiles, which means none of its tests run.
