I hit a nasty correctness bug in ClickHouse's best-effort datetime parsing when the input string carries a timezone offset. When a value sits close to the boundary of the standard 32-bit date-time type's representable range, applying the offset to convert to UTC can shove it just outside that range, and right now nothing detects that. Instead of upgrading to the wider-range high-precision date-time type, it silently produces garbage, either wrapping around the upper limit or clamping at the lower limit, so you get data loss on edge-case but totally valid timestamps.

Concrete cases: a timestamp representing the very last second of the representable range in a timezone that's an hour behind UTC becomes a UTC time exceeding the max, but the parser doesn't notice and hands back a wrong date instead of picking the high-precision type that covers the wider range. And a timestamp right at the start of the epoch in a timezone ahead of UTC goes negative once converted, and rather than recognizing that and switching to the high-precision type, it keeps the standard type with a bogus (clamped to zero) value.

What I want: whenever the timezone adjustment pushes the UTC timestamp outside the valid range for the standard date-time type, either above the max or below the epoch into negative territory, the parser should recognize it and infer the wider-range, high-precision date-time type instead, preserving the actual UTC value. Anything whose timezone-adjusted UTC timestamp still fits inside the standard type's valid range should keep being inferred as that standard type, unchanged. This lives in the best-effort date parsing path, so the detection needs to happen right where the offset gets applied and the result type gets decided. It's a real data-corruption issue for users storing near-boundary timestamps with non-UTC offsets, so I care about the value staying correct, not just the type widening.
