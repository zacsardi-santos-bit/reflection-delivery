I'm hitting a wall with decimal fields in my Hudi ingestion pipeline. We pull JSON records off a message queue and decimal-typed fields come in as Base64-encoded byte arrays, basically the unscaled integer bytes of the decimal value, and when I run these through the JSON-to-Avro conversion layer the decimals just don't survive. Doesn't matter whether the target schema wants a byte-based decimal or a fixed-width one, the converter has no clue how to decode that Base64 payload into a real decimal, so values get silently mangled or the whole ingest blows up.

Two things I need on the Avro utilities class. First, a method that tells me whether a given Avro schema contains any decimal logical type field at all, and it's got to catch decimals wherever they live, top level fields sure but also decimals nested as map value types or as array element types. Downstream logic keys off that to decide if special decimal handling kicks in. Second, a method that takes the raw unscaled bytes of a decimal and converts them into the fixed-width Avro representation, so byte-encoded decimals can actually be written into fixed-type decimal fields correctly.

Then the JSON converter itself should lean on those two so it handles records where decimal fields show up as Base64-encoded strings. Whichever the schema expects, byte-based or fixed, it needs to spit out the correctly-typed and correctly-valued Avro field.

Oh and I also want the test data generator to support producing records that conform to a schema with multiple decimal fields, different precisions and scales, values encoded in this same Base64 byte format that mirrors real queue payloads, so I can write integration tests over the full ingestion flow. This matters because pipelines ingesting from queues run into byte-array-encoded decimals constantly, and without this the decimal just gets lost or the ingest fails. I want the value to survive the round-trip from source message all the way to the stored Avro record intact.
