I'm hitting a couple of related bugs in our editor extension's session event pipeline and want to fix both.

First one is about oversized events. Right now when a message produces an event that's too big (like a really long user request), the code just truncates the content, cuts it short, slaps on a truncation marker, and still lets the event through into the output. I don't want that anymore. When an individual event's estimated serialized size goes over the allowed max, I want the whole event dropped and excluded entirely, not trimmed. Two things have to happen when we drop: increment a counter on the session state so callers can see how many events got lost, and (this is the tricky bit) keep the parent-child ordering chain intact. The next kept event needs to link back to the last successfully kept event, not to the one we just dropped, otherwise we get dangling parent references pointing at IDs that don't exist anymore. That's exactly the corruption we're seeing today when oversized events get filtered in a later batch step, it wrecks the session history view and you can't reconstruct the conversation flow. This drop-instead-of-truncate logic needs to apply in both the span translator and the debug log entry translator, not just one.

Second thing, the max character lengths for user messages and assistant responses stored in the session database are hardcoded in a bunch of places right now. I want them pulled out as named constants exported from one shared module so the session reindexer (and any other consumer) can import and use them directly, so if the limits ever change everything stays in sync automatically instead of silently diverging. And the reindexer should actually enforce those exported limits, meaning stored user messages and assistant responses don't exceed them.
