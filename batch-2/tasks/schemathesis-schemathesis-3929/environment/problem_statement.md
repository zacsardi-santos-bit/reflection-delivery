I'm running Schemathesis against a Go-based API and it just doesn't get the validation errors my service sends back. When my API rejects a request because a field's too short, has the wrong format, sits outside a numeric range, or carries a value that isn't in the allowed set, Schemathesis can't learn anything from that feedback and keeps firing off inputs that trip the same constraint over and over, which drowns the real bugs. It already interprets 4xx validation envelopes from Python, JS, PHP, Ruby, and .NET frameworks to refine its test generation, so I want the Go validation ecosystem brought up to the same level.

The Go validator I use emits errors two ways: a compact text format that's a single error string describing which fields failed and why, and a structured JSON format that's a list of individual error objects, each carrying the violated rule, the constraint value, the namespace, and the field's data type. I want a new parser that recognizes both shapes as a go-validator envelope on a 400 response and tells them apart from the other frameworks' formats, and just as important, all the existing parsers should decline anything go-validator-shaped so observations don't get misattributed.

From the compact text form it should pull the self-describing stuff (required fields, format constraints like email, URL, UUID). From the structured form it should extract the full set: required markers, format expectations (email, URL, UUID, date, datetime), string and array length bounds (min, max, and exact-length), numeric range bounds both inclusive and exclusive on min and max, and enumerated allowed values. Build the parameter path from the namespace info, handling nested structs and array element references, and convert Go-style field names to their JSON counterparts. For GET (read) operations that take query params instead of a body, attribute the observations to the query location. And please silently skip any entry that's malformed, uses an unrecognized rule, or has a constraint value you can't interpret, don't blow up. This lines up with the existing parser code so look at how the other framework parsers are wired in and follow that pattern.
