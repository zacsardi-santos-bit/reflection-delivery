I'm adding AI content generation blocking trigger support to the Firebase CLI deploy flow. Right now if a developer writes a cloud function that hooks into AI content generation, either before or after the model processes a request, the CLI has no clue how to deploy or tear down those triggers, so people end up managing that registration by hand outside the normal deploy path which is error-prone and inconsistent with everything else. I want to fill in both the service layer and the underlying API client code.

On the service side I need validation that runs before deploy: if someone configures two functions for the same AI event type in the same scope (like two global hooks for the same event, or two regional hooks for the same event in the same region) deployment should fail with a clear error message about the conflict. But one global plus one regional hook for the same event type is fine, and hooks in different regions are fine, and functions for entirely different event types (say one before-generate and one after-generate) coexist no problem.

On the API client side I need functions to register (create or update) and unregister (delete) these triggers. When creating, if the trigger already exists, which the server signals via a conflict response, fall back to updating it instead. Any other server error during creation should propagate as-is, don't try to update in that case. Deletion should be tolerant of the trigger not already existing, so a missing trigger on delete isn't an error. Oh and for location, global triggers use a "global" location while regional triggers use the endpoint's own region. Wire this so registering happens when deploying such a function and unregistering happens when the function is removed.
