I'm working on the naming convention lint rule and I keep hitting a wall trying to configure it to allow non-ASCII characters in identifiers. Right now if I add an option to permit non-ASCII names I just get an error about an unknown config key, it's not recognized at all, so there's no way to opt in. I want a proper boolean option (call it something like allowNonAsciiNames) that when enabled suppresses diagnostics for identifiers containing non-ASCII characters. Teams writing code in non-English languages naturally use accented characters or non-Latin scripts in their variable and function names and they shouldn't have to fight the rule or disable it entirely.

Default behavior should stay strict though, so when the option isn't set the rule keeps rejecting non-ASCII identifiers, but with a clear diagnostic that actually explains what's going on and references the option name by name so devs know exactly what to flip on. Same for the hint message, point them at the option.

Oh and while I was digging into this I noticed two other things. Identifiers with consecutive underscores (like two underscores in a row between words) are currently accepted as valid constant-case, which is wrong, real constant-case only allows single underscores as separators. So the rule should flag those and suggest a properly formatted alternative. Also a couple of the existing strict-case diagnostic messages have slightly inconsistent wording that should get cleaned up for consistency and clarity.

Basically this closes a gap where malformed constant names slipped through and it unblocks multilingual codebases. Fix should live wherever the naming convention rule is defined.
