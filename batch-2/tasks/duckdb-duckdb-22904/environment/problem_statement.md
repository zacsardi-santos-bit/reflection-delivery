I'm poking at our CI test runner script and hit two things I want fixed. First one's small: when a test blows past the configured runtime threshold and we log that, right now the line looks identical to every other log line so people scroll right past it in long CI output. I want that message clearly prefixed as a warning so operators can eyeball performance regressions without digging. Just mark it as a warning condition, that's it.

Second one's bigger and it's about flakiness. We've got no way to confirm a newly added or selected test is actually stable, it might pass once in CI and then intermittently fail on reruns. So I want a stabilization mode, gated behind a flag, where after the normal full run each test in the list gets rerun individually a fixed number of times. Fast tests should get more reruns than slow ones since rerunning a fast test is cheap, so the per-test rerun count keys off whether a test's classified fast or slow.

Also this needs to kick in automatically when I'm using the changed-tests feature. If some tests show up in the changed list but weren't in the original base list, those brand-new ones should get auto-stabilized with the same per-test fast/slow rerun counts. Oh and one edge case: if there are more than 500 new tests, doing per-test reruns takes forever, so in that case just rerun the whole batch of new tests a small fixed number of times instead of repeating each one individually, keeps total runtime sane. And if any of these stabilization reruns fail, the whole pipeline should immediately report an overall failure with a clear error message in the output. The point is flaky or slow tests shouldn't silently sneak through a single run and surface later, this gives us an automated safety net plus visible warnings without manual log inspection.
