I'm hitting a nasty correctness bug in Flink's compressed operator state during checkpoint restore. When several state entries share a single compressed stream, the byte positions we record while writing turn out to be bogus seek targets on the way back in. Looks like the compressed output side reports its current position before flushing its internal compression buffer, so the offset we save doesn't line up with any real boundary in the underlying raw byte stream, and later seeking to it returns garbage. So the output stream's position accessor needs to fully flush first, and only then report where we are, so that recorded offset is actually a reliable seek target.

The read side has its own problem: when the compressed input stream seeks to a new position in the raw byte stream, it doesn't drop the decompressed bytes it already has buffered. Those stale bytes get handed back by the next reads instead of the data at the new position. Classic case is reading only part of an entry, then seeking elsewhere, and the leftover buffered bytes corrupt what I read next. So seeking has to discard any buffered decompressed data before it repositions.

Between the two, snapshot restore silently returns wrong or missing values whenever compression is on, which hits every job using compressed state that reads back individual entries by their stored offsets (the normal restore path for partitioned list and broadcast states). Once both sides are fixed, operator state snapshot and restore should come back correct both with and without compression, covering empty states, states merged from multiple handles, and states repartitioned across different parallelism levels. Please fix the flush-before-position on the compressed output side and the discard-before-seek on the compressed input side.
