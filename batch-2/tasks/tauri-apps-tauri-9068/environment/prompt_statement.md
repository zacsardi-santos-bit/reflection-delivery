I'm chasing down a bug in Tauri's ACL resolution where scopes from multiple capabilities for the same command get incorrectly merged. Say two capability files both grant the same command but with different path scopes, one scoped to config files and another to resource files. Right now the resolver collapses those into a single combined entry, so the merged scope ends up applying across all windows instead of staying pinned to the window and capability that actually defined it. That breaks least privilege, which is the whole point of the capability system, developers expect a scope defined for a specific window to only apply there, not bleed into unrelated windows.

The fix is really about how resolved command permissions get stored. Instead of a composite key that groups by both command name and execution context, I want the map keyed by command name only, and each value should be a list of individual resolved entries. Every permission grant produces its own separate entry carrying its own context, window patterns, and scope identifier, rather than being folded together with other grants for the same command. So the execution context moves out of the map key and into each individual resolved entry.

Also the scope identifiers, right now they're derived by hashing scope content, I want them to become sequential integers assigned in the order scopes are encountered during resolution. That makes the output deterministic and way easier to inspect. And this needs to hold up in multi-window setups where one window has capabilities with several different path scopes and another window has a simpler read-only capability, each grant's scope stays tracked independently with no cross-window bleed-over. A command allowed by multiple capabilities with different scopes should show up as multiple independent entries, and the same command granted to different windows by separate capability files should stay as independent entries too.
