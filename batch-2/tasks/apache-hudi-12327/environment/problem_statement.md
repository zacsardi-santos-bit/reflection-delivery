I'm working on the version upgrade/downgrade handlers in Apache Hudi, the ones that migrate a table between the older and newer table format versions. Right now when I flip a table between versions the config props don't fully carry over, so I end up with stale or missing settings around partition fields, record merge strategy, bootstrap index type, key generator type, and the initial table version marker, which leaves the table in an inconsistent state that bites me later on reads and writes.

What I want is proper property migration on both paths. On upgrade (older to newer) the handler should record the initial table version, derive and set the correct record merge mode off the existing payload class config, populate the bootstrap index type from its class name, carry over the key generator type from its class name, and set the partition fields, all based on the existing table config. On downgrade (newer back to older) it should do the reverse: drop the newer version's initial version marker, remove the record merge mode prop and swap in the equivalent legacy payload class name, and strip out the bootstrap index type and key generator type fields since those don't exist in the old format.

I'd like these done as static utility methods on the respective upgrade and downgrade handler classes so they can get invoked during the actual upgrade and downgrade flows. Each method takes the write config, the current table config, and the map of properties to add, and reads/writes against those inputs. Basically both directions need to handle every one of those relevant props so a version transition is safe and doesn't leave anything inconsistent behind.
