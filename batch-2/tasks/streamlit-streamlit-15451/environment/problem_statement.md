I'm doing a refactor on Streamlit's internal runtime, specifically how per-run mutable state is organized inside the script run context. Right now the context object has a bunch of related fields sitting as top-level attributes: the widget ID tracking sets, form tracking sets, fragment tracking sets, and command telemetry are all just scattered directly on the context. It makes it awkward to reset them atomically and hard to reason about which state is actually shared across threads during a single run, which matters for correctness when you've got parallel fragments running.

What I want is a new dedicated container class that groups all this shared mutable state together (widget ID sets, form ID sets, fragment ID sets, and the command telemetry). The context should then hold a single instance of this container as one attribute, and any code that needs those sets or telemetry accesses them through the container instead of poking the context directly.

The container needs a reset method that clears everything in one call, so all the sets get emptied and telemetry goes back to empty state. For the command telemetry bit specifically, it should store tracked commands in a thread-safe way so concurrent writes from multiple threads don't lose any entries, it should return an immutable snapshot of recorded commands (not a mutable list you could accidentally mutate), expose a count of how many commands are currently stored, and support a per-command cap limiting how many times a single command name shows up in the stored list while still tracking the raw total count for each name separately. Oh and each context instance needs to own its own independent container, not share one across context instances, and when the context itself gets reset the container's state should clear too.
