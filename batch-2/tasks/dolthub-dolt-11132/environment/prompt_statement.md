I'm chasing a really nasty data corruption bug in Dolt that only bites people who created tables on an older version and then upgraded. The newer version picked a different default storage encoding for text, blob, JSON, and geometry columns, and here's the problem: any ALTER TABLE on one of these legacy tables, even something totally unrelated like dropping some other column, silently rewrites the schema record so the affected columns now claim the new encoding default. But the actual on-disk row data never gets rewritten, so it's still sitting there in the old format. Everything looks fine until someone queries those columns later and the reader expects one storage layout but hits the other, and the whole thing crashes with errors about malformed or unexpected data structures. Super subtle because the corruption and the crash are separated in time.

What I want is for the schema-modification path to preserve a column's existing persisted storage encoding rather than stomping it with the current global default, as long as the column stays in the same type family. So widening a text column, or dropping an unrelated column and leaving the survivors alone, should carry the original encoding forward untouched. The only time it's ok to let the new default apply is a genuine cross-family type change, like flipping a column from one kind of text-type to a completely different kind. The invariant I care about is no silent encoding flip on a same-family column during any schema modification, and it has to cover all four families: text, blob, JSON, and every geometry type. Net result, tables made on older versions stay readable, no panics, after running schema changes on a newer version. This matters because upgraders usually have real existing databases and right now a routine maintenance ALTER can quietly turn into a data-loss event.
