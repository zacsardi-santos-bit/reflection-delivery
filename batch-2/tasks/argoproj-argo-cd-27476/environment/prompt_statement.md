I'm hitting a real annoyance where cluster operations in Argo CD blow up when the main system secret doesn't have its crypto key field populated. Creating/registering a cluster, listing clusters, watching for cluster changes, and resolving a cluster's server address by name all fail in that situation, even though none of them actually care about that key. The root cause is they all call the general settings loader on the settings manager, which validates the whole secret (including the key) before returning anything. During bootstrapping or in certain deploy configs that key just isn't there yet, and it shouldn't matter.

The only thing these cluster ops really need is a single boolean: is the in-cluster Kubernetes API server allowed as a cluster or not? And that value lives in the configuration map, not in the secret. So I want a lightweight method on the settings manager that reads just that one setting straight from the config map, no full settings load involved. It should default to enabled when the key isn't explicitly set in the map. And when the config map itself can't be found, it should still return the default (enabled) but hand back an informational error too so the caller knows something's off.

Then go update all the cluster operations that currently check whether in-cluster is enabled so they use this new lightweight method instead of loading full settings. The goal is those ops (registering, listing, watching, name resolution) succeed when the secret is missing its crypto key, as long as in-cluster isn't explicitly disabled. But if an admin has explicitly turned off in-cluster access in the config map, then trying to register an in-cluster cluster still needs to get rejected with a clear error. Operators and automated provisioning tools shouldn't be blocked from managing clusters just because the system secret hasn't been fully initialized, since this check is independent of the crypto key anyway.
