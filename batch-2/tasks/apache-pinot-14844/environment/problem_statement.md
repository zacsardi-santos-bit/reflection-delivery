I'm trying to lock down the Groovy transform function support in Apache Pinot because right now any Groovy script embedded in a SQL query can run shell commands, call system-level stuff, or import arbitrary Java classes with zero checks, and that's a real problem for any deployment where query input isn't fully trusted (data exfil, crashing the server, host access, the whole mess). I want a configurable static analysis layer that inspects Groovy scripts before they execute.

The policy config should drive everything: a list of allowed class receivers, allowed imports, allowed static imports, disallowed method names, and a flag for whether method definitions are permitted at all. It needs sensible defaults (ship default allowed-receiver and allowed-import lists) plus a factory method that hands back a default configuration. It's gotta be JSON-serializable so I can store and distribute it as part of system config, and it has to survive a full JSON round-trip (serialize then deserialize) with no data loss. Also the config must be swappable at runtime, so setting a new one immediately affects all subsequent validations, and setting it to null disables the analysis entirely, no restart needed.

For the actual analysis, reject scripts that try to run shell commands (like executing a string or list as a process), invoke system exit, reach forbidden class hierarchies through indirect imports, or call other disallowed operations. Each violation type needs its own descriptive error message so whoever's operating this can tell what got blocked. Oh and Groovy function calls in a query must have at least 2 arguments, fewer should be treated as invalid with an appropriate error.

Then there's the query-validation logic that can globally disable Groovy. Update it so it either rejects all Groovy queries outright with a clear "disabled" error, or, when Groovy's permitted, runs the static analysis against any Groovy scripts found across all the query clauses (SELECT, WHERE, HAVING, ORDER BY, GROUP BY). Basically the disabled path short-circuits with the disabled message, and the enabled path funnels everything through the policy checks.
