I'm hitting a nasty bug in our workflow orchestration system, specifically the bulk task run event recorder. Right now when multiple events collide on the same logical task it just blows up with a database integrity error instead of dealing with it, and that fails the whole batch and forces the consumer into retry logic that doesn't even fix anything. Two kinds of collisions happen: two events that describe the same logical task (matching flow run identity, task key, and dynamic key) but carry different internal task run IDs, or events sharing the same task run ID that show up more than once with updated state or metadata. This is normal in distributed land, tasks get retried, events get replayed, multiple workers emit for the same logical task at once, so I want it handled gracefully, not crashing.

What I need: when conflicting events arrive, whether in the same batch or across separate batches, update the existing task run to the latest state and metadata instead of raising. When two events describe the same task but carry different identifiers, consolidate them onto one canonical record and don't leave the duplicate identifier hanging around in the database. All state records from every conflicting event need to end up attached to that single surviving canonical record, and both the state's task run reference and the internal detail reference inside the state details must point at the canonical record, with the full chronological state history preserved. Oh and chains matter too, where one event's identifier overlaps an existing record and another event's natural key overlaps the first, all of it should coalesce onto one canonical record.

Also, and this is important for avoiding deadlocks, order the rows submitted during bulk insert by the natural conflict key so concurrent recorders acquire row-level locks in the same order every time.
