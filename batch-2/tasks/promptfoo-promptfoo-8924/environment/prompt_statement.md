I'm cleaning up the eval API on our server and there are a couple of gaps I keep bumping into. First, we don't have formal response schemas for two of the eval endpoints, and malformed responses could slip out to clients without anyone noticing. I want a schema for the eval table API response that validates the whole envelope shape, so the table object plus the counts, metrics, config, author, version, id, and stats fields. Important thing though, it has to validate the table body shallowly, meaning just confirm the body is an array without reaching into individual row items, because those rows get really big and deep-parsing them would be expensive. Oh and it should reject the case where version comes through as a string instead of a number. Then for the rating submission response I just want it validated as a simple message envelope. Both of these need to be reachable through our existing schema registry under the right namespaces (see the eval type definitions for where these live).

Second thing is query param validation on the eval table endpoint. Right now it happily accepts any string for the export format and any decimal for pagination, which means we silently take inputs we can't actually handle and blow up downstream. The format param, when given, should only be one of the recognized export formats, and limit and offset should be whole numbers (decimals aren't valid). When any of these fail I want a 400 back with a message that says which parameter was bad, and it's gotta happen before we touch the database, no db calls on invalid input.
