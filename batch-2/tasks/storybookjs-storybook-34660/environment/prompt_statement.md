I'm adding an automated codemod to the Storybook React Native generator that patches a project's Metro bundler config during Storybook init. Right now people have to hand-edit the Metro config after running the initializer and it's a real friction point, the required changes are non-obvious and setup fails a lot because configs can be CommonJS or ESM, might be TypeScript, and projects can be Expo or plain React Native. I want the codemod to run as part of the RN generator during init, read the Metro config file, figure out its module format, and wrap the exported config with the Storybook integration helper while injecting the right import at the top.

A bunch of edge cases matter here. If the config already imports/uses the Storybook integration it should skip silently and not touch the file, and running the codemod twice should be idempotent with no duplicate changes. If multiple Metro config files exist, prompt the user to pick one. For Expo projects, try generating the Metro config via the Expo CLI first before proceeding. If the config is missing and we're not in non-interactive mode, prompt for a custom path. And if the export shape is unrecognized and can't be transformed automatically, fall back to prepending a guiding comment and report the result as a fallback.

Module format detection needs to be careful, oh and files with certain extensions should always use ESM-style imports, while files that look like ESM but have that syntax hidden inside template literals should still get the CJS form. If the config already imports the integration helper under an alias, reuse that alias instead of adding a duplicate import. Also TypeScript type annotations on exported functions have to survive the transform intact, and any leading file-level pragmas (type-check suppression comments, strict-mode directives) must stay at the very top of the file after the import gets injected.
