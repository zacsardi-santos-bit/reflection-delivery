I'm hitting a nasty correctness bug in the deep learning framework we support that handles multiple integer element types for tensors. When I do a bitwise left shift on an integer tensor, the results come out wrong for basically every integer type except one specific 32-bit unsigned type. Digging in, it looks like the GPU/JIT backend is silently converting all the integer operands to that one fixed 32-bit unsigned type before doing the shift, and then handing back the result in that fixed type instead of the original declared element type. So a 16-bit tensor, a 32-bit signed tensor, a 64-bit tensor, they all get the wrong answer because the type got swapped out from under them.

What I want is for the bitwise left shift (and the analogous shift ops) to actually operate on the tensor's native integer element type with no silent upcast or conversion sneaking in beforehand. A shift on a 16-bit int tensor should give 16-bit results with 16-bit shift semantics, a 32-bit signed tensor should give 32-bit signed results, a 64-bit tensor should give 64-bit results, and in general the declared native integer type needs to be preserved and used all the way through the operation rather than getting quietly changed.

Oh and while you're in there, the existing test for bitwise left shift needs a guard so it skips for very small integer types (like 8-bit) where the test values would overflow the type, since those cases aren't meaningful with the current test data and just produce misleading failures that hide the real correctness issue. This matters because bitwise ops show up in numeric algorithms, hash computations, and low-level data manipulation, and silently getting wrong results from a type swap is exactly the kind of bug that's brutal to track down.
