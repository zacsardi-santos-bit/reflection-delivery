So I'm chasing down a storage leak in our Ozone object store around how block cleanup works during commit. The gist is clients pre-allocate more storage blocks than they actually use, and during commit only the blocks they really wrote get finalized. The leftover allocated-but-unused blocks are supposed to be scheduled for garbage collection, but that's not happening in all cases right now, so we're silently leaking storage capacity that can't be reclaimed without manual intervention.

Two specific gaps. First, when committing a part of a multipart upload, the pre-allocated blocks that never got committed aren't being queued for deletion at all, so they end up orphaned forever. Second, overwrites with uncommitted blocks. When an existing key or multipart upload part gets overwritten and the new write itself also has uncommitted blocks, neither the old version's blocks nor the new write's uncommitted blocks get fully accounted for.

Here's how I want the cleanup queue to break down. Whenever a commit confirms fewer blocks than were allocated, the surplus allocated blocks need scheduling for deletion. For a multipart upload part commit that only has uncommitted blocks and no overwrite, the response should carry exactly one deletion entry for those uncommitted blocks. For a multipart part overwrite without uncommitted blocks, one entry for the overwritten part. For a multipart part overwrite that also has uncommitted blocks, keep them as two separate deletion entries (old part's blocks and the uncommitted blocks tracked apart). And for a regular key overwrite with uncommitted blocks, it's one entry that contains both the overwritten key and the uncommitted pseudo-key together.

The commit response objects need updating so they carry a map of keys to their associated block lists that need deleting, and that map has to be exposed through the response so callers can inspect what's queued for cleanup. Then all entries in that map must actually get written to the deleted table when the response is committed to the database during the batch write. That last part matters, oh, it's the whole point, otherwise nothing gets reclaimed.
