I've got a lint rule in my linter that flags string literals sitting directly inside exception raise statements, and it also ships an autofix that pulls the string out into a local variable and then references that variable in the raise instead. The bug is the fix always picks the same hardcoded variable name every single time, no matter what's already going on in the function. So if I've already got a variable defined earlier in the same scope with that exact name, applying the fix silently clobbers it (shadows it, really), and any later code that referenced my original variable now unexpectedly reads the freshly introduced one, which quietly changes the program's behavior in a way that's a pain to track down. An autofix should never introduce a correctness regression like that, especially when it was only meant to clean up a style nit.

What I want is for the fix to be smarter about naming. Before it commits to the default variable name, it should check whether that name is already bound in the current scope, and if it is, fall back to a non-conflicting alternative, like appending a numeric suffix and incrementing until it finds a free name. My existing variable with the conflicting name has to stay completely untouched after the fix runs. This needs to work for all the variants the rule handles, so plain string literals, f-strings, and format-method strings inside raise statements should all generate correct fixes.

Also the snapshot files the tests compare against need updating to match this behavior, both the new case where a conflicting name is present and picks the suffixed alternative, and the existing fixtures where a prior binding of the same name already shows up. A good sanity check is a function that defines a variable and then raises an exception with a string literal inside a try block, it should get a fix using a fresh, non-conflicting name rather than reusing the one that's already there.
