I'm on TypeORM's Expo SQLite driver and want to kill the boilerplate where people have to hand-inject the SQLite library module into their data source config. In the latest TypeORM this manual injection is pointless since the framework can load the lib itself, so I want that driver field in the config to become optional, and when it's omitted TypeORM should auto-load the appropriate Expo SQLite library on its own.

While I'm in there, the driver should validate whatever module it ends up with, whether the user passed it explicitly or it got auto-loaded. Older Expo SDK versions only exposed a legacy synchronous API and we only support the modern async one now, so if the module lacks that async API I want a clear error telling the user to upgrade to a newer Expo SDK version, and this should fire for both the explicit and the auto-loaded case. If the library isn't installed at all, throw a descriptive package-not-installed error naming the missing library. Oh and be careful, errors from other missing packages that the lib itself depends on (transitive deps) should be re-thrown as-is so we don't misattribute them to the Expo SQLite package being missing, and any other unexpected load errors get re-thrown unchanged too.

Also I need a codemod transform to clean up existing codebases by stripping the now-redundant explicit driver injection from Expo data source configs. It should only remove the driver when the value is confidently the plain default import of the SQLite library, so don't touch member-access extractions like reaching for the default export, don't touch values assigned from a variable, and don't touch a different or patched package. And it shouldn't mess with objects that just happen to share property names but aren't really data source configs, specifically leave alone any object missing a database property even if the type value looks right. It's gotta handle quoted property keys, exported default configs, factory/spread patterns, and the case where driver is the only extra property in the object.
