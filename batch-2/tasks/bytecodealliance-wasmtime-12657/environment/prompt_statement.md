I'm hacking on the component bindgen in wasmtime and hit two things that block valid binding configs. First problem is host resource drop handlers. The generated glue for a resource's drop just returns the drop result directly, which is fine for the normal result type but falls apart the moment I turn on the flexible error handling mode, because now the drop handler's return type doesn't match what the runtime expects anymore. I want folks implementing host resource drop methods to be able to return either the standard result type or the extended result type that flexible mode uses, and the generated code should convert transparently. So instead of returning the drop result naked, route it through the uniform result-conversion trait wrapper (the same standard conversion path everything else goes through) so the return type checks out no matter which mode is active.

Second thing, and it's related, I can't combine the flexible error handling mode with custom error type remapping in the same binding definition right now. The two options are basically mutually exclusive because of how they interact in the code generator, so I get a compile failure even though they should play fine together. I'd expect to write one macro invocation that specifies both the flexible error mode and custom error type mappings and get correct, working binding code out of it. No reason to force a choice between flexible error propagation and custom error remapping when both are genuinely useful at once.

So to boil it down, the drop handler codegen should always wrap its result through the standard result-conversion trait so the return type works in all modes, and the binding macro should accept the flexible error handling option alongside custom error type mappings without erroring out. This matters because anyone doing host-implemented resources needs the full range of error handling options without artificial limits, otherwise turning on flexible mode breaks resource cleanup and pairing it with custom errors just won't compile.
