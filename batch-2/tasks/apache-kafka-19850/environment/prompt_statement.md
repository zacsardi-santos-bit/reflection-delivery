I'm adding rack awareness to the Kafka producer's built-in partitioner and could use a hand wiring it through. Right now when a producer sends records the partitioner picks partitions with no idea which availability zone or rack the leader broker sits in, so in cloud deployments we end up shipping records cross-zone even when there's a local option, which bumps both latency and the metered network cost. What I want is for the built-in partitioner to take config for the producer's own rack identifier and prefer partitions whose leaders live in the same rack. When all the local-rack partitions go offline it should fall back gracefully to partitions in other racks so we keep sending, and once local ones come back it should return to preferring them. And if the brokers don't advertise any rack info at all, the partitioner needs to behave exactly like before and treat every partition equally, no special casing.

This also has to play nice with the adaptive load-based partitioning path. When rack info is available the adaptive logic should focus on rack-local partitions, and I want a way to query how many of the load-stats entries correspond to the local rack (basically expose the size of the rack-local portion of that stats table). Oh and the partition load stats update method should be extended to accept rack information for each partition too, so the stats it builds know the rack layout.

Last thing, over in the record accumulator the partitioner config and the factory method that creates partitioner instances both need updating to carry the new rack-aware flag plus the rack identifier through to the partitioner so it actually gets the values. Look around the built-in partitioner and accumulator code for where these hook in. The whole point is letting operators keep producers local whenever possible for better latency and cost, without losing availability when local partitions drop.
