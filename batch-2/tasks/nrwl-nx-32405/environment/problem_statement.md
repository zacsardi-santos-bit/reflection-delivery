I'm hacking on our TypeScript plugin for the monorepo build system and hit two related snags around output tracking. First one: when a TS library project doesn't set an explicit output directory (`outDir`) in its compiler options, the plugin right now falls back to a single directory path as the build output, and that just doesn't capture everything TypeScript actually emits. I want the fallback to instead be a set of glob patterns covering all the common compiled artifact types, so JavaScript files, source maps, declaration files, declaration maps, and build info files, all scoped to the project root. The current behavior makes task caching unreliable for these projects, it ends up marking too many or too few files as outputs so builds get re-run unnecessarily or outputs don't get tracked right, especially for packages that compile output inline alongside their sources.

Second thing, there's a helper buried in the plugin that decides whether a package is genuinely set up for building versus being a source-only library. It looks at the compiler options plus the package's entry points (the exports config or the legacy entry point field) to figure out whether the published API points at compiled output rather than raw `.ts` source. I want that pulled out and exported from a utility module so it can be tested and reused on its own, properly typed. It's gotta handle all the modern export shapes: the primary root entry (`.`) as either a string or a conditional object, null entry points, wildcard patterns, and the legacy `main` style field too. And it needs to cover all three cases correctly, when an output file is explicitly configured, when an output directory is explicitly configured, and when neither is set (in which case it falls back to checking whether the entry points reference files outside the TypeScript include patterns, i.e. non-source files). Can you knock out both of these?
