I'm working with our distributed tracing SDK and I keep hitting a wall with how parent-child span relationships get set up. Right now the only way to make a new span a child of another is if the parent is actively attached to the current scope, which means I can't attach a new span to a parent that already ended or one that was created in some other context. I want to just pass the parent in directly.

So here's what I'm after: all three of our span creation utilities (the auto-finishing one, the inactive one that doesn't get set on scope, and the manually-finished one where I control ending) should accept an optional parent span as part of their options. When I hand it an explicit parent, the new span needs to record that parent's span ID as its own parent span identifier, and it shouldn't matter at all whether that parent is currently active on any scope. Establish the relationship based on whichever span I pass in, not whatever happens to be active at the moment. This is really about building custom span hierarchies without me having to poke at scope state, so I can associate async work or work in a different context with a span that started (and maybe already finished) somewhere else.

Oh and while we're in there, for the manually-managed spans I want to simplify how they get finished. Right now there's a separate finish helper passed as a second argument to the callback, and I'd rather just call the span's own end method directly. Drop that finish-callback helper parameter entirely, it's unnecessary indirection.
