I'm hitting a fairness problem with Kueue's wait-for-pods-ready feature. When a workload gets evicted because its pods didn't become ready before the timeout, Kueue re-queues it but sorts it in the scheduling queue using the eviction time instead of when it was originally submitted. So a workload that had been running and got evicted can land behind newer workloads that showed up while it was running, even if those arrived way later. It ends up looking "newer" than it actually is and waits longer than it should.

What I want is a configurable knob inside the existing pods-ready waiting settings that lets operators pick which timestamp drives the ordering of re-queued workloads. Two strategies: an eviction-timestamp mode, which is the current behavior where the workload is treated as if it arrived at the moment of eviction, and a creation-timestamp mode, where the workload keeps its original submission time so it retains its priority position and isn't penalized for getting evicted. The eviction-timestamp strategy stays the default so existing behavior is preserved and it's backward compatible.

The behavior I'm after: when creation-timestamp mode is active, a workload submitted earlier than a competing workload should get re-admitted first after eviction, even if that competitor has been sitting in the queue since before the eviction happened. And this needs to hold consistently in both the blocking and non-blocking pods-ready admission modes. The idea is transient pod readiness issues shouldn't cost a workload its queue spot, so operators can tune scheduling fairness for their setup.
