I'm hacking on Kopia's backup engine and hitting nasty GC pressure under load. The hot paths (encryption, compression, that kind of in-memory work) allocate fresh temporary byte buffers on every single operation, and under high-throughput concurrent workloads the garbage collector just melts. I want to add a reusable buffer pool to the internal utilities so I can pre-allocate a fixed set of fixed-size memory segments up front and then hand out slices from them on demand, recycling them across goroutines instead of churning the heap.

Here's what I need from it. I want to create a pool with a configurable segment size and an identifier string, and be able to add segments to grow its capacity. When I allocate from the pool I need back a buffer with exactly the requested size (both length and capacity have to match, not just length), and the buffer should report itself as pooled so callers can tell where it came from. Releasing a buffer returns it for immediate reuse. If the pool is nil or otherwise unavailable, allocation should fall back gracefully to a plain heap allocation without panicking, and that returned buffer should correctly say it's not pooled. Releasing a non-pooled buffer has to be safe too, no panic whether or not it actually came from the pool. Oh and the pool needs to be closeable to stop whatever background work it spawns.

The payoff I'm after: under realistic concurrent load, many goroutines each doing millions of allocate/release cycles, using the pool should cut total heap allocation dramatically compared to allocating fresh each time (think kilobytes, not megabytes), so the footprint stays basically constant after warmup.

Also, separate but related, the block manager doesn't currently clean up the buffer pools it holds when its own close runs, which risks goroutine leaks in long-running or repeatedly-opened sessions. I want its close method to actually shut down all associated resources (including those pools) and return a nil error when everything tears down cleanly.
