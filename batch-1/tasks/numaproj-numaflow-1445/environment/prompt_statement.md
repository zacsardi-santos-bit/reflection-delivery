I'm making two changes to our streaming pipeline framework and could use a hand wiring them up.

First thing, the three windowing strategies we've got, fixed, session, and sliding, all need their constructors to take a vertex instance as an extra parameter on top of the timing config they already accept (window duration for fixed, gap for session, length plus slide for sliding). Right now there's no way for a windower to know which vertex or pipeline it's running on, so it can't tag anything. I want to pass that vertex context in at construction time and have the windower hang onto it so we can later emit per-vertex, per-pipeline window count metrics for observability. That's the whole point, operationally we need window metrics tied to specific vertices and pipelines.

Second, our built-in tick-based message generator currently spits out messages at a fixed rate with deterministic event times, which is fine except I can't easily test out-of-order handling in reduce pipelines. So I want an optional jitter field (a duration) in the generator config. When it's set and positive, say 10 seconds, each generated message's event time should get randomly shifted back by 0 to 10 seconds relative to actual generation time, so messages look like they arrived out of order by up to 10s. When jitter isn't set or is zero, behavior stays exactly as it is today, no changes.

Oh and as part of that, the internal helper that converts nanosecond timestamps into time values needs to take the jitter duration as a second parameter now. With jitter at zero it behaves like before, returning the exact time for valid timestamps and the current time for invalid ones. Also I want to drop the old approach of parsing event time back out of the JSON payload and instead just use the event time directly since we already know it at generation time.
