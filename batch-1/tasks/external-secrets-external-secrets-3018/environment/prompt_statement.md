I'm trying to get external-secrets working against a Vault instance that's locked down with mutual TLS, so Vault wants the client to present its own cert when connecting, not just verify the server. Right now the Vault provider only lets me point at a CA cert for verifying Vault's identity, but there's no way to hand it a client certificate and private key, which means anybody running Vault with client certs required at the transport layer is stuck. I want to add client-side TLS to the Vault store spec so I can stash the client cert and the client key in a Kubernetes secret and reference them from the store config, basically the same shape as how the CA cert reference already works.

A couple things I care about behavior-wise. The store validation needs to require both the certificate reference and the key reference together, so if I only give one of them it should get rejected instead of silently half-configuring. Then during Vault client init the referenced secret(s) get fetched and the TLS credentials loaded, and if the key material is malformed I want a clear error back rather than some cryptic failure, and if valid creds are there the client should init fine and actually use that client cert for all its connections. Oh and while you're in there, when a Kubernetes secret lookup fails during init the error should include the secret's namespace, right now it's a pain to figure out which namespace the missing secret was in. This all lives in the Vault provider code so the spec types and the client init/validation logic are what need touching. Lots of orgs run Vault with mTLS for the extra security layer and without this external-secrets just can't talk to them.
