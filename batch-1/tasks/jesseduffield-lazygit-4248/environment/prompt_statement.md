I'm hitting a nasty bug in lazygit where our fast goroutine ID lookup is handing back the wrong value. If I grab the current goroutine's ID via the fast library and then compare it to what I get by parsing the ID straight out of the Go runtime's stack trace (the number after "goroutine " at the top of the stack dump), the two don't agree. Pretty sure the library just hasn't kept up with changes to Go's internal goroutine struct layout that landed in a recent Go release, so it's reading the wrong offset and silently returning garbage.

This matters because we lean on a deadlock-detection library too, and that thing internally depends on the same goroutine ID lookup, so if the IDs are wrong then deadlock detection, goroutine tracking, and general debugging all get unreliable. What I want is for the fast lookup to return the exact same ID the runtime reports for the current goroutine.

Can you bump these dependencies to versions that correctly support the current Go runtime, both the goroutine ID library and the deadlock-detection library that depends on it, keeping them at mutually compatible versions? The vendored copies need updating to match too, so `@go.mod`, `@go.sum`, and the relevant packages under `@vendor` should all reflect the new versions. Goal is just that fast lookup == runtime-reported ID again.
