I'm cleaning up the executor setup in this build tool library and it's driving me nuts. Right now every call site that wants an executor has to hand-initialize the config object field by field, which means everyone needs to know the exact internal field names and types, so we've got this tight coupling everywhere and no way to bake in defaults, you always spell out every field even when the zero value would've been fine. I want to add a constructor that takes a variadic list of option functions, spins up a new executor with sensible defaults, applies each option in order, and hands back the configured thing. Basically a functional-options pattern.

Each knob should get its own named option function following whatever naming convention the codebase already uses, so working directory, the stdout/stderr/stdin writers, temp directories, force flags, network settings, verbose/silent/dry-run modes, concurrency, output style, all of it. Oh and one thing that really bugs me: turning on verbose logging today means importing an internal logger package and building a logger object as a separate step, which leaks an implementation detail out to callers. After this, verbosity should just be one more option function, no separate logger construction or import needed.

It's gotta be a drop-in replacement for the direct field init, so every existing executor method keeps working exactly the same once you build it this way, identical behavior. A few fields that only matter in weird cases, like terminal simulation during testing or user working directory overrides, can stay directly settable on the returned value, they don't need their own option functions. The whole point is to hide the config behind a stable API so we can add fields or change defaults later without touching every call site, and honestly it just reads way cleaner when you only list the options you actually care about.
