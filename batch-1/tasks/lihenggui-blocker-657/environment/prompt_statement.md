I'm building out the app-detail screen in the Blocker app and there's a gap I need filled. Right now when someone opens an app and looks at its components (activities, services, receivers, providers) they all just dump onto the screen and there's no way to search by keyword or reorder any of it. With apps that have hundreds of components this gets unusable fast, people need to find a specific receiver or service quickly and see whether it's actually running or blocked.

So I want a new use case that takes a package name plus an optional search keyword and returns a stream of results grouped by component type. If a keyword's passed, only components whose name contains that keyword show up, otherwise return everything for that package. The results need to be sorted per the user's configured preferences, either by the component's short name or its fully-qualified name, ascending or descending, and it also has to respect a show-priority setting that pushes disabled-first, enabled-first, or no priority. Oh and running services need to be detected and flagged as running in the results. If the package name doesn't match any installed app, just return an empty result.

Also, separate cleanup while I'm in here: the component-detail repository contract is named with an "I" prefix like it's an interface, which doesn't match how our other repository contracts are named. Drop the prefix so it follows the same convention as the rest, and update anything that implements or references it, including the test doubles in the unit tests. The fake for that repo also needs its data-injection method changed to accept a list of items instead of a single one, and the fake service controller needs a way to inject a set of running service names so tests can actually verify the running-service detection works.
