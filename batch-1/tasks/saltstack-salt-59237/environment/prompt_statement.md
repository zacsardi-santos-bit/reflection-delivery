I've been looking into how Salt minions handle return retries and noticed that the configured retry count isn't actually being passed to the transport layer when sending data back to the master. There's a minion option that lets you control how many times the minion should retry a return send, but when the actual channel send calls are made — both for synchronous requests and asynchronous requests — the retry count is never included in the call. The mine data send has a similar problem: it's not passing a timeout or retry count to the channel at all.

The result is that the retry configuration has no real effect on what the transport layer does. I'd expect each of these sending methods to forward the configured retry count to the channel, so the retry behavior is actually honored. Can you fix the minion's request and mine-send methods to include the retry count (and timeout, where missing) when calling the channel's send operation?
