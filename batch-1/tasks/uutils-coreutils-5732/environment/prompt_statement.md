I'm hacking on the `head` utility and hit two annoying things. First one, when I pass a negative count to print everything except the last N bytes or lines (the `-c -N` / `-n -N` style), it falls over on those special Linux virtual filesystem files under `/proc`. Those pseudo-files get generated on the fly by the kernel, they report a size of zero, and they don't support seeking at all. The current backward-reading logic assumes it can seek to figure out the file bounds before reading in reverse, so on something like `/proc/version` it either fails or spits out nothing. What I actually want is for `head -c -5 /proc/version` (and the lines equivalent) to succeed and give me real non-empty output, matching what GNU coreutils does. So when seeking isn't available I need it to fall back gracefully and just read the content sequentially, buffering as it goes, then output all but the last N bytes or lines instead of relying on a seek to the end.

Second thing, smaller, the error message that shows up when someone gives a count value that's too big for the platform to handle only talks about bytes right now, but that same overflow can hit in lines mode too. So I want that message updated to say both bytes and lines can trigger it, not just bytes, since it's misleading otherwise.

Both live in the head implementation, so check around `@src/uu/head/src/head.rs` for the count parsing, the overflow error text, and the backward/seek-based reading path that needs the no-seek fallback.
