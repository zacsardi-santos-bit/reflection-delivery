Snowflake rejects that outright because it requires ranking window functions to always carry an ORDER BY, so the SQL blows up at runtime even though the PRQL itself is totally idiomatic.

That keeps users from having to sprinkle dummy sort expressions into their queries just to please Snowflake's stricter parser.

The other half of this: when I *do* provide an explicit sort inside the group expression, I want that sort column used as-is in the window function's ORDER BY, and no fallback injected in that case. So the fallback only kicks in when nothing else is there.

Can you update the SQL generation logic so the Snowflake target adds this fallback ORDER BY (constant 1) only when one isn't already present, and otherwise respects the user's sort? Other dialects shouldn't need this workaround, it's specifically Snowflake's window function requirement we're accommodating here.
