I'm building out the SQL query receiver and right now it's basically a skeleton, the metrics receiver creation function is a no-op that returns nothing so you deploy it and get zero data with no clue why. I want to implement the actual collection logic so the receiver runs its SQL statements against a database, turns each result row into a separate OpenTelemetry metric, and streams those out to the downstream consumer.

Alongside that I need to flesh out the per-metric config. Each metric should carry a data type that's either gauge or sum, a value type that's integer or floating-point, an aggregation mode of cumulative or delta (only meaningful for sums), a monotonicity flag (the old monotonicity field got renamed so update references), plus optional attribute columns to tag data points and optional description and unit fields.

There's also no config validation at all today, which means misconfigured receivers fail silently. I want validation at startup that checks the required stuff is present and non-empty: the driver, the datasource, the SQL statement, each metric's name, and its value column. It should reject unknown enum values for the type and aggregation fields with a message naming the bad value, and catch incompatible combos like specifying aggregation when the data type is gauge (gauges don't support aggregation). When one metric has several problems I want all of them reported together, not just the first.

At row-conversion time errors should be handled gracefully too, so if a value can't be parsed as an integer or float, or a referenced column isn't in the result set, report which row failed and why and keep collecting the rest of the row errors rather than bailing on the first failure.

Oh and I'll want a batch of test YAML configs to exercise this, covering valid setups plus the invalid cases: each missing required field, bad enum values, the gauge-plus-aggregation incompatibility, and a single metric with multiple errors at once.
