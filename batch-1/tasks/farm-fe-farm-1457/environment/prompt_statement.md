I'm digging into our module resolution system and hit a wall with how rigid it is. Every call to the resolver's main resolution method leans entirely on the global compilation context, so there's no clean way for a caller to pass in-call configuration. Say a CSS plugin wants to try a custom list of file extensions when resolving a module, but a JavaScript plugin wants something different, right now they'd have to mutate global state to pull that off, which is brittle and leads to wrong dependency resolution.

What I want is a new per-call options type that callers hand directly to the resolution method. I want that options parameter to sit between the resolve kind and the compilation context in the signature, and callers who don't need anything special should just pass a default (no-op) value with zero setup, so a plain default value works out of the box.

Also there's a cache bug tied to this. The package metadata cache keys only off the file path today, which means two resolution calls for the same path but with different options can incorrectly share a cached result. I want the cache key to fold in the options too so different option values for the same path produce distinct entries. Oh and expose a public method on the package metadata loader that computes this combined key from a path plus options, so the cache internals and any callers (and tests checking cache state) all derive the key the same way.
