I'm cleaning up the trie layer in reth and the package boundaries are muddy. Right now the core trie library (`@crates/trie/trie`) defines and exports cursor types that need direct database access, even though we already have a dedicated database integration package (`@crates/trie/db`) that's supposed to be the home for that stuff. So any consumer of the general trie abstraction ends up with db-specific types mixed into the core API even if they never touch a database, which makes the whole thing harder to reason about.

What I want is to move the database-backed hashed cursor factory along with its account and storage cursor implementations, plus the database-backed trie cursor factory with its account and storage trie cursor implementations, out of the core trie library and into the db integration package. After the move these types should be publicly re-exported from the db package so existing callers can just update their imports, and they should no longer be reachable from the core trie library at all. Anything that used to import them from core has to pull them from the db package instead.

Also the integration tests for these types belong in the db package since they need a real database to run. That includes checking that the hashed account cursor correctly merges and orders entries from both the database and the in-memory post-state (post-state wins, deleted entries excluded), that the hashed storage cursor handles wiped storage and filters out zero-value entries, and that the trie cursor implementations traverse lexicographically when driven by the trie walker. Keeping the abstraction layer free of direct db deps makes the separation of concerns explicit and enforced.
