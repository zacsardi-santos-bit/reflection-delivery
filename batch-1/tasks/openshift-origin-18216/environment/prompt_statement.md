I'm digging into the Horizontal Pod Autoscaler controller and the way it normalizes replica counts is bugging me. Right now when the autoscaler figures it needs more pods than allowed, it doesn't clearly separate two very different limiting factors: the configured maxReplicas ceiling versus the built-in scale-up rate limiter. Both can cap the final number but they mean totally different things operationally, and operators currently have no reliable way to tell whether their configured max is actually the constraint or if it's the rate limiter that's slowing things down. That makes HPA tuning and diagnosing scaling behavior way harder than it should be.

What I want is to pull the replica normalization logic out into a standalone, rule-based function that returns both the normalized count and a specific reason for any adjustment, so it's easy to reason about and test on its own. The rules I need it to handle: if the desired count already sits within the acceptable min/max range, no adjustment and no limiting condition reported. If it's below the minimum, raise it to the minimum and report that reason. If it's zero or below even when the minimum is configured as zero, an absolute floor of one replica still applies. If the desired count exceeds the configured maxReplicas (even when the scale-up rate limiter would allow more), cap at maxReplicas and report the configured maximum as the binding reason, don't let it silently fall into some generic limiting case. And if it only exceeds the scale-up rate limit but not the configured max, cap at the rate limit and report that as the reason instead.

Oh and one more thing, when the metric-calculated desired count would naturally push above the configured maxReplicas, the controller should cap at that maximum and explicitly report the reason as the configured maximum being exceeded, not the rate limiter.
