I'm hitting a cluster of type inference bugs in the Nussknacker expression type system and could use your help sorting them out. When I write a ternary conditional where the two branches have different types, the checker either rejects the whole thing as invalid or hands back some unusable "empty" type instead of computing a sensible common type. What I actually want is that incompatible branches resolve to an unresolved generic (unknown) type rather than being flagged invalid, and when both branches are record types the result should be a merged record carrying all fields from both, and when one branch is a record and the other is a generic map it should type accordingly. This is blocking legit scenarios where someone picks between two record shapes or between a record and a map-typed variable.

Related, equality comparisons are busted too. Comparing two record literals with different field sets, or a record against a map variable, gets flagged as a type error even though that's totally valid at runtime and should just return a boolean, oh and this shows up as spurious mismatch errors when records mix simple classes with nested records.

On the API side, finding the common supertype of two types is way too fiddly right now, callers have to build strategy objects with a bunch of config flags. I want that collapsed down to two named predefined strategies: an intersection one that keeps only what both types share (for arithmetic and strict field matching) and a default one that's more permissive and falls back to a generic object type when there's no specific supertype (for ternary and list inference). Also the expression type-checking component shouldn't take an explicit strategy at construction, it should just pick the right one internally per operation. And while you're in there, kill the old strict type checking config flag since the right strategy now handles that automatically. There's a previously skipped nested JSON schema validation test that should pass once this all lands. Keep strict behavior where it matters (arithmetic) but loosen it up in the right places.
