I'm working on the Nussknacker expression type system and running into several related issues. When I write a conditional expression with two branches that have different types, the type checker either rejects the whole expression as invalid or produces an unusable "empty" type — but I'd expect it to infer a reasonable common type (like an unknown type for truly incompatible branches, or a merged record if both branches happen to be records). This is blocking valid scenarios where the user picks between two record shapes or between a record and a variable typed as a generic map.

There's also a problem with equality comparisons: comparing two record expressions that have different field sets, or comparing a record literal against a map variable, is being flagged as a type error even though such a comparison is perfectly valid at runtime and should simply return a boolean.

On the API side, the way callers find the "common supertype" of two types is unnecessarily complex — you have to construct strategy objects with multiple configuration flags. I'd like this to be simplified to two named, predefined strategies: one that uses an intersection approach (keeps only what both types share, used for things like arithmetic and strict field matching) and one that's more permissive and falls back to a generic object type when no specific supertype is found (used for things like ternary operators and list inference). The expression type-checking component should not need to be configured with an explicit strategy at construction time — it should use the right strategy internally for each operation.

As part of this, the old strict type checking configuration flag should be removed, since its behavior will now be handled by the appropriate strategy being chosen automatically. The previously skipped test for nested JSON schema validation should also pass after these fixes.
