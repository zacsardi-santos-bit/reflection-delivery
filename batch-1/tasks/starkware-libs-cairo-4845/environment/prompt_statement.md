I'm digging into the gas metadata computation for Cairo programs over in the sierra gas crate and the gas solution output is missing a bunch of runtime cost components that I actually care about. Right now when I compute gas metadata for a program, the per-statement and per-function cost maps only show a subset of stuff like constant gas, Pedersen, Poseidon, bitwise, and elliptic curve operations, but execution steps, memory holes, and range check operations aren't tracked separately at all.

So if I look at the gas solution for a function doing range-check arithmetic, the range check cost just doesn't show up as its own field, and same deal for execution steps and memory holes, they're completely absent from the breakdowns. That makes gas accounting incomplete since callers and tooling can't see the full picture of where gas is being consumed.

I want the metadata computation to support computing and reporting these extra runtime cost components. There should be a config flag to enable computing runtime cost components, and when it's active the gas solution output (both the LP solution and the linear solution) should include steps, holes, and range checks as individually tracked entries alongside the existing cost types, for each code statement and each function. Also, even in the default config without explicitly flipping the flag on, these components should still be present in the output maps, populated with correct values including zeros where no such cost applies. Functions that do range-check operations should show nonzero range check values, functions with memory alignment gaps should show nonzero hole counts, and every function should have its step count tracked. The values need to be correctly attributed to each statement and function based on the operations they actually perform. This matters because gas transparency is what lets devs optimize contract performance, and right now the reported totals don't reflect all the actual resource consumption.
