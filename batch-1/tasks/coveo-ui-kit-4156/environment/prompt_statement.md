I'm working on the commerce facet search stuff and I hit a gap where the backend can't tell whether a facet search request came from a search results page or a product listing page. Right now every facet search API call looks identical no matter where it fired from, so the backend has no way to process them differently by page type, and that's causing wrong behavior in one context or the other. What I want is a context type, either search or listing, that rides along from the facet controller config all the way down to the actual API request. The controller options should require this context type as part of their configuration, and it needs to get automatically appended to the API request URL as a parameter so the backend receives it. The sub-controllers for search pages and listing pages should each have their own context type wired in automatically so consumers don't have to pass it per-controller every time, that's the annoying part I want to avoid. Also the action creators that execute the facet search and field suggest operations need updating to accept and forward this context type alongside the facet identifier they already take.

Oh and separately, I noticed field suggestion requests are missing a query field that the standard facet search API contract expects to always be there. So field suggest requests end up structured inconsistently compared to regular facet search requests. All facet search request objects, including the field suggestion ones, should consistently carry that query field so everything conforms to the expected contract regardless of request type.
