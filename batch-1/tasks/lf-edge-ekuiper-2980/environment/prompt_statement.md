I'm adding WebSocket server-side support to the ekuiper stream processing engine because right now there's just no way for external clients to push data into the engine over a WebSocket connection, the engine can't act as a WebSocket server endpoint at all. I want to implement a WebSocket source that lets the engine listen for incoming client connections on a configurable endpoint, receive messages from those clients, and route the raw payloads into the processing pipeline. This matters a lot for IoT and event-driven setups where WebSocket is the preferred transport, otherwise folks are stuck on workarounds.

Concretely I need a global server manager that can be initialized with an IP and port, plus individual endpoint registration and unregistration at runtime. When a connected client sends a message to a registered endpoint, the raw payload should get delivered to any downstream consumers of that endpoint. Also when a client closes its connection the engine has to detect that and cleanly remove the connection from its internal tracking, so the count of active connections drops back to zero, don't want leaked closed connections hanging around.

On top of that I want a source abstraction wrapping this server-side infra that follows the standard lifecycle: configuration with validation (an empty or missing endpoint path should be rejected with an error), connection setup, subscription with a data/payload callback, and clean graceful shutdown. Oh and I also need a connection factory function so this WebSocket source can be registered with the engine's broader connection management infrastructure.
