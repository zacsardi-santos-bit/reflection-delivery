I'm working on the gRPC Swift library and the message deframing layer needs splitting up because right now it's one component wired directly onto the channel pipeline interface, which mixes two totally different concerns and makes the thing impossible to reuse outside that pipeline. I want to break it into a low-level wire format decoder and a higher-level buffered deframer.

The low-level piece plugs into the channel pipeline as a single-step byte-to-message decoder and owns the actual parsing: it reads the gRPC framing header (the compression flag plus the payload length) and it checks that the payload fits within a configured maximum size before it reads any of the payload bytes, so the limit is enforced as soon as the header comes in. It optionally decompresses too. Error handling here has to be precise, so exceeding the size limit should give back a resource exhaustion error that includes both the configured max and the actual size in the message, and a payload that's flagged compressed when there's no decompressor configured should return an internal error, oh and a decompressed payload that ends up too large should also be a resource exhaustion error.

The higher-level deframer wraps that decoder and gives a simple push/pull API: I push raw bytes in whenever they arrive and pull decoded messages out one at a time, and if a full message isn't there yet the pull just returns nothing instead of blocking. It needs to handle messages that get drip-fed as partial byte sequences, and it should manage memory, so when new bytes get appended after I've already read some messages, the already-consumed bytes in the internal buffer get discarded so it doesn't grow without bound. Splitting these makes both testable and usable on their own.
