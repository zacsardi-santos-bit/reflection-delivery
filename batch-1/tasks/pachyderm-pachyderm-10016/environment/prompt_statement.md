I'm dealing with a nasty panic in our Go logging library that keeps biting us in production. The setup is we create a span off a context that's got a timeout or deadline on it, and if that deadline expires before we call the span's done function, the whole logging system panics. Timeouts are completely routine in our workloads (operations get cancelled or finish early all the time), so this crash keeps recurring and it's not acceptable. What I want is for the span to complete cleanly and without panicking whether or not the underlying context is still alive when done gets called. Same goes for any logging calls, debug and info level both, made against an expired or cancelled context, those should just succeed quietly instead of blowing up.

There's a related thing too: the system panics when it hits an unrecognized log level value internally. That should be handled gracefully instead of being fatal, there's really no reason for an unknown level to crash anything.

Oh and I also need a test helper that spins up an info-level logger, basically mirroring the existing debug-level bench logger helper we already have, so I can benchmark the filtering path. When debug messages get sent to an info-level logger, nothing should be written to the output, and I want to be able to measure that case.
