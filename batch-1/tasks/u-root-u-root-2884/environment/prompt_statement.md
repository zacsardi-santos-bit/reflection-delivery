I'm working on the ARM64 boot loading package and the kernel image loading is basically untestable right now because the main loading function reads the physical memory map straight from hardware via the device tree. That means there's no way to run unit tests against the core pipeline, which is annoying since segment placement, device tree updates, and boot stub generation can only really be checked on real hardware today.

What I want is to pull the core segment-building and device tree config logic out into a separate function that takes the memory map as an explicit parameter, so callers and tests can hand it a synthetic memory layout. Then I can verify the kernel, initramfs, device tree, and boot stub segments all land at the right physical addresses with the right contents. It should handle loading with or without an initramfs, set up the device tree's boot configuration node, and generate the small ARM64 boot stub.

Error handling matters a lot here, I need distinct checkable errors depending on which stage fails: one when the device tree has no boot configuration node, and separate ones when there isn't enough physical memory for the kernel segment, for the initramfs segment, or for the device tree segment, plus the case where an input file just can't be read. Oh and some input files aren't seekable (pipes and such), so it needs to fall back to reading them sequentially into memory instead of memory-mapping them.

Also, over in the memory package there's nothing to compare segment collections for equality, which I need so I can assert the loading op produced exactly the layout I expect. So add utilities that compare individual segments (matching physical address range and data contents) and entire collections too, checking addresses and data all match.
