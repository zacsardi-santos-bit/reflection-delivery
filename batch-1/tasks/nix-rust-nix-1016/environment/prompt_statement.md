I'm building out a Rust library that wraps Linux syscalls and there's a real gap right now: no way to watch a directory for filesystem changes. If someone wants to know when a file gets created, opened, closed, renamed, or deleted inside a directory they care about, they're stuck dropping down to unsafe raw syscalls themselves, which defeats the whole point of a safe wrapper layer. I want to expose Linux's inotify-style filesystem event monitoring as a new safe, idiomatic module inside the syscall wrapper layer, available on both Linux and Android targets.

Here's the shape of what I need. Developers should be able to create a watcher instance, optionally in non-blocking mode. Then they register a directory (or a file) for monitoring, specifying which categories of events they actually care about. Then they read back structured event records. Each event needs to carry the type of operation that happened (creation, open, close, move, and so on), the name of the affected file within the watched directory, and a correlation token, a cookie basically, that links related events together so the two sides of a rename (source and destination) can be matched up by the caller.

Couple of behaviors that matter: when the watcher's in non-blocking mode and there aren't any events ready yet, the read call should hand back a "try again" style error rather than blocking. And when filesystem operations do happen, the events need to come back in the order they actually occurred, accurately reflecting the sequence of what went on. So if I create a file then rename it, I should see those in the right sequence with the rename halves sharing a cookie. Wire it in as a new module under the system-call wrapper layer so it's picked up on Linux/Android.
