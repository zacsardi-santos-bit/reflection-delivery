I'm cleaning up the FFI layer in our Rust crypto library before we can wire up address and leak sanitizer runs in CI, and I keep hitting memory ownership bugs that make the whole thing unsafe from foreign-language callers. The core issue is that a few functions allocate a string on the heap and hand back a pointer, but the return type is declared as a read-only const pointer, which is wrong because the caller has to actually own that memory to free it later. The random UUID generator is the clearest offender, it uses an ownership-transferring allocation internally but still returns a read-only pointer, so anyone using proper ownership semantics gets a compile error. I want that fixed to return a mutable owned pointer, and same treatment for the other functions that allocate and return heap strings, namely the hex encoding and base64 encoding paths, since they're all signaling "you own this, go free it."

Also the bit reader utility has a create function but no matching destroy/delete, so every bit reader we spin up just leaks. Please add the missing destroy function so callers (and the tests, which want to call it after use) can release resources. Oh and the base32 encode and decode functions take the alphabet argument, and since they only read it, those should accept a read-only const pointer to match what callers actually pass. Right now the test suite won't even compile when it tries to use correct ownership patterns.
