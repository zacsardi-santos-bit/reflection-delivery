I'm working in a schema library that encodes and decodes typed values to and from wire formats, and it's got Either support already but only for tagged unions where there's a discriminator on the wire. What I actually need is the untagged case. Think of an API that hands me back a field that could be a date string or a numeric string with no tag telling me which one it is, and I want to model that as a single schema that decodes straight into an Either value. So I need a new combinator that takes two schemas, one for the left (error/fallback) case and one for the right (success) case, and gives me back a schema over Either.

The decode side should try the right schema first and fall back to the left schema if the right one fails, so when both could match the same input the right case wins, that priority matters. Encoding goes the other way, a Left gets encoded with the left schema and a Right gets encoded with the right schema. It's gotta roundtrip cleanly, encode then decode gives me back the original Either. Oh and error messages need to be clear when neither schema can decode the input, and also when encoding fails, don't leave me guessing.

Right now people hand-roll this transformation logic every time which is repetitive and easy to get wrong, so having a proper combinator that sits alongside the existing tagged-union Either support keeps schema definitions concise for these ambiguous-type fields. It should follow the same conventions as the rest of the library's combinators.
