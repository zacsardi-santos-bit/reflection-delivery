I'm working with a gRPC-Gateway setup and I've discovered a bug with how path parameters and query parameters interact. When I define a route that captures a value from the URL path — like a resource identifier embedded directly in the path — and a caller also happens to send a query parameter for that same field, the query parameter value overwrites the path value. That's completely wrong: the path parameter should always take precedence.

The problem also shows up with nested fields. If a path segment maps to a nested field on the message, and a caller provides a query parameter targeting that same nested field using a different case convention (e.g., camelCase vs. snake_case), it still manages to override the path value. Meanwhile, query parameters for fields that are *not* part of the path should continue to work as expected.

I need the gateway to ensure that values captured from path parameters are never overridden by query parameters, and that this protection works consistently regardless of how the query parameter key is cased. The echo service example should also include new routes and message fields that demonstrate this behavior — one route that maps a simple path parameter to a resource identifier field, and another that maps a path segment to a nested field.
