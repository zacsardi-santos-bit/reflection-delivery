I'm hitting a nasty bug in my gRPC-Gateway setup around how path params and query params interact. When I define a route that captures a value straight from the URL path, say a resource identifier embedded in the path segment, and the caller also sends a query parameter targeting that same field, the query value silently overwrites the path value. That's just wrong. Path params are part of the route definition, they're the canonical identity of the resource, so they should always win. Right now a caller could accidentally (or maliciously) pass a conflicting query param and get back a totally different resource than the one named in the path, which is both a correctness and a security gap.

It also breaks with nested fields. If a path segment maps to a nested field on the message and someone sends a query param for that same nested field but using a different case convention (camelCase vs snake_case, that kind of thing), it still manages to override the path value. So the protection needs to hold no matter how the query key is cased. Meanwhile query params for fields that aren't set by the path should keep working normally, don't touch those.

What I want: once a field's been populated from a path parameter, any query parameter aiming at that same field just gets ignored, path value stays authoritative, and that's true regardless of the query key's casing. Oh and please update the echo service example to actually demonstrate this, add a new route that maps a simple path parameter to a resource identifier field, plus another route that maps a path segment to a nested field, along with whatever new message fields those routes need. That way the behavior is visible in the example and not just buried in the runtime handling.
