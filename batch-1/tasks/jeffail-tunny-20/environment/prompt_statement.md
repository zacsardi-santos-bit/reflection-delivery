I'm working on a goroutine pool library and I'd like to redesign its public API to be simpler and more ergonomic. Right now, creating a pool requires chaining a constructor with an open call and checking an error that's almost never meaningful — I'd like to collapse that into a single constructor that returns a ready-to-use pool.

I also want to rethink how jobs are submitted. Currently there's a function that returns both the result and an error, but for the simple synchronous case I'd prefer to just return the result and panic if the pool is closed. For cases where callers need a timeout, there should be a timed variant that returns a result plus an error, giving back a clear sentinel when the job times out or when the pool isn't running.

I'd like to be able to resize the pool at runtime — growing or shrinking the number of active workers dynamically — and query the current size. Closing the pool should reduce the size to zero and cleanly terminate all workers.

For advanced use cases where each goroutine needs its own state, I want a single unified interface that covers: blocking until ready for the next job, processing a job synchronously, handling interruption when a job is cancelled, and cleaning up when the worker is removed from the pool. There should also be a convenience constructor for the case where jobs are just closures to execute, with a recognizable sentinel value returned when the payload isn't callable.
