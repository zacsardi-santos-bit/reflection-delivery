I'm cleaning up the public API on our goroutine pool library over in `@tunny.go` and it's gotten too verbose and honestly a bit error-prone. Right now to get a pool you chain a constructor with a separate open call and then check an error that's basically never meaningful, so I want to collapse all that into one constructor that just hands back a ready-to-use pool with no error to check on creation.

Job submission needs a rethink too. For the simple synchronous case I'd rather return just the result, no error, and if the pool's closed the caller should get a clear panic instead of some silent error nobody notices. Then for folks who need a deadline there should be a timed variant that returns a result plus an error, giving back a recognizable sentinel when the job times out and a different one when the pool isn't running.

Also I want to resize the pool live, growing or shrinking the number of active workers on the fly without restarting anything, plus a way to query the current size. Closing should drop the size to zero and cleanly terminate all the workers.

For the advanced cases where each goroutine carries its own state, I want a single unified worker interface (not the fragmented pile of optional interfaces we have now) that covers blocking until it's ready for the next job, processing a job synchronously, handling interruption when a job gets cancelled, and cleaning up when the worker's removed from the pool. Oh and a convenience constructor for the common case where jobs are just closures to run, where a non-callable payload produces a recognizable sentinel value. The whole point is people shouldn't have to babysit meaningless errors or lifecycle plumbing the library can handle itself.
