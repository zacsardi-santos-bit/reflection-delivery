I'm hitting a bug in our Snowflake data connector around timestamp handling. When Snowflake returns a timestamp column as a plain 64-bit integer (seconds since epoch) instead of the structured type it normally sends with separate epoch and fractional fields, the timestamp conversion just blows up with an error rather than giving back valid data, so queries against those columns fail entirely. Turns out some Snowflake configs or certain query types return timestamps as bare integers rather than the structured objects, and right now we only handle the structured shape.

What I want is for the conversion function to cover both cases. Keep the existing structured-type path working exactly as it does today, but also accept the plain-integer form. When it's a plain integer array of epoch seconds, convert to Arrow's nanosecond timestamp format by multiplying each value by 1,000,000,000 (so e.g. an epoch of 1,696,164,330 seconds becomes 1,696,164,330,000,000,000 nanoseconds). And this needs to work in both timezone-aware and non-timezone-aware modes, so whether or not timezone metadata is required, the integer path should produce correct results either way.

Oh and if the input is neither the known structured format nor a plain integer array, don't silently do anything weird, just return an error saying that input type isn't supported. Basically making the connector handle both representations Snowflake might use for timestamp data so people stop getting failures instead of rows.
