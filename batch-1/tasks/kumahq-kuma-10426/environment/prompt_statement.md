I'm hitting a stale-services bug in our multizone mesh and I could use a hand wiring up a fix. Setup is each zone has one or more ingress proxies, and the list of available services a zone ingress advertises only gets computed and stored when that ingress is actively connected and pulling config. Problem is when an ingress goes offline and the set of reachable services changes (say a service gets removed because all its dataplanes went away), the offline ingress just gets skipped, so when it comes back it's still advertising the old list. Other zones trust that advertised list to know what's reachable, so this causes intermittent routing failures and bad service discovery, especially during rolling restarts with several proxies in play.

What I want is a dedicated background component that runs on a regular, configurable interval and periodically computes the available services from all dataplanes and external services in the zone, then writes that updated list to every zone ingress resource in the store, not just the connected ones. So an ingress that was offline when a change happened converges to the right state as soon as it reconnects or the store's queried, and when all dataplanes for a service are gone every zone ingress (offline ones included) eventually shows an empty list. The interval should be tunable by operators through the zone control plane config, both via the config file and an environment variable.

Also, right now there's a function that mixes computing which services are available with the store update, which makes it hard to reuse. I'd like the computation split out into a pure, side-effect-free operation I can call without touching the resource store, so the background updater does the storing separately. Can you introduce the background updater and separate the computation from the store write?
