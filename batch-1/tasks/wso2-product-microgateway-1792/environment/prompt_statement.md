I'm working on the API gateway and its CORS support has a gap I keep hitting. Right now operators can configure allowed origins, methods, and request headers for cross-origin requests, but there's no way to say which response headers should be exposed to browser clients. Per the CORS spec browsers block JavaScript from reading most response headers unless the server explicitly lists them via `Access-Control-Expose-Headers`, so frontend apps calling our APIs can't read custom headers like pagination metadata, rate limit info, or custom status fields even when they really need them.

I want to add an expose headers field to the gateway's internal CORS configuration model so operators can set this both per-API and globally at the gateway level. Then the logic that builds CORS policies needs to populate the expose headers from that field. When expose headers are configured they should show up as a comma-separated list on the generated policy, matching the pattern we already use for allowed headers. And when nothing's configured the expose headers on the generated policy should just come out empty (so the `access-control-expose-headers` response header isn't set). The key thing is the internal representation has to carry this new field through so policy generation actually reflects what was configured, otherwise consumers building web apps stay stuck not being able to read those cross-origin response headers.
