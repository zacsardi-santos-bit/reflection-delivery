I'm migrating a bunch of our popover-based components (dropdown menus, tooltips, educational popovers, help buttons, overlay panels) over to a new version of the underlying popover engine, and the test suite isn't keeping up. The new engine behaves differently under test because it leans on browser intersection detection APIs that just don't exist in the test runner, so elements that render end up hidden instead of visible. That's breaking a lot of assumptions.

The main thing I need is a shared testing utility that takes a feature flag name plus a component and renders that component with the flag turned on, so tests can actually exercise the new popover code path. Right now there's no clean way to opt into the new behavior and every test file would have to duplicate the boilerplate, which is why I want this centralized. Several tests across the different component files should be able to reach for it.

Then I need to fix up the visibility checks. Tests that assert an element is visible need to instead check for presence in the document, since the new implementation renders things that are present but hidden (because of that missing browser API). So swap visible-style assertions for in-the-document ones wherever the new engine is involved.

For the dropdown keyboard navigation tests, finding menu items by their internal DOM IDs is too fragile, so I want to locate them by a test identifier instead. That means the dropdown item and link components need to support a prop that stamps a test id onto the rendered element, and the keyboard nav tests should use that to verify which item has focus.

Oh and there are some snapshot tests for these popover components that used to use a different rendering approach, so their snapshot files need to be cleared or updated so they regenerate against the new DOM-based output next time they run. Basically I want the suite to validate both current and updated behavior without misleading failures.
