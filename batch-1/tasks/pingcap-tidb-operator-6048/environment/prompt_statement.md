I'm poking at our TiDB operator and the bootstrap SQL config is in a weird spot. You know, the SQL that runs once when a cluster first comes up. Right now it lives inside the TiDB component's security settings, which feels wrong because bootstrap SQL is a cluster-wide init thing, not some per-instance security property. It's harder to discover there and it couples our initialization logic to component-level security where it really doesn't belong.

What I want is to lift that field up to the cluster spec so it sits as a top-level field on the cluster specification alongside the other cluster-wide settings. That way it's clearly scoped to the whole cluster instead of individual TiDB component groups. Reflects its true scope since it's an init step for the entire cluster, not a security concern of any single TiDB group, and honestly it'll make the API way more intuitive for operators configuring clusters.

So concretely: add bootstrap SQL as a top-level field on the cluster spec, and anywhere that currently reads bootstrap SQL from the TiDB component's security configuration needs to read it from the cluster spec instead. Oh and the TiDB security type should no longer expose the bootstrap SQL field at all, drop it entirely from there. Basically move it, rewire the readers, remove the old field.
