I'm working on Biome and there's a real gap I want to close: our JS/TS linter has no way to catch hardcoded secrets that people accidentally paste straight into source. Cloud access keys, OAuth tokens, private key material, webhook URLs, database connection strings with the password baked in, all of that sails through today with zero warning, and committing that stuff is one of the easiest ways to leak credentials. I want a new nursery-category lint rule that scans string literals in JavaScript and TypeScript and flags anything that looks like a secret.

It should recognize specific well-known token formats first, things like AWS access keys, various OAuth tokens, RSA private key headers (the usual `-----BEGIN ... PRIVATE KEY-----` style stuff), service-specific webhook URLs, and database connection strings that have an embedded password. Then, for strings that don't match any known provider pattern, fall back to entropy analysis so high-randomness values still get caught. When it finds something, the diagnostic should name the type of secret detected (so the message is specific, not generic) and walk through how to fix it safely: remove it from git history, move it to an environment variable, or suppress the warning if it's genuinely a false positive.

Oh and it needs to be smart about what it leaves alone, otherwise it's just noise. Plain numbers, short readable strings, long human-readable sentences, and connection strings that already reference a runtime variable in place of a hardcoded credential should all pass clean with no warning. The remediation guidance is the whole point of making this actionable rather than just alarming, so keep those steps clear and specific to the secret type detected.
