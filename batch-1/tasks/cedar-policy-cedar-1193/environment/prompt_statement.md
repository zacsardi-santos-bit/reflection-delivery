I'm hitting a correctness bug in Cedar's schema-based entity validation and it's making me nervous because the schema is supposed to be the contract every entity satisfies. When an entity has a record attribute containing extra fields the schema doesn't allow, validation just passes silently instead of rejecting it. Like if my schema says a record should only have one specific field, but the entity ships that field plus an extra one, that should fail with an invalid entity error, and right now it doesn't. Same deal for wrong-typed fields on a record, those should be rejected too.

The really annoying part is this leaks into nested structures, so think sets of sets of records where a record buried in the innermost set is missing a required field, that should get rejected but it slides right through. So whatever fix goes in needs to recurse properly through sets of records, sets of sets of records, etc, catching extra fields, wrong types, and missing required fields at every level. Meanwhile valid entities that actually conform (required fields present, optional fields either absent or correctly typed) have to keep passing, don't want to over-correct and start rejecting good data.

Can you fix the entity validation logic so record attributes get checked against the schema the way they should? Silent schema violations let malformed data flow through authorization checks undetected and that undermines the whole point.

Oh and while you're in there, it'd be handy to have direct count methods on a policy set for both policies and templates, instead of grabbing an iterator and calling count on it just to tally them up.
