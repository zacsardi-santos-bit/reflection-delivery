I'm extending the Cortex ingester with per-labelset series limits and could use your help wiring it up. Right now I can cap active series per user or per metric name, but there's no way to bound the number of active series that share a specific combination of label values, so a tenant can still blow up cardinality on one label dimension (think a single environment, job, or region value) inside their overall quota. I want operators to configure one or more limits per tenant, each being a labelset (one or more label name-value pairs) plus a numeric max series count, and it needs to be per-tenant config so updating one tenant's limits takes effect for subsequent pushes without restarting anything.

When a push would take the number of series matching a configured labelset over its cap, reject it with a 400 Bad Request that names which labelset constraint was violated. Composite limits matter too, so if a series matches both a single-label limit and a multi-label composite limit, check it against both independently and honor whichever it trips. For example "no more than 100 series with environment=prod" for a given tenant.

Also I want a new gauge metric tracking the current count of active series per user and per configured labelset so operators can watch utilization. It's gotta update dynamically as series come and go, and stay in sync with config changes: when a labelset limit gets removed the corresponding metric should disappear, and when a new limit is added to a running ingester the count should be bootstrapped from the existing persisted data so series that already exist get counted against the new limit correctly. Oh and the per-labelset counts plus the underlying series data both need to survive an ingester restart. This lives in the ingester code under `@pkg/ingester`, with the limit config plumbed through the per-tenant limits/validation layer around `@pkg/util/validation`.
