I've got a project with a git dependency pinned to a branch, and when I run `cargo pkgid` for it, cargo hands me back an identifier with the git repo URL where the branch shows up as a query string parameter (something like `?branch=whatever`) and the version tacked on as a URL fragment. Makes sense so far. The annoying part is when I take that exact string, the one cargo itself just printed, and pass it straight back to `-p`/`--package` on a `cargo build` or `cargo check`, it blows up. It comes back with a "no package matching" style error instead of building the thing I asked for.

Digging in, it looks like the package selector logic is treating the `?` in the URL as a glob wildcard character during matching, so of course it can't find anything that lines up. I really just want to be able to grab the canonical package ID cargo reports and feed it right back in as a selector with zero edits, oh and manually stripping or escaping the query string before use is exactly the kind of error-prone workaround I'm trying to avoid.

So the fix I'm after: when a package ID contains a URL query string, cargo shouldn't interpret the question mark as a glob wildcard when it's used as a package spec. Setup to repro is basically add a git dep with a branch, generate the lockfile, look up the pkgid, then pass that id to a build via the package flag. After the fix that id should be recognized as a valid specifier and build the package successfully, with the branch still encoded as a query param and the version as a fragment in what pkgid returns.
