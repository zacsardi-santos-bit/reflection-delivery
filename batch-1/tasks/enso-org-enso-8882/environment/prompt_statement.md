I'm poking at the dashboard's JSON schema utilities and there's a gap I keep hitting: we've got no standard way to reason about schemas programmatically. Right now if I have some runtime value and want its JSON schema equivalent, or I want to check whether a value actually satisfies a schema's constraints, or pull back out the single constant a restrictive schema encodes, I end up writing ad-hoc logic every time, which is how we end up with inconsistencies across features. This stuff is foundational for things like dynamic form generation and config UIs where the app has to programmatically figure out what values a schema accepts and validate user input, so I want it living in one place.

Can you add three utility functions exported from the JSON schema utilities module. First, one that converts a constant value (a string, number, or integer) into an equivalent JSON schema, and returns nothing if it can't represent the value as a schema. Second, one that checks whether a given value matches a schema, and it needs to handle type constraints for string, number, and integer, plus exact constant equality, and also numeric "multiple of" constraints (so an exact integer multiple of N matches but a non-integer multiple like N × 1.5 does not match). Third, one that extracts the constant value out of a schema and returns it as the first element of an array (a tuple), so callers can grab the encoded constant.

Oh and these three should give me a round-trip guarantee: converting a value to a schema and then extracting the constant back always recovers the original value, and that original value should also match the schema it got converted from.
