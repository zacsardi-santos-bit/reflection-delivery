I'm working with Verus and hitting a wall trying to formally verify Rust code that uses the standard library hash maps. Right now there's just no support in the verification library for reasoning about `std::collections::HashMap`, so when I write asserts like "after I insert a key the map contains it" or "looking up a key gives back the value I inserted" the verifier can't prove any of it. Same story for removal and clearing, there's no abstract state to reason about. I want specs added so I can prove key membership, value lookup, insertion, removal, and clear all work the way you'd expect against the map's abstract contents.

I also need to reason about the standard hasher, `std::collections::hash_map::DefaultHasher` basically. I'd like it to have a verifiable abstract state that tracks the sequence of bytes/data written to it, and I want to prove that two hashers given the same sequence of writes produce the same output. That "same writes means same result" property is the key thing.

For primitive key types and boxed primitives this should just work automatically, no extra annotations. For user-defined key types I get that I'll probably need to explicitly state an assumption that the type's hash and equality behavior is consistent enough for the model to apply, and here's the important part, if that assumption is missing the verifier should reject the proof, so map content assertions on a custom key type without the assumption need to fail rather than silently pass.

Oh and two specialized cases I want too. First, a wrapper map type for keys that carry a separate logical view, so I can write proofs in terms of the abstract/logical key instead of the concrete one. Second, a dedicated map type for string keys that represents each string as its sequence of characters in the abstract, so proofs talk about the char sequence. This all lands in the Verus vstd library alongside the other collection specs. The motivation is that tons of real Rust code leans on hash maps heavily, and without this Verus just can't touch those programs, so getting it in unlocks verifying a big class of ordinary map-using code.
