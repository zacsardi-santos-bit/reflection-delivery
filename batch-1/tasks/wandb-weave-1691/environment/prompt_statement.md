I'm working on the call trace server and I keep hitting a wall when I try to query calls. Right now I can only filter by structural metadata like op names, call IDs, trace IDs, that kind of thing, but I can't touch what's actually stored inside the dynamic fields (inputs, outputs, attributes, summary). So there's no way to say "give me all calls where the input value was greater than 5" or "find calls whose output contains some substring" without pulling everything down and filtering client-side, which is slow and doesn't scale at all.

What I want is an optional expression-based filter on the call query API that filters on the content of those dynamic fields. The expression language should handle equality, greater-than, and greater-than-or-equal comparisons, plus logical AND, OR, and NOT that compose with the comparison operators. I need to reference nested fields using dot notation, and array elements within those nested fields should be reachable with dot-notation numeric indices too.

Also I want type conversion support so I can treat a stored JSON value as a specific type (like coercing something to an integer or a string) so comparisons across types actually work. Important detail: when a conversion fails for a given record, just exclude that record from the results rather than blowing up with an error. Oh and substring matching matters a lot, and it should support both case-sensitive and case-insensitive modes.

On top of all that I need a separate stats/count endpoint that takes the exact same filter expression but returns only the total count of matching calls instead of the full records, which is handy for pagination and aggregations. It has to always produce the same count as the number of results the regular query endpoint would return for the same filter, otherwise it's useless.
