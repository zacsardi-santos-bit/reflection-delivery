I'm building out a CSS linter and I want to give teams a way to restrict which selector relationship types (combinators) are allowed in their stylesheets. Right now there's no way to say "never use the descendant combinator" or "only allow direct child and sibling," and folks want that for performance and maintainability reasons, like preventing accidentally broad style application or enforcing an architectural convention.

So I'd like two complementary rules. One is basically a blacklist: you hand it a list of forbidden selector relationship types and it reports a violation any time one of those shows up in a selector. The other is a whitelist: you give it the list of allowed relationship types and it flags anything used that isn't in that list.

A few gotchas both rules need to handle. The descendant combinator can be written with a space, a tab, or a newline between selectors, and all of those whitespace forms should be treated as the same descendant type when comparing against the configured list. Also combinators can show up nested inside pseudo-class selectors (think negation selectors like `:not(...)`), not just at the top level, so both rules have to walk into those and check them too. And there's a non-standard reference combinator syntax where a word gets wrapped in forward slashes (from some CSS working drafts), oh and that one should just be quietly ignored by both rules rather than triggering a violation.

To make all this work I also need a small utility function that takes a combinator node from the selector parser and tells me whether it represents standard CSS syntax, so it returns false for reference combinators and true for all the standard ones. Both rules should lean on that so the reference-combinator skipping stays consistent.
