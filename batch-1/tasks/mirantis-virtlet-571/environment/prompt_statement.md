I'm working on virtlet's image download subsystem and the big gap I keep hitting is there's no way to cancel a download or pull once it's started. If a caller wants to bail on an in-flight image download, say a request got terminated by the container runtime or a context deadline expired, the thing just keeps chugging until it finishes or errors out on its own, which wastes resources and leaves us unresponsive when the broader request lifecycle has already moved on.

What I want is proper cancellation support threaded through both layers. The low-level download interface should take a cancellation signal (a stop channel) as part of its call signature, and when that signal fires mid-download it needs to actually stop and return an error indicating the operation was cancelled. Same deal one level up: the image pull operation should accept and propagate that cancellation signal down to the underlying download layer, and if cancellation triggers during a pull it should return a cancellation error too. So both the low-level download and the higher-level pull change their signatures to carry the stop channel and behave correctly when it's closed.
