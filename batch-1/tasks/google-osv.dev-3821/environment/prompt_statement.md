I'm working on the OSV vulnerability database and we need to build an automated recovery system for cloud storage synchronization failures. Right now, when a vulnerability record fails to be written to cloud storage — whether because of a transient error, a concurrent modification conflict, or the record simply going missing — there's no automatic recovery. The failure gets logged or silently dropped, and the storage entry stays stale or missing until a full reimport happens.

I need to create a new recovery worker module that processes queued failure messages. The worker needs to handle several distinct scenarios: retrying a failed write using the serialized vulnerability data that was queued (being careful to skip the write if cloud storage already has a newer version of the record), regenerating a missing record by re-fetching it from the database, and re-applying a specific derived field (like aliases or upstream relationships) when a concurrent update caused a generation mismatch. There also needs to be a generic fallback handler for any unrecognized message types that logs the problem and clears the message from the queue. All handlers should indicate success or failure via a true or false return value.

Additionally, I need to create a shared utility function that other parts of the codebase can call to publish failure messages to the recovery queue. This utility should accept the payload bytes and any additional message attributes, and publish them to the appropriate topic. If the cloud project isn't configured, it should log a clear error message and raise an exception rather than silently failing.
