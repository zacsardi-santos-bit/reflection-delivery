I'm working on the OSV vulnerability database and I keep hitting a gap where records that fail to write to cloud storage just stay stale or missing forever. Right now when a write fails, whether it's a transient error, a concurrent modification conflict, or the record simply going missing, we log it (or worse, silently swallow it) and there's no automatic recovery until somebody does a full reimport. I want to close that.

I need a new recovery worker module that consumes a queue of failed-task messages and handles each scenario. One handler retries a failed write using the serialized vulnerability data that got queued, but it should skip the write if cloud storage already has a newer version than what was queued. Another regenerates a missing record by re-fetching the live record from the database and rebuilding the storage entry. Another re-applies a specific derived field (aliases or upstream relationships, that kind of thing) when a concurrent update caused a generation mismatch, so it re-queries the current database state for that field and applies it to the storage copy. And there's a generic fallback for any unrecognized task type that just logs an error and acknowledges the message so it doesn't block the queue. Each handler takes a Pub/Sub message and returns true or false depending on whether it handled things successfully.

Oh and separately, a bunch of places (alias computation, upstream computation, the API server) have TODO comments where they mean to publish a failure message when they detect one of these situations. I don't want to copy-paste Pub/Sub boilerplate everywhere, so I also need a shared utility function that other parts of the codebase call to publish a failure message to the recovery queue. It should accept the payload bytes plus any extra message attributes and publish them to the right topic. If the cloud project isn't configured it needs to log a clear error and raise an exception rather than failing silently. Without this the storage copy can permanently diverge from the database and the API ends up serving stale or missing data, so getting the auto-correction in place matters.
