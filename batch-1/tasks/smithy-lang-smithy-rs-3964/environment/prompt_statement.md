I'm chasing a retry bug in the smithy-rs SDK runtime and the token bucket system just isn't doing its job for standard retry mode. The whole point of the bucket is to be a global rate limiter on retries, operations that fail consume tokens, and once the bucket's empty no more retries should happen even if we haven't hit the configured max attempt count yet. That's what keeps a retry storm from piling more load onto a service that's already struggling. Right now though the bucket never gets placed into the operation's config bag before the retry loop starts, so the retry strategy sees it as absent and skips enforcement completely, and clients just retry all the way up to their max attempts ignoring the quota.

There's a second half to this too. Buckets are supposed to be shared across every operation hitting the same service, partitioned by service name, so if one operation drains the quota a second operation on that same service should notice the bucket's depleted and get stopped after a single attempt. Currently each invocation effectively gets its own independent bucket state so exhaustion from one doesn't affect another, which defeats the purpose.

So what I want from the standard retry setup: always put a token bucket into the operation's configuration bag before the retry loop begins, share that bucket globally via the service partition so after one operation burns the quota the next one for the same service stops early, and keep buckets for different services fully independent from each other. This is tracked as aws-sdk-rust#1234 and adaptive mode leans on the same wiring, so getting the partitioned global bucket right matters for both.
