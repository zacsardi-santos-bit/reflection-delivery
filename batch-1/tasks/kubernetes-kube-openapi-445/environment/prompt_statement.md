I'm working on the Go OpenAPI schema generator for Kubernetes API types, the one where developers annotate struct fields and types with comment markers to pick up basic validation like numeric bounds, string length limits, and patterns and embed them in the generated schema. What I'm missing is a more expressive rule-based validation system. I want to write indexed validation rule entries directly in Go comments on a type or field where each rule entry carries a rule expression and optionally a human-readable message, a message expression, and a flag for how the old value gets handled. Multiple rules on a single type or field should be consecutive indexed entries starting at 0, and the parser needs to enforce that these indices show up in order without gaps, so non-consecutive indices should be rejected with a clear error. When the schema is generated these rule annotations should come out as the standard Kubernetes validation extension (x-kubernetes-validations) on the corresponding schema entries, both at the type level and at the individual field level.

While I'm in here the comment parser error messages need tightening up too. Errors for duplicate keys and invalid values should include better context so it's obvious what went wrong. And the type-constraint validation errors, like using a numeric constraint (minimum, maximum) on a string type, should be returned directly from the parsing step instead of coming back through a separate validation method, so callers get those failures inline as they parse rather than needing a second pass.

Oh and the integration test golden files plus the generated code for the test types need updating so that CEL annotations on those types produce the expected validation extension in the output schema. The point of all this is co-locating expressive validation rules with the type definition so the schema stays self-documenting and doesn't drift from the Go type, since controllers and admission webhooks lean on these generated schemas to enforce correctness.
