I'm chasing a CSS scoping bug in the Svelte compiler and it's actually two opposite problems at once. When I write selectors with an explicit combinator, direct-child (`>`), adjacent-sibling (`+`), or general-sibling (`~`), the element on the source side (left of the operator) is getting the component scoping attribute even though it shouldn't. The combinator already constrains the structural relationship so scoping both sides is redundant and produces wrong, bloated output. Only the right-hand element of the combinator should get scoped.

The flip side is descendant selectors, where I just put a space between elements. Right now only the last element in the chain gets the scoping attribute and the intermediate ones don't, which means styles can leak out and match elements from outside the component that happen to sit under the outermost scoped element. I want all the intermediate elements in a descendant chain scoped too, and that scoping class needs to show up in the rendered HTML output, not just the CSS.

A few more things while you're in there. A selector whose full descendant chain doesn't match any element in the template should be flagged as unused. Also chains of multiple globally-declared selectors (like `:global(...)` stuff) followed by a local element should work fine with no false "unused selector" warnings. Oh and I'd like native CSS nesting supported properly so styles written inside other style rules get correctly scoped, with unused or empty nested rules annotated as comments in the output. Last thing, attribute selectors whose values contain special characters aren't parsing right now and the output gets corrupted, so those need to be preserved correctly.

The scoping decision logic lives in the compiler's CSS handling, so that's where the source-side vs right-side combinator behavior and the descendant chain fixes need to land. Both bug classes matter because under-scoping leaks component styles out and over-scoping messes up selector specificity, and both are miserable to debug in real apps.
