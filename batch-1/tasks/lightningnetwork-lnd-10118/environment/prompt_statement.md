I'm cleaning up the SQL database layer and want to add a general-purpose cursor-based pagination helper. Right now anything that iterates over big result sets by advancing a position marker has to hand-roll the loop, the cursor advancement, and the error handling every single time, which is duplicative and easy to get subtly wrong. So I want one shared utility that does it all.

The helper should take a starting cursor, a fetch function that returns a page of results given a cursor plus a page size limit, a function to pull the next cursor out of a returned item, and a callback to process each item. It keeps fetching pages until results run dry, meaning it stops as soon as it gets an empty page or a page with fewer items than the configured max page size (that's the signal we've hit the last page). It needs to propagate errors from both sides: if the fetch fails, the error message should say which cursor value was in use when it failed, and if item processing fails, the error should wrap the original so callers can still inspect the underlying cause and processing halts right away.

While I'm in there I also want to rename and consolidate the existing batch query config. The current name only reflects the one use case (batch IN-clause queries), but now that we're adding pagination it should be a single unified config type with separate fields for the batch size and the page size. Rename the existing batch query execution function to match, and update all the call sites over to the new names. Oh and the graph store configuration struct references the old field too, so update that to use the renamed field.
