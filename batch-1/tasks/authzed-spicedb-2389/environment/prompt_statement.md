I'm working on the secondary dispatch system in SpiceDB and I need to add a configurable cap on the primary hedging delay. Right now when the dispatcher routes a request to a secondary cluster it introduces a delay before falling back to the primary, giving the secondary a head start, but that delay is driven entirely by observed latency statistics with no upper bound per secondary. I want each secondary cluster configuration to carry a maximum hedging delay field that caps how long the primary can be held back, so operators can say the primary is never delayed more than a few milliseconds for a given secondary, or disable it entirely. If that max is set to zero the primary dispatcher shouldn't be delayed at all, even on the very first request which normally incurs the default starting delay, so zero really means fully suppressed.

While I'm in there I want to pull the primary hedging sleep logic out into its own self-contained component. It needs to support explicit cancellation so an in-progress sleep can be cut short via a cancel call, context cancellation, or a context deadline expiring. One subtlety, calling the cancel function before a sleep actually starts should have no effect on that upcoming sleep, it only interrupts sleeps already in progress. Also it's got to be safe to call concurrently from multiple goroutines, oh and it should keep tracking metrics during each sleep like the current code does. Without this cap the delay grows unbounded from latency data and there's no way to turn it off for one specific secondary, which makes dispatch behavior hard to tune in production.
