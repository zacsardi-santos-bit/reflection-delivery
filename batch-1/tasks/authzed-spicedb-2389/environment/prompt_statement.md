I'm working on the secondary dispatch system in SpiceDB, and I need to add a configurable maximum cap on the primary hedging delay. Right now, when the system routes a request to a secondary cluster, it introduces a delay before falling back to the primary — and this delay is determined by observed latency statistics with no upper bound per secondary configuration. I want each secondary cluster configuration to be able to specify a maximum hedging delay, so the primary is never held back longer than that limit. If the maximum is set to zero, the delay should be completely suppressed — even on the very first request, which normally incurs a default starting delay.

I also need to refactor the hedging sleep logic into a dedicated, self-contained component. This component should support explicit cancellation — an in-progress sleep can be cancelled early via a cancel call, context cancellation, or a context deadline. Importantly, calling the cancel function before a sleep starts should not affect the upcoming sleep; it should only interrupt sleeps that are already in progress. The component also needs to be safe to call concurrently from multiple goroutines, and it should track metrics during each sleep.
