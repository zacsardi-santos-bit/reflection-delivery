Right now it only lets me join against a single top-level query field, so if the data I want lives behind an intermediate resolver type I'm stuck writing custom resolver logic to compose it. What I want is to write a join whose selection path spans multiple type levels, so it first calls an intermediate resolver with arguments pulled from the parent object, and then selects a field on the result of that call, and that inner field can take its own arguments too.

A few things that matter here. The variables coming off the parent object (the type that declares the join) should be usable as arguments at any level of the nested path, not just the first hop. Literal argument values need to work alongside those variable references in the same nested path. When the chain runs, each resolver in it should get invoked in order with the result of one step becoming the parent context for the next step. And the final value the whole join produces should be whatever the terminal resolver returns, whether that's a scalar or an object.

Basically I want to extend the join directive so it supports this kind of multi-level field selection path instead of being limited to one top-level field. That'd let me link data across a chain of resolvers declaratively and drop a bunch of boilerplate, keeping the schema definitions clean. Can you make that work?
