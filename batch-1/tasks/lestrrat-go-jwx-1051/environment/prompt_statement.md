I'm hitting a couple of problems with our JWS library and could use a hand. First one's a panic, and it's the security-sensitive kind. When we get a JWS message in the JSON serialization format (not the compact dot-separated one) and it's missing its protected header field, the library panics instead of handling it. That's bad because a crafted or just malformed input can trigger it, which means anyone sending us a token could knock over a service that parses JWS, basically a DoS. I want parsing to succeed on those inputs even though they're incomplete and can't actually be verified, and then when you go to verify such a message it should fail cleanly with a clear error rather than blowing up. Important caveat though, this only applies to the JSON format. The compact format (three dot-separated base64 segments) should still return an error when the header segment is missing or empty, don't loosen that.

Second thing, when verification fails I can't tell why. Right now there's no way to know if the error came from an actual cryptographic verification failure versus something else like a structural problem with the message or a failed key fetch. I want a helper I can call on an error that tells me whether it's specifically a verification error, returning true for the crypto verification case and false for everything else. That way I can handle them differently in my code, like retrying a key fetch versus just reporting a hard crypto failure. So to sum up what I need: parsing a JSON-format JWS with a missing protected header succeeds without error, verifying that incomplete message fails with a clear error instead of panicking, and there's a utility function available to check whether a given error is specifically a cryptographic verification failure.
