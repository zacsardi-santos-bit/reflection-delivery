I'm building out a Microsoft 365 security scanner and there's a gap around Teams security reporting that I want to close with two new checks. Right now nothing tells me whether users can actually report suspicious or malicious messages from their Teams chat, or whether the backend submission policy is routing those reports where they should go, so admins are basically blind to misconfigs that would keep user-flagged attacks from ever reaching the security team.

First check looks at the global Teams messaging policy and verifies end users are allowed to report security concerns straight from their chat interface. If the policy's there and the setting is on, it passes; if it's disabled, it fails; and if there's no policy data at all, it should produce no finding (don't want noise when we just didn't get the data).

Second check inspects the Defender report submission policy and only passes when it's fully wired up to send reported content to custom org addresses across all three categories, junk, not-junk, and phishing, each with non-empty destination address lists, plus chat message reporting to Microsoft directly is disabled while reporting to a custom address is enabled. Any deviation from that (missing category, empty list, chat-to-Microsoft still on, chat-to-custom off) is a FAIL. If the policy doesn't exist, no finding again.

Oh and both service layers need updating so the checks can actually read this stuff, the Teams service has to fetch and store the global messaging policy object, and the Defender service has to fetch and store the report submission policy object.
