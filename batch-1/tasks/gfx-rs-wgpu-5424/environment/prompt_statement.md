I'm hacking on naga (the shader compiler) and there's a gap I keep running into with WGSL built-ins for raw byte packing. We already handle the normalized float versions like pack4x8snorm and friends, but we don't recognize the integer ones that pack a four-component int vector into a single u32 by grabbing the low 8 bits of each component, or the two unpack functions that go the other way. I want the four of these wired up: pack4xI8 and pack4xU8 (taking a signed vec4 and an unsigned vec4 respectively), plus unpack4xI8 which sign-extends each extracted byte back to a full 32-bit signed int, and unpack4xU8 which extracts without sign extension into an unsigned vector.

This needs to go through the whole pipeline. The WGSL front-end parser needs to recognize these four names, the IR needs new variants to represent them (alongside wherever the existing pack/unpack math functions live), and then every codegen backend has to emit correct code: GLSL in `@naga/src/back/glsl`, HLSL in `@naga/src/back/hlsl`, MSL in `@naga/src/back/msl`, SPIR-V in `@naga/src/back/spv`, and the WGSL writer in `@naga/src/back/wgsl`. The parsing side lives around `@naga/src/front/wgsl` and the shared IR/math enums in `@naga/src/lib.rs` or wherever MathFunction is defined.

Key correctness bits: the pack variants must use only the low 8 bits of each component and combine them in little-endian byte order (component 0 is the lowest byte), and the signed unpack must sign-extend each byte correctly from 8-bit to 32-bit, which is the easy thing to get wrong. Point is, a WGSL shader using any of these four should compile and produce idiomatic output on all backends. Can you implement it?
