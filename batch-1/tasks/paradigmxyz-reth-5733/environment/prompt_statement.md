I'm cleaning up how we generate and parse snapshot filenames and there's this annoying coupling I want gone. Right now a snapshot filename encodes both a block range and a transaction range, but the transaction range really shouldn't be in there at all. Snapshots are indexed by block position, so the block range alone uniquely identifies a file, and dragging the tx range along means callers have to go look up and supply transaction data just to build or read a filename. That's pointless complexity I keep hitting.

So I want the filename format to encode only the segment type plus the start and end block numbers, nothing about transactions. This needs to flow through all three spots. The method that builds the base snapshot filename should take just the block range and drop the transaction range parameter entirely. The config-based variant that appends compression and filter info should likewise drop its transaction range param but keep tacking on that filter/compression stuff. And the parser that turns a filename back into a segment plus range should stop returning any transaction range, just give back the segment and the block range.

Also, actually, while I'm in there, the parser should accept a plain string instead of the current platform-specific path component type it takes now, cleaner that way. And it's gotta still correctly reject malformed filenames, so if either the start or end block number is missing it returns a failure result rather than silently parsing garbage. Everything else about the naming convention stays the same, I just want the tx range out of the picture so the API's easier to reason about and less coupled to transaction-level indexing.
