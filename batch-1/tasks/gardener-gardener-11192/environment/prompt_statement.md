I'm working on the garden operator and I need to wire up garden-level extensions, right now the Garden resource spec has no way to say which extensions are active so I want to add an extensions list to the spec where each entry carries an extension type identifier plus optional provider-specific config (basically a raw extension config blob per entry). Alongside that the Garden validation logic needs to grow so it catches the case where the same extension type shows up more than once in that list, that should come back as a descriptive validation error that points at the duplicate entry by its index/position in the list. A garden that has a clean duplicate-free set of extensions should just pass validation with no errors, so don't over-reject.

On the extension component side there are two lifecycle ops missing that I need for teardown. Today there's already logic to delete only the stale extension resources and to wait for those stale ones to disappear, but there's nothing to delete all of the managed extension resources (not just the stale subset), and nothing to wait until every managed extension resource is fully gone. I want both added so the garden teardown path can clean everything up when a garden is removed or updated. The delete-all op should remove all extension resources it manages, and the wait op should block until they've all been cleaned up and return an error that identifies any resource still hanging around by its namespace and name. Without this the operator can't register extensions at the garden level, can't catch accidental duplicate registrations, and can't cleanly tear down, so it's blocking real extension lifecycle work.
