I'm working on the data coordinator client and noticed that several of the index-related operations don't properly surface communication errors to callers. When the remote service fails at the transport level — connection refused, network timeout, that kind of thing — the error gets swallowed and the caller gets back what looks like a successful (or at least non-error) response. This makes it impossible to tell whether the operation actually worked or just silently failed.

The expected behavior is: if the underlying remote call returns a communication error, that error should be returned to the caller. On the other hand, if the remote call succeeds at the transport level but the server reports a non-success status inside the response body, the response should be passed back to the caller as-is (so they can check the status code), without converting it into a Go error.

The issue seems to affect specifically the index-related operations — things like creating an index, retrieving index state, retrieving index build progress, describing an index, getting index statistics, and dropping an index. Other operations in the same client appear to handle this correctly already. Can you fix the index-related methods to properly propagate transport-level errors?
