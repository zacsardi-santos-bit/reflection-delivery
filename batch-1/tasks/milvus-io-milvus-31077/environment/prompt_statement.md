I'm digging into the data coordinator client and there's a real correctness bug in how the index operations handle failures from the remote service. When the underlying remote call fails at the transport level, connection refused, network timeout, that sort of thing, the error just gets swallowed and the caller ends up with what looks like a successful or at least non-error response back. That makes it impossible to tell whether the op actually happened or silently died, which is bad news for anything trying to do retry logic or fail fast on top of these calls.

Here's the behavior I want. If the underlying remote call returns a communication error, that error needs to propagate straight back to the caller. But if the remote call succeeds at the transport level and the server just reports a non-success status inside the response body, then I want the response passed back as-is (so the caller can check the status code themselves) without turning it into a Go error. So it's really about separating transport failures from server-reported statuses.

The methods hit by this are the index-related ones specifically, creating an index, retrieving index state, retrieving index build progress, describing an index, getting index statistics, and dropping an index. Other operations in the same client already do this right, so use those as the pattern. Just fix the index methods to propagate transport-level errors correctly, oh and don't accidentally convert a bad-status-but-successful-call into an error while you're in there.
