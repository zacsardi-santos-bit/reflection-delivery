I'm digging into the spatial view code for rendering 3D point clouds and the way it's structured right now is bugging me. The rendering pipeline is glued directly to a specific query abstraction, it takes a high-level query result object and just processes it inline, so there's no clean way to swap in a different query strategy (cached vs uncached, that kind of thing) without duplicating a bunch of code, and I can't benchmark the rendering pipeline on its own without eating all the query overhead too.

What I want is a new intermediate data container over in the visualizers module that holds borrowed slices of all the component data needed to draw a batch of 3D points, so that's positions, colors, radii, labels, keypoint ids, class ids, and instance keys, all as references into existing data rather than owning anything. Then the existing rendering methods should take this container instead of the raw query result, so it becomes the bridge between whatever query backend fetches the data and the shared rendering logic.

Oh and one important bit, the container has to be publicly visible from the visualizers module, since I want benchmarks (and potentially other subsystems) to construct it directly and measure the actual cost of rendering work without going through the query machinery at all. That's really the whole point, decoupling the render path from query fetching so I can drive it from both cached and uncached paths and profile it honestly.
