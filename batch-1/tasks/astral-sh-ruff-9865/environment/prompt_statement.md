I'm digging into our missing-interpolation-prefix lint, the one that flags string literals with brace-formatted variable names that look like they should've been interpolated strings but weren't. It's got a handful of bugs and I want them sorted.

There's a false negative first. When one of these strings gets passed as an argument to a method that's invoked through attribute access on an object (so you're grabbing a method off an object and calling it), the rule just skips it and never warns. That's wrong, those are exactly as likely to be accidentally non-interpolated as strings handed to a plain function call, so it should flag them same as anything else.

Then there are three false positives that are annoying me. One, grouped implicit concatenation with explicit formatting: when several string parts are grouped together and the format method gets called on the whole combined result, the rule shouldn't warn about the individual parts, but right now it does. Two, chained attribute method calls, if a string literal (or a function result that got the string) has multiple levels of attribute access and method calls applied, not just one, the rule only suppresses at the first attribute call and then warns on the deeper chaining. It should stay quiet at any depth. Three, positional argument names, right now it only looks at keyword args, so if a string goes to a function alongside a positional argument whose name matches the variable inside the string's braces, it warns anyway. It should treat that as an explicit formatting context and suppress, just like it already does for keyword arguments.

Oh and while doing this cleanup, split the test fixtures into two files, one with the cases that should trigger the rule and one with the cases that shouldn't, and delete the old single combined fixture file. These bugs make the rule both miss real problems and spew noise, which kills trust in it, so I want it tightened up.
