I'm doing an accessibility pass on our dropdown select components and hit a couple of gaps I want fixed. Right now the trigger button on both the single-select and multi-select dropdowns exposes a generic button role, which doesn't tell screen readers these are actually selection widgets. I need that trigger element to identify itself as a combo box control to assistive tech instead of a plain button, for all the select-style dropdowns.

The bigger issue is there's no way to give these components a stable accessible label. The control's accessible name currently just mirrors whatever's selected (or the placeholder), so the moment someone picks a value the label changes and they lose track of what the field was even for. I want both the single-select and multi-select components to accept a developer-supplied accessible label prop, and when it's provided it should stay as the control's accessible name no matter which option(s) get selected or deselected.

This needs to play nice with custom openers too. If the component has an accessible label and a custom opener is used, pass that label down to the custom opener. But if the custom opener already defines its own accessible label, that one wins, don't clobber it. Basically the opener's own label takes priority over the inherited one.

Oh and while I'm in here, the exported TypeScript types for the labels config on both components should be renamed so they better reflect what they actually represent. And accessibility audits should come back clean with no violations once an accessible label is supplied, so make sure the a11y checks pass in that case.

This all matters because screen reader users depend on stable, descriptive names to understand what a form control is for, and a name that keeps shifting with selection state strips that context away. Correctly marking these as combo boxes also gets assistive tech to apply the right interaction model, which helps keyboard and screen reader usability across the board.
