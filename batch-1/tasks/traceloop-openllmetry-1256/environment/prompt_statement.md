So I'm tracing OpenAI assistant runs with the OpenTelemetry instrumentation package and hitting a frustrating gap. When I create a run manually and poll its status myself, I get a proper span with everything I'd want, the operation type, the model pulled from the assistant definition, the system instructions from both the assistant's base config and any run-level overrides, plus all the completion messages from the thread. Great. But the moment I switch to the convenience method that creates the run and automatically waits for it to finish (the create-and-poll one-call approach), I get nothing, no spans at all. Empty traces even though the assistant clearly did the work and completed fine.

It looks like the instrumentation only wraps the manual create path and just misses the automatic polling variant entirely, even though the end result is identical, a completed assistant run. What I want is for both approaches to produce the same telemetry, a single span with the same name and structure as the manual one, recording the operation type, the model, both sets of system instructions (assistant base instructions and run-level overrides), and every message produced during the run. And importantly the internal polling requests that keep checking run status shouldn't spin up their own extra spans, just the one span for the whole operation.

This matters because lots of real-world integrations prefer the simpler one-call API, and right now those teams have a blind spot in their observability, traces show up empty which makes it really hard to audit or debug or monitor assistant usage in production. Can you add support for the automatic polling approach so it emits the same telemetry as the manual approach?
