I'm cleaning up our configuration management library, the one that stashes cluster and node config in a distributed key-value backend, and the constructor is bugging me. Right now to spin up a manager you have to hand it a lifecycle context object alongside the backend handle, and honestly that's just noise for most people. Nobody wants to think about context management, they just want to connect to storage and start reading and writing. Can you change it so creating a manager only takes the backend connection, no context parameter at all?

While you're in there, the get/set stuff needs to actually round-trip correctly. If I set a cluster configuration and then read it back, I want the exact same data I stored, byte for byte. Same deal for node configs, set one and then fetch it by its node ID and it should come back identical to what went in. Right now I don't fully trust that.

Oh and the watch/callback feature, that's the big one for me. I want to register named callback functions that fire whenever a cluster or node configuration gets updated, and the callback needs to receive the full updated configuration object, not just a key or a flag. So registering a named watcher for cluster config changes should invoke that callback with the new config every time a cluster config is written, and likewise a named watcher on node config changes should get called with the new node config on every node write. Right now the triggering isn't reliable enough to lean on in production, callbacks just don't fire promptly (or sometimes at all) after a change lands.

So basically: drop the context from the constructor, make the set/get round-trips consistent for both cluster and node configs, and make registered watchers actually get invoked with the correct configuration data whenever a write happens. This is all about making the API easy to consume and trustworthy enough to build reactive config workflows on top of. Thanks!
