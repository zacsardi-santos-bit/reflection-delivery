I'm hitting a wall with DataFusion's logical-plan-to-SQL conversion. I've got some custom logical plan nodes (user-defined extension nodes) that model domain-specific query operations, and whenever I try to unparse a plan containing one of them back into SQL it just blows up with a not-implemented error. There's literally no hook to teach the SQL converter how my extension nodes should be rendered, so round-trip conversion is impossible for anything with custom extensions in it.

What I want is a way to register custom conversion handlers on the SQL converter (the unparser side) so it knows what to do with my nodes. Two cases matter to me: sometimes a custom node is a whole SQL statement on its own and should convert straight to a standalone statement, and other times it shows up as a source/relation inside a bigger query and needs to be embedded as a subquery within the containing statement. So the mechanism should let me attach one or more handlers, and each handler can either handle a given node or pass on it (decline). The first handler that successfully handles the node wins and the rest get skipped. And if no handler can deal with a node, keep the existing behavior, meaning it still fails with a clear not-implemented error like before.

One more thing that's blocking me: the internal AST builder types used to construct the SQL AST fragments (the subtrees I'd return from a handler) aren't accessible from outside the crate right now, so I can't actually build the SQL representations I need to return. Those need to be public so external implementors like me can construct them. This all lives around the unparser code in `@datafusion/sql/src/unparser`. Without it any codebase using custom plan nodes is locked out of the built-in SQL generation, which kills query export and any tooling that round-trips logical plans back to SQL strings.
