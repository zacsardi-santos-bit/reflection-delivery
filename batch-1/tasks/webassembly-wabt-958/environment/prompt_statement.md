I'm poking at the wabt binary toolkit and the disassembler is spitting out wrong stuff for a couple of cases, would love a fix. First bug: when I disassemble a binary that has really wide instructions, like a 128-bit vector constant which is 18 bytes, or one of those big 64-bit integer constants that runs 11 bytes, the output just drops the bytes that don't fit on a line. It's supposed to wrap the overflow onto extra display rows with the right file offsets but instead it silently truncates, so the line shows fewer bytes than the instruction actually has in the file. I want every byte of every instruction to show up, wrapping to additional rows as needed, and each row should hold at most 9 bytes (that's the display width constant the code already defines). The continuation rows should carry the extra bytes plus their correct offsets but no instruction mnemonic, since the mnemonic only belongs on the first row.

Second bug, and this one's annoying: any instruction that starts with a prefix byte (atomics, SIMD, the saturating conversion ops all do this) shows the wrong byte offset at the start of the line. It's pointing at some interior opcode byte instead of the address of the first byte, the prefix byte, of the instruction. Also for SIMD instructions where the sub-opcode value is >= 128, that sub-opcode takes two bytes in the file thanks to LEB128 encoding, but the disassembler only prints one of the two. So both the offset and the byte count come out wrong for these. I want the offset to point at the first (prefix) byte and all the bytes accounted for.

Net: fix both so the disassembler shows all bytes of every instruction, wrapping as needed, with the correct file offset pointing at the first byte. Right now folks debugging with this are getting truncated output and bad addresses, can't line up disassembly with actual file positions or verify encodings.
