I'm working on our GitHub Actions security scanner and template injection findings are coming out miscounted whenever a workflow reaches an env var through the expression context, you know, when a step reads an environment variable by name via the expression syntax instead of just using it as a plain shell variable. The scanner's supposed to figure out whether the env var it's pulling that way is static (platform-controlled, always the same no matter what a user does) or dynamic (something workflow logic or user input could influence), and right now it botches this in both directions. It sometimes treats unknown env vars as safe when they really might not be, and it sometimes fails to suppress findings for the well-known runner-provided vars that are definitely static. So auditing any workflow that uses this env var expression pattern gives me the wrong finding and suppression counts.

What I want is for it to correctly recognize which env vars accessed through the expression context are the known platform defaults, the ones the runner always sets automatically, and mark those static and suppress their findings (or drop them to just a very low severity pedantic note), while references to unknown or user-defined vars stay flagged as potentially non-static and get reported. Basically the false negatives (unknown or user-defined vars treated as static/safe) and the false positives (missed suppressions on the always-static runner vars) both need fixing, and the overall finding counts for the affected workflows should land right once that logic's correct. The whole point is the reports get noisy with spurious warnings on safe patterns and silently pass on the dangerous ones otherwise, which kills the trustworthiness of the output. The fix lives in whatever code decides static-ness for env-context accesses, so the known-static set of runner variables needs to actually drive suppression versus detection there.
