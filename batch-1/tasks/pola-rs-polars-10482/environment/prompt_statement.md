I'm hitting two problems with as-of joins in polars when I use the nearest matching strategy.

First, there's just no tolerance option for nearest. With backward and forward I can pass a max distance so any left row without a right row inside that window comes back null, but nearest ignores all that and always grabs the globally closest value even when it's absurdly far away. For time-series work that's a real limitation, a match that's too far in time is often worse than no match at all, and right now people work around it by post-filtering which is error-prone. I want to pass a numeric distance for numeric keys, or a duration string for date/time keys, and also just hand it a time-interval object directly for date/time keys instead of having to spell it out as a string (only strings are accepted there today). Anything beyond the tolerance should produce a null/missing result for that left row. Oh and this needs to work when the join is grouped by one or more columns too, same tolerance behavior.

Second, there's a correctness bug in nearest. When the last row on the right side is the nearest match for several consecutive left rows, only the first one gets matched right, the rest come back wrong or missing. Looks like some internal distance value is sticking around across left rows instead of getting reset. Both the plain nearest join and the grouped variant are affected, so please fix the state issue in both.

Can you knock out both of these? The nearest-with-tolerance pattern shows up all over financial and scientific pipelines where two event streams should only count as matching if they happened close together, so getting tolerance plus the correctness fix in place matters.
