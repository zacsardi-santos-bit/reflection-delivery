We're pulling checkout out of the subscriptions module. Right now creating and retrieving payment processor checkout sessions lives inside subscriptions as this "subscribe session" concept, but checkout is really its own concern and shouldn't be tangled up with subscription logic. I want a new dedicated checkout module with its own endpoints, service, and schemas, and the old subscribe-session service plus its endpoints under the subscriptions module deleted entirely, all that functionality replaced by the new module.

So the new module needs an API endpoint for creating a checkout session. Callers pass a product price ID and a success redirect URL, and optionally a customer email. Validate inputs properly, the product and price both have to exist and not be archived, the redirect URL has to be a valid URL, and any customer email has to be valid email format. Also if an authenticated user already has an active subscription to that product, reject the request with a specific error.

The behavior varies by who's calling, which is the fiddly part. Anonymous users just get a basic checkout. Cookie-authenticated users get their existing payment processor customer ID associated with the session and their user ID tracked in the metadata. API token users who supply a customer email should have that email forwarded to the processor without associating a customer account. Oh and products that have tax-applicable benefits need to create the session with tax collection enabled. Also when a user with an active free subscription is initiating a paid checkout (i.e. upgrading), stick the existing subscription ID into the session metadata.

Then there's a separate endpoint to retrieve a checkout session by its ID, which looks it up from the payment processor and resolves the associated product and price from the session metadata, returning the session details including customer name and email when they're available. If the metadata is missing or incomplete (no valid product price reference) the retrieval should fail with a not-found error.

The point of all this is just cleaner organization and less coupling so we can extend checkout later (one-time purchases, more payment methods, whatever).
