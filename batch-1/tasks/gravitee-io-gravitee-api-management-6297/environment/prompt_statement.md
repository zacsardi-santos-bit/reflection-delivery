I'm cleaning up our CI/CD pipeline for publishing Helm charts and hit a bunch of sequencing bugs I want fixed. The big one: when we tag a release, the pipeline bumps the Helm chart's version as part of the release tagging commit itself, but that's wrong. The chart version should only advance in the subsequent "prepare next version" commit, not when we tag the current release, otherwise the chart version sitting in the repo after a release reflects the released version instead of the upcoming one. And at that same "prepare next version" point, when the chart version gets bumped, the changelog annotation in the chart metadata needs to be cleaned up too. Right now both of those happen at the wrong time.

Then there's the Helm publishing job itself. The repository checkout step runs too early, before credentials and tooling are set up, so it needs to move to after the setup steps. For real (non dry-run) releases the job also has to explicitly check out the specific release tag before it packages the charts, which it doesn't do today, and that could mean packaging the wrong chart files. Also the publish step currently updates both the chart version and the app version in the chart metadata, but only the app version should be touched at publish time since the chart version bump is handled elsewhere. Oh and the commands that push packaged chart archives to the registry use hardcoded version-specific filenames that'll break the moment the version changes, so switch those to wildcard patterns instead.

Last thing: I want pull request builds on our main development branches to also publish the Helm chart to the internal repository in dry-run mode, so chart changes get validated during normal PR review. That step is missing from the PR pipeline entirely right now, so add it. Can you help me sort all this out?
