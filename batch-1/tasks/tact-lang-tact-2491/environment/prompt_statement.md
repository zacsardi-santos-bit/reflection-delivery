I'm poking at the Tact compiler and hit a gap with our built-in debugging output function (the dump one). Right now it'll happily take a value of pretty much any type, including custom or non-standard primitives that it has no idea how to serialize, like the internal string builder primitive. The call just sails through compilation and then blows up later at runtime or during codegen in a way that's way harder to trace back. I want a proper compile-time type check on the argument so devs get told immediately when they've passed something the function can't handle.

The behavior I'm after: all the normal stuff should keep working with no error, so integers, booleans, strings, addresses, cells, builders, slices, null, void returns, optional types, and maps all stay fine. But anything outside that supported set, a custom primitive or other non-standard type, should trigger a clear compile-time error. The message needs to actually name the offending type and point the developer at the relevant docs so it's actionable, not just a vague failure. Basically move the failure to the earliest possible stage instead of letting it silently surface way down the line.

Btw the fix lives in the compiler's type checking / build path for that built-in, so the guard should reject the unsupported type right where the argument gets validated.
