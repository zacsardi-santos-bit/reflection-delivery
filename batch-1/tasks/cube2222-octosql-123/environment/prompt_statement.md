I'm chasing a bug in the query optimizer's filter pushdown and it's producing wrong plans. The issue is it merges filter predicates into data source scans even when one side of the predicate isn't a plain column reference. Data sources can only filter against direct column references, they can't evaluate arbitrary derived expressions like a function call wrapping a column, so pushing those down gives me an incorrect query plan that either silently returns wrong results or blows up at execution time when the source gets a predicate it can't handle.

Concretely, if I have a predicate that applies a function to a local data source column and compares that against a column from another source, the optimizer should leave it as a standalone filter instead of pushing it down. Same deal if both sides reference the same data source but one side goes through a function call, that predicate needs to stay in the filter layer. But if a function's inputs come entirely from external sources and the other side of the predicate is just a plain direct column from the data source, that one is still fine to push down.

The fix has to land in two places, the part of the optimizer that decides whether a predicate can be moved into a data source, and also the part that actually performs the move. Key thing is only plain direct column references qualify as the data-source-local side of a comparison when deciding pushdown eligibility, not any expression derived from those columns (a function call over a column shouldn't count). So both the eligibility check and the move logic need to distinguish direct column refs from derived expressions and treat only the former as pushable.
