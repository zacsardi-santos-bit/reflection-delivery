We're hardening our GraphQL server against DoS-style introspection abuse and I keep hitting gaps in the current protections. Right now we catch some repeated introspection requests in a single query, but a bad actor can just alias the same introspection field over and over and slip right past us, so I want that alias-based repetition treated exactly the same as unaliased repetition when we decide a query is acting in bad faith. Also there's no cap on total field count, so someone can craft a massive query that bloats memory before we even execute anything.

What I need first is a configurable maximum field count applied when we build the normalized/executable representation of an operation. If a query blows past that limit, abort immediately with a clear message that says the actual count versus the limit, don't let it keep going. And the operation object that comes out of that build should expose the total field count and the maximum nesting depth that were observed, since I want to feed those numbers into monitoring and defensive tooling.

On the depth side, our existing introspection depth check only raises a soft validation error today. For deeply nested introspection queries (beyond a reasonable threshold), I want it to hard-stop execution instead of running to completion. Oh and we should expose publicly accessible constants that define what the library considers the maximum acceptable field count and maximum depth for a good-faith introspection query, and the standard introspection query that ships with the library needs to fall within those limits so we're not tripping our own guard. Basically configurable field-count limits, depth tracking exposed as metrics, alias-aware bad-faith detection, and a hard abort path all together to close these attack vectors and give operators the observability to tune things.
