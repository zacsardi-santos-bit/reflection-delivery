I'm deep in the streaming infra for our ML platform and I hit a nasty bug in the test utilities that validate streaming message behavior. There's a helper that sorts and compares expected vs actual upsert and deletion messages, and it's got two issues. First, when it sorts the expected deletions list it accidentally passes the upsert slice as the sort comparator instead of the deletions slice, so any deletion comparison silently produces wrong results. Second, it runs the sort unconditionally even when a slice has zero or one element, which panics or otherwise behaves wrong on nil/single-element slices. I need the deletion messages sorted using the correct comparator (the deletions slice, not the upserts), and the sort guarded so it only runs when there are at least two elements.

Once that's fixed I also want integration test coverage for four scenarios that I couldn't reliably test before. One, updates outside subscription scope: when a db update hits an entity that isn't covered by a client's subscription, the streamer should silently ignore it and the subscriber only gets updates for entities inside their subscription. Two, offline catch-up fall-in: when a client reconnects after being offline and entities that now fall within its subscription got created while it was gone, the reconnection sync delivers those missed upserts. Three, offline catch-up fall-out: when a client reconnects and entities it previously knew about were deleted while offline, the sync delivers deletion notifications listing those removed IDs. And four, online scope changes: when an entity moves into or out of a subscription's scope in real time (say its parent object changes) the streamer immediately sends the right upsert or deletion to the active subscriber, both the moving-in and moving-out directions. Btw all four of these should pass reliably once the comparator and guard fixes land, since right now the results are either silently wrong or they crash.
