I keep hitting a nasty bug in the build scheduler where certain graph shapes make builds either fail outright or just hang forever. Here's what's going on: the scheduler merges edges between different build graph vertices that share the same cache key, it does this as a perf optimization since identical cache keys mean identical work. Problem is, under specific ordering conditions those merges can introduce cycles into what should stay an acyclic directed graph, and once you've got a cycle the build deadlocks or errors out.

What I want is for the scheduler to detect when an edge merge would create a cycle and just not do it, it should pick the safe merge direction instead of blindly proceeding in whatever direction it happened to land on. This needs to cover two situations. First the simple one, two different vertices with the same cache key whose edges would form a cycle when merged (which way it goes depends on input ordering). Second the trickier case where a vertex has already been merged multiple times through different ownership chains, and then a further merge through one of those owners would introduce a cycle, that one still needs to resolve cleanly.

In both cases the build should complete successfully and return the correct computed result with no errors coming back. Btw the reason this matters so much is it's order dependent, so it shows up non-deterministically depending on how vertices get processed and it's a pain to reproduce, but it does happen with real graph topologies in practice. The fix should make the scheduler reliably handle edge merging for any valid acyclic build graph even when identical cache keys are in play.
