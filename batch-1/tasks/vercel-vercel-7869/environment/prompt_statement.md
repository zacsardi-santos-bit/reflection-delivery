I'm hitting a nasty bug in the Vercel CLI's local build command. When I run `vercel build` in one project dir and then kick off another build in a different project dir inside the same process session, the outputs land in the wrong spot. An API-only project ends up with a `static/` output directory it shouldn't have (looks like leftover artifacts from the previous build of a different project), and the build manifest lists builder entries that don't belong to it.

Digging in, the issue is that the `.vercel/output` directory path gets resolved as a relative path, so where it actually lands on disk depends on the process's working directory at the moment the command runs, not the project dir being built. When the cwd changes between builds the output location drifts. I want the build command to resolve its output as an absolute path anchored to the project directory being built (the working dir when `vercel build` is invoked), so each project's artifacts stay isolated to that project's own `.vercel/output/`.

Also the file paths used for builder detection should be normalized to forward slashes so matching works right across platforms (Windows vs posix).

Concretely after a clean successful build: a static-only project should produce its files in `.vercel/output/static/` and list only the appropriate static builder in the manifest. An API-only project with files just under `api/` should produce function dirs under `.vercel/output/functions/api/`, should NOT produce a `.vercel/output/static/` directory, and should list only the API builder entries (no spurious static builder). And a project using a third-party builder should produce the correct function output directory structure including a runtime configuration file inside each function dir, again without any spurious static output directory. This matters because folks running builds locally or in CI expect each project's outputs isolated to its own directory, otherwise deployments silently include wrong files or miss functions.
