I'm running into a problem with the MySQL CDC connector when it tries to read schema information from tables that have advanced index definitions — specifically, tables that use expression-based or function-based index keys, which are supported in newer versions of MySQL. The connector tries to parse the full table definition to extract schema details, but the DDL parser doesn't handle the complex expression syntax inside those index definitions, so it ends up with nothing and then throws an error. The pipeline can't start at all for these tables.

What I'd expect is that if the primary method of reading the schema fails or produces an empty result, the connector should automatically fall back to a simpler alternative that retrieves column definitions directly from the database. This simpler method should still correctly identify each column's name, data type, nullability, and whether it's a primary key — and the resulting schema should be fully usable for change data capture. Right now, there's no fallback at all, so any table with this kind of index definition is completely broken.
