I'm hitting a wall with the MySQL CDC connector when it reads schema info off tables that use fancy index definitions, specifically the expression-based or function-based index keys that newer MySQL versions support. The way it works now, the connector grabs the full table DDL and parses it to pull out column details, but the DDL parser chokes on the complex expression syntax inside those index defs, so it comes back with an empty schema result and then throws an error. End result: the pipeline just can't start at all for any table shaped like that, which is a real problem since computed and function-based indexes are totally valid and common in modern deployments.

What I want is a fallback. If the primary schema read (the DDL parse path) fails or produces nothing usable because of that unsupported syntax, the connector should automatically switch to a simpler alternative that queries the column definitions straight from the database instead of parsing DDL. That fallback still needs to get every column right, its name, data type, nullability, and whether it's part of the primary key, and the schema it builds has to be fully usable for change data capture so the connector reports column types and PK info without erroring out. Right now there's no fallback whatsoever, so these tables are just broken end to end. Basically I want it to degrade gracefully instead of blowing up at startup, so CDC works across a wider range of real-world schemas.
