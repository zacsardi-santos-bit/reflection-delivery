I'm cleaning up our Radom payment processor integration in the order management system and the checkout session creation path is way too loose right now. When we build a Radom checkout session for an order there's basically no validation up front, so if the order has no items, or the item metadata is missing the success redirect URL, the cancel redirect URL, or the product identifier, the whole thing either fails silently or spits out some confusing error that tells you nothing. I want each of those four cases to produce its own distinct, matchable error so a caller can look at it and immediately know what went wrong instead of guessing at config issues. Also any client error we hit while actually talking to the payment processor should get propagated so callers can identify the cause, and on the happy path the checkout session response needs to include the session identifier that the processor hands back.

While I'm in there I need a second variant of the checkout session creation method that takes an explicit expiry time instead of always deriving it from the current moment, since always computing it from now makes it a pain to test and pins down the timing behavior.

On the storage side the order repository is missing a way to persist 64-bit integer values, which we need for blockchain data coming off payment webhooks (chain IDs, block numbers, that kind of thing where you actually need the full int64 precision). So I want a new method that appends or updates an i64 value by key in a given order's metadata, and when the target order doesn't exist it should come back with a recognizable "no rows changed" style error rather than pretending it worked.

Oh and to unit test the checkout session logic without dragging in a generated mock framework, the payment processor client package needs a simple hand-written mock with a configurable function field so we can stub out the create-session call per test. Wire it up alongside the existing Radom client code and the order repo so all of this is actually testable.
