So I'm digging into the raft mesh controller for our multi-controller cluster setup, and I hit an annoying gap. The method that registers a newly connected peer (the peer connect operation in the mesh) doesn't return anything at all, so callers are flying blind. If something goes sideways during registration, like there's already a connection for that peer's address, nobody upstream can tell. The op just silently proceeds and moves on.

Here's the real problem: when two controllers dial each other at the same time during cluster formation, one controller's connect attempt can quietly overwrite the other's existing peer connection with zero error reported. That leaves the old connection handler dangling and can push the cluster into an inconsistent state that's a pain to diagnose later, orphaned connections, bad routing decisions, all that.

What I want is for that registration method to return an error. On a successful register with no conflict it should signal success to the caller, and on a duplicate (connection for that address already exists) it should surface the failure so the calling code can retry, close the dupe, or at least log it instead of corrupting state.

Oh and one thing I don't want to break: the mesh's readonly mode logic, which keys off peer version matching. If a peer connects with a non-matching version, the mesh should still flip into readonly mode like it does today. The error return needs to reflect whether the connection was actually accepted, not whether the versions lined up, so those two concerns stay independent. Basically the readonly state should keep updating correctly based on version matching regardless of what the error signaling does.
