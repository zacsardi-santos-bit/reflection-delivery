I'm hitting a bug with a cloud custodian policy that fires when a DynamoDB table gets created. Problem is when the policy triggers on the creation event, the table isn't fully active yet, so custodian chokes trying to work with it. You can't tag or act on a table while it's still being created, so I need the live API fetch path to wait for the table to become available before moving on, and that wait needs a configurable timeout. This has been biting us across a few reported issues (things like newly-created tables not being ready, taggable failures, etc).

Key thing: that wait logic should live only on the live API fetch path in the DynamoDB resource code. When table data comes from the configuration history service instead, there shouldn't be any waiting at all since those are stable historical records that are already good to go. Triggering the wait there just adds pointless delays.

Also on the config history side there's an encryption metadata mismatch. The configuration history stores the encryption field names with different capitalization than what the live API returns, so policies that inspect encryption settings behave differently depending on where the data came from. I want the config source to normalize those encryption fields to match the live API's casing so both sources produce consistent resource data and filters work the same regardless of source.

Oh and one more related thing, results coming back from the configuration source aren't returned as a proper list right now, they're some lazy iterator, which breaks downstream code that tries to count results or compare resource sets. Wrap that up as an actual list so counting and comparisons work.
