I'm poking at the async runtime metrics and it's bugging me that basic observability stuff is locked behind the unstable cfg flag. Specifically the worker thread count and the count of currently alive tasks are only reachable when you build with the special unstable compilation flag, which feels wrong. These two are fundamental, safe metrics with no dependency on experimental internals, so blocking them from stable production builds makes no sense to me. Library users who just want to see how many workers a runtime has or whether tasks are still alive shouldn't have to opt into experimental features to do it.

What I want is to promote those two metrics (the worker thread count and the alive task count) to stable status so they're available in normal builds without any special flags. At the same time the metrics that genuinely lean on unstable internals need to stay gated behind the unstable flag, don't accidentally expose those. It's really just about drawing a clean line between what's stable and supported versus what's still experimental so the API surface reads clearly.

Oh and while you're in there, I'd like the tests reorganized so there's a dedicated spot for the unstable metrics tests, separate from the stable ones. Right now they're all mixed together and it muddies the distinction. Moving the unstable ones into their own file makes it obvious to contributors and users which metrics are which, and helps keep that separation from eroding later.
