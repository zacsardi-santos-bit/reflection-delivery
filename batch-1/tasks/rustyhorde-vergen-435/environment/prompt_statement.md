I'm hacking on a Rust build tool that bakes version metadata into the binary from git info, and I hit a behavior that's honestly kind of misleading. When git data isn't available, say I'm building outside a git repo, the tool just silently stuffs a static placeholder default into every git-related build variable, and it does this even in the normal default mode. So the build "succeeds" with totally fake values and nobody's the wiser, which is bad.

What I want is to split the two modes cleanly. In the default non-idempotent mode, when it can't retrieve git info, I want it to emit a warning per variable it couldn't populate, something along the lines of "Unable to set <variable name>", and crucially not insert any default value into the build environment. In idempotent mode the old behavior should stay, so it still writes the placeholder default and announces it via a warning saying that variable has been set to a default value. And idempotent mode needs to be an explicit opt-in by the caller, not the thing you get by default.

This needs to be consistent across all the git backends the tool supports, so the idempotent vs non-idempotent distinction has to be threaded through everywhere it matters, including the config types that handle the error fallback logic. The motivation is basically that folks building outside a git repo should get real diagnostic feedback about which variables couldn't be set instead of silently getting fake placeholders, while CI reproducibility builds that rely on idempotent mode keep working exactly as before as long as they turn it on explicitly.
