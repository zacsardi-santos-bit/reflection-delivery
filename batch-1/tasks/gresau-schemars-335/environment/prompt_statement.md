I'm using schemars to generate JSON schemas for my Rust types and the schemas don't reflect whether they're for reading or writing. When I have fields or enum variants excluded during serialization or deserialization via serde attributes, that distinction just vanishes from the output. What I want is to generate two separate schemas per type: a deserialization schema showing what the type accepts as input, and a serialization schema showing what it produces. A field that's excluded from deserialization can only be read, so it should show up as read-only in the serialization schema and be absent entirely from the deserialization schema. A field that's excluded from serialization can only be written, so it should appear write-only in the deserialization schema and be missing from the serialization one. Oh and in the default unconfigured schema, deserialize-excluded fields should be fully omitted, not shown with a read-only marker.

Also I use separate serde rename rules for serialize vs deserialize sometimes, including whole-type renames and per-field ones, so if a field is "foo" when deserializing and "FOO" when serializing, the serialization schema needs to say "FOO" and the deserialization schema "foo". This has to work consistently across named structs, tuple structs, and every enum tagging style (external, internal, adjacent, untagged). For tuple structs the schema in each mode should reflect the actual visible element count, compacted with no gaps where fields got excluded.

A few more things while I'm in here. Single-value tag constraints on adjacently-tagged enum variants should use the JSON Schema `const` keyword instead of a single-element enum list, it's more precise. Enums with no valid variants should produce a schema that can never match any value. And decimal number types should accept both numeric and string JSON inputs, with the validation pattern updated to cover scientific notation.
