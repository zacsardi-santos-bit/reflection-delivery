I'm working with a Rust JSON schema generation library and I need it to produce schemas that correctly reflect either the serialization or deserialization contract of my types. Right now, when I have fields or enum variants that are excluded during serialization or deserialization (via serialization attributes), the schema doesn't capture that distinction at all. A field that can only be read (excluded from deserialization) should appear as read-only in a serialization schema and be absent from a deserialization schema. A field that can only be written (excluded from serialization) should appear as write-only in a deserialization schema and be absent from a serialization schema.

On top of that, when I use separate rename rules for serialization vs deserialization — including for whole types or their fields — the generated schema should use the correct name for whichever context it's targeting. For example, if a field is called "foo" when deserializing and "FOO" when serializing, the serialization schema should say "FOO" and the deserialization schema should say "foo". This should work consistently for named structs, tuple structs, and all enum tagging styles (external, internal, adjacent, and untagged).

Additionally, there are a few other issues I'd like addressed: single-value tag constraints on enum variants should use the more precise JSON Schema constant keyword rather than a single-element allowed values list; enums with no valid variants should produce a schema reflecting that no value can ever match; and decimal number schemas should accept both string and numeric JSON inputs, with the validation pattern updated to cover scientific notation.
