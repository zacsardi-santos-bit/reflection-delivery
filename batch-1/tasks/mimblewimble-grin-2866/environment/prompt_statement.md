I'm hacking on a blockchain node that runs both a production chain and a separate test network, and the header version validation is bugging me because it uses one hard-coded hard fork schedule no matter which network the node's actually on. That means the test network is stuck using the exact same fork block heights as mainnet, so we can't rehearse upcoming protocol upgrades on testnet before they hit production, which is kind of the whole point of having a testnet.

What I want is for the header version validation in the consensus module to be network-aware. It should consult the existing network-type detection over in the global module (that already tells us production vs test network) and then pick the right fork schedule based on that. On mainnet it keeps the mainnet fork heights, and on the test network it uses an earlier, independent set of fork heights, with the test network's first hard fork happening at a dedicated block height that's different from and earlier than mainnet's.

There's also a boundary bug I keep hitting: on mainnet the second protocol version isn't being accepted right at the first fork activation height. It should become valid exactly at that first fork boundary, not one block after it, and it should be invalid before that window and after its active window closes too.

Oh and I need a constant for the test network's first hard fork block height defined and exported publicly from the consensus module so other code can reference it. Also, protocol version 3 shouldn't be valid on either network at the heights we care about right now since no third hard fork is scheduled yet, so make sure nothing accidentally activates a third fork.
