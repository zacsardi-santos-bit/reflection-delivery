We have a search index service that's doing too many things at once. Right now it's responsible for both managing the Elasticsearch index and handling the logic of synchronizing annotations between the database and Elasticsearch — checking the job queue, determining whether each annotation needs re-indexing, and cleaning up completed jobs. Those two concerns should really be separate.

I'd like to extract the synchronization logic into its own dedicated service. The new service should take over all the queue-processing and comparison logic: fetching jobs from the queue, checking whether each annotation exists and is up-to-date in the search index, re-indexing where needed, and returning a breakdown of what happened (e.g. how many were synced because they were missing, how many were already up-to-date, how many were force-synced, how many were deleted from the database, etc.). The search index service itself should be simplified — it shouldn't need to know about the queue service, batch indexer, or database session anymore.

The indexer task that currently calls sync on the search index service should be updated to use the new dedicated sync service instead. The new service should also be properly wired up with a factory function so it can be registered and used like other services in the application.
