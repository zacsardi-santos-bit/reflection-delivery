We've got a search index service that's grown into two jobs at once and I want to split it up. Right now it manages the Elasticsearch index for annotations and it also handles all the syncing logic, reading from the job queue, comparing what's in the database against what's stored in Elasticsearch, deciding whether each annotation needs re-indexing, skipping the ones that are already current, and cleaning up completed jobs. Mixing those two concerns makes both harder to test in isolation and muddies the dependency graph, so I'd like to pull the sync piece out into its own focused service.

The new sync service should own everything queue-related, so fetching jobs from the queue, checking whether each annotation exists and is up-to-date in the search index, re-indexing where needed, and returning a breakdown of what happened, meaning how many got synced because they were missing, how many were already up-to-date, how many were force-synced, how many were deleted from the database, that kind of tally. It'll need the queue service, batch indexer, and db session as its dependencies since those are exactly what's moving out of the search index service.

Speaking of which, once the logic's extracted the search index service should be simplified so it no longer takes or manages the queue service, batch indexer, or database session in its constructor, it just does the Elasticsearch index management. The indexer task that currently calls sync on the search index service needs to point at the new dedicated sync service instead. Oh and please wire the new one up with a factory function so it registers and gets used like the other services in the app.
