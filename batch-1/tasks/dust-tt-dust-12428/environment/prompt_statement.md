I'm seeing a real security gap in our file management API, right now it doesn't enforce any role-based permissions on write operations, so any authenticated user, even someone with the most basic workspace access, can upload content to or delete files that belong to workspace-level storage like folder documents. That's bad, those workspace-managed files should only be modifiable by folks with builder-level access or above. A regular low-privilege user could inadvertently or maliciously overwrite or remove workspace content that's supposed to be protected, which totally undermines role-based access control for file storage.

What I want is for the upload/replace and delete endpoints to gate write operations on non-conversation files behind a builder permission check. Conversation-related file attachments should stay fully open to everyone since users need to freely attach and manage files in chat, so no builder restriction there, preserving existing chat behavior. But anything outside the conversation context needs to be gated. So when a non-builder user tries to upload, replace, or delete a file that isn't a conversation attachment, reject it with a 403 permission error. Users with builder or admin privileges should be allowed to upload or delete any file regardless of its purpose.

This has to apply consistently to both the internal session-authenticated (private) API and the external API key-authenticated (public) one. Oh and for the public API specifically, regular non-system keys should also be blocked outright from write operations on non-conversation file types, before the builder check even gets applied.
