I'm building an upload utility for pushing CI build artifacts to cloud storage, and right now everything lands there with no HTTP content metadata at all. So gzip-compressed log files get served as raw binary blobs instead of being transparently decompressed and shown as readable text in a browser, and our JSON result files and plain text logs have no Content-Type either, so clients are stuck guessing the format. I want a function that infers the right HTTP metadata (content type plus content encoding where it applies) purely from a filename, and returns both the metadata map and the filename to use as the storage key.

Here's how it should behave. If a file has a double extension, like a compressed text log, treat it as a compressed version of the inner type, so strip the compression extension off the stored filename and attach both the inner content type and a gzip content encoding header. If it ends with a compression extension but there's no recognizable inner extension, still strip the compression suffix from the filename but only tag it with a generic compressed-archive content type and no encoding header. There's a tricky edge case too: if the whole name has no dot and is just the bare compression suffix word itself, leave the filename unchanged and give it only that generic archive content type. Standard extensions like plain text and JSON should get their correct content type with the filename left alone. Oh and the lookup has to respect MIME type registrations done at runtime through the system MIME registry, so custom extension mappings work. And if the filename is empty or is just a single dot, return an empty metadata map. This runs at upload time to set the object metadata, so whatever filename comes back (possibly stripped) becomes the storage key and the map gets attached to the upload.
