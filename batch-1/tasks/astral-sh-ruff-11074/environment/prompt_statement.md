I'm poking at our Python linter and hit a real blind spot in the rule that flags functions missing an explicit return (the implicit-return check). Here's the pattern it misses: a function does an if/else where the if branch returns a value fine, but the else branch ends in a `with` context manager block that has no explicit return at the bottom. That branch implicitly returns nothing, which is exactly what this rule is supposed to warn about, and right now it just sails through clean. So the coverage is wrong and anybody leaning on this rule to guarantee explicit returns could be shipping silent implicit returns they think were checked.

What I want is for that function to actually trigger the diagnostic. The diagnostic should point at the last statement inside the context manager block (the thing sitting at the end of the `with` body in the else branch), since that's where the flow falls off without returning. And it should come with a suggested fix, marked unsafe, that inserts an explicit return right after that last statement in the with block, matching the correct indentation level of the surrounding code so the edit is actually valid Python.

Basically the visitor logic that walks conditional branches to find terminal statements needs to descend into `with` blocks the same way it handles other terminal cases, treat a non-returning context manager tail as an implicit return, and emit both the pointing diagnostic and the unsafe autofix. Test it against a function with a returning if branch and a with-block else branch with no return, and make sure it flags at the right spot with the right fix.
