I'm cleaning up the timer gate components in the Cadence workflow engine, the ones the history queue processor leans on for scheduling. Right now they're defined as internal types inside the queue processing package and it's bugging me for a couple reasons: the method names are inconsistent with what you'd want from a general abstraction, and the real-time variant spins up a background goroutine in its constructor with no way to shut it down. That leak means the goroutine leak tests only pass if we explicitly ignore the dangling goroutine, which isn't a real fix, it's a bandaid.

What I want is to move both the real-time and the event-driven timer gate types into the shared clock package so other components can actually reuse them. The real-time one should work with any time source and expose a channel for timer notifications, an update method that takes a new target time and returns whether the update was accepted, a way to check whether it'll fire after some given time, and a clean stop that leaves no dangling goroutines. Oh and after stopping it should still be resumable, so calling update again brings it back to life.

The event-driven variant is for remote/standby cases where time advances via external signals instead of wall-clock time. It also needs a notification channel and an update method, but instead of stop it gets a method to advance its internal current time, which should return whether time actually moved forward and should fire the channel if the target's now been reached. Also once a timer fires it should only fire at most once until it's updated again.

Then update the history queue processor to use the new shared timer gate, renaming the channel-access method and the teardown method to line up with the new interface, and drop the goroutine leak exception from the tests since the new constructor won't start anything in the background.
