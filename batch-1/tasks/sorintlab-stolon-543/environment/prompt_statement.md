I'm trying to get a standby cluster to stay in sync with its primary through WAL archiving instead of a live streaming connection, and right now the cluster spec just won't let me. The way the standby settings are modeled in our cluster specification (see the standby config in `@pkg/apis/postgresql/v1/cluster_types.go` and the recovery/bootstrap wiring in `@pkg/apis/postgresql/v1/postgresql_type.go`) is a flat structure that only carries streaming replication connection info, so there's nowhere to put archive recovery settings for the ongoing replication phase after the initial restore is done.

What I want is to turn the standby config into a richer container that can optionally hold streaming replication connection settings and archive recovery settings independently, so I can specify either one or both depending on the setup. With archive recovery in place I should be able to run a standby that replays WAL segments from an archive to stay current with the primary rather than needing a direct streaming link. And it's got to be promotable, an archive-backed standby should be able to become an independent primary, with the database role flipping over to master once promotion happens.

Existing streaming-based standby clusters need to keep working too, just by nesting the current connection settings inside the new container, so the old behavior lives on under the new shape. Oh and the tests we already have for streaming standby clusters will need updating to use this new nested configuration structure. This matters because folks running geo-distributed or DR setups usually lean on WAL archiving between clusters, not direct streaming, so without archive-based recovery in the ongoing standby phase those configs just aren't possible today.
