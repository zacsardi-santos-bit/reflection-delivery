I'm digging into our device listing logic on the server and there's a couple things off with how we decide whether a pending device can be accepted when listing devices for a namespace. First one is in community self-hosted mode: when we list pending devices we're firing an extra DB call to count previously removed devices, but that number isn't used at all in community mode so it shouldn't happen there. That count only belongs in the cloud-hosted path.

The bigger issue is that when a namespace still has room to accept more devices, the returned devices don't get their "acceptable" flag set to true for non-accepted ones. So even when we're under the limit, operators can't tell which pending devices they're actually allowed to accept, the flag just stays false which is plain wrong, and it means they can't accept devices through the UI or API without workarounds.

I want the acceptability logic cleanly split by deployment mode since cloud, enterprise, and community each have different rules based on namespace capacity. Cloud mode needs to factor in how many devices were historically removed when it computes whether the limit's been reached, while enterprise and community each just check the current device count against the limit (but they work differently from each other, so keep them as distinct paths). All modes should derive the acceptability mode from the namespace's current device count versus its configured limit. When there's capacity, or when there's no limit at all (a limit of -1), mark non-accepted devices as eligible for acceptance; when the limit's been reached, don't mark them acceptable.

Oh and cloud mode should return an appropriate error when it fails to retrieve that removed-devices count so callers can handle the failure correctly. Can you update the device listing service and the underlying data layer to fix all this across the three deployment modes?
