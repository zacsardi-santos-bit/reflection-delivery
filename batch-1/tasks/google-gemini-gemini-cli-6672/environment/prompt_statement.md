I have a hook in the CLI UI that manages editor preference settings. Right now it reads the configuration data from a shared React context, which means every test that exercises this hook has to set up a context provider wrapper just to give it access to settings. This feels unnecessarily coupled — the hook should just accept the settings object as a direct parameter, so callers (and tests) can pass it in explicitly without relying on a global provider.

I'd like to refactor the editor settings hook to take the loaded settings as its first argument instead of pulling it from context. The hook should still support all its current behaviors: tracking whether the editor selection dialog is open, opening and closing that dialog, handling editor selection (including persisting the preference, validating whether the editor is available or allowed in the current environment, and clearing the preference), and properly surfacing errors if saving the preference fails.
