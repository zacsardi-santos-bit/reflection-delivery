I'm hacking on a Merkle Mountain Range in Rust and hit a cluster of issues I want fixed together. Biggest one first: the storage backend assumes every element it stores is a fixed, compile-time-known number of bytes. That's just not true for stuff like block headers which vary in size, so I need the backend constructor to take a parameter saying whether elements are fixed-size or variable-size, and that choice has to get threaded down into the underlying file storage layer so the right strategy gets picked at construction time.

While I was in there I found some correctness bugs too. The logical size of the tree (the total node count the full un-compacted tree would have) keeps drifting after I prune some entries and compact the files. It should stay rock constant no matter how many prune, compact, or sync operations I run, but right now the reported number wanders off from the truth.

Also rewinding is broken. After I rewind the tree back to a previously captured position, the Merkle root should match what it was at that historical point, but it doesn't. There's an assertion for this that was disabled in the tests because it was known to fail, and I want it passing.

Oh and one more, after a full lifecycle where I prune everything, compact the files, then rewind back to an empty state, the storage files aren't cleaned up right. The data file should end up with zero entries and the hash file with at most one, but they aren't getting set correctly.

So basically the storage layer needs reworking to handle both fixed and variable-size elements, and the pruning, compaction, and rewind logic needs fixing so all those invariants hold. This matters because a bad root hash after rewind breaks proof verification, a drifting size count breaks everything size-dependent, and the fixed-size limitation blocks using the backend with variable-length types. Fix it all so it's consistent.
