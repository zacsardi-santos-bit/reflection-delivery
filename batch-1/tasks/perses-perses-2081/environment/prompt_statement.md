I'm on the Perses monitoring side and I've hit a wall with service discovery. When the discovery module finds a datasource service (say via Kubernetes or some HTTP endpoint), there's no way to turn that into an actual usable global datasource without hardcoding each plugin's structure by hand, which is exactly what I don't want to do. I'd like a new utility package that bridges CUE schema definitions and real datasource plugin configs.

Here's the shape of it. First I want to read any datasource plugin's CUE schema and derive a structured tree of its fields out of it. That tree needs to capture the field names, their types (string, boolean, integer, float, or struct), and any concrete/fixed values that already appear directly in the schema. Optional fields should get excluded, they don't belong in the tree. Oh and the tree should be sortable by field name so processing stays deterministic.

Then, once I've got a tree built from a schema, I need a second piece that combines that tree with a discovered HTTP proxy config. The proxy (URL and related config) should get injected into the right spot in the spec, identified by a proxy kind marker found in the schema tree. The result should be a fully-formed plugin object with its kind set from the schema's concrete kind value, and the spec populated with the schema's field structure plus the injected proxy.

This needs to work for at least the Prometheus and Tempo datasource schemas, both of which follow the standard layout of a top-level kind and spec. The whole point is closing the gap so discovered endpoints can become registered datasources automatically instead of admins creating them by hand.
