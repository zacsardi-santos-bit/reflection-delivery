I'm fixing up the Prometheus config generator in our Kubernetes operator, specifically the scrape configs it emits for our three core database components. Two things are broken and they're related.

First, the address relabeling. Right now we pull the IP out of the pod's address field and glue it to a port annotation, which is fragile and breaks the moment a pod IP changes. I want to switch to DNS-based addressing built from the pod name and the cluster instance label so the target resolves through the component's peer service. The final address should follow the peer service naming convention, basically the pod name, the cluster name, the component type, and the port stitched together into a DNS-resolvable hostname.

Second, the scheme. The http-vs-https setting needs to actually show up in the rendered config and track whether cluster TLS is on. When TLS is enabled, two of the three components should get scraped over HTTPS using the cluster client cert files (CA, cert, and key paths) with strict certificate verification, no skipping. The third component doesn't support HTTPS scraping yet, so it stays on HTTP with cert verification skipped even while the cluster TLS flag is on. When TLS isn't enabled at all, every one of the three explicitly uses HTTP, don't leave the scheme implicit.

So every scrape job for the three components always carries an explicit scheme, and the rendering function has to handle both the TLS-enabled and TLS-disabled paths correctly. Oh and the model handed to that render function needs to carry the flag saying whether cluster TLS is active, otherwise it can't branch. The why here is real: without stable DNS targets Prometheus loses components after IP churn, and without the scheme wired up right an encrypted cluster gets scraped over the wrong protocol and you either get scrape failures or silent insecure connections.
