I'm hacking on the printf utility in our Rust coreutils reimplementation over in `@src/uu/printf` (the actual float formatting logic lives down in the number formatting code under `@src/uucore/src/features/format`) and I've hit two bugs with how non-finite floats (positive/negative infinity and NaN) get handled once you throw field width or padding flags into the format spec.

First one: when I use the space-sign flag, you know the one that asks positive values to get a leading space instead of a plus, that space just isn't applied to positive infinity or positive NaN. So if I format positive inf with a space-sign flag and a width of 5, I want it right-aligned in 5 chars with a leading space acting as the sign, but instead the output comes out one character short of the width and everything's misaligned.

Second one, and honestly the bigger deal: zero-padding gets wrongly applied to non-finite values. If I zero-pad positive infinity in a field of width 5 I'm getting "00inf" when POSIX and standard C printf say zero-padding should be suppressed for non-finite values and spaces used instead, so I want "  inf". Basically formatting any non-finite value with zero-padding should give the exact same result as space-padding. Negative non-finite values should still pick up a minus sign and get right-padded (well, space-padded) as normal.

This matters because numerical output pipelines lean on printf for column-aligned output and these specials break alignment. I want it matching POSIX and the C library.
