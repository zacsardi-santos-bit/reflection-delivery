I'm poking at the Tigera operator and the Dex auth service container is coming up short on security hardening in how we build its pod spec. Right now the container's security context does the non-root thing (runs as a non-root user and group, which is fine and should stay), but it never drops all Linux capabilities and it doesn't set a seccomp profile, so it fails the baseline pod security standard that a lot of clusters enforce. In hardened setups the API server just rejects the Dex pod, and in permissive ones it's running with way more privileges than it needs, extra attack surface for no reason.

What I want is for the Dex container's security config, wherever we assemble the container security context for the Dex deployment component, to also drop all capabilities (the full ALL drop on the capabilities list) and apply the runtime default seccomp profile at the process level, on top of keeping the existing non-root user/group enforcement intact. So basically the securityContext ends up with runAsNonRoot plus the user/group ids we already set, plus capabilities dropping everything, plus a seccomp profile type of RuntimeDefault. Just those three pieces together on the Dex container. That should get it passing baseline PSS and stop the rejections in the locked-down clusters.
