I'm working on KubeVirt live migration and hit a couple of gaps I need closed.

First, the migration eligibility check only inspects traditional persistent volume claim volumes and completely ignores data volume sources. So if a VMI uses a data volume backed by non-shared storage, we don't catch it during validation, and migration looks like it succeeds at first then fails later. I want the validation to treat data volume sources the same as PVCs, so a VMI on non-shared data volume storage gets rejected immediately with a clear error saying the disks aren't live-migratable, and the VMI's migratability status condition should reflect that it can't be migrated in that case.

Second, there's no way to override the hypervisor-level migration safety checks even when an admin knows the environment is safe. If a VM has a shared iSCSI filesystem volume (say ext4), libvirt refuses to migrate it because filesystem volumes can be unsafe for concurrent access, but there are legit cases where this should be allowed. I want a cluster-wide config flag that, when enabled, passes the appropriate "unsafe" flag through to the hypervisor during migration so it bypasses those safety checks.

Oh and the test utilities need updating for all this. The iSCSI PV/PVC creation helpers currently hardcode block mode, so they should take an explicit volume mode parameter (block or filesystem) instead. Same idea for the data volume creation helper, it should accept an explicit access mode parameter. Also I need a new helper that creates an iSCSI persistent volume without an associated PVC, and a new container disk type representing an empty disk formatted as a filesystem, which the iSCSI target pod setup needs to support. Wire these through wherever the existing helpers are referenced so the signatures stay consistent.
