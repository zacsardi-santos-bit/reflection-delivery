I'm poking at the intersection type simplification in our Python type checker and something's off with how string literal types combine with truthiness constraints. Say I've got a string literal type intersected with an "always truthy" constraint. The checker should know the empty string is the only falsy inhabitant of a string literal type, so the result ought to collapse down to that same string literal type but with the empty string dropped out. Right now that narrowing only fires in some cases and not others, which is annoying.

The two spots I keep hitting: first, member ordering matters when it shouldn't. If the string literal comes before or after the constraint I get different results, and I also see the same breakage when the constraint is expressed as the negated form, so "not always falsy" instead of "always truthy". For string literal values those two are equivalent, so intersecting with a negation of "always falsy" should give me the same empty-string-excluded result as the plain "always truthy" case does.

Second issue is when there's an "unknown" type sitting in the intersection too, alongside the string literal and a falsy constraint (or the negation of truthy). In that situation the simplification loses the unknown part. What I want back is an intersection of the unknown type with just the empty string literal, but instead the unknown gets clobbered and the result is wrong.

Can you fix the intersection simplification logic so all these orderings and constraint forms behave consistently? Whether the members appear in any order, whether the constraint is the direct or negated form, and whether or not an unknown type is also present, the narrowing on the string part should be correct (empty string excluded for truthy, just empty string for falsy) and any unknown component should be preserved.
