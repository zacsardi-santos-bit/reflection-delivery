I'm hitting a wall with scheduled task creation when the request comes from a browser session instead of a direct API token. Right now if a session-authenticated user does a POST to our task creation endpoint, it either fails outright or creates a task with no authorization token attached, which is useless because the task engine needs a token to run jobs unattended. Token-authenticated requests work fine, it's specifically the session path that's broken since we never generate a token in that case.

What I want is for the system to transparently provision a correctly scoped token during task creation. To do that properly I need a way to look at a compiled query spec and figure out exactly what permissions it'll need at runtime before anything runs. So for example a query that writes data to a named bucket should produce a write permission scoped to that specific bucket, and I mean resolved by name into its actual bucket ID and owning org ID, not just carrying the name around. Once I can compute required permissions from a query, task creation from a session should compute those perms, mint a new authorization token with them, and associate it with the task record.

Oh and that auto-created token has to be persisted so the task engine can retrieve it later by value through the authorization service. End state I'm after: a session-authenticated POST returns 201 with a valid task record, the underlying task has a real token attached, and I can look that token up by its value afterward. Without this, session or browser-based users are basically blocked from creating tasks at all, and there's no automated way to scope task credentials to exactly what the task needs for secure background execution.
