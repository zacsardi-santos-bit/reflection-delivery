I'm deep in the Linkerd destination controller working on the endpoints slice management for external workloads, those are workloads running outside the k8s cluster that get registered through a custom resource. Right now when an external workload gets updated there's no way to figure out which services are actually affected, so the controller would either do a wasteful full-namespace sweep or miss updates entirely, and I want to queue only the services that genuinely need reconciliation.

Two pieces of logic I need. First, something that compares the old and new version of an external workload and tells me whether the spec materially changed, meaning the IP addresses or the port definitions differ. Second, given the old and updated workload, a method that returns the minimal set of services needing reconciliation, and the answer depends on what changed: if nothing changed return an empty set, if only the network config (IPs/ports) changed return the services currently selecting the workload, if only the labels changed return the services that gained or lost a match but not the ones that matched both before and after (those are unaffected), and if both labels and config changed return the union of services matching either the old or new version.

Also the controller itself needs wiring, a constructor and a start method, so it can register event handlers against the external workload informer using the existing fake API infrastructure we lean on in tests. Oh and that fake API doesn't know about the external workload resource type yet, so it needs updating to support it, otherwise the controller can't register its handlers at all. The whole point here is efficiency: don't churn on reconciliation we don't need, but still guarantee every service whose endpoint slices went stale actually gets queued.
