I'm building out the GC path for collection version histories and I need a proper two-phase cleanup so we don't just yank data without recording intent first. Right now there's no safe way to earmark old versions before removing them, so GC can't durably say "these are going away" ahead of actually dropping them, and meanwhile the version history keeps accumulating stale entries forever. What I want is two new catalog-layer operations: one that marks a set of specific versions inside a collection's version history as pending deletion without removing anything (so the history file still has every version, just with the requested ones flagged), and a second that permanently drops those entries so the history ends up holding only the non-deleted versions. Both should take multiple collections in a single request and return a per-collection success indicator, and each collection's outcome has to be independent, so if a collection doesn't exist, or the versions I asked to mark aren't actually in the history, that's a failure for just that collection and not an error for the whole call. I also need a little helper to look up the current version tracking file name for a given collection since downstream callers need that after they mark or delete. On the infra side the object storage interface needs a method to delete a single version file by name, and the database layer needs a compare-and-swap that atomically updates the version file name for a collection, succeeding only when the current stored value matches what I pass in as expected. Oh and the underlying protocol definition needs new message types for both these operations plus new fields on the version history entries, specifically a pending-deletion flag and the version file name. Without all this the GC has no durable way to track what's scheduled for removal or to trim the history once cleanup completes, which is why the metadata just grows unbounded today.
