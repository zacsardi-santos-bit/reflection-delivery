I'm cleaning up the naming in our FRI implementation for this zero-knowledge proof library and it's bugging me. Right now we call the thing that holds the mathematical and security properties of the FRI protocol a "config", stuff like the blowup factor, number of queries, and proof-of-work bits, but these really aren't software config, they're cryptographic parameters that define the protocol itself. The word "config" is misleading and doesn't match how the broader crypto community talks about these values, so I want to rename the main FRI protocol type so it reflects that it holds parameters (params for short) instead of config (or cfg).

There's also a related generic strategy type that the PCS implementations use internally to abstract over how FRI folding gets done, and its current name makes it sound like a generic configuration type when actually it describes a folding strategy, so rename that trait to say folding strategy, and rename the concrete two-adic implementation of it to match the new convention too.

Oh and this ripples out everywhere: all the public helper functions that build instances of this type for testing and benchmarking need to move to the new name, and any struct fields across the codebase that hold this type should get renamed from the old cfg/config naming to the new params one. Since this touches the public API, callers referencing these names need to work against the new ones. Basically I want it self-documenting so anyone integrating the library reads "parameters" and immediately gets it, instead of tripping over "config".
