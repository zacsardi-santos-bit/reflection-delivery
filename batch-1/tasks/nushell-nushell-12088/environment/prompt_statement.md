I'm working on the nushell plugin system and want to clean up how plugin custom values are represented internally, because right now the custom value type keeps its type name, binary payload, and plugin source as directly accessible public fields and every place that creates one uses struct literal syntax. That's fragile, any time I want to add a field I have to touch every construction site, and there's no way to enforce invariants. So I'd like to refactor construction to go through a proper constructor function instead of named-field literals, and have the internal bits read through getter methods. The constructor should take the type name, the binary payload, a boolean flag for drop notification, and an optional source identifier, and then getters expose the type name, the payload, and the source, plus a new getter that says whether the plugin wants to be told when a value gets dropped.

That drop notification flag is the new capability I need, oh and here's the tricky part: when it's set the plugin should get notified (printing a message to stderr is fine) when the value goes out of scope, and it has to fire exactly once even if the value was cloned or shared around multiple times. This opens the door to plugins doing cleanup or lifecycle callbacks when their custom values get garbage collected.

Also I want these plugin custom values to behave like normal nushell data, so users can navigate into them with cell paths both by numeric index and by string key, sort collections of them, and concatenate them with the append operator. The relevant code lives in the plugin interface crate under `@crates/nu-plugin/src`, so update the type definition and all the construction sites accordingly.
