I'm adding support for self-managed signing keys to the signing configuration workflow in cosign (the go-based signing pipeline), because right now it only accepts ephemeral keys. If I try to sign a blob or create an attestation using a signing config with my own key, say something backed by a hardware security module, a KMS, or just a key file on disk, the tool bails out immediately and tells me only ephemeral keys are supported. I need that restriction lifted so teams that manage their own long-lived keys (stricter key governance, HSMs, KMS, whatever) can actually use the newer signing format without giving up their existing key infrastructure.

The main piece I want is a new adapter type in the internal key package that wraps any existing signer/verifier implementation so it plugs into the signing pipeline's keypair interface. It needs to support ECDSA, RSA, and ED25519 keys and return a clear descriptive error for anything else. It should expose the key algorithm string, a public key hint computed from a hash of the public key bytes, the hash algorithm, the PEM-encoded public key, and a sign method that takes data and returns both the signature and the digest. Oh and when the underlying signer errors out during signing, pass that error through unchanged, don't wrap it. But for errors retrieving the public key, wrap them with context about which operation failed. That way I can sign blobs and create attestations through the signing configuration workflow with my own keys instead of being forced into ephemeral ones.
