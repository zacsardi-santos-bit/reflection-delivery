I'm building out an OAuth library and I keep hitting a wall with public clients. Right now everything gets treated like a confidential client that must present a client secret, which totally breaks mobile apps and single-page/browser apps that can't safely store a secret. Per the OAuth 2.0 spec there are two client types, confidential (server-side apps that can keep a secret) and public (native/SPA apps that can't), and I want the library to actually respect that.

So I want to add an explicit confidentiality flag on OAuth applications marking each one as confidential or public, and the auth logic across the library should adapt to it. A public app should be able to get tokens presenting just its client identifier with no secret required, but here's the catch, if a public client does send a secret and it's wrong, reject the request anyway (missing secret is fine, wrong secret isn't). Confidential apps keep needing the full credentials, so identifier plus secret, and a confidential client that omits the secret should have its token request fail.

Same distinction on revocation. Tokens issued to public apps should be revocable without any client authentication, while tokens for confidential apps only get revoked when the correct client is authenticated. Oh and if the wrong client tries to revoke a confidential app's token, the endpoint should still return a success response (the spec wants that) but must not actually revoke the token.

Couple more things. The application model should validate that this new flag is explicitly set, so leaving it undefined (neither true nor false) makes the app invalid. The database needs a matching column defaulting to confidential so existing deployments don't break. And the client credential handling needs updating so credentials with a valid client identifier aren't treated as "blank" even when there's no secret present.
