I'm working on an OAuth library and need to add proper support for distinguishing between confidential and public OAuth client applications. Right now, the library treats every application as if it needs a client secret for authentication, which breaks public clients like mobile apps or browser-based apps that can't safely store a secret.

I'd like to add a flag to OAuth applications that explicitly marks them as either confidential or public. The authentication logic throughout the library should then adapt: public applications should be able to get tokens by presenting only their client identifier, with no secret required. However, if a public client does present a secret and it's wrong, the request should still be rejected. Confidential applications must continue to require a full set of credentials — if a confidential client omits the secret, the token request should fail.

The same distinction should apply to token revocation: tokens issued to public applications should be revocable without any client authentication, while tokens issued to confidential applications should only be revoked when the correct client is authenticated. If the wrong client tries to revoke a confidential app's token, the endpoint should still return a success response (as required by the spec) but should not actually revoke the token.

The application model should also validate that this new flag is explicitly set — leaving it undefined should make the application invalid. The database needs a corresponding column, defaulting to treating existing apps as confidential to avoid breaking existing deployments. Finally, the client credential handling should be updated so that credentials with a valid client identifier are not considered "blank" even when no secret is present.
