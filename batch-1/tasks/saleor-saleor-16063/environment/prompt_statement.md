I'm chasing down a cluster of payment flow bugs in our Saleor checkout backend and want to knock them out together.

First one is about order events. When an order gets marked fully paid after a payment capture, the order event we record has nothing about which gateway actually processed it, which makes tracing payment origin in the event log a pain. I want that "order fully paid" event to carry the payment gateway identifier in its metadata whenever a gateway is known, so operators and integrations can tell which provider was used from order history.

Second, there's a routing bug in checkout completion. When a checkout has both modern transaction-based payment items and an active legacy payment, the completion logic wrongly picks the transaction flow instead of the legacy one, and that can blow up checkout when the customer meant to pay the legacy way. The selection should prefer the legacy payment flow whenever an active payment exists on the checkout, and only fall back to the transaction flow when there's no active payment.

Third, if a checkout is already being completed (locked) you can still call the transaction initialize or transaction process mutations on it, which invites race conditions. Instead those should detect the locked state and immediately reject with a clear error saying checkout completion is already in progress, and not proceed to process anything.

Last one, related. When a transaction gets initialized or processed on a checkout that still has active legacy payments, those payments stay active, so the checkout could get completed through two different payment mechanisms at once. I want transaction initialization and processing to atomically deactivate any pre-existing active legacy payments as part of the same operation. Together these prevent double-processing, clean up the audit trail, and kill the completion race conditions.
