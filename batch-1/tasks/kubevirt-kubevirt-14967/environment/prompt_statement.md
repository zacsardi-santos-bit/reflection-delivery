I'm cleaning up architecture support boundaries for live update in KubeVirt and the current code is wrong about arm64. Memory hotplug is really only for x86_64 VMs, not arm64, but our validation logic treats arm64 as supported and the error message for unsupported architectures says memory hotplug is available for both x86_64 and arm64. That needs to just say x86_64. So the fix is to stop treating arm64 as a valid memory hotplug arch, correct the error string, and make sure we don't configure maximum guest memory for arm64 or s390x VMs at all (memory hotplug stays x86_64 only).

CPU hotplug has a related bug: we're applying the maximum CPU socket config to arm64 where it isn't supported. CPU hotplug should only get configured for x86_64 and s390x, and never for arm64, so please make the max sockets logic skip arm64.

Also the test suite needs work. Right now some tests lean on runtime architecture skip guards that silently bypass on unsupported arches instead of explicitly parameterizing per architecture. I want those replaced with proper per-arch test entries labeled with architecture-requirement decorators. Concretely, add three new decorators for requiring x86_64, s390x, and arm64 respectively, and rip out the deprecated skip-on-s390x helper function. The tests covering unsupported machine types and panic devices should be parameterized with the arch-specific machine type names and device models, each decorated so it only runs on the relevant architecture.

Why it matters: without this arm64 VMs can end up with memory or CPU hotplug settings that aren't actually supported there, plus the validation message is straight up lying about arm64. And swapping the skip guards for explicit arch labels means future regressions on any arch get caught instead of quietly skipped.
