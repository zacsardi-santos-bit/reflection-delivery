I'm working with xarray and often create datasets with regularly-spaced coordinate axes — things like uniform spatial grids or evenly-spaced time steps. Right now, xarray has to materialize the entire coordinate array in memory even though the whole thing can be described by just three numbers: where it starts, where it ends, and the spacing between values. I'd love to have a built-in index type that stores only those three parameters and generates values lazily, the way standard range-based array constructors work.

The new index type should support both a step-based constructor (start, stop, step) and a count-based constructor (start, stop, number of points, with or without including the endpoint). It should expose the start, stop, and step as readable attributes. When I slice the dataset by integer position using a slice, it should return a new dataset still backed by the range index with updated bounds. When I select by label, it should support nearest-neighbor lookups for scalars, arrays, and slice objects. Array-based indexing should gracefully fall back to a standard in-memory index. Renaming either the coordinate or the dimension should preserve the range index type. I should also be able to convert it to a regular in-memory index when needed for compatibility.

Separately, I noticed that the approximate-equality comparison utility doesn't work when I pass standalone coordinate collection objects to it — it only seems to handle datasets, data arrays, and variables. That should be fixed too.

Finally, there's a bug where datasets using coordinate transforms lose their identity after a rename round-trip (rename coordinates to temporary names, then rename them back). After the round-trip the dataset should be identical to the original.
