I'm hitting a wall with the `#[rpc]` derive macro that generates both a server and client from one trait definition. My trait mixes regular RPC calls (the ones returning a `Result`) with notifications, which are those fire-and-forget methods that return nothing (just unit) and don't expect any response from the server. The regular calls work fine, but the generated client code for the notification methods is straight up broken, it's just `unimplemented!()` under the hood so calling a notification method on the generated client panics at runtime instead of actually sending anything over the wire.

What I want is for the derive macro to emit a real working client method whenever a trait method is marked as a notification by returning unit. That generated method should send the notification over the wire and return a future that resolves once the notification's been dispatched, so I can await it or chain on it just like a regular call. And when a notification goes out from a generated client, the server's notification handler needs to actually get invoked with the right parameters.

Oh and the underlying client transport also needs a way to do this, so both `TypedClient` and `RawClient` should grow a `notify` method that dispatches a fire-and-forget message to the server without waiting for a response. Right now this whole thing makes the feature unusable for any trait with notification methods, which breaks a core piece of the JSON-RPC spec, so please wire up proper notification support in both the macro's client code generation and the client transport layer.
