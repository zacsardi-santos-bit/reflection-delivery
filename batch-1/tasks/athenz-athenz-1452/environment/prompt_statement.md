I'm cleaning up the proxy access authorization in our token auth flow and hit two things I want fixed together. Right now when someone declares which principals are allowed for proxy access inside an authorization detail, they name exactly one principal as a plain string, which is too limiting. I want that changed to a list of principals so you can name one or more allowed proxies in a single entry, and the token issuance endpoint needs to accept requests using that new list format.

The bigger gap is on validation. When someone presents a certificate alongside an access token that carries proxy access authorization details, we don't actually check whether that cert's identity is among the allowed principals, so the proxy claim isn't bound to the presenting certificate at all, which is a real security hole. I want cert-bound token verification to pull the certificate's SPIFFE identity URI and compare it against the allowed principals list, and if it matches any entry the token validates fine. If the authorization details are missing, can't be parsed, use the wrong format for the principals list (like the old single-string shape), or the cert's identity just isn't in the list, verification should fail with a confirmation error.

Oh and to do that comparison I need a small utility that extracts the single SPIFFE identity URI from an X.509 cert. It should return nothing when there are no SPIFFE URIs on the cert, and also return nothing when there's more than one SPIFFE URI, since the identity is ambiguous in that case and I don't want to guess. Only the unambiguous single-URI case should give back a value.

Net effect I'm after: the list format makes it flexible enough to declare multiple valid proxy principals per authorization detail, and the verification step cryptographically ties the proxy access claim to the certificate actually used to present the token.
