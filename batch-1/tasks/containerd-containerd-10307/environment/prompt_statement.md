I'm hacking on the containerd runtime and hit a gap: when a container runs inside a Linux user namespace, every UID and GID inside the container gets translated to some other UID/GID on the host through one or more ID mapping ranges, and we've got no shared helper to do that container-to-host translation. Right now any code that needs the host-side identity of a containerized process, like when we remap file ownership on a container's snapshot, either re-implements the mapping inline or only handles the simple single-range case, which is fragile.

I want a new internal package with a utility that takes a container-side UID and GID pair plus separate lists of UID mapping ranges and GID mapping ranges, and returns the matching host-side UID and GID. It's gotta handle multiple non-overlapping ranges correctly, not just one. If the container UID or GID doesn't fall inside any provided range, return an error instead of silently spitting out a wrong value.

Also, be careful with the arithmetic: adding the offset to the base host ID can overflow a 32-bit unsigned int, so if that would wrap around, catch it and return an error. And treat the max 32-bit unsigned value as a reserved sentinel, so if a computed host ID lands on that, reject it with an error too. This makes the runtime safer near the integer boundary and lets us actually support more complex user namespace setups.
