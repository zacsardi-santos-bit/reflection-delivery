We've got a nasty availability bug when partition reassignments run against older Kafka brokers. Here's what I'm seeing: while a reassignment is underway, an older broker's metadata responses carry leader epoch info that isn't reliably maintained, the broker doesn't propagate updated epochs during the reassignment, so my client caches those stale epochs and then forwards them in Fetch, ListOffsets, and similar requests, and the broker rejects them as having a fenced leader epoch. That blocks reads and writes for the entire duration of the reassignment, which is bad since reassignments are routine ops work.

I want to fix this two ways. First, I need the metadata response itself to signal whether the leader epochs it contains can actually be trusted. When a response comes in through the legacy binary wire-format path that predates reliable epoch propagation, don't trust the epochs, store a sentinel "no epoch" value instead of whatever the response claims. When it arrives via a sufficiently modern wire-format version, or gets constructed from the modern typed data objects, the epochs are reliable and should be cached as-is. Right now the client can't distinguish trustworthy from untrustworthy responses so it just caches whatever, including bad values.

Second, when a metadata update shows up carrying a lower epoch than what's already cached for a partition, that's stale, ignore it. Leave the existing cached partition info alone (ISR, epoch, replicas all unchanged), and keep the cached last-seen epoch at the higher value rather than overwriting it downward.

Get both of these right and consumers and producers should keep working normally straight through a partition reassignment instead of getting wedged on fenced-epoch errors.
