I'm hitting a nasty data integrity bug in Realm Core around deleting objects whose links live inside mixed-type fields or collections. When I delete a source object, whether directly or through a batch delete, the backlink counts on the destination objects it pointed at don't get decremented down to zero, they just stay stale. And it's worse with recursive deletion: if an object points to another object through a mixed-type column, that transitively linked object doesn't get deleted even though it has no other references and should go away.

This shows up across all the container shapes, a plain mixed-type column, a list of mixed values, a dictionary of mixed values, and the nested stuff too like lists-of-lists or dictionaries-of-dictionaries. It also seems to fall apart with big datasets, more than a thousand objects, probably because of how the internal cluster tree rebalances during random-order deletions and leaf nodes collapse or merge.

What I want: when objects get deleted and they (or their embedded children) hold links via mixed-type columns or mixed collections, the backlinks on referenced objects need to update accurately to zero. Recursive deletion should follow links embedded in mixed columns, so a transitively linked object with no remaining references gets deleted too. Oh and if that linked object still has other references (backlink count greater than 1) it should stay valid but have its count decremented correctly. All of this needs to hold even when the cluster is larger than the internal B+ tree node size. After recursively deleting all the source objects, both the source and destination tables should end up completely empty. Storing links in mixed columns is a totally valid, common pattern and right now it's silently corrupting the object graph, so I need the lifecycle managed right across every supported link storage format.
