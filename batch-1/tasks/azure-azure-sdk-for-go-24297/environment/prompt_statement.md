I'm working on the Azure Service Bus Go SDK and right now it's basically a black box for distributed tracing. When someone sends, receives, or settles messages there are no spans and no trace context flowing through, so you can't correlate Service Bus activity with the rest of an app's telemetry or see how long operations take. I want to add a new internal tracing package (somewhere under the sdk's internal tree for Service Bus) that handles all this.

Couple things it needs to do. First, propagate trace context through the message application properties so headers injected on the sender side can be extracted again on the receiver side, and the carrier that wraps a message for propagation has to handle a nil message without panicking. Second, pull out useful message metadata like the message identifier, conversation identifier, delivery count, and enqueue time and expose those as span attributes.

Third, classify each operation into the right span kind following standard messaging observability conventions. Creating a message or sending a single message should be a producer span, while batch sends, receives, settlement ops, and session-related operations are client spans, and anything that doesn't fit a known category falls back to internal.

Oh and starting a span should just be a no-op returning the original context unchanged when there's no tracer configured or no operation name given. When a destination (queue or topic name) is available the span name should combine the operation name and that destination.
