I'm building out New Relic agent instrumentation for the Azure Functions serverless platform and I need to write the instrumentation module basically from scratch. Right now when Node.js apps run as Azure Functions and register HTTP handlers through the official SDK, the agent is blind, no transactions, no attributes, nothing lands in New Relic. This is a real gap since Azure serverless is everywhere now and people need to see latency, cold starts, and downstream calls.

What I want is a new instrumentation module that wraps the handler registration methods the Azure Functions SDK exposes, so whenever a dev registers an HTTP handler (generic `http`, or the shortcuts `get`, `post`, `put`, `patch`, `delete`) we transparently wrap it to create a web transaction named after the function, record the FaaS attributes (invocation ID, function name, trigger type derived from the trigger config, plus a fully-qualified Azure cloud resource identifier built from the deployment env vars), and finalize the transaction when the handler finishes. No manual code changes from the user.

Some details to get right: the very first invocation after deploy should be flagged as a cold start but only that first one, incoming distributed tracing headers need to be read and linked to the parent trace, queue time should be derived from request headers when they're there, and grab the port off the request URL too. Oh and if someone passes a handler function directly instead of wrapping it in an options object, that should still work.

Also, if the required deployment env vars aren't present or aren't in the expected format when the instrumentation initializes, don't throw and don't silently carry on, instead log a warning with structured diagnostics saying which vars we expected and what values we actually found.

Separately I need the agent's logging utility to support embedding a structured data object under a named key when writing a log entry, so this kind of diagnostic data can ride along with a message in a structured way. That logging change is what makes the startup warning above actually useful.
