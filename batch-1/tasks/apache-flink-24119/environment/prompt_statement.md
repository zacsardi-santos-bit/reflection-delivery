I'm working on adding observability to Flink's checkpoint restoration process. Right now, when a task recovers from a checkpoint, we have no way to know how much data was restored or where it came from — whether it was in memory, on local disk, or in remote storage. I'd like each kind of state handle to be able to report its own size categorized by storage location, and then have that information aggregated and surfaced as task initialization metrics so operators can see a per-location breakdown after recovery completes.

To support this, I also need a utility that can recursively compute the total byte size of all files within a directory, returning zero when the directory is empty. Directory-based state handles should use this to pre-compute their size at creation time.

The component that coordinates backend restoration should also be updated to carry along a size-collection context so that sizes are tracked throughout the full restoration flow. The resulting metrics should use a consistent naming scheme based on storage location names, so tooling can easily aggregate and display the breakdown. The constructor for one of the incremental snapshot strategy classes also needs to be simplified by removing a parameter that is no longer needed.
