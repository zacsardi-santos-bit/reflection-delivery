I'm adding some observability to Flink's checkpoint restoration because right now when a task recovers from a checkpoint we've got basically zero visibility into how much state got restored or where it came from, whether that was in-memory buffers, local disk files, or remote/cloud storage. That makes diagnosing slow recovery or comparing storage tier costs really painful, so I want each kind of state handle to categorize and report its own size by storage location, and I'm thinking the locations are local memory, local disk, remote/cloud, and unknown for anything that doesn't fit.

To make this work I need a utility that recursively walks a directory and sums up the total byte size of every file inside it, and it should return zero when the directory is empty. The directory-based state handles should call into that at creation time so their size is pre-computed up front rather than lazily.

Then the component that coordinates restoring backends needs to carry along a size-collection context through the whole restoration flow so sizes get tracked end to end. Once a task finishes restoring, the task initialization metrics should surface a per-location breakdown, and all those per-location size entries should share a consistent metric name prefix based on the storage location names so tooling can aggregate and display them easily. Oh and while I'm in there, one of the incremental snapshot strategy class constructors has a parameter that's no longer needed, so drop it and simplify the signature.
