I'm doing some cleanup on the kinflate command and hit two related gaps I want you to close.

First one's about configmap management in manifests. Right now the only move I've got is appending a new configmap entry, which means if I add the same name twice I get duplicates, ugh. I want a proper find-or-create: given a configmap name, look through the manifest's existing entries and hand back the one that matches, otherwise build a fresh one and append it, so I never end up with dupes. On top of that I need a merge helper that folds data sources into an existing configmap instead of clobbering what's already there. Literal key-value sources and file sources should accumulate across repeated calls (append, don't overwrite). Env file sources are the exception, each configmap gets exactly one, so if there's already an env file source set and something tries to set another, that should come back as an error rather than silently replacing it.

Second thing, the manifest read/write code currently does direct filesystem calls which makes it a pain to unit test. I want that pulled out into a reusable loader that takes a pluggable filesystem, so tests can wire in an in-memory fs and never touch real disk. A couple behaviors matter here: writing to an empty filename should fail with an error, and anything I write through the loader should be fully recoverable when I read it back, data integrity intact (round-trip should match). The relevant bits live under the kinflate code paths (see `@pkg/kinflate` and wherever the manifest loader and configmap helpers land), so keep the loader and the configmap helpers as separate reusable pieces.

Why bother: this makes the configmap commands safer and more composable, and it makes the manifest I/O layer testable without a real filesystem, which is foundational for building and testing kinflate workflows reliably.
