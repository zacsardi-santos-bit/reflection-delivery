I've been working on improving the checksum verification tools and have found several issues that need to be fixed to match standard GNU coreutils behavior.

First, when a file listed in a checksum file doesn't exist, the error message is currently being written to standard output alongside the verification results — it should go to standard error instead. This makes it hard to script against the output cleanly.

Second, the asterisk prefix used in checksum files to indicate binary mode isn't being handled correctly depending on the separator. When there's a single space between the hash and the filename, a leading asterisk should be stripped (it marks binary mode, not part of the filename). When there are two spaces (the standard format), a leading asterisk should be treated as a literal part of the filename. Right now these two cases aren't distinguished.

Third, checksum files that use only a single space as the separator between the hash and the filename should be accepted — this format appears in many real-world checksum files and is supported by GNU coreutils.

When a checksum file references a directory instead of a regular file, the tool should fail and report a useful error message to standard error. Similarly, when a tool tries to verify a checksum file generated by a completely different algorithm, it should say no properly formatted checksum lines were found — not vaguely warn about improperly formatted lines.

The status mode should produce no output at all when all checks pass. The quiet mode should suppress output for successful checks but still report failures. And when an entry in a checksum file is incomplete or truncated, the tool should report that no properly formatted checksum lines were found.
