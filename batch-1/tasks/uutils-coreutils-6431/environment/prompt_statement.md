I've been cleaning up our checksum verification tools to match GNU coreutils and hit a bunch of spots where we drift. The big one is error routing: when a file listed in a checksum file doesn't exist, we currently print the "file not found" message to stdout mixed in with the verification results, which makes it a pain to script against, so that should go to stderr instead.

There's also an asterisk handling bug. Checksum files use a leading `*` before the filename to mark binary mode, but how we treat it depends on the separator. With a single space between the hash and the filename, a leading asterisk is the binary-mode indicator and should get stripped off the filename. With the standard two-space separator, that asterisk is a literal part of the filename and should stay. Right now we don't distinguish those two.

Related, we should actually accept the single-space separator format at all, since tons of real-world checksum files use one space instead of two and coreutils supports it.

A few more edge cases: if a checksum file references a directory instead of a regular file, we should fail with a useful message on stderr rather than silently doing something weird. And when say md5sum tries to verify a file that's really SHA1 checksums (wrong algorithm), it shouldn't vaguely complain about improperly formatted lines, it should say no properly formatted checksum lines were found. Same message when an entry is incomplete or truncated, oh and partial writes count here too.

Then the output modes. Status mode should produce zero output when all checks pass. Quiet mode should suppress output for the successful checks but still report the failures. The relevant logic lives around the checksum handling in the coreutils crate, so poke at wherever the cksum/md5sum style verification and line parsing happens.
