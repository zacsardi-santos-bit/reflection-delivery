I'm hitting a concurrency bug with the ORM's lazy connection init. The way it's supposed to work is the physical database connection gets deferred until the first query runs, that's the documented behavior. And for plain non-transactional queries this works great, if I fire off a ton of concurrent simple queries right after configuring the ORM (before any connection actually exists) they serialize the connection setup so only one task does the init, everyone else waits, and then they all proceed independently and succeed.

Problem is transactions don't behave the same. When I start a big batch of concurrent transactions immediately after init, before anything has warmed up the connection, they step on each other during that initial setup phase. Looks like a race where multiple tasks each try to establish the physical connection at the same time, and some of them fail with errors.

What I want is for concurrent transactions to be exactly as safe as concurrent simple queries in this scenario. So running many concurrent transactions on a freshly initialized but not-yet-connected database should all succeed, same as the simple query case already does, and only one physical connection init should actually happen even when a whole pile of transactions kick off simultaneously. My real use case is startup and test setups where I dispatch parallel background transactions right away without warming up first, and I need that to be reliable and not intermittently fail depending on timing.
