I'm running into a concurrency issue with the ORM's lazy database connection initialization. When I initialize the ORM and then immediately fire off many concurrent transactions before any query has been executed, some of them fail. The ORM is supposed to lazily establish the physical database connection on the first query, which works fine for regular (non-transactional) concurrent queries — those serialize the initialization properly and all succeed. But when I do the same thing with concurrent transactions, they seem to step on each other during the initial connection setup and I get errors.

My use case is firing off a large number of concurrent transactions right after ORM initialization, without warming up the connection first. I'd expect this to work the same way concurrent simple queries do — the first task to need the connection establishes it, and all the others wait and then reuse it. Is there a known issue with how concurrent transactions handle an uninitialized connection, and how can it be fixed so that concurrent transactions are as safe as concurrent simple queries in this scenario?
