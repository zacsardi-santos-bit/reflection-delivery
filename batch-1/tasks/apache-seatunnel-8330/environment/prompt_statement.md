I'm hitting a wall with SeaTunnel's Debezium JSON format support where change data capture events from a bunch of databases just aren't deserializing right. When I pull CDC events from MySQL, SQL Server, Oracle, and PostgreSQL through Debezium, tons of field values come out wrong or fail to parse entirely, and it's basically silent data corruption or runtime blowups mid-pipeline.

The root issue is that each database connector encodes the same logical types differently in its Debezium JSON output and the current deserializer doesn't cover all the variations. Date and time values might show up as integer epoch counts in days, milliseconds, microseconds, or nanoseconds, or as ISO 8601 timestamp strings with a timezone suffix, and the exact unit depends on both the connector and the specific column type. Oracle's the nastiest one, its NUMBER and FLOAT decimal/numeric types come through as a structured object holding a base64-encoded binary value instead of a plain JSON number. Binary and bit fields are also base64-encoded strings that need decoding and then type-appropriate conversion.

I want the deserializer (this lives in the debezium-json format handling under `@seatunnel-formats/seatunnel-format-json`) to correctly handle all the major type encodings for each of these four databases. For MySQL that means all the integer, floating-point, decimal, string, binary, bit, date/time, and timestamp fields deserialize properly, including the epoch-based date/time values and the ISO timestamp strings. For SQL Server, date/time values encoded in nanoseconds, milliseconds, and ISO strings (including datetimeoffset) all need to convert to SeaTunnel temporal types with the timezone info stripped off. For Oracle, those base64-structured NUMBER and FLOAT columns must convert to decimal values, and the date and timestamp columns encoded in various numeric and string formats need to yield correct local date-time values. For PostgreSQL, every temporal encoding variant (microseconds, milliseconds, ISO strings, and time-with-timezone strings) has to produce the expected local time and local date-time results. Across all of them, date and time fields should map into SeaTunnel's local date, local time, and local date-time types (stripping timezone from ISO strings), and decimal, binary, boolean, and numeric fields convert according to their source encoding. Oh and the timezone stripping matters, ISO strings with offsets shouldn't leak that offset into the final value.
