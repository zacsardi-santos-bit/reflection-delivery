I'm dealing with Certificate Transparency pre-certificates and the function that builds to-be-signed (TBS) certificate data from a pre-cert's raw TBS bytes before it gets embedded in an SCT. Right now it's way too strict. It bails with an error whenever the pre-certificate or the pre-issuer cert is missing an Authority Key Identifier (AKI) extension, but that's actually a perfectly valid situation and it shouldn't be rejected.

What I want is for the function to handle every combination of AKI presence and absence cleanly. If both the pre-cert and the pre-issuer have an AKI, the result should use the pre-issuer's AKI value. If the pre-cert has an AKI but the pre-issuer doesn't, strip the AKI from the result. If the pre-cert has no AKI but the pre-issuer does, add the AKI using the pre-issuer's key identifier. And if neither has one, the result just has no AKI at all.

When a pre-issuer is provided and it's a valid CT pre-issuer (meaning it carries the required Certificate Transparency extended key usage marking), replace the issuer field with the pre-issuer's own issuer and point the AKI at the real issuer's key. Oh and if a pre-issuer is passed in but it's missing that CT extended key usage, still return an error like before. Also the no-pre-issuer case should keep working, just return the TBS with the original AKI unchanged.

Couple of invariants that always hold: the CT poison extension must get stripped from the result, and the returned bytes have to be valid, fully parseable TBS data with no trailing content left over. The reason this matters is certs issued through a CT pre-issuer intermediate may or may not include AKI extensions, and the tooling needs to cope with all of it instead of unnecessarily rejecting valid pre-certificate submissions.
