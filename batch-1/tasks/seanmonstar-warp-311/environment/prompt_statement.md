I'm messing with warp's rejection system and the way you define custom rejection types is way more work than it should be. Right now if I want my own rejection I have to implement a bunch of HTTP-specific trait methods, stuff for figuring out status codes and generating actual HTTP responses, and honestly my domain error types shouldn't have to know anything about HTTP just to exist as a rejection. That coupling feels wrong, the whole point of a custom error is it's custom, the HTTP translation should happen later when I'm actually recovering from it, not at the point where I define the type.

So what I want is to redesign this so a custom rejection type only needs to derive debug output and implement some lightweight marker trait that has no required methods on it. Like I should be able to write a minimal struct or enum and then a one-line impl of that marker trait and be done. The function that builds a custom rejection should just take any type that implements that marker trait directly, no wrapping it in a boxed error object, no implementing the std error trait, none of that.

Oh and the other big thing, I want a clean way to pull the original typed value back out. So on the rejection value itself there should be a type-safe lookup method where I query it with a type and it hands me back a reference to the stored custom error if that's what's actually in there (and nothing if it isn't). That makes recovery handlers so much nicer since I can check what kind of rejection happened and get a typed reference to deal with it properly, deciding right there how to turn it into a response. The relevant code lives around `@src/reject.rs`.
