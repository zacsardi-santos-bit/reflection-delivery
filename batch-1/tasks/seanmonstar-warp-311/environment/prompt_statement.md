I'm working with a Rust web framework's rejection system and I'd like to simplify how custom rejection types are defined. Right now, to create a custom rejection, my types need to implement several HTTP-related methods — for status codes and response generation — which feels like too much coupling. My custom error types shouldn't need to know about HTTP concerns just to exist as rejections.

I'd like to redesign the rejection API so that a custom type only needs to derive debug output and implement a simple marker trait with no required methods. The function that creates a custom rejection should accept any such type directly. I also want a convenient way to inspect a rejection and retrieve the original typed value — essentially a type-safe lookup method on the rejection value that returns a reference to the stored custom error when you query it with the right type. This would make recovery handlers much cleaner since they can check what kind of rejection occurred and get a typed reference to handle it appropriately.
