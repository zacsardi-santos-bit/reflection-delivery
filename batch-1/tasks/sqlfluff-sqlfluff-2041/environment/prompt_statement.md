I'm hitting a wall using SQLFluff to lint our Postgres codebase because the parser chokes on anything involving materialized views. Any file that creates, alters, drops, or refreshes one throws parse errors, and since materialized views are all over our database architecture that basically means we can't lint a huge chunk of our SQL. I want the Postgres dialect to actually parse these statements with a correct parse tree.

For creating a materialized view, it should handle the variants with and without the `IF NOT EXISTS` guard, with optional storage options, a parenthesized or bare query body, and with or without the trailing data-population clause. Altering one has a ton of forms, so cover column attribute changes, storage settings, clustering, tablespace reassignment, ownership changes, dependency declarations, renames, schema moves, and the bulk "all in tablespace" reassignment form too. Dropping should let me drop multiple views in one statement, with or without `IF EXISTS`, and with cascade or restrict. Refreshing needs the `CONCURRENTLY` form plus the optional data clause.

Oh and one more thing, that data-population clause (`WITH DATA` / `WITH NO DATA`) that already shows up in the create-table-as-query statements is currently parsed as loose keywords instead of a proper named clause. I'd like it recognized as its own distinct parse element, and that same grouping should apply both to the existing table-creation-from-query statement and to all the new materialized view statements that support it. The dialect work lives in `@src/sqlfluff/dialects/dialect_postgres.py`. Also there's a typo in one of the existing test fixture filenames that should get fixed while we're in here.
