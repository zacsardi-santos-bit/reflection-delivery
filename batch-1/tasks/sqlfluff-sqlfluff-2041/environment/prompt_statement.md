I'm using SQLFluff to lint our PostgreSQL codebase, but the parser fails on any file that contains materialized view statements. When we try to create, alter, drop, or refresh a materialized view, SQLFluff doesn't recognize the syntax and reports parse errors. Since materialized views are central to our database architecture, this effectively blocks us from using the linter on a large portion of our SQL.

I'd like the Postgres dialect to fully support parsing these statements — covering all the common variants like creating a view with or without the "if not exists" guard, with optional storage configuration, and with or without the data-population clause at the end. Altering a view also has many forms (changing column attributes, storage, clustering, tablespace, ownership, dependencies, renaming, and the bulk tablespace-reassignment form). Dropping a view should support dropping multiple views at once with optional cascade behavior. Refreshing a view should support the concurrent option and the data clause.

I also noticed that the data-population clause ("with data" / "with no data") that already appears in table-creation-from-query statements is parsed as loose keywords rather than as a proper named clause. It would be cleaner to have it recognized as a distinct parse element, and that same grouping should apply to all the new materialized view statements that support it as well.
