I'm working on a change data capture pipeline and DDL events are getting dropped too early. Stuff like adding a column to a table that's within replication scope is being silently skipped by the DDL puller, even though those events should flow downstream for proper evaluation. The root cause is that we've merged two different filtering ideas into one check, so the puller ends up making skip decisions based on transaction start timestamps and event-type rules that really should only be evaluated higher up where the full event context exists.

I want to split these into two concepts. There's a coarse "discard" check, which means the DDL is completely out of scope, either the wrong DDL type (not in the allowed list) or the table/schema name doesn't match the configured replication rules. A discarded DDL isn't tracked in internal schema storage and isn't sent downstream. This check only needs the DDL type plus the table/schema name and should return a simple boolean with no error, and it belongs at the puller level.

Then there's the finer "ignore" check: the DDL is in scope, but the user configured it to be excluded from downstream delivery based on transaction timestamps, SQL query patterns, or event type filters. An ignored DDL still gets tracked in schema storage but doesn't go downstream. This one needs the complete DDL event object (timestamp, query text, event type) and should return a boolean and an error, and it belongs at the manager level. So the DDL manager needs to receive the filter so it can apply this ignore check when deciding whether to forward events, and the puller should stop using the job's start timestamp as a skip criterion since that responsibility moves up.

The reason this matters is that right now tracked tables can lose their DDL events before filters are properly evaluated, which breaks replication. Also, when specific DDL event types like table truncation or schema alteration get filtered out by event rules, the affected tables should still replicate correctly downstream, so data insertions and other operations keep syncing. Oh and it'd be good to expand integration coverage to verify that event-type filtering (truncate, alter schema) works right end to end.
