I'm working on the webhook configuration logic in our Kubernetes policy engine and I've noticed a bug in how admission operation types are merged when multiple rules or policies target the same resource kind. If I have two rules for the same resource — one that explicitly specifies a single operation like "create", and another that doesn't specify any operations (which should mean it applies to all operations) — the resulting webhook configuration should cover all the operations that the broadest rule applies to. But instead, it seems like the operations aren't being combined correctly, and the webhook ends up configured with too narrow a set of operations.

The same issue applies when processing multiple policies sequentially: each policy's rules should contribute to a growing union of operations per resource kind. Currently, there seems to be a bug where the accumulation doesn't work right.

There's also a utility function involved in building the final operation list from an internal boolean map. Currently, this function computes the result entirely from scratch each time it is called, ignoring any operations that may have already been accumulated before this point. This means that when operations are gathered across multiple calls or passes, previously collected results are discarded rather than being carried forward and merged into the final set.

For validating webhook configurations, the default set when no operations are specified should be all four operation types. For mutating webhook configurations, the default should be only the create and update operation types.
