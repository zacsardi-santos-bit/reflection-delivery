I'm chasing down a bug in the webhook config logic for our Kyverno policy engine, specifically around how admission operation types (create, update, delete, connect) get merged when multiple rules or policies hit the same resource kind. Here's the thing: if I've got two rules for the same resource, one that explicitly says just "create" and another that specifies no operations at all (which is supposed to mean it applies to all operations), the resulting webhook should cover everything the broadest rule implies. But right now the operations aren't combining correctly and the webhook ends up with too narrow a set. Same deal when I process multiple policies one at a time, each policy's rules should contribute to a growing union of operations per resource kind, but the accumulation isn't working.

There's a utility function that builds the final operation list from an internal boolean map, and the problem is it computes the result from scratch every call, throwing away any operations already accumulated before that point. It needs to carry forward previously collected results and merge them in instead of discarding them. So the merged set should always be the union across all matching rules whether they're in one policy or spread across several.

Also the defaults matter: when a rule has no explicit operations, for validating webhook configs the default set is all four operation types, and for mutating webhook configs it's just create and update. If any matching rule omits operations, the merged result has to include that full default for the webhook type. This actually matters a lot because under-configured webhooks silently let admission requests slip through unchecked, so resources could get created, updated, or deleted without being validated or mutated by rules meant to cover them, which is a real security blind spot.
