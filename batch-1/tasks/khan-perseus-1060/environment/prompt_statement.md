I'm cleaning up the Explanation widget in our Perseus question renderer and it's kind of a mess. Right now it renders differently depending on context, so mobile vs desktop and article vs exercise all take separate paths, and on mobile it uses a non-semantic anchor tag styled to look like a button while on desktop it wraps the button text in brackets. Neither is actually accessible and maintaining the split paths is painful.

What I want is one unified implementation that works identically in all contexts. It should use a proper semantic button element with standard ARIA attributes that communicate the expanded vs collapsed state to assistive tech, and the button's label needs to reflect the current state and flip when toggled (show the prompt when collapsed, the hide prompt when expanded). The content section the button controls should always live in the DOM instead of being conditionally rendered, with visibility handled through CSS so we can do smooth animated transitions when expanding or collapsing. The content area's own visibility and accessibility attributes should stay in sync with the button's expanded state too.

Oh and the transitions should only kick in when the user hasn't asked for reduced motion, so check their motion preference and skip the animation if they prefer reduced motion. Keyboard folks should be able to expand and collapse using a mouse click, the Enter key, or the Space bar, all of them.

Also, separate but related, I want to update the graded-group widget's hint button labels. They currently do the "[Hint]" / "[Hide hint]" bracket thing and I'd rather they read more naturally for students, so "Explain" to show the hint and "Hide explanation" to dismiss it. The whole point here is screen reader users get proper state info, keyboard nav works reliably everywhere, and we drop the awkward bracket-wrapped text.
