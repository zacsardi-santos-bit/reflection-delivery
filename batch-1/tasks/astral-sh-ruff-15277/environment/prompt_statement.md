I'm hitting a bug with the lint rule that strips unnecessary int() conversions around expressions that are already integers, over in the ruff checks. It works fine most of the time but breaks on some valid multiline Python. When someone writes a call with the function name on one line and the opening paren of its args on the next line (which is legal style), the auto-fix just yanks the outer conversion off and leaves the inner stuff as-is, so what used to be a single function call turns into two separate expressions. The code still parses but it does something totally different now, silently, which is exactly the kind of thing a "safe" fix is not supposed to do.

What I want is for the fix to notice this. If the function name and the argument-opening parenthesis land on different lines, wrap the inner thing in parentheses so the call semantics stay intact. If they're on the same line (even when the arg body keeps going onto later lines) then no wrapping is needed and the existing behavior is correct, just remove the outer conversion directly.

Also comments. If there are comments between the opening of the outer conversion call and the start of the inner argument, or between the end of the inner argument and the closing paren of the outer conversion, the fix can't be done without maybe dropping those comments or reshuffling structure, so it should be marked unsafe instead of safe. Right now those get flagged safe, which is wrong. Context is https://github.com/astral-sh/ruff/issues/15263 if you want it.
