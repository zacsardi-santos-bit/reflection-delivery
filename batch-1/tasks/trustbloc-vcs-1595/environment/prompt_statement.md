I'm building out an OIDC4VCI credential issuance system and I hit a gap in the authorization code flow. Right now if a wallet client doesn't send `authorization_details` we just bail with an error, but the OpenID4VCI spec actually lets clients ask for a credential type using plain OAuth scopes instead, so I need to support both paths. This matters because a bunch of wallets prefer or only do the scope-based flow, and rejecting them makes us non-compliant.

What I want: when authorization details aren't supplied but scopes are, the service should pull the issuer's credential configuration metadata and find a matching config by the scope value (each credential config entry in the issuer metadata can define a scope value used to match incoming requests). It needs to check the credential format and type in that matched config line up with the active transaction, and then only the valid matched scopes come back in the response. Duplicate or unknown scopes should just be silently ignored, no error. Oh and if nothing matches, or the metadata's missing entirely, reject with an appropriate error, and if the issuer profile can't be found during scope validation return a proper profile-not-found error.

Also the credential configuration identifiers in the issuer profile metadata are supposed to be distinct identifier values, not just reusing the credential type name. Some existing config and tests lean on the type name as the id, so that needs updating to a real separate identifier.

Couple more edge cases while pushing authorization details: when the credential configuration ID doesn't match any supported configuration, return a validation error to the caller, and when authorization details are supplied but contain neither a credential format nor a credential configuration ID, return a descriptive error explaining that.
