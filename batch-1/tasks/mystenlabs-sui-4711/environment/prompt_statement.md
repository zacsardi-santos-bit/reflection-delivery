I'm building out the Sui TypeScript SDK and right now the end-to-end story is basically nonexistent, there's just a placeholder with a todo comment where real operational coverage should be. I want the SDK to actually work against a running local node for both reads and writes, so reading transaction data, reading owned objects, and executing transactions all behave correctly.

The big thing I need is a local transaction builder, basically a serializer inside the SDK that constructs transaction bytes entirely on the client without a network round-trip to the full node. Today the only supported path builds transactions via a server-side RPC call where the node constructs the bytes for us, and folks who want offline signing or lower-latency building have no option. So the signer should accept an optional local serializer and use it to build transactions for split-coin, merge-coin, Move function calls, transfer object, and SUI transfers, and each of those should execute successfully when submitted to a full node. Oh and the same five operations (split coin, merge coin, Move call, transfer object, transfer SUI) need to keep working through the standard RPC-backed approach against a gateway node too, so both paths are confirmed.

On the read side I want to grab the total number of transactions, fetch a recent transaction by its digest and confirm the digest comes back preserved in the response, read the objects owned by an address plus pull individual objects, and check the Move type of a coin object. Also I want an optional provider variant that caches fetched object state so it works as a drop-in replacement for the standard provider, handy for apps that read the same objects over and over and don't want redundant network requests. Without this coverage, regressions in basic SDK functionality just slip through unnoticed.
