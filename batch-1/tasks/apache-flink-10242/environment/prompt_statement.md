I've been digging into how Flink loads user code when a program gets submitted, and the annoying thing is the class loader always uses a hardcoded child-first resolution order, so user code classes always win over framework classes no matter what the operator configured. There's just no way to change this for packaged program submissions, not through the CLI and not through the web UI, which is bad news for anyone hitting class conflicts between their own libs and Flink's bundled ones. Right now they've got no recourse short of editing the application itself.

What I want is for the packaged program infrastructure to respect the class loading order coming from the Flink configuration when it builds the class loader for user programs. Default should stay exactly as it is today, child-first, where user code resolves before parent/framework classes, so nobody's existing behavior breaks. But when the config says to use parent-first ordering, the loader should flip and resolve framework/parent classes ahead of user code. So basically thread the configuration through so the class loader gets built according to whatever policy's specified.

Oh and the jar handling piece that the web submission UI uses, the handler that lists and prepares submitted jars, needs updating too so it accepts and passes along this same configuration. That way class loading behaves consistently across all the submission pathways (CLI and web) instead of only some of them respecting the setting. Point is to let operators pick whether user code or framework classes take precedence at runtime and get predictable behavior without touching their app code.
