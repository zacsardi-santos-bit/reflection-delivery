I'm cleaning up the peer-to-peer networking layer in our blockchain node and the callback pattern is driving me nuts. Right now to make a request to another node you pass in two callbacks, one success handler and one error handler, that fire asynchronously when the response comes back. It makes the code impossible to follow and error propagation basically never works right. I want the network request method to just be a plain synchronous call that returns the response bytes and an error directly, like any normal Go function, no callbacks.

Related to that, the functions that fetch data from peers all take a whole list of peers and fan out internally using those same callbacks. I'm talking about the ones that get the list of known malicious node identities, fetch layer data, and get layer opinions. I want each of those to operate on a single peer and return its result directly instead. Then the callers can loop over peers themselves, which actually makes partial failure handling clean, so if one peer fails but others succeed that's fine, and only if all peers fail do we surface the error.

There's also a bug where higher-level sync operations swallow errors from downstream fetches. When something like fetching malfeasance proofs or ballot data fails, the error just gets ignored right now. Those need to bubble up to the caller so they get handled instead of silently dropped.

Oh and on the activation transaction side, the internal processing function should directly return a malfeasance proof when it detects a node submitting duplicate ATXs for the same epoch, rather than only side-effecting. Then the outer handlers can decide what to do with it, broadcast the proof when we received the thing via gossip, or just store it when we're syncing. That makes the sync versus gossip distinction explicit instead of buried down in the processor.

Basically I want linear, readable error handling everywhere and no more silent failures during sync.
