I'm hitting a wall with our design system's static feedback APIs. We've got a global provider set up with custom class prefixes, an icon prefix, RTL direction, and locale overrides, and all of that flows through fine when I render components normally because the tree inherits from the provider. But the moment I switch to the static programmatic calls for toasts, notifications, and confirm dialogs, none of that applies. Those things always render with the default class prefix and completely ignore my RTL setting and my locale config, which is a pain since half our app fires messages through the static APIs.

What I want is for the global config API on the provider to take a render wrapper option so I can wrap the internal container of all the static feedback elements, and have them inherit the same theming, icon prefix, reading direction, locale, and component-level constraints (things like max visible item count) that the rest of the app already uses. So when I set a custom prefix or icon prefix in that wrapper, static messages, notifications, and modals should come out with those class names instead of the defaults, RTL from the wrapper should show up in the rendered output, and locale stuff like localized confirm dialog button labels should apply to dialogs triggered statically too. Constraints like max count set via the wrapper need to be respected as well.

Oh and there's gotta be a clear priority order here: component-level config wins over the wrapper, and the wrapper wins over the global provider config, most specific level always taking precedence. This should behave the same across the static toast message API, the notification API, and the confirm dialog API. Also it'd help a lot if I can reset the holder state between usages so I can test config changes cleanly without stale state leaking across.
