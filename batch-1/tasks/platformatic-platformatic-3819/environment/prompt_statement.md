I'm using a tool that generates TypeScript client code from OpenAPI specs, and I just noticed that any description or summary text attached to individual response definitions gets thrown away completely. The generated response types come out with no doc comments at all, even when the original spec has rich descriptive text for every response. That's annoying because I lean on IDE hover docs to remember what each response type actually means, and right now I have to keep flipping back to the raw API spec to figure it out.

I want the generator to carry that documentation through into the emitted types. So when a response entry has both a summary and a description, the generated TypeScript type should be preceded by a documentation comment block with the summary on the first line, then a blank separator line, then the description underneath. If there's only a description and no summary, the comment block should just contain the description by itself, no separator or empty leading line. And if the response has neither a summary nor a description, don't generate any comment at all, just keep the current behavior exactly as it is today.

The whole point is that documentation from the API spec should flow through to the generated client so developers get useful inline context right in their editors without having to consult external docs.
