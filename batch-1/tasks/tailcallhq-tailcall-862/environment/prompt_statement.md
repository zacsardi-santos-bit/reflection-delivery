I'm building out a GraphQL schema engine and hitting a wall with resolvers. Right now every field gets exactly one resolver type, HTTP or gRPC or GraphQL or a constant value, and there's no way to say "use this data source when condition X holds, otherwise fall back to that one." That's blocking anything where the endpoint depends on a runtime value, like routing based on query params or some calculated thing, and today people have to split logic across extra fields or push it upstream which is gross. I want the schema itself to be the source of truth.

So I want a new field-level directive that takes a resolver expression, and that expression should support all the existing resolver variants (HTTP, gRPC, GraphQL, constant) plus a new conditional branching variant. The conditional needs three required sub-expressions, a condition, a branch evaluated when the condition is truthy, and a branch evaluated when it's falsy, and at runtime it evaluates the condition and returns the result of whichever branch applies.

The validation has to be precise here. If the required expression argument is missing, or an unknown/unrecognized expression variant is used, or any of the three required sub-fields of the conditional (the condition, the truthy branch, the falsy branch) is absent, I want a clear structured error message saying exactly what's wrong and where in the schema it happened, not some vague blob. Also fields using this directive need to count as properly resolved so they don't get flagged as missing resolvers by the unresolved-field checks.

Two more things. The server-side schema should serialize and deserialize this directive round-trip safe, so writing it out and reading it back gives you the same thing. And the client-facing schema should strip this directive entirely so consumers just see plain fields, since it's an internal implementation detail. Wire this through wherever the existing resolver directives and expression handling live so it fits the current patterns.
