I'm hitting a couple of SQL transpilation bugs with Snowflake time conversion functions, specifically around TO_TIME / TRY_TO_TIME and how they lower to DuckDB and roundtrip in Snowflake. First problem is compact format strings. When I write a time conversion with a format string that jams hours, minutes, and seconds together with no separators (so the time value is one run of digits and the format descriptor has nothing between the components), the transpile to DuckDB breaks or gives wrong output, even though the same call with a dotted or colon-separated format works fine. I want the compact no-separator style recognized and converted to whatever equivalent format each target dialect uses, and while we're at it the format strings should come out normalized to a consistent case in the Snowflake output.

Second, the safe/nullable variant, the one that's supposed to return null instead of throwing on bad input, is getting lowered to DuckDB with strict parsing and casting. That's wrong, it should use the error-tolerant equivalents for both steps, so the string-parsing function should be the nullable one that returns null on failure and the cast should be the nullable cast, not the strict versions. This is happening even for the plain case where I use the safe variant with no format string at all, so don't assume it only matters when a format is present.

Also the type inference side needs love, calling these time conversion functions with a format string should be recognized as producing a time type when expression types get inferred. Oh and when the input's already a timestamp-typed expression, it should get wrapped or cast appropriately on the way to other dialects. Net goal is that Snowflake SQL using compact time formats or the safe variant transpiles reliably to DuckDB and other dialects instead of raising errors where it should quietly return null, or producing nothing for valid compact formats.
