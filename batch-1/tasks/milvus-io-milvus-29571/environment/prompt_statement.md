I'm poking at the data node's write buffer and there's basically no way to see how much data is piling up in memory before it gets flushed out to storage. We've got a metric that's supposed to track buffer data size per collection per node but it's wrong, looks like it's computing the size off only the primary key fields instead of the full insert data, so the numbers are way off from actual memory usage and operators can't use it to watch for memory pressure or diagnose ingestion pipeline slowdowns.

I want to fix this two ways. First, the internal routine in the data node that buffers incoming insert records should hand back the actual memory size of what it just buffered, in addition to the field data and error it already returns, so callers can use that real figure directly instead of recomputing it. That memory size needs to come from the full insert data, not just the pk fields. Second, right after data gets buffered, update the per-node, per-collection metric to reflect the total amount currently sitting in the write buffer. And when a segment's data gets flushed or synced, the metric should drop accordingly, actually hitting zero once everything's been synced out.

Point is I want operators to have real visibility into write buffer memory consumption so the metric's actually useful for monitoring and alerting, tuning flush policies, catching buffers that are growing unexpectedly, that kind of thing.
