I'm poking at the managed database controller in our CloudNativePG operator and the way it does SQL right now is a pain to test. All the Postgres database operations, checking whether a database exists, creating one, modifying its props, dropping it, are jammed straight into the reconciler methods so I can't exercise them without standing up a whole cluster. I want to pull those four SQL operations out into standalone functions that take a connection and can be tested on their own: one that detects whether a given database already exists, one that creates a new database with the full option set (owner, tablespace, connection limits, and the template flag), one that updates an existing database's properties, and one that drops a database.

While I'm in there I also want to fix the error handling. Today when a SQL op fails the reconciler just propagates the error up through the loop, but I'd rather it record the failure on the managed database object's status, marking it not ready and stashing the error message in the status error field, while the reconcile call itself returns cleanly with no error. And on success it should flip the status to ready with the error message cleared. I want explicit helper methods for those two transitions, one for succeeded and one for failed, instead of doing it inline. This way operators can see why a database isn't ready from the object status without digging through controller logs.

Oh and the reconciler's dependency on the running Postgres instance should be an interface rather than the concrete type, so a test can inject a fake that hands back a mock database connection without a real instance running. That's really the whole point, get these pieces decoupled enough to unit test the SQL and the status logic in isolation.
