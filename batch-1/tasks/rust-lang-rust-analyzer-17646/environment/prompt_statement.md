I'm poking at the rust-analyzer parser and hit a gap with how we recognize dynamic trait object types in older editions (pre-2018). Back then the `dyn` keyword isn't reserved so it's contextual, and the parser has to peek ahead to decide whether it's actually starting a dynamic trait type or just being used as a plain identifier. The current lookahead is way too narrow, it only checks a tiny set of following tokens, so a bunch of valid forms slip through and either fail to parse or come out wrong.

The forms I want handled correctly: `dyn` followed by a path parses as a dynamic trait type, and a reference to that (`&dyn Path`) parses as a reference wrapping a dynamic trait type. Also `dyn` followed by a lifetime bound, `dyn` followed by a question-mark-prefixed bound, `dyn` with a for-binder (higher-ranked trait bounds), and `dyn` with a parenthesized bound list all need to parse as dynamic trait types with those respective bounds. But the identifier cases should NOT trigger dyn-type parsing, so `dyn` used as a module name in a path (followed by a path separator `::`) should parse as an ordinary path type, and `dyn` followed by angle-bracket generic args should parse as an ordinary generic path where `dyn` is just an identifier.

What I want is a dedicated helper that consolidates all this lookahead logic into one spot so the parser classifies each of these syntactic forms right, instead of the scattered narrow check we have now. Oh and the existing parser test covering weak dynamic trait types needs expanding to hit all these cases, plus the corresponding parse-tree test data files need updating to reflect the correct output. The whole point is that older-edition code using lifetime bounds, question marks, for-binders, or parenthesized bounds on dyn types should parse correctly and produce the right trees, which it doesn't today.
