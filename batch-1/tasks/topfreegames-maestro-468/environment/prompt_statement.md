I'm dealing with a background worker in our Go stack that watches for game room instance events coming off a runtime, and it spawns a bunch of concurrent processors (goroutines) that pull from a shared event channel and handle add, update, and delete events as they come in. The annoying bug is that when the runtime closes the event channel, say because the connection dropped or the watcher got stopped on purpose, the worker just hangs forever instead of returning. What's happening is it blocks waiting on the context to cancel even though all the goroutines have already exited because the channel is closed, so nothing ever wakes it up.

What I want is for it to notice the channel closure, let the goroutines drain and finish, clean up the runtime watcher (stop it properly), and then return with no error, since a closed stream is a normal shutdown, not a failure. Without this the worker blocks indefinitely and we can't restart or recover from a dropped runtime connection, which breaks clean lifecycle management.

Don't break the existing behavior though. If the initial watch setup fails (can't even begin watching), that should still return an error. And event processing errors should still just get logged and handled gracefully without stopping the worker, so add, update, and delete events keep flowing normally.
