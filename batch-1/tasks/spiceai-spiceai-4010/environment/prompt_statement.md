I'm adding write-access control to our flight data ingestion path and right now it's basically wide open. All the API keys are flat strings with no access level attached, so any client with a valid key (or honestly even no key at all) can push data over the flight protocol, which is a real security gap for multi-client deployments where I want to hand some clients read-only keys and others full write access.

What I want is two access levels for API keys, read-only and read-write. Keys stay as configured strings but with an optional suffix that designates the access level, and anything without a recognized suffix should default to read-only. The tricky bit: when I compare an incoming bearer token against a configured key, only the key portion before the access-level suffix should be used for matching, so a plain bearer token still authenticates correctly against a key that carries a suffix.

Then on the flight ingestion endpoint I need actual authorization enforcement. Unauthenticated requests get rejected with an error, requests coming in on a read-only key also get rejected with an error, and only read-write keys are allowed through to actually ingest data. Oh and the existing flight and HTTP auth flows for read operations need to keep working exactly like before, don't break those.
