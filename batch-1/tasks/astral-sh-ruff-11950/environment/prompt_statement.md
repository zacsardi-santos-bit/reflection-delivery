I'm hitting this thing where my Python linter just gives up the moment it sees a syntax error. Like if there's an unclosed bracket or an unterminated string somewhere in the middle of a file, everything past that first bad token vanishes from the output, trailing comma violations, blank-line issues, invalid characters in string literals, all gone, even for code that's totally valid before or after the error. I want it to keep chewing through the whole file and report everything it finds so I see the syntax errors and the rule violations together instead of just the first failure.

The reason this matters is I'm often working on partially-valid files, adding new syntax, refactoring half-finished code, or using features the parser recovers from, and silently dropping all the non-syntax violations gives me a misleading picture. So instead of bailing at the first error token, keep going and surface actionable feedback for the parts that are fine.

There's a subtle bit around code structure too. Rules that care about whether something is at the top level versus nested inside parens or brackets need to handle a delimiter that never got closed because of a syntax error. In that situation I want the linter to treat the recovery point, where parsing picks back up after the error, as if the open context got closed there, so subsequent top-level definitions still get recognized correctly and blank-line rules and the like don't get confused about what's top-level.

Also for the string-inspecting rules, files with unterminated strings need care: violations inside strings that are properly terminated should still be reported, but characters sitting inside an unterminated string shouldn't trigger false positives.
