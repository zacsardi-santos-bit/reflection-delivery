I'm working with the bounded async MPSC channel and I want to reserve capacity for a whole batch of messages at once instead of grabbing one slot at a time. Right now the sender only lets me reserve a single slot before sending, so if I need to guarantee space for `n` messages I have to call the single-slot reserve repeatedly, which is inefficient and doesn't give me an atomic hold on a contiguous block of capacity. That matters because producers that generate messages in batches want all the slots lined up before committing to the work, otherwise there's risk of producing messages that can't be sent or holding back-pressure wrong.

So I want two new methods on the sender. One blocking async variant that reserves `n` slots, waiting until enough capacity frees up, and one non-blocking synchronous variant that tries to grab `n` slots immediately and returns an error right away if the channel doesn't have enough room rather than waiting. Both should hand back something I can iterate over, yielding one send permit per reserved slot, and each permit can be used to send exactly one message.

Behavior I'm expecting: reserving zero slots succeeds immediately (returning an empty result) as long as the channel's still open, even if the buffer is currently full. Asking for more slots than the channel's total capacity, or more than the system-wide maximum, should fail with an appropriate error. And when the channel is closed, any reservation attempt fails including a zero-slot one. Oh and drop semantics matter a lot here, if I drop the iterator before consuming all the permits, the remaining reserved capacity has to get released back to the channel and wake up any tasks waiting to send, so we don't leak capacity when the iterator gets discarded early.
