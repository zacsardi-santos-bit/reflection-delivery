I'm adding resizable array buffer support to Boa, our JS engine, and I've hit a wall with the internal allocation helper. The ECMAScript spec lets you create an array buffer with an optional maximum byte length so it can grow dynamically up to that ceiling, but right now the function that creates the underlying byte data block only takes a fixed size, there's no way to pass in a max capacity alongside the initial length. I want to update that create-byte-data-block helper so it accepts an optional maximum byte length as an extra parameter, and it needs to go between the existing size argument and the context argument (so the order is size, then the optional max, then the context). The whole point is this lays the groundwork for the engine to actually create and track resizable buffers with a known upper bound, since without it we can't represent the constraints for those buffers at all and it blocks the resizable array buffer proposal.

The key thing is when no maximum is passed (the option is absent, i.e. None), the behavior has to stay exactly as it is today. So allocating memory for a valid, reasonable size still succeeds, and trying to allocate something impossibly huge (like the maximum possible integer value, way past memory limits) still fails with an error. Basically don't regress the existing path, just thread the new optional param through so the None case is identical to now. This is over in the array buffer code under `@boa_engine/src/builtins/array_buffer`, wherever that byte block creation function lives.
