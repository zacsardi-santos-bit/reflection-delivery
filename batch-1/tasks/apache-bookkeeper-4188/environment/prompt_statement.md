I'm working on the Apache BookKeeper bookie client and I want to add a batch read capability, because right now the client can only pull one ledger entry at a time and there's no way to grab multiple consecutive entries in a single call. That's really inefficient for anything that scans or replays a long sequence of entries (think ledger recovery or replication), since every single entry needs its own round trip to the bookie server, which kills throughput.

So I want a new method on the client interface that lets callers request a range of entries starting at a given entry ID, with a maximum count and a maximum total response size. The bookie should return as many consecutive entries as it can, stopping at the first gap (a missing entry in the sequence), at the count limit, or when the cumulative frame size would go over the specified limit. The caller gets all the returned entries together in one async callback, and that callback should receive a result code, the ledger ID, the starting entry ID, and a list of entry buffers. Each buffer needs to carry the standard entry fields (ledger ID, entry ID, last confirmed entry, cumulative length, digest, and payload) in the same on-wire format already used for single-entry reads.

A few edge cases I really care about: if the very first requested entry is missing, the whole thing should fail with a "no such entry" error. But if entries exist and there's a gap partway through the requested range, it should succeed and return only the entries before the gap, not error out. Oh and the size limit has to account for the response framing overhead (the header bytes plus per-entry length prefixes) on top of the raw entry data, so it's not just summing payload sizes. Basically it's a batch variant of the existing read path so it should slot in alongside how single reads already work.
