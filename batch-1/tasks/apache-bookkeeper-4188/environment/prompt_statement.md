I'm working with Apache BookKeeper and I need to add a batch read capability to the bookie client. Right now, the client can only read one ledger entry at a time — there's no way to request multiple consecutive entries in a single call. This is really inefficient for workloads that need to scan or replay large sequences of entries, since every entry requires its own round trip to the bookie server.

I'd like to add a new method to the client interface that lets callers request a range of entries starting at a given entry ID, with a maximum count and a maximum total response size. The bookie should return as many consecutive entries as it can — stopping at the first gap (missing entry in the sequence), at the count limit, or when the cumulative frame size would exceed the specified limit. The caller gets all the returned entries together in a single asynchronous callback.

The callback should receive a result code, the ledger ID, the starting entry ID, and a list of entry buffers. Each buffer should contain the standard entry fields — ledger ID, entry ID, last confirmed entry, cumulative length, digest, and payload — in the same format already used for single-entry reads.

A few edge cases that need to work correctly: if the very first requested entry is missing, the operation should fail with a "no such entry" error; if entries exist but there is a gap partway through the requested range, the operation should succeed and return only the entries before the gap; and the size limit should account for the response framing overhead (header bytes plus per-entry length prefixes) in addition to the raw entry data.
