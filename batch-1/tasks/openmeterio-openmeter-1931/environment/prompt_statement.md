I'm working on our billing service that hooks into external invoicing apps, and right now we can validate invoices against a connected app but we never actually push anything back out, so the external system stays totally in the dark. I want to wire up the full invoice lifecycle so the app gets called at each stage.

When an invoice gets synced to draft, the connected app should be able to assign external identifiers to the invoice itself and to individual line items, but only the fee-type lines, not the usage-based ones. When an invoice is finalized, the app needs to both sync it and then finalize it, and whatever payment reference the app hands back should get stored on the invoice. And when an invoice is deleted, the app should be notified too.

The error handling is where it gets fiddly. If deletion fails with a validation-level error, I want the invoice soft-deleted with a "delete failed" status and that error surfaced back to the caller as a validation error. If deletion instead fails with a generic (non-validation) error and the caller retries, the error should show up as a validation issue on the returned invoice. Oh and for retries in general, before reattempting a failed invoice the system should first demote any existing critical validation issues down to a lower severity, otherwise those old blocking errors just kill the retry before it starts.

Last thing: the component name we attach to validation issues should include the specific operation that was running (validate, sync, delete, finalize) in a dot-separated format, so it's obvious which step actually produced the issue when I'm digging through them later.
