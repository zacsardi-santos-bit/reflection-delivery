I'm cleaning up how the data node bootstrap system is wired together and there are a couple of interface changes plus a concurrency behavior I want nailed down. First off, the peer source, the thing that manages connections to peer nodes, currently makes every caller pass in a logger at construction time, which is just redundant boilerplate since all the other components already use the shared application-level logger we have globally. I want to drop that explicit logger argument from the constructor and have the implementation grab the global one internally instead.

Second, the bootstrap manager takes a full top-level options bundle even though it only actually needs the bootstrap-specific subset, and that creates a needless dependency on unrelated config. Change its constructor so it accepts just the focused bootstrap-specific options type rather than the whole top-level object, cuts the coupling between subsystems.

The bigger thing though is concurrency, there's no coverage for it right now. If ten goroutines all call the bootstrap method at the same time while a bootstrap is already running, the manager shouldn't kick off ten more cycles, it should just track that there's a pending request and run exactly one more after the current one finishes. So ten simultaneous calls should result in at most two actual underlying bootstrap executions, current one plus one queued, the rest get discarded. This dedup matters a lot under load and has never been verified. Oh and I also want the manager to reliably expose whether bootstrapping has completed and when the last successful bootstrap finished so callers can check that state.
