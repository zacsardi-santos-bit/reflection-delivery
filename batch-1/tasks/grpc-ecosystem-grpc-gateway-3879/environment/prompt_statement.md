I'm hitting a weird gap in the grpc-gateway runtime around field mask generation from JSON request bodies. When I send a body where one of my fields is set to an empty object `{}`, like a variant type that picks an option with no sub-fields, that field just vanishes from the generated field mask. So my partial update operations don't pick it up at all, even though the client obviously included it in the request. It's getting treated as if the field wasn't present, which silently drops the client's intent.

What I'd expect: if the JSON body has a field whose value is an empty object, that field should still count as present and show up in the resulting field mask with a path for it. Right now the code walking the decoded JSON only adds paths when it recurses into non-empty objects, so an empty map contributes nothing and the field never lands in the mask. That's the bug. An empty object is intentional input, not absence.

So can you fix the field mask generation (see the runtime's field mask helper that builds paths by walking the parsed request body) so that fields with empty object values still get included? Basically when it encounters a field mapping to an empty object, it should add that field's path rather than skipping it. Everything else about how nested non-empty objects expand into dotted paths should keep working the same, I just want empty objects to stop being dropped so clients using variant fields or similar empty-message constructs can actually signal their intent through a partial update.
