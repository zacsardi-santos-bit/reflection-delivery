I'm adding preemptive proxy auth to OkHttp and could use your help wiring it up. Right now when we make HTTPS requests through an HTTP proxy, we only send proxy credentials after the proxy challenges us, so we wait for the proxy to reject the initial tunnel-establishment request before supplying anything. That reactive-only path costs an extra round trip on every new connection even when the app already knows the right proxy credentials, which is wasteful.

What I want is for the proxy authenticator to get consulted proactively, before that first tunnel-establishment request goes out. It should be handed a synthetic challenge that signals this is a preemptive opportunity so it can recognize the situation and optionally hand back a request with credentials already attached. If it does, we use that credentialed request for the initial tunnel attempt. If it declines and returns nothing, the tunnel request goes out bare and the existing reactive challenge-response flow takes over if the proxy actually demands auth.

Here's the tricky bit, when both happen on the same connection (say the authenticator passes on the preemptive opportunity but then the proxy sends a real challenge), the authenticator gets called twice in sequence, first with the preemptive synthetic challenge and then with the real proxy challenge. And credentials meant for tunnel establishment can't leak into the origin-server requests that follow, they only belong on the tunnel requests.

Oh and the test helper authenticator also needs updating so it can filter by auth scheme, otherwise an authenticator set up for one scheme (like basic) might accidentally respond to the preemptive synthetic challenge when it shouldn't. Basically it should stay quiet unless the scheme matches.
