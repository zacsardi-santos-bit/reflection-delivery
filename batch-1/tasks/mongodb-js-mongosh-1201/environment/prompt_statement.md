I'm working on the analytics and telemetry infrastructure for a shell tool, and I'd like to refactor how telemetry gating is handled. Right now, a boolean flag is passed with each bus event to indicate whether telemetry is currently enabled, and the analytics provider is passed as a factory function that creates the analytics object. This makes the code awkward — every event handler has to read the flag, and we have to handle the case where the factory throws.

What I'd like instead is a design where the analytics object itself handles the "should I send this now?" decision. I want a wrapper type that starts in a paused state — buffering events without forwarding them — and can later be enabled (which flushes the buffer and starts forwarding immediately), paused again (which resumes buffering), or disabled (which permanently discards any buffered events so they're never sent, even if the wrapper is later re-enabled).

With this wrapper in place, the logging setup function should just accept a plain analytics object directly (not a factory), and the bus events for user identity and user updates should drop their telemetry-enabled flag — the wrapper itself handles the on/off decision. I'd also like to add handling for a new bus event that fires when a global configuration file is loaded, so we get a log entry recording the file's path.
