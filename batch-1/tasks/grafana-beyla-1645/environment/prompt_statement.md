I'm digging into Beyla's SQL detection and hitting a frustrating gap where legit database queries get silently dropped even after we've already figured out the connection is talking to PostgreSQL. The problem is the validation logic insists on pulling both the SQL operation keyword and the table name out of the raw network bytes before it'll accept the traffic as a valid SQL span, but plenty of real PostgreSQL queries (especially the ones with complex join expressions using quoted identifiers, or certain prepared statement formats) fail table extraction even though the operation like SELECT or INSERT is sitting right there. So those spans just never show up in traces or metrics and users see holes in their db telemetry.

What I want is for the validator to be context-aware. When Beyla already knows the database type is PostgreSQL, finding just the SQL operation should be enough to accept the traffic even if the target table couldn't be extracted. For generic or unknown TCP connections though, keep the stricter both-operation-and-table rule so we don't start throwing false positives.

There's a related thing in the PostgreSQL query parser too. Queries using double-quoted identifier notation for table and column names should get all their participating tables extracted correctly and joined as a comma-separated string, covering both the primary table from the FROM clause and any tables pulled in through JOIN clauses. Basically the parser needs to handle those quoted identifiers right and not choke on multi-table joins.

The net effect I'm after: fewer false negatives for known PostgreSQL connections without loosening correctness for the unidentified ones.
