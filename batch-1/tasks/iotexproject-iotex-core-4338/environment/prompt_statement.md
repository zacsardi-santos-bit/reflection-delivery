I'm working on the IoTeX core codebase and I need to add a second embedded storage engine as an alternative backend for the key-value store layer. Right now we only support one engine, but I'd like to be able to swap in an LSM-tree-based alternative without changing any of the application code that reads and writes data.

The new backend should be created through a constructor that takes the same configuration struct the existing backend uses (with a path to the database directory). It needs to implement the full set of operations: opening and closing the database, reading a value by namespace and key, writing a value, deleting a key, writing a batch of operations atomically, doing a range-filtered scan over a namespace, and iterating over all entries in a namespace.

Some specific behaviors I need: reading from a nonexistent key should return a recognizable "not found" error; deleting a nonexistent key should be a no-op; batch writes should deduplicate entries for the same key using last-write-wins; a filtered scan that finds no matches (including when the namespace doesn't exist) should return a "not found" error; and iterating over an empty or nonexistent namespace should succeed with no entries rather than returning an error. Keys from one namespace must not be visible in another namespace even if the raw key bytes are the same.
