I'm working on the zkSync commitment generator and I want to derive the events queue straight from the raw VM events we already store in the database instead of always pulling it from that separate dedicated table. Right now the events queue (the structured sequence of log records we use to compute cryptographic commitments for each L1 batch) only comes from that table, so there's no way to independently verify or regenerate it from first principles, and honestly we're too coupled to a table that we'd like to drop eventually. So step one: give me a conversion function.

What I need is a new function in the types library, living in the event types module, that takes a list of raw VM events and turns them into the equivalent sequence of log query records. The encoding is specific: each VM event maps to one or more log query records where the first record is a header encoding the number of indexed topics, the length of the event's data value, and the event's contract address, and then the following records carry the actual topic and value data packed in pairs of 32-byte words. Events can have one through four indexed topics, and the data value can span multiple records or be as short as a single byte (pad that out to 32 bytes). The output has to match exactly what the commitment generator currently reads from the database so we can cross-check the two sources.

Oh and to make room for this the event module needs reorganizing from a single file into a directory module with a separate test submodule. The tests load their expected inputs and outputs from JSON test vector files, so please create those alongside the implementation with the correct input events and their expected log query outputs (cover the varying topic counts and the multi-record data value cases). This is the foundational step so that later the generator can confirm the computed queue matches the stored one and we can eventually delete the stored events queue table entirely and just compute it on the fly.
