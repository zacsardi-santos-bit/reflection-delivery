I'm hitting a crash in the TypeSpec C# client code generator around paging operations. When I define a list op that carries paging metadata but doesn't actually specify a next-link URL or a continuation token, basically an implicit or single-page pattern where the API hands back everything in one response but I still model it as a collection, the generator either blows up or spits out wrong code instead of valid output.

What I want is for these token-less pageable ops to still emit the full set of collection result wrapper classes, both the synchronous and asynchronous variants and both untyped and typed flavors. Each of those wrappers should follow the usual shape where it stores the client and parameter state, yields a single page result off the raw pipeline, and returns null for the continuation token since there's no next page to go grab. And the client method signatures for these operations need to return the correct pageable collection result types.

There's also a related bug I noticed: right now the generator only counts an operation as pageable if it has a next-link or a continuation token, so ops that have paging metadata but no token config get wrongly treated as non-paging. I want any operation that has paging metadata set to be treated as pageable, regardless of whether a next-link or continuation token is configured. Oh and to be clear, an operation with no paging metadata at all should still stay a plain non-paging operation, don't over-correct that direction.

The motivation here is that folks writing list operations in their TypeSpec specs sometimes model single-response collections as pageable for consistency or future extensibility without bothering to set pagination tokens, and the generator should just produce clean correct client code for that case.
