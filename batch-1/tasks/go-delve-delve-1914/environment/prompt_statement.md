I'm building out goroutine listing in the Delve DAP server and right now the thing just bails on any threads request, returns an error saying it's unsupported, which is a problem because listing threads is a core part of the Debug Adapter Protocol and even a bare minimum implementation has to hand back at least one placeholder entry. So when a client like VS Code starts a session and asks which goroutines are running it currently gets an error instead of a real response, and I want to fix that.

What I need: when the debugger's paused at a breakpoint with live goroutines, a threads request should come back with the actual goroutines, each carrying a numeric ID and the name of the function it's currently executing. When goroutine info isn't populated yet (early startup, that kind of thing) the server should return a single placeholder thread entry like the protocol spec wants. And when the debugged program has already terminated, just return an empty threads list. Stack trace requests can stay unsupported for now, that's fine, but they should still return a proper error response rather than blowing up.

On the client side (the DAP test client), I need to add the ability to send goroutine/threads listing requests and stack trace requests, plus methods to read back the matching responses. Also the client's request sequence counter starts at 0 right now but VS Code actually starts numbering at 1, so that needs correcting since it affects how response sequence numbers get validated. Oh and the client currently logs raw protocol messages to stdout on every send, which is noisy during testing and should be cleaned up so it stops doing that.

The why here is simple: without goroutine listing, debugging tools can't show the user which goroutines are active when stopped at a breakpoint, and that's essential for any multi-goroutine debugging workflow and expected by any DAP-compliant client.
