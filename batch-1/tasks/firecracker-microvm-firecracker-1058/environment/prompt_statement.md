I'm working on simplifying the CPUID processing API in a virtual machine monitor. Right now, when creating a VM specification object, callers have to explicitly pass in the CPU vendor identifier — but that's an internal detail that the code should be able to determine on its own by querying the host. I want to change the constructor so it only takes the parameters callers actually control: the virtual CPU index, the total VCPU count, and whether hyper-threading is enabled. The vendor information should be looked up internally, and since that lookup can fail, the constructor should return a result type to let callers handle errors gracefully.

This change will require updating all the places in the codebase that currently call the old four-argument constructor form to use the new three-argument form instead.

Along with this, I also want to clean up the CPUID entry transformer infrastructure. Instead of each transformer directly implementing per-entry logic in a single method, the trait should expose a composable structure: a default method that iterates over all CPUID entries and dispatches to an entry-specific transformer function, and a separate method that implementors override to return the appropriate per-entry transformer for a given entry's function code. The top-level CPUID filtering function and the CPU template setup functions should also be updated to take a pre-constructed VM specification rather than creating one internally.
