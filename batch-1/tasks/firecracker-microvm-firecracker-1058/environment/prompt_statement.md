I'm cleaning up the CPUID processing API in our VMM and the VM spec constructor is bugging me. Right now when you build the VM spec object you have to hand it the raw CPU vendor identifier, but that's really an internal detail the code can figure out on its own by querying the host. Every call site ends up separately looking up the host CPU's vendor before constructing the spec, which is redundant and easy to get wrong. I want the constructor to take only the stuff callers actually control, so the virtual CPU index, the total VCPU count, and whether hyper-threading is on, and then determine the vendor identifier internally. Since querying the host CPU can fail, the constructor should return a result type instead of a plain value so those failures get surfaced to callers rather than silently lost, oh and every existing call site including the ones in tests needs to move from the old four-argument form to the new three-argument form.

While I'm in here I also want to fix up the CPUID entry transformer infrastructure. Instead of each transformer implementing per-entry logic directly in a single method, the trait should expose a composable structure: a default method that iterates over all CPUID entries and dispatches to an entry-specific transformer function, plus a separate method that implementors override to return the right per-entry transformer for a given entry's function code. Also the top-level CPUID filtering function and the CPU template setup functions should take a pre-constructed VM spec rather than building one internally. Leaking the vendor lookup into the public API makes this harder to use correctly and blocks proper error handling, so simplifying it and restructuring the transformer layer should help both correctness and maintainability.
