I'm working on a database migration testing framework and I want to improve how constraint violations are verified in tests. Right now, when we check that an insert is correctly blocked by a database constraint, we only confirm that it fails — but we don't verify the reason for the failure. This means a test could appear to pass even if the insert failed for the wrong reason, like bad test data or a type mismatch, rather than the actual constraint being enforced.

I'd like to add a way for tests to specify exactly which category of database constraint violation they expect — for example, whether the failure is due to a referential integrity rule, a conditional check, a not-null requirement, or a uniqueness requirement. Ideally this would be done by introducing a small set of named, reusable identifiers for each violation category, stored in the shared test utilities package, so any test file can reference them consistently.
