I'm building out a database migration testing framework and I keep hitting a gap in how we check constraint violations. Right now when a test wants to confirm that an insert gets blocked by a constraint, we only verify that it failed, not why it failed. So a test that's supposed to prove a foreign key is enforced would still pass if the insert actually blew up for some totally unrelated reason like a schema mismatch or a type error in the test data. That's a silent trap because a flawed migration or a bad test fixture could mask the real database behavior and we'd never know.

What I want is a way for tests to declare exactly which category of constraint violation they expect, so the test infra can confirm the database error matches that specific category rather than just any old failure. I'm thinking a small set of named, reusable identifiers for each violation type, living in the shared test utilities package so any test file can pull them in consistently. Those constants should cover the ones we actually test against: referential integrity (foreign key) violations, conditional check constraint violations, not-null violations, and uniqueness (unique constraint) violations.

The point is to make each constraint test say out loud which rule it's exercising, so it's self-documenting and we can trust that a blocked insert was blocked by the intended rule and not by accident. Please add those shared category constants and wire the verification so tests can assert against the exact error category.
