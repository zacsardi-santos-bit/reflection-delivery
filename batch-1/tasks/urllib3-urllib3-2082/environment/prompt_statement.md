I'm cleaning up how our HTTP library picks TLS ciphers and it's bugging me that every time we build an SSL context we unconditionally slam our own hardcoded cipher list onto it, even on boxes where the underlying SSL library already ships strong, regularly-updated defaults. That means an admin literally can't manage cipher policy at the OS or SSL-library level because we always win, which is backwards, and it can also cause compatibility headaches when our static list drifts out of date.

What I want is a flag that controls this. When the underlying SSL library is modern enough to be trusted (newer versions of the modern SSL/TLS lib have solid built-in defaults these days) we should skip applying our own cipher override entirely and just defer to whatever the platform is configured with. If the caller explicitly passes in a set of ciphers, honor those every time, no matter what version we detect. And when we're on an older library whose defaults we can't trust, keep the current behavior of applying our own safe default cipher list.

The point is so a sysadmin can set cipher policy once at the OS/SSL level and have everything, including apps on this library, actually respect it instead of getting steamrolled by app-level defaults.

Oh and while I'm in there I want to reorganize the existing SSL unit tests into a class so the same suite can get reused cleanly when we run it against alternative SSL backend implementations. Right now they're just loose functions and that makes it a pain to point the whole thing at a different backend.
