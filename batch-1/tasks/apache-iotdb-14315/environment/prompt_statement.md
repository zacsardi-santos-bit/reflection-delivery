I'm working on the table-model deletion feature and have found several gaps that need to be addressed. The plan node that represents a table deletion is missing a database name field — without it, when the same deletion is sent to multiple storage regions or needs to be recovered after a restart, there's no way to associate it with the correct database. The field needs to be added to the constructor and included in the serialization format (with an absent value being valid for cases where the database is already implicit from context).

Beyond the plan node, the file that records which data has been deleted (used during reads to filter out deleted points) doesn't support the table-model deletion entry types at all. I need it to accept batch writes of multiple entries, and I also need it to handle compaction properly — right now, if you write many deletion records for the same table using a "match-all devices" predicate, they never get merged, so the file just grows forever. Compaction should merge entries for the same table-and-predicate group into a single entry with the broadest time range, but only when the file is large enough (at or above 1 MB); smaller files should not be aggressively compacted. When there are multiple distinct groups (for example, different tables or different predicate types), each group should compact independently.

There's also no upgrade path for systems that have deletion records stored in the old file format. I need a way to read those legacy records, convert them to the new format, write the new file, and delete the old one — with the ability to run the conversion either synchronously or in a background thread. During and after the upgrade, the file should remain writable so that new deletions can continue to be appended without waiting for the conversion to finish.
