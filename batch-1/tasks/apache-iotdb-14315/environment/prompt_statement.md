I'm deep in the table-model deletion feature and keep hitting gaps that make it fall apart end to end. First the plan node that represents a table delete is missing a database name field, so when the same deletion gets forwarded to multiple storage regions or has to be recovered after a restart, there's no way to know which database it belongs to. I want that field added to the constructor and carried through serialization and deserialization, and an absent value should be totally valid since sometimes the database is already implicit from context.

Then there's the modification file, the thing that records deletions so reads can filter out deleted points. Right now it doesn't understand the table-model deletion entry types at all. I need it to accept batch writes of multiple entries at once, and I need those entries with their various predicate types (match all, match by segment, match by full device identity, or match by table name only) to serialize out and come back cleanly.

Compaction's also busted. If you write a ton of deletion records for the same table using a match-all-devices predicate they never merge, so the file just grows forever. Compaction should merge entries sharing the same table and predicate into one entry with the broadest time range, but only once the file is big enough, at or above 1 MB. Below that threshold don't aggressively reduce anything. And when there are multiple distinct groups (different tables, or different predicate types) each group compacts independently.

Last thing, there's no upgrade path for modification files written in the legacy format. I want a mechanism that reads those old records, converts them to the new format, writes the new file, and deletes the old one, runnable either synchronously or in a background thread. During and after the upgrade the file has to stay writable so new deletions can keep getting appended without waiting for the conversion to finish, and afterward the old file is gone, the new one exists, and all entries are preserved.
