So I'm working on this repo-packaging tool and it's getting painfully slow on big repos, hundreds or thousands of files, because everything runs sequentially on the main thread right now, file collection, content processing, security scanning, token counting, all of it, and that doesn't touch the extra cores sitting idle. I want to refactor the heavy stuff to run in parallel via a background worker thread pool so multiple files get processed concurrently, and the observable output should stay exactly the same, just faster wall-clock time.

The plan is each major operation gets its own dedicated worker module that handles a single unit of work: file collection, file content processing, per-file metrics, output metrics, and security checks. The orchestrating functions dispatch tasks into the pool. I also need a small utility that decides how many worker threads to spin up given the number of tasks and the available CPU count, so it should scale threads up as task count grows, cap at the CPU count, and always use at least 1 thread no matter what.

A couple of signature changes go with this. The function that aggregates all the per-file metrics should take a token encoding name string directly instead of a pre-built counter object, since the counter now lives inside the worker. And I want a new separate function just for computing the token count of the final output string, also running in a worker.

For security, move the secret-detection config setup and the per-file linting into their own worker module. The outer security check orchestrator handles the parallelism and error reporting, and the old "run only if enabled" wrapper should go away, just inline that enabled/disabled check at the call site instead. Oh and all the orchestrating functions should accept optional dependency injection for their task runners so I can still test them by swapping in fakes.
