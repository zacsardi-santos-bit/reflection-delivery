I'm poking at the DynamoDB state store and noticed its init is way too optimistic. Right now when the component starts up it just parses the config metadata and spins up a client, but it never actually talks to DynamoDB to confirm the table's really there or that the credentials can reach it. So if someone points it at a table that doesn't exist, or gets the region wrong, or hands it creds without the right permissions, everything looks totally healthy at startup and then blows up later when the first real read or write hits. That's the worst kind of failure, it surfaces in production under an actual workload instead of at boot.

What I want is for the initialization path to do an upfront table access check, basically reach out to the configured table and verify access is possible before it considers init done. If that check fails (table missing, wrong region, missing perms, whatever) I want init to fail immediately with a descriptive error that names the specific table it couldn't get to, so it's obvious what's misconfigured. If the check passes, init just carries on like normal.

One thing I care about, and it's mostly for testing, I need to be able to inject a pre-configured client before init runs so the access check can be exercised without making real AWS calls. So the init logic shouldn't blindly create a fresh client and overwrite it, if a client's already been set it should use that existing one for the validation check instead of replacing it. Basically respect what's already there.

Fail fast, clear error, and keep the client injectable.
