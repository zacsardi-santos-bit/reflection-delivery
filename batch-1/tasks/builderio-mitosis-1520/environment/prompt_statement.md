I'm hitting a state init ordering bug in the Mitosis Angular generator. I've got a component where a state variable gets initialized from one of the component's input props, and then that same state variable shows up in a complex binding, like a spread/merge expression, that I pass down as a binding to a child component. When it compiles to Angular the lifecycle code comes out in the wrong order, the computed binding that depends on the state is getting set up before the state has actually been initialized from the prop. So the child component ends up receiving an incorrect, basically uninitialized value on the very first render.

What I want is for the generated Angular component to respect these init dependencies. Whenever state depends on a prop value, that state should be initialized from the prop first in the lifecycle hook, and only after that should any computed/bound expressions that rely on that state be calculated. Right now it's doing it backwards. So the fix is: first set up all the prop-dependent state values, then initialize the bound expressions (like the spread binding to the child) that depend on those state values.

This is the kind of thing that's a pain to debug because the component looks syntactically fine but behaves wrong at runtime since the data-flow dependencies aren't honored in the emitted code. The Angular generator lives in the mitosis packages under the core generators (something like `@packages/core/src/generators/angular.ts`), that's where the lifecycle emission ordering needs to change so prop-initialized state comes before the computed bindings that consume it, ensuring the child gets the right value during initial render.
