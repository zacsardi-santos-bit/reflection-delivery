I'm hitting a problem with the block results RPC endpoint on a node that's been carrying historical data from an older version of the software. When I query block results for heights that were processed before the current unified block finalization model came in, the endpoint either fails outright or hands back wrong data (zero-valued or missing fields). The root cause is that the old format stored begin-block, deliver-tx, and end-block responses separately, while the new format uses a single finalization response, and the state store doesn't reliably detect which format it's reading. Turns out the old data can sometimes deserialize as the new format without throwing any error, just with bogus field values, so plain deserialization isn't enough to tell them apart.

Here's what I want. First, the block results response is missing the application hash the app produced at end of block processing, so please include that field alongside the usual stuff (transaction results, events, validator updates, consensus parameter updates) so clients can verify the app state root. Second, make the legacy detection smarter by keying off whether the application hash is absent after deserialization, if it's absent, re-attempt using the legacy format and convert from there.

When legacy data is detected and converted to the current format, merge the events from the old begin-block and end-block phases into the unified events list, and tag each event to indicate which phase it came from. Also the conversion needs to handle cases where the begin-block or end-block portions may be missing entirely, don't blow up on those. And fields that didn't exist in the old format (like the application hash) should just be left absent in the converted response rather than erroring out.

Why this matters: nodes running since before the unified finalization model hold historical data in an incompatible serialization format, and without proper detection plus conversion, operators can't query block results for those heights, which breaks tooling, explorers, and any client verifying historical state. Getting the app hash into the response closes the state-integrity gap too.
