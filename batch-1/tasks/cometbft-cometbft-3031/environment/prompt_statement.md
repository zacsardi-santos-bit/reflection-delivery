I'm running into a problem with the block results RPC endpoint on a node that has historical data from an older version of the software. When querying block results for heights that were processed before the current block finalization model was introduced, the endpoint either returns incorrect data or fails entirely. The issue is that the old format stored begin-block, deliver-tx, and end-block responses separately, while the new format uses a single unified block finalization response — and the state store doesn't properly detect which format it's reading from.

There are also two related gaps I'd like to address at the same time. First, the block results response is missing the application hash that the application produced at the end of block processing — this field should be included so clients can verify the application state. Second, the fallback logic for detecting legacy data needs to be smarter: since it turns out that the old format can sometimes be deserialized as the new format without returning an error (but with wrong field values), we need to use the presence of the application hash as an additional signal to decide whether re-parsing as the legacy format is necessary.

When legacy data is detected and converted to the current format, the events from the old begin-block and end-block phases should be merged into the unified events list and each event should be annotated to indicate which phase it came from. The conversion should handle cases where the begin-block or end-block portions of the old data may be absent. Fields that didn't exist in the old format, such as the application hash, should simply be left absent in the converted response rather than causing an error.
