We're running into a nasty deadlock in the gossip sync subsystem when a bunch of peers apply gossip filters all at once. Under rate-limited conditions multiple goroutines end up competing to send the exact same backlog of messages simultaneously, which blocks the gossip processor, causes redundant work and resource contention, and sometimes deadlocks the gossiper entirely. Nodes with lots of simultaneous peer connections are the most exposed here, a burst of filter requests can stall the whole thing.

I want to fix this two ways. First, add an atomic flag on the gossip syncer that tracks whether a backlog send is already in progress, so any concurrent caller can check it and return early instead of kicking off duplicate work. Only one goroutine should ever be actively sending the backlog at a time, and if one's already running the extra requests just get dropped gracefully rather than piling up.

Second, incoming gossip filter requests should go into a bounded, non-blocking queue that gets processed asynchronously one at a time so the gossiper never blocks waiting on the rate limiter. The queue needs a configurable capacity with a sensible default, and it's drained by a background goroutine that starts when the syncer starts and exits cleanly when the syncer stops (also needs to shut down properly on node shutdown). If the queue's full, drop the new request with a warning instead of blocking the caller. Concurrent access from multiple goroutines has to be safe, and messages must be processed in the order they came in.
