I'm poking at the snapshot subsystem in our distributed SQLite setup and hit a nasty gap. When we take an incremental snapshot we flush the write-ahead log as part of the process, and that checkpoint can fail, say because another connection has the db open with an active transaction and it's locked. Right now when the WAL flush fails during snapshotting the operation does correctly bail out and return an error, which is fine, but that's literally all it does. Nothing handles the failure beyond propagating the error up.

The problem is the next snapshot attempt just tries the same incremental approach again, probably hits the same lock, fails the same way, and meanwhile the replication state is sitting in a bad spot. Incremental snapshots depend on a consistent sequence of WAL files, so if a checkpoint dies partway through, the main db file and the WAL are out of sync and the next incremental snapshot would be built on a broken foundation.

What I want is for a failed WAL checkpoint during snapshotting to automatically mark that the next snapshot has to be a full, complete snapshot of the whole database instead of an incremental one. So still return the error like before, but also record that flag. Then any check for whether a full snapshot is required should report that yes, one is needed, so a call asking whether we need a full snapshot after such a failure confirms the flag got set. That way even when the incremental path is broken the next snapshot captures the entire database state and restores consistency across all replicas, avoiding cascading failures.
