I'm working on the garbage collection worker and its delete range loop is way too fragile right now. If any single storage node chokes on a delete range request, whether that's an outright RPC error, or an absent or empty response, or a response that's missing the field we care about, or a response that carries an embedded error message inside it, the whole batch aborts and returns an error immediately. That means every remaining range in the queue gets skipped for that GC cycle even though those ranges have nothing to do with the node that failed. A brief blip on one store shouldn't block cleanup of unrelated data from a bunch of other jobs, so I want this to be fault-tolerant instead.

What I'm after: when a delete range request fails for a particular range (any of those failure types above), log the error, skip that range, and keep going through the rest. The function itself should return successfully with no error even when some individual ranges failed along the way. The important bit is that any range that wasn't successfully sent to all stores has to stay in the pending list so it gets retried next cycle, don't mark it complete.

Oh and the same tolerance needs to apply to the redo delete ranges path too. It should continue on per-range failures the same way and leave the failed ranges in their tracking table rather than removing them.

Also, the current code only catches the outright RPC errors, it doesn't notice the malformed cases at all, so make sure the failure detection covers all of it: communication failures, absent or empty responses, a missing response field, and responses containing an error message. All of those count as failures and should trigger the skip-and-continue behavior.
