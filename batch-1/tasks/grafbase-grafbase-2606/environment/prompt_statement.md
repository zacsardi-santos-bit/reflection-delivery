I'm building a federated GraphQL gateway that supports schema extensions with typed directive arguments, and right now there's a real gap: when an extension directive gets declared with typed args (say it requires a specific input object, some scalar, or an enum), nothing validates those argument values at schema construction time. So mistakes like handing a string where an int is expected, dropping a required argument, or referencing an unknown type all slip through undetected, which makes debugging awful because you only find out at runtime or you silently get wrong behavior.

What I want is for the engine to validate directive argument values against their declared types while building the schema. That means catching unknown argument names, missing required args, incorrect scalar types, malformed input objects (wrong shape, unknown fields, missing required fields), bad enum values, and incompatible list wrapping. Also if an argument references an undefined type, or a type that can't be used as input (like a plain object type instead of an input object), construction should just fail with a clear error. Each error needs to report the location, meaning whether it's a field-level or schema-level directive and which extension and directive is involved, plus the precise path within the argument value where the problem sits.

Beyond validation I need the standard coercions working too: a single value should get promoted to a list when a list type is expected, and a whole-number float should be accepted where an integer scalar is wanted. Default values defined on directive arguments and on input object fields should be applied automatically when values are omitted. Custom scalars should accept any value without validation, since we can't reason about their shape. Oh and there's a subtle bit I care about, actually: explicitly passing null for a nullable argument versus just omitting the argument entirely aren't the same thing. The explicit null should show up in the output as null, while the omitted one should be absent altogether. Getting all this caught at build time gives me actionable feedback before the schema goes live.
