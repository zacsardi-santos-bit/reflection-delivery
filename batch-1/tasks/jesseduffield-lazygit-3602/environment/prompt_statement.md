I'm poking at the "find base commit for fixup" feature in lazygit and hit a real gap. Right now it only figures out the base commit when my diff has deleted lines, it uses those deletions to trace which earlier commit the changes belong to. But if my changes are purely additive, like inserting a new line or dropping a comment into code I added in an earlier commit, the feature just bails instead of trying to find the right base. That's super common, so I want it to handle the case where the whole diff is only added lines. In that scenario it should look at the lines surrounding each insertion point and figure out which commit that surrounding context came from, and use that as the base commit.

There's also a parsing bug I keep hitting. When a hunk has both deleted and added lines, it should count as a deletion hunk and only the deleted line count should matter, but right now it's getting misclassified as addition-only, which throws off how the feature picks its strategy. So the diff parsing logic needs to cleanly split hunks into two buckets, ones that contain deleted lines (doesn't matter if they also have additions), and ones that are only additions. That split is what drives which strategy runs to find the base commit.

Couple of other behaviors I want to hold onto while doing this. If there are no staged or unstaged changes at all, it should still surface an appropriate error rather than doing something weird. And when changes actually trace back to multiple different base commits mixed together, it should report that multiple base commits were found and prompt me to stage a subset of the changes. The payoff is the feature stops forcing me to manually dig through commit history for these everyday additive edits.
