I'm cleaning up how the Opentrons desktop app lets people change the Python interpreter path in settings and it's kind of a mess right now. When someone hits "Add override path" the UI leans on a hidden file input element stuffed into the settings page, and clicking that button programmatically clicks the hidden input so the browser pops a file dialog, then we compute the directory from whatever file got picked. It's fragile, browser-dependent, and needs a workaround to set those non-standard directory-selection attributes React won't set natively. I want to rip that out and use a proper shell-level native directory picker so the app-shell owns the dialog directly, no hidden input at all.

While I'm in here, the two actions for Python interpreter management shouldn't be sitting in the general config module, they're really about protocol analysis so the coupling is annoying. One action triggers opening the currently configured Python interpreter directory in the OS file explorer, the other triggers the directory picker for changing the override path. Both should move into a new dedicated protocol-analysis module that works from both sides, the UI layer dispatches them and the app-shell layer handles them.

On the shell side I need a handler registered at startup alongside the other shell handlers, it should take the main browser window as an argument and return an action handler responding to these two new actions. For the change-path action it opens the native directory picker and only if the user actually picks a directory does it dispatch a config update with the chosen path (bail quietly otherwise). For the open-directory action it opens the current configured path in the OS file explorer. Oh and the shell's dialogs module should expose a utility for opening a directory path in the file explorer so the handler can reuse it. Basically native dialogs everywhere and better separation of concerns.
