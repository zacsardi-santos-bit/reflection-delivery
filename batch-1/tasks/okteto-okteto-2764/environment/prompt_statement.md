I'm hitting a sync problem with the deploy command. When a deployment dies in the build phase, say the Dockerfile is missing or invalid, the pipeline state living in the cluster never gets flipped to reflect that failure. The configmap that tracks pipeline status just sits at whatever it was before, so our dashboards and CI/CD integrations that watch that configmap keep seeing the last known status instead of the actual error. The error does bubble back to the caller, but the cluster-side state is totally out of sync, which makes diagnosing failures or triggering automated recovery a pain.

What I want is for the deploy flow to actually update the pipeline configmap to an "error" status whenever a build step fails, and do that before the error propagates out. Also the build error message should get written to the log output buffer so users and integrations can actually see what went wrong.

Oh and when the deploy command kicks off, it should create a configmap to track pipeline progress in the first place, populated with all the deployment metadata (name, namespace, repository, branch, filename, icon, and the manifest content). I'd like a standalone helper for building that initial configmap straight from the pipeline data, encoding the manifest content and filling in the standard fields like name, namespace, branch, icon, repository, status, and output.

One more thing, when a Dockerfile is invalid or missing the build should produce a consistent, clearly identifiable error message that shows up in that log output buffer, so it's not some random varying string each time. Operators lean on this configmap to know what's really happening, so getting the error state written correctly is the whole point here.
