I'm extending the health probe port validation in kube-linter and there are two gaps I keep running into. Right now the liveness probe check only validates HTTP and TCP socket probes against the container's exposed ports, so the newer gRPC-based health probe type slips through completely. If a container declares a gRPC health check against a port number that isn't in its exposed ports list, nothing flags it, and I want that caught for liveness probes just like the HTTP and TCP socket cases already are.

The gRPC diagnostic should match the style of the existing HTTP and TCP socket messages but reference the port by its integer number and clearly call out that it's a gRPC-based probe in the message text.

Second thing, readiness probes and startup probes aren't checked for port validity at all right now, so a misconfigured readiness or startup probe pointing at an unexposed port goes undetected. I want new lint checks for those two probe lifecycle types, analogous to the existing liveness one, applying the same logic: flag any probe (HTTP, TCP socket, or gRPC) that references a port not exposed by the container. Oh and containers with no probe configured, or with an exec-style command-execution action, should be left alone, no warning there.

Why this matters: misconfigured health probes can make Kubernetes never mark a pod ready or fail liveness checks unexpectedly, and catching these port mismatches at lint time before deployment helps folks spot the problem early. Covering all three probe lifecycle types (liveness, readiness, startup) plus the gRPC mechanism closes the gap in the current validation.
