I'm hitting a wall with the Terraform Azure provider around Data Factory pipelines that use web activities with expression-typed HTTP headers. In the Azure Data Factory API a header value can be either a plain string or a structured expression object (something like a value plus a type, which is how you do dynamic headers), but the SDK pipelines client the provider leans on only understands one of those shapes. So whenever a pipeline has a header written with expression syntax (a JSON object instead of a plain string), Terraform blows up trying to read the pipeline back after creating it, and the provider can't deserialize the API response. This basically means create/read/update/import all break for that whole class of pipelines, and expressions are a core Data Factory feature people use for dynamic pipelines, so it's blocking real production infra-as-code work.

What I want is a compatibility layer inside the datafactory service package that wraps the existing SDK pipelines client and swaps in custom types for the pipeline resource and its activities. It needs to expose the same interface as the existing client so it drops in cleanly for reading and writing pipelines, but the custom pipeline activity model should treat web activity headers as a flexible type that can hold either a string or a structured object. Put it in a new sub-package under the datafactory service directory (somewhere like `@internal/services/datafactory/`) so both the pipeline resource implementation and its test code can import it, oh and the existing test infra that checks a pipeline exists in Azure already expects to use this wrapper. Bottom line, pipelines with mixed header value types should round-trip: what I apply should read back cleanly without errors.
