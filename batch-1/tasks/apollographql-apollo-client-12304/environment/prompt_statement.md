I'm hitting a frustrating ambiguity with the Apollo Client cache. When I read data that's absent or only partially there, the cache hands me back an empty object instead of something that clearly says "there's no data here." I literally can't tell whether I got a successful empty result or the cache just had nothing to give me, which makes writing reliable checks in my code basically impossible.

A few related things I want fixed. When a cache read results in no data (all fields missing, or the root object doesn't even exist), I want a clear absence indicator rather than an empty object. Right now in some missing-field scenarios the cache actually throws instead of returning a structured result, so I'm stuck wrapping normal "data not ready yet" cases in try/catch, which is silly. I want those reads to stop throwing and instead return a properly structured incomplete result that says it's incomplete and describes what's missing. Also, when the cache does report missing fields, the error info comes back as an array even when there's really just one logical missing-field error, so I'd like that surfaced as a single structured error object instead of an array wrapping one thing.

Oh and for observable queries that have no complete cache data, the emitted results should reflect this too with a data value that unambiguously means "nothing available" rather than an empty object. Btw it'd also help if the class representing a missing-field error were directly importable from the cache package's main entry point, so I can reference the type without digging into internals.

The whole point is predictability: returning an empty object for "no data" creates confusing ambiguity for callers, and throwing for missing fields forces try/catch on what should just be a normal incomplete-cache path. A clear no-data indicator plus a single structured error object makes this way easier to integrate with my app's data handling.
