I'm digging into the Gleam compiler's error reporting and the big annoyance is that the type checker bails out of a module the moment it hits certain errors, so I only ever see the first problem per compile. Stuff like a function with no body/implementation, a body that doesn't match its return type annotation, a general annotation mismatch, an invalid external declaration, or a function that isn't supported on the current compilation target, all of those halt analysis of the rest of the module. Same deal for type definitions, e.g. a type with duplicate type parameters just stops everything after it.

What I want is fault tolerance during analysis so the compiler keeps going through the whole module and reports every error it finds in one pass. Two important bits beyond just collecting errors: when a function has errors in its body but still has type annotations, those annotations should still get registered so the rest of the module can type-check against it, meaning callers get real type errors instead of confusing "function not found" messages. And when a function has no support for the current target, the analyzer should still know about it so call sites produce a proper "unsupported target" error rather than pretending it's undefined.

The type-definition case should behave the same way, a duplicate type parameter reports its error but subsequent type definitions still get checked. This matters a lot in bigger modules where one structural issue early on can otherwise hide a dozen real problems, and iterating fix-recompile-repeat is miserable. So basically continue analyzing after these errors, keep annotated-but-broken functions usable for downstream type-checking, and surface all the diagnostics together.
