I'm poking at the TaskRun reconciler in Tekton Pipelines and the way it ties a pod to its parent TaskRun feels way too fragile. Right now it stashes the pod's name in the TaskRun status and then later does a direct name lookup to find the pod again, so if that name field is missing or drifts out of sync the reconciler just can't find or manage the pod at all. I want to switch to a label-based approach instead.

So every pod we create for a TaskRun should get tagged with the TaskRun's name using the standard Tekton label key for TaskRun ownership, and the reconciler should discover the pod by listing pods with that label selector rather than fetching by the stored name. That's more resilient and it lines up with normal Kubernetes ownership conventions.

Also the cancel path is broken, it only updates the TaskRun's condition and leaves the running pod orphaned. When a TaskRun is cancelled I want the reconciler to set the failure/cancelled condition and actually delete the associated pod found via that label query. If there's no pod yet for the cancelled run, still set the cancelled condition and return without error. But if the pod list operation itself fails, surface that error out of the reconciler.

Oh and there's a related thing with the metrics recorder. When it hasn't been initialized properly its recording methods currently just silently no-op, which hides bugs. Give the struct a boolean field tracking initialization state and have all three recording methods check it and return an error when it's not initialized.
