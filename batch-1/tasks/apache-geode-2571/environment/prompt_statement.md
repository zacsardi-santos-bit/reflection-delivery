I'm cleaning up the distributed transaction commit handling in Apache Geode because two behaviors in the recovery flow are basically impossible to unit test right now, they're buried inside large monolithic methods with tons of side effects and external deps that need a live cluster to exercise. I want to pull them apart into individually overridable methods so I can verify each case without spinning up an actual distributed system.

First one is the logic that tracks whether a transaction is currently being processed by a remote member. I need to check that condition on its own, including the case where there's no message at all (null input should be handled gracefully). Related to that, the lookup for a transaction's commit status should be cleanly separated so I can tell apart the three outcomes: the transaction is currently in progress, or it was found in the recovery history, or neither of those. Each of those cases needs clear testable logic.

Second, there's the behavior that fires when the originating cluster member departs and the transaction hasn't been acknowledged yet. Right now creating and sending a commit-process query to the remaining members and then waiting for replies is all entangled with infrastructure that requires a running cluster. I want that broken into steps I can each override and verify in isolation: creating the reply processor, creating the query message, actually sending it, and waiting for the replies. So the departure recovery path should create and send the query, then wait, and I should be able to stub any one of those pieces.

The reason this matters is that without unit coverage, regressions in the transaction recovery path (think a node crashing mid-transaction) could slip through and only show up in production under failure scenarios. Refactor the relevant classes so these behaviors live as small overridable methods with clear logic per case. Keep the existing external behavior intact, just make it testable.
