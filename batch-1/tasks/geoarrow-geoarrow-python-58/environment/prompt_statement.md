I'm working in this geospatial type library that leans on Arrow metadata to describe geometry types, CRS included, and right now the only way to attach a coordinate reference system is to hand it a full structured PROJJSON object. That's annoying because a lot of the time I just want to reference a well-known CRS by a short authority string and not go construct the whole PROJJSON dictionary. Passing a plain string today either fails silently or gets rejected outright, which isn't great.

What I want is a new CRS type that just wraps a plain string, available in the type system and usable everywhere a full structured CRS is accepted: constructing type specs, calling methods or functions that set the CRS on a geometry type, all of it. And when a raw string gets assigned as a CRS value it should auto-convert into this new string wrapper instead of erroring.

The wrapper should be a little smart about its contents too, so if the string is actually a valid JSON object it's usable directly, if it's an authority code it can delegate to an external CRS library for richer stuff like converting to WKT or full JSON, and a plain quoted JSON string input just gets transparently unwrapped.

There's a serialization gap alongside this. When type metadata serializes to a string there's currently no way to tell whether the CRS field started as a structured JSON object or a plain string, so round-tripping isn't reliable across formats. I want a discriminator field added to the metadata when the CRS is a structured object, so on the way back out parsing restores the same CRS type that went in. Concretely, string-based CRS values without that discriminator should come back as the new string CRS type, and structured values carrying the discriminator should come back as the existing structured type. That keeps metadata round-trips stable and unambiguous, and saves people from writing out a full PROJJSON dict when all they wanted was a short authority code.
