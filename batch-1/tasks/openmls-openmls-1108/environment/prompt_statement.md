I'm working on an MLS protocol implementation and I've found that the validation rule for when a commit requires an update path is incorrect. Currently the check only looks at whether a commit contains Remove or Update proposals, but this misses other proposal types that should also require a path — like group context extension changes. On the flip side, commits that only contain member-add proposals or pre-shared key proposals don't need a path at all, but the current logic doesn't cleanly express this.

I'd like each proposal type to have an explicit way to declare whether it requires a path, and then have the commit validation and commit generation logic use that declaration. The rule should be: a commit requires a path if at least one of its proposals requires a path, or if the commit is empty (an implicit self-update), or if it's an external commit.

To support testing all the proposal type combinations, some internal group functionality also needs to be made accessible within the crate — specifically the ability to manually queue individual proposals and clear queued proposals between test iterations, as well as the ability to serialize and restore group state so the same group can be reused across multiple test cases.
