I'm deep in an MLS implementation and I hit a bug in how we decide whether a commit needs an update path. Right now the check just looks for Remove or Update proposals, but that's too narrow. It misses group context extension proposals, which absolutely need a path for security reasons, and it also doesn't cleanly handle the cases where a path isn't needed at all, like commits that only add members or only inject pre-shared keys. Those currently might get treated as needing a path depending on the combination, which is wrong.

What I want is for each proposal type to explicitly declare whether it requires a path, and then have both the commit validation logic and the commit generation logic lean on that declaration instead of hardcoding proposal types. The actual rule should be: a commit requires a path if and only if at least one of its proposals requires one, or the commit is empty (that's an implicit self-update), or it's an external commit. Concretely, Add and pre-shared key proposals should not require a path, while Update, Remove, and group context extension proposals should. So when a commit only carries no-path proposals, generating it should produce a commit without a path, and receiving such a pathless commit should succeed. But if even one proposal requires a path, receiving that commit without a path needs to be rejected with the appropriate error.

Oh and to actually test all the proposal type combinations I need some internal group functionality opened up within the crate. Specifically I want to be able to manually queue individual proposals and clear the queued proposals between test iterations, plus serialize and restore group state so I can reuse the same group across multiple test cases without rebuilding it each time. This is all about correctness and completeness so we follow the MLS spec for every proposal combination, not just the two we happened to check before.
