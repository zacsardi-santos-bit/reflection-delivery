So I'm hitting a wall with SQL functions that use expression-based defaults for their parameters and how they show up in our GraphQL layer. Picture a function where a param defaults to calling some helper (like one that returns the current user's ID), or where the default is an arithmetic expression rather than a plain literal value. When I expose that through the GraphQL API, it breaks: instead of the parameter showing up as optional, the GraphQL extension can't parse the complex default expression and either marks the param as required or drops the function from the schema entirely. Neither outcome is what I want.

What I'd expect is that any SQL function with a well-formed default expression, however complex, still lands in the GraphQL schema. In introspection, those params should appear in the field's argument list but with a null default value, since the expression isn't a static literal you can represent as a GraphQL default. And the function needs to be callable both ways: with an explicit argument value (returning the right result), and without supplying the optional argument at all, in which case the database itself evaluates the original default expression and applies it.

This matters because developers lean on this pattern all the time, defaulting a param to a helper function call or some computed value, and right now those functions are just broken in the API since the param gets treated like it has no default, making it unusable or wrongly typed. I want the whole flow working: schema exposure, correct null-default introspection, and callability with and without the arg for both the function-call and arithmetic-expression default cases.
