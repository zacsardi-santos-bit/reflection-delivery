I'm hitting an annoying inconsistency in the Python formatter around how it handles return type annotations, specifically the long generic subscript kind like parameterized container types. Right now if a function has parameters and a long return type, it does the right thing, opens the bracket on the same line, drops the elements onto the next line, and doesn't slap extra outer parentheses around the whole thing. But take that exact same function and remove all the parameters, and suddenly it wraps the entire return type in extra outer parens when it doesn't fit. That divergence bugs me because it doesn't match what the reference formatter produces, and it creates pointless churn when you're refactoring and adding or removing params, plus the extra parens are just visual noise.

What I want is for functions with parameters to never get those extra outer parentheses around a subscript return type, they should just expand the brackets inline, and this needs to hold in both the current stable mode and in a new preview mode. For functions without parameters, keep the existing stable behavior where it parenthesizes the return type when it doesn't fit on one line, but under the new preview mode make them behave exactly like the ones with parameters, expanding the subscript inline with no extra wrapping. Also, list literals used as a return type annotation shouldn't get that tightly-grouped hugging bracket style that we normally apply to collection arguments inside function calls, that's the wrong context for it. And for the trailing-comma subscript return type cases on no-parameter functions, the output should match the reference formatter without adding unnecessary outer parentheses.

Oh and it'd help to add dedicated test fixtures that document the expected behavior clearly, split out separately for functions with parameters versus functions without parameters, so the difference is obvious.
