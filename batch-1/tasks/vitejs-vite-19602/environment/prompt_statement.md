I'm cleaning up how our Vite plugin hooks deal with filtering and want your help wiring in a built-in filter option. Right now every plugin's resolveId, load, and transform handler fires for every single module Vite touches, so each plugin author ends up writing the same boilerplate at the top of their handler to check the extension, bail on virtual modules, whatever. It's repetitive, easy to get wrong, and wastes work when the handler would immediately return for files it doesn't care about.

What I want is a declarative filter you can attach when defining the hook so Vite just skips calling the handler for non-matching modules, acting as a guard before it runs. For the resolve and load hooks I need a file-ID filter, and for transform I need both a file-ID filter and a code-content filter that matches against the raw source string. The ID filter should accept glob strings, regular expressions, or arrays of either, plus explicit include and exclude lists where exclude wins over include. Glob patterns should match against paths relative to the project root, should handle absolute paths correctly (an absolute path still matchable by a relative glob), and should never match virtual module IDs, the ones prefixed with a null byte.

The interaction between the two transform filters matters: if the ID filter gives a definite answer, that's final, so an explicit include means the handler runs no matter the code content, and an explicit exclude means it's skipped no matter what. Only when the ID filter is undecided (the file wasn't hit by any include or exclude pattern) do we fall back to consulting the code filter. Oh and all of this needs to behave identically in the dev server and the production build pipeline, no divergence.

Basically I want the declarative filter on the hook definition so plugins stop reinventing this, it's cleaner and lets Vite skip the handler call entirely.
