I'm hitting a wall with this SQL parser library when it comes to PostgreSQL-style ALTER USER statements that set a password. Right now if I try to parse something like altering a user and giving them a password as a string literal, it just fails, and same story if I set the password to null to clear it out, or if I mark it as encrypted. These are all totally standard PG user management patterns and without them I can't do round-trip parsing of credential SQL, which is kind of the whole point for the tooling I'm building.

So here's what I want. Setting a user's password to a literal string should parse cleanly and round-trip back to the exact same output. Setting an encrypted password to a string literal should parse and keep the encrypted marker in the output so it doesn't get lost. Setting the password to null (the clear-it-out form) should parse and round-trip back to that null form. And there's an optional leading qualifier keyword you can put before the password clause, btw, so that needs to parse too, but on output I want it normalized away so it comes back as the equivalent statement without that qualifier.

That's four cases basically, all valid SQL in PostgreSQL-compatible systems, so the ALTER USER parsing logic needs to grow support for them and make sure they display/round-trip correctly.
