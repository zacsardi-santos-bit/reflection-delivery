I'm working on the outbound routing layer in linkerd2-proxy and I want to add retry support to HTTP and gRPC route policies. Right now we do per-route timeouts fine, but when a backend returns an error response (a server failure status for HTTP, or a failure code sitting in the response trailers for gRPC) that error goes straight through to the caller, even when a second attempt would've succeeded. A pod restarting, a brief overload, a spurious blip, all of it leaks out to the calling service today, and I'd rather the proxy absorb the short-lived stuff transparently without app-level changes.

So I want route policies to optionally carry a retry config. It needs a max retry count (how many extra attempts after the first failure), a request body buffer size (max bytes of the request body we're willing to buffer so we can replay it), an optional per-attempt timeout, and the retryable conditions, which for HTTP routes is a set of HTTP status code ranges and for gRPC routes is a set of gRPC status codes read out of the response trailers. This config has to live in the client-policy types for both the HTTP and gRPC route flavors so the outbound stack can read it when it builds the service for a given route.

The tricky part is how this plays with the existing timeouts. When a request fails in a retryable way and attempts remain, re-issue it transparently. When the retries are exhausted, hand back the final response even if it's still an error. A per-attempt deadline should fire retries while attempts remain, but once they're exhausted that per-attempt deadline needs to get dropped so the final attempt doesn't get cut short unnecessarily. And if there's also a route-level overall request timeout active, it still applies, so if the retry budget's spent and that overall deadline has been reached, the caller should get a deadline-exceeded error rather than a normal response.
