I'm hitting a gap with external etcd clusters that bootstrap on Ubuntu via cloud-init. Right now when we set up the etcd bootstrapping tool we hand it a version number but never tell it where to grab the actual etcd binary, so if that binary isn't already cached on the node the whole bootstrap can fall over since it has to go find the binary itself. I want us to pass an explicit download URL as part of the node bootstrap config, pulled from the distribution release metadata we already keep in the version bundle.

So first the internal struct that tracks Kubernetes distribution info needs a new field for the etcd binary download URL, populated from the existing release metadata assets. Then the function that configures Ubuntu-based etcd clusters should stop taking just a version string and instead take the full version bundle plus the current cluster version, so it can decide whether to include the download URL at all.

The catch is the URL should only get set for cluster versions at or above a specific release threshold, otherwise older clusters get an unexpected config change that triggers rolling etcd restarts during an upgrade, which we don't want. Below the threshold, no URL. At or above, use the URL from the version bundle. Oh and the dev/unreleased build version should count as eligible too. I'd like a helper utility to encapsulate this logic: given a cluster version string and a version bundle, it returns the right URL or an empty string, and it should return a clear descriptive error when the version string isn't a valid semver. Also please add a test helper that returns a version value representing the dev build so we can wire up test cluster specs that exercise the URL-including paths. Explicitly providing the URL makes bootstrapping self-contained, which matters a lot in air-gapped or controlled network setups where a default location or cache isn't guaranteed.
