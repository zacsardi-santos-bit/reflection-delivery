I'm adding musl-based container support (think Alpine Linux) to our instrumentation naming logic in the common package. Right now nothing in Odigos can tell apart containers that link against glibc versus musl, and that's a real problem for .NET apps on Alpine images because the glibc and musl instrumentation libraries are fundamentally different and incompatible, so a glibc-linked native library just won't work on musl. When a .NET workload runs in an Alpine container we want to detect the C library variant and hand it a separate, musl-specific instrumentation resource, otherwise there's no way to instrument it correctly.

So I want a C library type concept in the common package with at least a glibc and a musl variant. Then the functions that build instrumentation plugin names and device names need to optionally take that C library type. When it's not provided, or when it's glibc, the generated names should stay byte-for-byte identical to what they produce today (don't touch the common case). But when musl is indicated, both the plugin name and the device name should get a distinguishing prefix so they're treated as distinct resources from the glibc ones.

Oh and the reverse path matters too. The function that parses a device name back into its language and SDK components has to handle these musl-prefixed names and correctly recover the original language and SDK, the prefix shouldn't leak into the returned values. Basically parsing a musl-prefixed device name should give back the same language and SDK as the unprefixed one would.
