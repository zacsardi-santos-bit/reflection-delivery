I'm hitting a bug in the lint rule that rewrites old-style type alias declarations (the `TypeAlias`-annotated assignment form) into the modern `type X = ...` syntax. The auto-fix is great, but it silently eats inline comments and still marks itself safe, which is corrupting source. Say I've got a comment on the same line as the declaration or tucked inside the declaration body, after the fix runs that comment just vanishes with zero warning. People put those comments there to document constraints or workarounds, so losing them quietly is a real correctness problem and folks won't notice until they're staring at a diff way later.

What I want is for the fix to actually respect where the comment lives. If there's a comment somewhere in the declaration that lands in a range the fix removes, then don't apply it silently, mark the fix as unsafe so it needs explicit approval. But if the comment is only inside the type value expression itself, the part that gets carried over verbatim into the new syntax, then keep the fix safe and preserve that comment as-is in the output since we're emitting that chunk anyway. And a trailing comment that comes after the end of the statement (same line as the closing bit, outside the replaced range) should just survive naturally and shouldn't flip the safety classification at all.

So basically three cases: comment in a to-be-deleted spot makes it unsafe, comment inside the preserved value stays and keeps it safe, trailing comment untouched and stays safe. Right now it does none of that, it drops the comment and calls itself safe. This lives in the type-alias-rewrite rule in the linter's rules crate, so check how it computes the fix range and comment ranges there, and add coverage for each of the three scenarios.
