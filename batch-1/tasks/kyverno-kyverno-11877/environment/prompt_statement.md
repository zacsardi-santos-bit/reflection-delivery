I'm hitting an annoying inconsistency in our policy validation. When someone submits a policy whose name blows past the 63-byte limit, the validation error we return uses old phrasing for the length constraint that doesn't line up with what the Kubernetes validation library uses these days. Upstream standardized the wording for "field too long" style violations and our message is stale, so any operators or tooling parsing these errors see the wrong language.

I want to update the validation logic so name-too-long errors use the current standardized Kubernetes detail phrase for length constraint violations. This needs to cover every policy type we support, so both regular policies (Policy, ClusterPolicy) and cleanup policies (CleanupPolicy, ClusterCleanupPolicy), and it's gotta be consistent across all API versions we ship, meaning v1, v2, and v2beta1.

For the full formatted error string on top-level policy resources, it should combine the name field path with a "Too long" prefix plus the standardized detail phrase. For cleanup policy resources the format should be the same idea except using the metadata name field path instead of the plain name path. Same standardized wording everywhere, just the field path differs between the two resource shapes.

Basically just swap in the new upstream phrasing wherever we emit that length error so everything stays aligned with the Kubernetes conventions and stops looking outdated.
