I hit a nasty XSS in SvelteKit's SSR path and I want to squash it. When a page fetches data in its load phase and that data contains strings with closing script tags (think user-supplied content or untrusted API responses), the framework embeds the raw fetched data straight into the inline scripts of the rendered HTML. So if some API returns a name field that contains something looking like the end of a script block followed by the start of a new one, the browser happily parses it as real HTML and any injected script actually runs. Not great.

Concretely, if an endpoint hands back a value with a script-tag sequence in it, navigating to that page should just show the string as literal visible text, angle brackets and slashes and all, not execute it. The no-JS pure SSR case makes it super obvious: a variable that should never get set ends up set because the serialized inline data breaks out of its containing script block before the client even boots.

What I want is for the framework to properly escape data fetched during server-side rendering before embedding it into the server-rendered HTML, so special characters like `<`, `>` and `/` in the embedded data can't be interpreted as HTML tag boundaries. This needs to cover all data fetched during the SSR phase regardless of content type, since anything that displays user-controlled or third-party API data on a server-rendered page is at risk (session hijacking, data theft, the usual). The serialization that inlines fetched responses lives in the SSR rendering path, so that's where the encoding needs to happen. Basically embedded data must never cause an injected script to execute, and the raw string should render as plain text every time.
