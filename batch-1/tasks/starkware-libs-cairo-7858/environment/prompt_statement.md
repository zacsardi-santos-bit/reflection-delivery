I've been poking at how our semantic layer figures out the type of code blocks, and I'm pretty sure there's a bug in how it handles blocks that always diverge and never actually produce a value. When a block ends with a statement that guarantees control never reaches the end, like a loop continuation statement or a call to a function that's typed as never-returning, the block itself should come out as the "never" type. Right now these are getting typed as the unit type instead, which is just wrong and it's causing downstream type inference to go sideways.

Concretely I want three things fixed in the block type inference logic. A block whose last meaningful statement is a loop continuation (think inside a loop body) should be "never". A block ending with an expression that is itself typed as "never", like a call to a never-returning function, should also be "never". And item declarations (constant definitions and the like) that show up after a diverging statement should be ignored when computing the block's type, so a diverging statement followed by trailing items still resolves to "never" instead of letting those items drag it back to unit.

Blocks that contain only items, or that are empty, should keep the unit type, don't change those. The whole point here is that when control flow is guaranteed to diverge the compiler needs to reflect that in the block's type, otherwise the type checking and analysis built on top of it can't reason correctly about the code.
