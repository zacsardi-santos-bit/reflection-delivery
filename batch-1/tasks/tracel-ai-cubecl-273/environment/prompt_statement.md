I'm hacking on the batch matmul side of a GPU linear algebra library and I keep hitting a wall with how rigid the grid-to-matrix mapping is. Right now the two batch-level matmul types over in the batch module each take a fixed set of generic params and they always assume the launch grid's cube position maps the same way: x is rows, y is columns, z is batches. Works fine for the common case but I can't express a transposed layout (x and y swapped) or a swizzled traversal that reorders tiles for better cache reuse, which is exactly what I need for workloads where there are few output tiles along rows but tons along columns, or on hardware where memory access patterns favor a non-linear order.

So what I want is a pluggable dispatch abstraction living in the batch module that controls how the grid's x, y, z positions get translated into matrix row, column, and batch indices. I need at least four concrete variants: a natural (default) mapping that keeps x=rows/y=cols/z=batch, a transposed one that swaps x and y, and two swizzled ones each parameterized by a swizzle width constant, one that prioritizes the x-axis and one that prioritizes the y-axis. All four have to give numerically correct matmul results, that's non-negotiable.

The two batch matmul types need to grow a new generic type parameter for this dispatch strategy. And it's important that nothing existing breaks, so all the current call sites should keep working by just passing the natural dispatch explicitly. Oh and export the new dispatch types publicly from the batch module right alongside the existing span types so folks can actually reach them.
