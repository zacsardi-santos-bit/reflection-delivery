I'm on the AI Gateway project and the config has this annoying naming inconsistency for API schema fields that I want to clean up. Right now when I specify the client-facing API schema on a gateway route resource, the top-level field is called one thing (like "inputSchema"), and when I specify a backend's API schema on a backend resource it's a totally different top-level name (like "outputSchema"), even though both are the exact same concept, just pointing at which API schema to use. And inside both of those the identifier sub-field is called "schema" which feels redundant and asymmetric next to the containing field.

I want to unify all of this so everywhere an API schema spec shows up, whether it's the gateway route, the backend, or the YAML filter config the external processor consumes, it always uses the same names. The containing object should always be "schema" and the identifier within it should always be "name". So no more inputSchema/outputSchema split and no more "schema.schema" weirdness.

This needs to land consistently across the Go types for both the filter configuration and the Kubernetes API types, the YAML configuration format, and the Kubernetes CRDs including their validation rules and OpenAPI validation. Oh and the validation error messages that reference these fields by their path need to reflect the new naming too, so when a schema is invalid or unsupported the error points at the right renamed path.
