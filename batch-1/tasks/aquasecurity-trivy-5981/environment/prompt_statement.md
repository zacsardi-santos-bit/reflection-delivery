I'm poking at Trivy's CycloneDX SBOM output and the tool metadata we're writing into the BOM's metadata section is stale. Right now the code sticks Trivy into a flat tool array (the `metadata.tools` list style), which is what an older CycloneDX spec version wanted, but that structure's been deprecated. The spec moved to representing tools as full software components so you get richer metadata, and that's what modern consumers and validators actually expect these days.

So what I want is to swap the legacy tool array for the current component-based structure whenever Trivy generates a CycloneDX doc. Trivy should show up as an application-type component, with its vendor going into the group field and its name and version carried as component attributes (so type application, group for the vendor, plus name and version). This needs to apply everywhere, container image scans, filesystem scans, aggregated results, all of it, consistently, not just one code path.

Oh and one more thing, backward compat matters here. There are CycloneDX SBOMs floating around that Trivy produced earlier using the old tool array format, and I still want Trivy to recognize those as Trivy-produced SBOMs when it reads them back in. So the detection logic on the parse/read side has to accept both the new component form and the legacy array form.

The reason this matters is our current output just doesn't conform to the current CycloneDX spec, which trips up tools and validators built around the newer format. Fixing it keeps our generated SBOMs playing nice with the rest of the ecosystem.
