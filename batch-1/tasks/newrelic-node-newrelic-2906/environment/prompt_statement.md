I'm working on the New Relic Node.js agent and I need to build a bridge that captures spans created through the OpenTelemetry tracing API and turns them into New Relic transaction segments. Right now if application code uses the OpenTelemetry API to make spans, those spans are totally invisible to us, they don't show up in transaction traces and we generate zero metrics off them, which is a real gap for teams that instrument their services with OpenTelemetry libraries and expect to see that work reflected in the New Relic UI without redoing instrumentation.

So the whole bridge needs to be gated behind a new feature flag so teams can opt in when they're ready. When the flag's off, skip initialization entirely and log a clear warning explaining why we bailed. When it's on, any span started via the OpenTelemetry tracer should get automatically translated into a New Relic segment, preserving the span name, the parent-child hierarchy, and the timing/duration. Internal spans should produce custom metrics under the transaction, and for the internal custom segment naming just use the span name directly, don't tack on any prefix. Outbound HTTP spans should generate proper external call metrics following the standard naming conventions (by host and method, etc).

Oh and it also needs to hook into the OpenTelemetry context propagation system, so when context values tagged with New Relic synthesis metadata get propagated, the context manager correctly picks up the active transaction and segment state. The context object should let you get, set, and delete values, and should expose the active transaction and the active segment as properties. Also, successful setup of the bridge should be tracked with a supportability metric so we can actually measure adoption.
