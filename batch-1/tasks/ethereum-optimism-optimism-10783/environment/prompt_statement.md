I'm refactoring the rollup node driver in the Optimism monorepo to use a small event-driven architecture. Right now, step scheduling and backoff logic live directly in a big event loop and are impossible to test in isolation. I'd like to extract them into focused, composable pieces.

Specifically, I need a broadcast dispatcher type in the core rollup package that holds a list of event handlers and forwards each incoming event to all of them in order — an empty list should be safe to use. I also need lightweight function adapters so a plain function can satisfy either the "handler" or the "emitter" interface without boilerplate.

For the driver package, I need a synchronous event queue: you emit events into it and later drain it, which processes them one by one in FIFO order. If a handler emits more events during a drain, those should be appended and processed in the same drain call. If the owning context is cancelled, draining should return the context error and stop immediately. There should be a package-level safety cap constant that drops events once the queue reaches that size.

I also need a step-scheduling component that separates "a step has been requested" from "it is time to actually attempt the step." It should expose two channels — one for immediate steps and one for delayed steps — that the driver's select loop can wait on. After each step attempt the component should count the attempt and route future requests to the delayed channel (with exponential backoff). A request carrying a reset flag, or a standalone backoff-reset event, should clear the counter and allow the next request to go to the immediate channel again.
