I'm refactoring the rollup node driver in the Optimism monorepo toward a small event-driven setup because right now step scheduling, backoff tracking, and pipeline advancement all live in one monolithic loop that's impossible to unit test in isolation, and every new handler means editing the central loop. I want to pull these into focused, composable pieces.

First, in the core rollup package I need a broadcast dispatcher that holds a list of event handlers and forwards each incoming event to all of them in order, and an empty handler list has to be safe to use without panicking. Alongside that I want lightweight function adapter types so a plain function can satisfy either the handler interface or the emitter interface without me having to define a named type for the boilerplate.

For the driver package I need a synchronous event queue where I emit events in and later drain them, processing one by one in FIFO order. If a handler emits more events mid-drain (recursive or cyclic events) those get appended and processed in the same drain call. If the owning context is cancelled, draining should stop immediately and return the context error. There should also be a package-level safety cap constant so once the queue hits that size, extra events are just dropped instead of growing without bound.

Last thing, I want a step-scheduling component that separates "a step got requested" from "it's actually time to attempt the step." It should expose two channels, one for immediate steps and one for delayed (backoff) steps, so the driver's select loop can just wait on both. After each step attempt it counts the attempt and routes future requests to the delayed channel with exponential backoff. A request carrying a reset flag inline, or a standalone backoff-reset event, should clear the counter so the next request can go back to the immediate channel again.
