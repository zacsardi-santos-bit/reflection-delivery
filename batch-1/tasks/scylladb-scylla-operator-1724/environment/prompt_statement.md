I'm reworking the node tuning controller in the Scylla operator and the way it figures out CPU pinning is driving me nuts. Right now to set up IRQ affinity it needs to know which CPUs are assigned to Scylla containers so it can hand the rest over to interrupt handling, and it gets that by querying the container runtime interface directly, then falling back to reading cgroup filesystem paths when the runtime doesn't cough up the info. That fallback is the fragile part, it's got separate path patterns for EKS, GKE, Minikube and so on, which is messy and breaks differently depending on which runtime you're on.

I want to rip all that out and go through the kubelet pod resources API instead, since it exposes CPU assignments for every pod the same way no matter the container runtime or cloud environment. So the function that computes the IRQ CPUs should take a client for the pod resources API rather than the container runtime client, and it shouldn't need the cgroup mount path parameter anymore at all. The CPU lookup should work by matching on pod name and namespace, then digging into that pod to find the Scylla container and pull its CPU IDs from there.

The actual IRQ logic stays the same, it's the host's full CPU set minus the CPUs assigned to Guaranteed QoS Scylla pods, and Burstable pods should still get skipped and left out of the pinned CPU calculation. Oh and I need a new client interface plus an implementation for talking to the kubelet pod resources API, and the old cgroup fallback plus all the platform-specific directory patterns should just be gone.
