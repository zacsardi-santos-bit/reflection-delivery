I'm adding TLS support to Fission's HTTP trigger ingress config and right now it's just missing entirely. When I create or update a route with ingress enabled there's no way to point at a TLS secret, so everything comes out as plain HTTP and I end up manually patching the Kubernetes ingress object whenever I want HTTPS, which is error-prone and totally out of step with how the rest of the ingress management works.

What I want is to pass the name of a Kubernetes Secret (the one holding the TLS cert and key) when I create or update a route, and have the resulting Kubernetes ingress get built with a TLS section that references that secret plus the ingress host. On update I should be able to swap in a different secret too. Oh and I need a way to strip TLS off an existing route, so passing a designated single-character sentinel value should signal removal. And importantly, if I don't pass any TLS option during an update, whatever TLS config already exists should just be left alone, preserved as-is.

This touches a few layers. The ingress configuration logic needs updating to handle the create/update/remove/preserve cases, and the code that generates the Kubernetes ingress spec has to actually emit the TLS block referencing the secret and host. Also the data model that represents an ingress configuration needs a new field to hold the TLS secret name, since there's nowhere to stash it today. The point of all this is so operators can manage HTTPS termination for their serverless routes through the normal CLI workflow instead of maintaining ingress TLS out-of-band, which is a pain and makes the full lifecycle of secure routes harder to keep consistent.
