I'm poking around the SpiceDB codebase and want to clean up two internal data structures that are bugging me.

First thing, there's this general-purpose set type for tracking object-namespace-relation identifiers sitting in a shared utility package, but honestly it's only ever used by the dev membership subsystem, so it's just an unnecessary cross-package dependency. I want to move it into the internal development membership package and make it a struct-based value type instead of a pointer type. Give it a constructor that takes optional initial elements, and it should do all the usual set stuff: add (which returns whether the element was actually new), membership check, bulk-add from a slice, intersection, subtraction, and union, where union doesn't mutate the original and instead hands back a new set. Oh and conversion to a slice too. Then the membership tracking type in that same package needs to use this local set for its relationships field so it stops importing from the shared package, and once that's done rip out the old implementation and its tests over in the shared utility package.

Second, the permission check dispatch logic in the graph package needs a proper data structure for batching sub-problems. Right now it's awkward to group and chunk check requests before dispatching, especially when some relationships carry caveats (conditional access) and some don't. So I want something that accepts relationship tuples and produces chunks grouped by subject type, split by a configurable chunk size. The important bit: subjects with caveats and subjects without have to land in separate chunks, and each chunk carries a flag saying whether any of its members have caveats, because the checker applies a different evaluation strategy per group and I don't want conditional and unconditional cases getting conflated. It also needs reverse lookups, so given a subject I can get back the list of resources that have a relationship with it, and multiple resources pointing to the same subject must be tracked individually preserving the per-resource-subject caveat.

Both pieces should live in their respective packages with the exact names and signatures the rest of the codebase expects to call.
