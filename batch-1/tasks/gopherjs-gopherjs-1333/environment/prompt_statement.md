I'm hitting build failures trying to get GopherJS working against a newer Go release. The standard library reshuffled its internal elliptic curve crypto packages into a new location, but the GopherJS native overlay files (the ones that replace or supplement stdlib packages when we compile Go to JS) are still pointing at the old internal paths that don't exist anymore, so anything depending on those packages just won't compile.

So I need the native overlay files for the elliptic curve crypto packages moved over to match the current stdlib layout, and the old overlay files at the outdated paths deleted so they don't conflict with the new ones. Once that's done the field arithmetic package should actually compile clean under GopherJS again.

The other thing, some of these tests lean hard on 64-bit arithmetic which is painfully slow when it's emulated under GopherJS. Right now our only escape hatch is skipping the test entirely, which stinks. I'd rather run them with fewer iterations. So I want to add a mechanism to the GopherJS property-based testing support that lets a test override set an upper bound on the max number of iterations, basically a cap, so slow tests still run just with a reduced count instead of being disabled outright.

The point of all this is that folks using GopherJS with a newer Go can't currently compile or test code that touches these internal elliptic curve packages at all, and I don't want to make them either break the build or sit around forever waiting on tests. Fixing the overlay paths plus adding the iteration-cap utility gets both back to working.
