I'm chasing down some correctness bugs in the Babel plugin that compiles explicit resource management syntax, you know the `using` and `await using` declarations, and the compiled output diverges from how native engines handle async disposal in a few annoying ways.

First thing, when an object has an async disposal property that's present but not callable, including the case where it's explicitly set to null (not just absent, and that distinction actually matters here), the compiled code does the wrong thing. Right now it falls back to the synchronous disposal method for the null case, but it should reject instead. Also the error message is off, it currently references some disposal-related property name rather than just telling me the object isn't in a disposable state. So both non-callable and explicit null async dispose should always reject with an error about the object not being disposable.

Second, when I declare multiple `await using` resources all set to null in the same block, the compiled output spins up an unnecessary async delay for each null entry, which throws off microtask timing versus a native impl. Those multiple null async disposals should get collapsed together so the async overhead stays bounded and predictable instead of multiplying per null.

Third, when a sync dispose method gets used as a fallback inside an async disposal context (object has no async dispose), two things break. If that sync method throws synchronously, the error needs to be wrapped and propagated asynchronously, as a rejected promise basically, so other pending microtasks can interleave before any catch block runs. And if that sync method returns a Promise, that return value should just be ignored, not awaited by the disposal machinery.

These matter because Babel-compiled code ends up behaving differently from native implementations of the proposal, so people hit subtle timing bugs and wrong error messages in production. Fixes go in the plugin's compiled async disposal helpers.
