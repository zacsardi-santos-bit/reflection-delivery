I'm building out a JSX accessibility linter and I want to add a new rule that stops people from wiring up interactive event handlers on static HTML elements. The core problem is that stuff like generic containers, inline text-formatting tags, and a bunch of structural or metadata elements carry no semantic meaning for assistive tech. Screen readers won't announce them as clickable and keyboard-only users can't reach or activate them, so if someone slaps a click handler or keyboard handler on one without giving it a real accessibility role, the result is silently inaccessible and nobody catches it today.

So I need a rule that flags any static element (one with no inherent interactive role) that gets a mouse event like click, a keyboard event, or a focus event handler, and the diagnostic should say static elements shouldn't be interactive plus a note suggesting the dev assign an appropriate role value to signal the interactive intent.

It's gotta be smart about what "static" means though. Don't flag natively interactive elements (form controls, buttons, properly linked anchors), don't flag elements hidden from assistive technologies, and don't flag anything that already has an explicit interactive accessibility role. Also non-interactive event types like scroll, media, clipboard, or animation events shouldn't trigger it at all. Custom components with capitalized names should be ignored too since we can't know their a11y semantics. On the flip side, elements with a "presentation" role or any abstract accessibility role still need to be flagged, since those roles don't actually make an element interactive. This mirrors the well-established a11y best practices already floating around the JSX ecosystem, oh and make sure the message is clear enough that a dev immediately knows to add the role.
