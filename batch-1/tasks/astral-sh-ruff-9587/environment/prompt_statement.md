I'm digging into the lint rule in the linter that catches when someone calls a dunder method directly instead of using the operator equivalent, and it's got some real gaps. Right now it silently ignores a call like `x.__neg__()` or whatever if it shows up under a unary operator on the receiver, or inside a lambda body, or in a conditional (ternary) expression, or nested in a container literal like a list, dict, set, or tuple, or inside any kind of comprehension (list/dict/set) or a generator expression, or in a subscript value, a starred expression, or a slice element. I want all those contexts flagged the same way we'd flag an unnecessary dunder call anywhere else, since folks write idiomatic Python in exactly these patterns and get zero guidance today.

Oh and there's a fix bug too. Even for the cases we do detect, the auto-fix sometimes emits code with wrong operator precedence. If the replacement operator expression lands as the right-hand operand of a multiplication, or directly under a negation, the fix has to wrap the result in parens, otherwise applying it silently changes behavior. Same deal when the argument passed to the dunder is itself a compound thing like a binary op, that argument needs parenthesizing in the fix. Also if a dunder gets flagged but has no simple operator equivalent, still report it but don't offer a fix.

All the operator-swap fixes should be marked unsafe since substituting an operator isn't always safe, and I want the parenthesization to always come out semantically equivalent to the original.
