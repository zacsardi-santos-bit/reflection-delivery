I've been working with the lint rule that detects when code directly calls special dunder methods instead of using the equivalent operator. The rule is missing violations in a lot of common scenarios. For instance, if a dunder method call appears under a unary operator like negation, inside a lambda, in a conditional expression, in a container literal like a list, dict, set, or tuple, inside any kind of comprehension or generator expression, or in a subscript, starred, or slice context — the linter doesn't flag it at all. These should all be detected the same way as any other unnecessary dunder call.

There's also a bug with the auto-fix. Even for cases the rule currently detects, the suggested fix sometimes produces code with incorrect operator precedence. If the replacement expression ends up as the right-hand operand of a multiplication, or directly under a negation, the fix needs to wrap the result in parentheses — otherwise applying the fix silently changes the behavior of the program. Similarly, when the argument to the dunder method is itself a compound expression like a binary operation, that argument needs to be parenthesized in the fix.

I'd expect all these contexts to be detected, the fixes to always produce semantically equivalent code with correct parenthesization, and the fixes to be appropriately marked as unsafe since they involve operator substitution that may not be safe in all circumstances.
