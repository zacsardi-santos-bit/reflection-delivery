I'm deep in the OTLP-to-Prometheus remote-write translation layer and hit a gap around histogram aggregation temporality. Right now the histogram conversion functions ignore temporality completely, so they emit the same thing whether the source is cumulative or delta, which silently misrepresents delta histograms in Prometheus (they look like they reset like counters when they shouldn't, and that wrecks query results for anyone monitoring off them). What I want is for delta histograms to come out marked as gauge-type, meaning no counter reset assumed, while cumulative histograms stay marked as unknown-reset counter-type metrics. To make that happen I need temporality threaded through as an explicit parameter into the internal histogram conversion functions so they actually branch on it.

Beyond the output shape, the top-level conversion function needs to validate temporality before converting each metric. Add a new config flag to the conversion settings that controls whether delta-temporality metrics are accepted, since operators running Prometheus as an OTLP ingestion target may want to reject deltas outright (Prometheus is inherently cumulative). When a metric is delta and delta isn't allowed by that setting, skip it and record an error; when temporality is unspecified, reject it as invalid no matter what the setting says. Metric types that don't carry temporality, like summaries and gauges, shouldn't be affected at all, and unsupported types should produce a descriptive error naming the unsupported type.
