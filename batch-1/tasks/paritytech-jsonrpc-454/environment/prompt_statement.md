I'm working with a JSON-RPC library that has a derive macro (the `#[rpc]` attribute) for defining RPC traits, and right now the only thing I can express is methods that return a result. But JSON-RPC 2.0 also defines notifications, the fire-and-forget calls where the server never sends a response back, and there's currently no way to declare a notification handler directly in a trait. That means anyone who wants to handle notifications has to bypass the macro or hack around it, which kind of defeats the point of the ergonomic API the macro is supposed to give you.

What I want is this: a trait method annotated with `#[rpc(name = "...")]` that has no return value (unit return type, so it's `()`) should be picked up by the macro and treated as a notification handler automatically. When a notification comes in (a request without an `id` field) for one of those methods, the server processes it silently and returns nothing at all. But if someone sends a normal method call with an `id` field to that same notification endpoint, treating it like a regular RPC call, the server should reject it with a "Method not found" error, code `-32601`, since notification handlers aren't meant to be callable as regular methods. Oh and these notification methods need to coexist cleanly with pub/sub subscription methods in the same trait, no conflicts between them.

The whole reason this matters is that without it the derive macro doesn't actually cover full JSON-RPC 2.0 semantics, so you can't express the intent of a fire-and-forget handler at the trait level and you're stuck with manual workarounds. Supporting unit-return methods as notifications rounds the library out into a complete solution.
