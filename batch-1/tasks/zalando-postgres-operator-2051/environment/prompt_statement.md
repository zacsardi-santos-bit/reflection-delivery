I'm working on the postgres-operator and hit a wall with the logical backup cronjobs it generates. Right now those backup jobs only get a fixed set of env vars baked in, and there's no way to inject environment variables from an existing Kubernetes secret. So if I need to hand cloud storage credentials or some custom auth token to the backup job, I'm stuck either embedding sensitive values straight into the operator config or doing some ugly workaround, neither of which flies in prod where we care about proper secret management, least-privilege, secret rotation, all that.

What I want is a new operator configuration option that takes the name of a Kubernetes secret. When it's set, every key in that referenced secret should automatically show up as an environment variable in the logical backup cronjob, with each var sourcing its value from the secret (via a secret key reference) rather than the value being embedded directly in the pod spec.

Couple of edge cases that matter. If the option isn't set, behavior stays exactly as it is today, no extra env vars added at all. And if the secret name is set but that secret doesn't actually exist in the cluster, I don't want it silently producing a broken job, I want the operator to fail with a clear, descriptive error instead. So the config plumbing, the cronjob generation logic that appends the env vars, and the existence check all need to hang together.
