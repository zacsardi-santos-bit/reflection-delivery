I'm cleaning up Ray Serve's proxy layer and want a shared abstraction so the HTTP and gRPC proxies stop diverging so much. Right now the ASGI proxy and the gRPC proxy each have their own way of pulling request metadata, figuring out route types, and building the request objects they hand off to replicas, and it makes writing any shared proxy logic painful. Can you add these to the proxy_request_response module (something like `@python/ray/serve/_private/proxy_request_response.py`)?

What I want is a `ProxyRequest` base class that both `ASGIProxyRequest` (for HTTP) and `gRPCProxyRequest` implement, giving consistent access to stuff like the request type (http, websocket, or grpc), the HTTP method or its gRPC equivalent, and the route path used for routing. It also needs to detect the special routes, so `/-/routes` for listing applications and `/-/healthz` for health checks, since both proxies use those. Each subclass should be able to spin up its protocol-specific request object to send to a replica, meaning a `StreamingHTTPRequest` on the ASGI side and a new `gRPCRequest` dataclass on the gRPC side. Oh and the gRPC side specifically needs to extract the application name, request ID, and multiplexed model ID out of the incoming metadata, plus send status codes, details, and request IDs back to the client through the gRPC context.

Also I need a unified `ProxyResponse` class that handles responses across both, covering status codes, unary responses, and streaming responses. Basically one place where response handling lives regardless of protocol.
