I'm running into a nasty bug in the linter rules that sort special Python collections, specifically the one that sorts module-level export lists (`__all__`) and the one that sorts class slot declarations (`__slots__`). When I run the auto-fix on a collection whose original definition has a trailing comma sitting in an unusual spot, the output ends up being invalid Python that won't parse. Concretely, if the trailing comma sits right before the closing bracket on the same line as the last element, or if it's got extra whitespace around it, or if it's parked on its own line (sometimes separated from the surrounding items by blank lines or comments), the fixer spits out two consecutive commas after the last element and breaks parsing.

The root cause looks like the fixer isn't checking whether the text that comes after the sorted items already begins with a comma before it decides to append its own trailing comma, so I want that edge case handled. What I need is for these rules to still correctly detect that the collection is unsorted across all these trailing-comma variants (comma before the bracket on the same line, comma before the bracket with extra whitespace, comma on a separate line surrounded by blank lines and comments, and commas interleaved with comments on their own lines between elements), and then produce a valid auto-fix that sorts the elements without ever introducing that double comma. Basically the fix should always come out parseable no matter which trailing-comma style the original used, since right now it claims to fix the code but leaves it broken.
