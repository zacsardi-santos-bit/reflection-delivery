I'm chasing a false positive in our Tor onion address cert linter. When a cert covers both a version 3 Tor hidden service address and regular DNS names (totally legit, think a company with a public website plus a Tor hidden service), we wrongly flag it as needing the Tor service descriptor hash lint. That descriptor hash validation only applies to the old version 2 Tor address format, so a mixed v3-plus-domains cert shouldn't trip it at all.

The root cause is the code uses "not a version 3 Tor cert" as a stand-in for "requires version 2 validation," which breaks on these mixed certs. Right now there's only a version 3 check and no explicit way to detect version 2 addresses, so I want to add one. Version 2 is the older format recognized by a 16-character base32 label ending in the onion top-level domain. Then update the linting logic that decides whether the descriptor hash is required to do positive version 2 detection instead of inferring it from the absence of version 3.

Also there's a helper that checks whether all names in a list satisfy some condition, and it currently returns false for an empty list. That's wrong, vacuous truth means "all items satisfy" over zero items should be true, so fix that too.

And I need a couple of test certificates: one real cert with both a version 3 onion address and regular domain names (should not trigger the descriptor hash lint), and one with an address that's neither version 2 nor version 3 so I can confirm we still report errors for genuinely invalid onion addresses.
