I'm trying to make Cilium recover on its own when its connection to the Kubernetes API server goes silent. Right now if the API server stops replying, our client connections just hang forever, no detection, no reset, and Cilium ends up unable to get policy updates or node events with no way out. I want a heartbeat function that probes reachability and forcefully closes connections when the server's unreachable so fresh ones can be made.

The logic I'm after: if we heard a successful response from the API server very recently (within some configurable time window) we skip the probe entirely and presume the connection's healthy. If we haven't had a success in that window, send a probe with a bounded timeout. If the probe times out, or if it comes back with an error from the API server, close all existing client connections. If it succeeds within the timeout, leave connections open.

To tell "recently talked and it worked" apart from "tried but failed", I need to extend the metrics package that already tracks the timestamp of the last API interaction. Add a new metric tracking the timestamp of the last successful interaction specifically (a success response like 2xx or 4xx status codes), distinct from the existing any-interaction one. That's what the heartbeat reads to decide whether to bother probing.

Keep the heartbeat decoupled and testable, so it should take the probe logic as a callback, a timeout duration, and one or more callbacks to invoke when connections need closing. It shouldn't know how the probe actually runs or how connections are managed, it just wires those together based on the last-success timestamp and the probe result.
