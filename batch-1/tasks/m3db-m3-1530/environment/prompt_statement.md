We already cache postings list results for regexp and exact term queries in our index storage layer, but there's a third kind of query we're skipping: field-existence queries that just check whether a given field is present in the index at all, no pattern to match against, only a field name. Right now every one of those checks goes straight to the underlying segment even when we've already run the same query, which is wasteful for workloads that keep asking whether some field exists on data that isn't changing.

I want to add a new query pattern type for field queries into the postings list cache, plus get and put methods that work without a pattern component (regexp and term entries key on segment UUID plus field plus pattern, but field-existence entries key on just segment UUID and field name). Then the read-through segment layer needs to consult the cache on the way in for field-existence lookups and populate it on a miss, same as we already do for regexp and term.

Keep the bypass behavior consistent too, so if caching is disabled through the existing options field queries bypass the cache the same way, and everything should still work correctly when no cache is provided at all (degrade gracefully, calls just go straight to the segment). Oh and these field entries need to participate in the normal LRU eviction and segment purge logic exactly like the other cached query types do, so they get evicted and purged right alongside regexp and term entries.
