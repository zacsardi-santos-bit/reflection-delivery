I'm reworking the telemetry system in our node software and want to kill off the background worker thread approach we have now. It's a pain to test, it couples metric delivery straight to a worker thread, and it just doesn't play nice with the rest of the node infrastructure. What I want instead is a proper class-based telemetry manager I can inject as a dependency, something that buffers metrics internally and ships them out through our existing worker pool.

The manager should take a config object, a worker pool, a logger, and a list of default tags when it's constructed. Whether telemetry is on or off comes from that config. When it's disabled, submitting a metric has to be a totally silent no-op, no state changes, no errors, nothing. When it's enabled, valid metrics get added to an internal queue. Oh and if a metric comes in with no fields, reject it with an error since a fieldless metric is invalid. The queue should auto-flush once it hits its max size, and there's also an explicit flush method that sends everything queued through the worker pool to the telemetry API. If the pool throws during a flush and the queue isn't already saturated (at max), keep those points around for a retry and log the error.

Also the metric data structure needs a required measurement identifier field, fixed to a single constant value that represents the data source, alongside the existing name and fields it already has. This new telemetry class should be the one place that owns enabling/disabling collection, queuing, and retry handling. Please put the telemetry class and the updated metric type in their own dedicated files inside the telemetry module (e.g. under `@src/telemetry/`).
