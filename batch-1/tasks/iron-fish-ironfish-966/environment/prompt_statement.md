I'm refactoring the telemetry system in our node software. Right now, metrics are dispatched through a background worker thread which is difficult to test and doesn't integrate well with the rest of the codebase. I'd like to replace it with a proper class-based telemetry manager that I can inject as a dependency.

The new telemetry manager should accept a configuration object, a worker pool, a logger, and a list of default tags at construction time. Whether telemetry is enabled or disabled should be determined from the configuration. When disabled, submitting a metric should be a complete no-op with no side effects. When enabled, metrics should be added to an internal queue. If a metric has no fields, the submission should be rejected with an error. When the queue hits its maximum size, it should automatically flush. There should also be an explicit flush method that sends all queued points through the worker pool. If the pool throws an error during a flush and the queue isn't at its maximum size, the points should be re-queued for a retry and the error should be logged.

The metric data structure also needs a required measurement identifier field that is fixed to a single constant value representing the data source, in addition to the existing name and fields. The telemetry class and updated metric type should live in their own dedicated files within the telemetry module.
