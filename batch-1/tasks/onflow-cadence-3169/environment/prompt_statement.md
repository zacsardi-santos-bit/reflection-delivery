I'm working on the storage migration framework and there are a few rough edges I want to smooth out. Right now every migration visits all storage domains even when it only cares about one or two of them, which wastes time and risks accidental side effects, so I want each value migration implementation to be able to declare which domains it applies to. Let's add a new method on the migration interface where an implementation returns the set of domains it cares about, and the framework should respect that by skipping any domain that doesn't match rather than running the migration and letting it silently do nothing. If a migration doesn't restrict domains at all (returns no restriction), it should keep running everywhere like before, including the inbox domain. Migrations that only touch the public and private path domains shouldn't be forced to scan everything, and declaring domains makes them self-documenting too.

The other annoyance is the single-account API. Migrating one account currently makes you wrap the address in an iterator object even when there's just one address, which is clunky, so I want to be able to pass the address directly. Update the tests to use that cleaner pattern.

Also there's a real bug: published values that contain a certain kind of capability value stored in the inbox domain aren't being processed correctly during migration, sometimes panicking, sometimes silently skipped. Fix it so migration over the inbox domain correctly visits and processes these published capability values with no errors and reports them as successfully migrated. This matters for data integrity on accounts that have published capabilities. Take a look at the framework and its interface to wire all of this up.
