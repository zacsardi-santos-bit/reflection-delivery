I've been cleaning up the notification tests and honestly they're a mess right now. Some of them are skipped outright and others just render the notification component directly instead of going through the real registration and display pipeline, so they don't actually catch regressions in the logic that decides whether a notification shows up at all (auth state, module connectivity, dismissal history, all that).

What I want first is a test utility that registers specific notifications into the test data store. It should take a registry, an optional set of notification configs to register, and a flag controlling whether a default baseline notification gets included alongside whatever I pass in. So basically an overwrite mode where only the provided ones get registered, plus a default mode that layers a baseline set in with the extras. That'd make it way easier to set up realistic scenarios.

Also I need the existing notification configurations exported as a named constant so tests can reference them directly instead of me duplicating the config objects everywhere.

Then the actual test updates: render everything through the standard notification display component with the right area identifier instead of rendering components in isolation. A few specifics I care about. The auth error notification shouldn't appear when the user isn't logged in, even if there are unsatisfied permission scopes. The tag-detection permissions notification should only show when that's the one and only missing permission, and if there's more than one missing permission the general auth error notification shows instead. And the linked-accounts success notification tests (currently skipped) need to be re-enabled and moved onto the pipeline, checking that it appears or gets suppressed correctly based on module status, whether accounts are linked, whether the report has data, dismissal state, and the current view context.

The whole point is getting these visibility conditions exercised through the same code path production users actually hit, so a regression in any of that logic trips a test automatically instead of giving me false confidence.
