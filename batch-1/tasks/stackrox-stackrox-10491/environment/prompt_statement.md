I'm cleaning up the database migration code and as of the 4.5 release we've decided to drop support for upgrading from or restoring backups that came from any database version predating 4.0. Right now the code still tries to handle those ancient paths and honestly it just makes everything more convoluted than it needs to be. What I want is for the system to flat out reject these attempts with a clear message instead of limping along with undefined behavior.

Concretely, when we detect a pre-4.0 database and try to migrate it into the current Postgres-based setup, the relevant migration function should return an error saying upgrades from pre-4.0 releases are no longer supported as of the 4.5 release. Same deal on the restore side, when a restore is attempted from a backup that originated from a pre-4.0 release, it should bail with an error indicating restores from pre-4.0 releases are no longer supported as of the 4.5 release. The wording matters since operators need to immediately understand why the thing failed.

Also the clone manager interface has gotten crufty. The method that decides which database clone to migrate currently carries an extra parameter for the "restore from legacy database" case, and since we're dropping that path entirely I want that flag removed to simplify the API. Callers shouldn't have to pass it anymore.

Oh and one more thing, the various migration helper methods are swallowing failures silently right now, which is a pain when something goes wrong mid-migration. I want those helpers to actually propagate their errors up to callers so we can detect problems instead of guessing. Keeping dead migration code around for scenarios that aren't valid anymore is just asking for bugs, so let's make the behavior predictable.
