I've been digging into how cargo unpacks packages from a registry and I hit two security problems I want fixed in the extraction path. First one is a symlink attack on the lock file. Cargo writes an internal lock file to mark a package as successfully extracted, but if a published crate ships a file whose name matches that lock file and it's actually a symlink pointing at one of the crate's own source files, then cargo's write follows the symlink and silently clobbers the real source file. So I want extraction to skip any tarball entry whose name matches the lock file name, it should never get extracted from the package at all, and cargo should always create that lock file itself from scratch using an exclusive-create open (the kind that fails instead of overwriting or following a pre-existing file). Once a package builds successfully the lock file should contain exactly 2 bytes and the source files should be intact and untouched.

Second thing, there's no cap on how much decompressed data we read when unpacking a compressed registry package, so a crafted or corrupt package could balloon into gigabytes and eat all the disk or memory with no warning. I want a maximum decompressed-size limit enforced during unpack, and if unpacking would go over it the whole thing aborts with a clear structured error that says which package tripped the limit and why. Also for testing let me override that max via an environment variable so the tests don't have to actually decompress something huge.
