I'm cleaning up Trivy's Gradle support and hit a few gaps I want fixed together. Right now when we scan a Gradle lockfile none of the discovered packages get flagged as indirect, which is wrong because everything in a Gradle lockfile is a resolved dependency that may well be transitive, so all of them should be marked indirect. Also the analyzer over in the Gradle lockfile code currently works against a single lockfile path, and I'd rather it scan a project directory and locate the lockfiles inside it so it lines up with the standard post-analysis pattern the other language analyzers already follow, taking a directory as input instead of one file handed in directly.

On top of that I want enrichment from the local Gradle artifact cache. When the standard env var pointing at the Gradle user home is set, we should look up the matching artifact metadata files in the cache and pull in license info plus the list of direct dependencies for each discovered package, so packages come back with their declared software licenses and their direct dependency relationships. If the cache isn't there the analyzer should still succeed fine and just return the packages without the extra metadata, no failures.

The metadata parsing has some edge cases too. If the group id or the version is missing from the metadata file itself, grab it from the file's cache path instead. And if a dependency's version is written as a reference to a build/project property rather than a literal value, resolve it to the real version using the properties declared in that same metadata file. Point is, without this we only get a flat package list with no license data and no dependency graph, which makes it hard to judge the compliance posture and real risk of Gradle-based Java projects since indirect deps and their licenses never surface.
