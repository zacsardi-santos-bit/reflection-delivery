I'm untangling our post publishing flow in the ActivityPub side of things. Right now everything that turns a blog post into federated activities and ships them out lives inline inside the webhook handler, so it's basically untestable and hard to follow step by step. I want to pull it apart into a real publishing pipeline with clean interfaces for each concern and concrete implementations that delegate down to the federation library.

The pieces I'm after: something to resolve federated actor identities by handle, something to build URIs for ActivityPub objects, something to store objects durably, something to track activities in an outbox, and something to send activities off to followers. Each of those should be an interface with a concrete impl backed by the federation lib, and all of it (interfaces plus implementations plus the service) should be reachable from a single entry point in the activitypub module.

The main publishing service takes these components through its constructor. Given a post with an id, title, content, excerpt, feature image URL, publication date, URL, and author handle, it should resolve the author's actor, create a preview object and a full article object, wrap those in a distribution activity, then store all three objects (preview, then article, then activity, in that order), add the activity to the outbox, and finally send it to the author's followers.

Error handling matters here too. If the actor can't be resolved, raise a clear error that says which handle failed. If any object being stored is missing its identifier, that's a descriptive error. Same deal when adding an activity without an identifier to the outbox. The whole point is each part becomes independently testable and the webhook handler can just delegate to this pipeline instead of orchestrating federation details itself, and it opens the door to alternative implementations later.
