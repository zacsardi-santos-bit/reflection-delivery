I'm poking around the reth storage provider layer and hit a gap: there's no clean way to pull uncle block headers (ommers) straight from the database provider. Right now if I want the ommers for a block I basically have to load the entire block and reach into its ommers field, which is way heavier than it should be, and there's no dedicated trait for this the way we have narrow interfaces for headers, receipts, and transactions.

What I want is a dedicated provider trait for fetching ommer headers so components that only care about uncle data can depend on a small, stable interface instead of the whole block machinery. Then the database provider (the one over in `@crates/storage/provider/src/providers/database/provider.rs` area) should implement that trait so callers can retrieve ommer headers by block number or block hash and get back the list of ommer headers for that block.

Couple things on the behavior: calling the ommer retrieval method on the database provider with a valid block number needs to succeed and return a result, and that result might legitimately be empty, like when the block has no uncles at all or it's past the Merge where ommers don't really exist anymore. Empty isn't an error, it just returns nothing. Keep it consistent with how the other block data accessors work through the standard provider abstraction.
