I'm digging into the linkerd2 policy controller and hit a real gap: the outbound policy indexer only knows about HTTP routes, gRPC routing configs just get dropped on the floor. Right now when the controller builds the outbound policy it distributes to proxies, it indexes HTTP routes and includes them, but if I define a gRPC routing resource pointing at some backend service, absolutely nothing happens, those routes never make it into the policy at all. So gRPC traffic routing is effectively unsupported even when the resources are defined correctly in the cluster, which means proxies can't apply any gRPC-specific traffic management.

What I want is for the outbound policy indexer to treat gRPC routes the same way it treats HTTP routes. When a gRPC routing configuration gets applied, the outbound policy should carry those routes in their own dedicated gRPC routes collection sitting alongside the existing HTTP routes collection. It also needs to track whether the services referenced as backends actually exist in the cluster, so if a gRPC route references a backend service that isn't registered with the controller yet, the policy should reflect that the backend doesn't exist. Then, and this is the reactive part, when that backend service later shows up (say it gets created after the route was already applied), the policy should update itself to mark the backend as now available, and anything subscribed to the outbound policy watch should get notified when that backend existence state flips. So basically full parity with HTTP: indexing, backend existence tracking, and reactive watch notifications on state changes, all handled in the outbound policy indexing logic.
