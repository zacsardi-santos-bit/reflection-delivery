I'm hitting a bug in PRQL where grouping the whole table with no partition columns silently drops the sort order from the SQL that comes out. So when I write a group with an empty partition and put a sort plus a take (row limit) inside it, the generated SQL keeps the limit but the ORDER BY just vanishes, which makes the query non-deterministic and that's obviously wrong. A group with no partition columns should really be treated as a full-table operation, it applies its inner pipeline across the entire result set, so any sort I specify inside it needs to survive and show up as an ORDER BY in the final query. The transparent behavior I want is: an empty group passes sort and limit straight through to the output SQL, selecting all columns from the source table with the sort order applied and the limit alongside it. Right now the compiler is eating the ordering when the partition is empty, and that's especially harmful with a take applied because the rows you get back become unpredictable. People rely on sort ordering inside group expressions to control result order, so it can't just disappear. Can you fix the compilation path so an empty group preserves both the ORDER BY and the limit? This is tracked as issue #5100.
