So I hit a security header bug in pomerium and want the proxy to be smarter about it. Right now we send the HSTS header (the Strict-Transport-Security one that tells browsers to only use HTTPS for a long max-age) on every response, even on plain HTTP connections that aren't using TLS at all. That's wrong, because that header should only go out when the server actually has a valid cert for the domain and the connection is genuinely secured. On plain HTTP, sending it can make browsers refuse to connect over plain HTTP when that's exactly what someone wants, so it locks people out.

What I want is for the proxy to decide which default security headers to add dynamically at request time based on whether the connection is TLS-secured, meaning the server has a certificate for the relevant domain. When the connection is TLS-secured, include the full set of default security headers including the long-term HSTS enforcement header. When it's plain HTTP, still include the other default security headers but leave out the Strict-Transport-Security one.

Also I need a clean way to turn off all the default security headers entirely, for when I'm running something in front of pomerium (like a load balancer) that handles those headers itself. So there should be a special disable key operators can set in the response headers config that signals pomerium shouldn't add any default security response headers at all.

And oh, the default options shouldn't hard-code the security headers as static config anymore. Instead of baking them into the static defaults, the choice of which headers to send needs to happen dynamically per request based on that connection context. This matters because HSTS on non-TLS is a real misconfiguration that can lock users out, and giving operators the opt-out is important for those fronted deployments.
