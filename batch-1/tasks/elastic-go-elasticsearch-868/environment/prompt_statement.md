I'm working on the Elasticsearch Go client and I want to make the integration tests self-contained. Right now all the integration tests assume there's already a running Elasticsearch server up at some default address, which is fragile and annoying for CI, because anyone (dev or pipeline) who wants to run them first has to stand up and configure an external Elasticsearch service. I'd rather each test run just spin up its own fresh, isolated instance using container tech, use it, and tear it down after, no manual setup at all.

Here's where things stand: the helper code for creating and managing containerized Elasticsearch instances plus the restructured test files have already been written, and the integration tests from multiple packages got consolidated into a single end-to-end testing package inside a dedicated testing sub-module. Problem is that sub-module doesn't have a Go module configuration file yet, so the whole integration test suite fails to compile. I need a proper Go module set up in there with the correct module name and the container orchestration library declared as a dependency so the tests can actually build and run.

Once that's in place, running the integration tests shouldn't need any externally running Elasticsearch anymore. They should automatically start a containerized instance using the same version as the client, with an option to override the version via an environment variable, and connection details (address, credentials, TLS certificate) should get derived from the running container at runtime. Oh and the container needs to be cleaned up properly when the tests finish.
