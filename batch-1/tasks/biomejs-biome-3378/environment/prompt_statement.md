I'm building out semantic analysis for GraphQL docs in the biome linter and right now there's just nothing there, no semantic model at all, so lint rules can't reason about how declarations and references relate in a schema or query. Like knowing that a type used in a field's return type actually got defined somewhere, or that a fragment spread points at a real fragment definition. I want a new crate that takes a parsed GraphQL document tree and builds a semantic model out of it.

The model needs to hand me all the name bindings in a document, so type definitions, directive definitions, fragment definitions, operation definitions, and variable definitions, plus tell me which references stayed unresolved. GraphQL has built-in scalar types and built-in directives that are always available without ever being declared, so don't flag those as unresolved. Also type extension constructs should resolve back to their original base type definition instead of being counted as brand new bindings.

The interesting bit is variable resolution across fragments. When a variable's used inside a fragment, and that fragment gets spread into an operation that declares that same variable, the reference should resolve to the operation's variable definition. This has to work transitively too, so if a fragment includes another fragment that uses a variable and an operation includes that nested fragment, the reference resolves up to the operation's definition. And when one fragment is used by multiple operations, a single variable reference in the fragment should resolve to all the matching variable definitions across all of them.

I also want to navigate both directions, from any reference node to its declaration (directive usage to directive definition, fragment spread to fragment definition, type extension to base type definition) and from any declaration back to all its reference nodes. Oh and for variable references that can't resolve, track which operation (if any) is responsible, meaning the operation that pulls in the fragment holding the variable even though it doesn't declare that variable. A fragment variable stays unresolved when no operation uses the fragment, or when the including operation just doesn't declare the variable, and in the reachable-via-operation case I still want to know which operation it belongs to. This is the foundation for schema-aware rules that catch undeclared type references, missing variable declarations, and spreads to nonexistent fragments.
