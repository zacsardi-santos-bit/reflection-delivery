I ran into a nasty CommonJS interop bug in the bundler and I need help tracking it down. So I've got a CommonJS module that conditionally re-exports one of two other CommonJS modules at runtime, basically it picks between them using a conditional expression evaluated at runtime (think `module.exports = cond ? require("a") : require("b")`). Then I import this thing from an ESM file as a default import and call it as a function, and the generated bundle comes out wrong.

The issue is the output is skipping the interop compatibility step. Instead of going through the interop layer to reach the actual exported function, the generated code tries to use the wrapper object directly, and at runtime that blows up because the real function value lives under an extra property inside the interop wrapper, not at the top level. Same deal with named property access btw, when an ESM file reads a named property off a namespace binding that came from a CommonJS module via interop, the bundler sometimes skips the interop compatibility accessor and reads the property straight off the wrapper, so it hands back the wrong value.

What I want is for the bundler to recognize when a CommonJS module uses a conditional require expression as its export and, in that case, not apply the optimization that strips out the interop compatibility accessor. The bundled output should always route through the proper interop layer when accessing the default export or any named property from a module like this. So access the default through the interop compatibility property rather than directly on the wrapper, and same for any named property on a namespace binding wrapping a CommonJS module, route it through the compat layer instead of hitting the wrapper directly.

This matters because anyone mixing CommonJS modules that conditionally pick dependencies at runtime with modern ESM imports is getting silently broken bundles right now. Function calls that should work just fail, or property reads return the wrong value, all because the generated code is missing that required property access step in the interop chain. Can you find where this optimization gets applied and make it correctly detect the conditional-require export pattern so it keeps the interop accessor in place?
