I'm working with a library that generates JSON schemas from GraphQL input types, and I've found two issues with the generated output.

First, when an optional (nullable) input field references another input object type, the generator is using the wrong JSON Schema combinator. It should use the combinator that allows any of the listed alternatives to match (either null or the referenced type), but it is currently using a different combinator that requires exactly one alternative to match. This causes compatibility issues with some validators.

Second — and more seriously — when the same GraphQL input type is referenced both as a required (non-null) field and as an optional (nullable) field somewhere in the schema, the generator only produces a single definition for that type. But a required field cannot be null while an optional field can, so a single shared definition can't correctly represent both constraints. The fix should generate two separate definitions for the type: one that permits null values (used for optional fields) and one that does not (used for required fields). The naming convention for the non-null variant should use a suffix to distinguish it from the nullable variant in the schema's definitions section.

This dual-definition behavior should also handle edge cases: if the same type is used multiple times but always as optional, only one nullable definition should appear; if it's always required, only one non-null definition should appear. The field declaration order in the GraphQL schema should not affect the output. These fixes should apply consistently across arrays, recursive types, and complex nested schemas.
