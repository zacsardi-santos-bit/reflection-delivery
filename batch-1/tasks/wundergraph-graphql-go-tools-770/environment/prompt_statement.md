I'm hitting a couple of bugs in our JSON schema generator that turns GraphQL input types into JSON Schema, and both come down to nullability being handled wrong. First one: when an optional (nullable) input field references another input object type, the generator picks the wrong combinator. It should express "either null or this referenced type" using the combinator that matches if any of the listed alternatives match (anyOf), but right now it's emitting the one that requires exactly one alternative to match (oneOf), and that trips up some JSON Schema validators that treat those differently. So I just want nullable references to use the any-of style.

Second one's worse. When the same GraphQL input type shows up as a required (non-null) field in one spot and as an optional (nullable) field somewhere else, we only spit out a single shared definition for that type. That can't be right, since a required field must not accept null while an optional field must, and one definition can't enforce both at once. I want two separate definitions generated: one that permits null (used wherever the type is optional) and one that doesn't (used wherever it's required). For the non-null variant, append a suffix to the name so it's distinct from the nullable one in the definitions section.

Also handle the consistent cases cleanly, so if a type is only ever used optionally I should get just the one nullable definition, and if it's only ever required I get just the one non-null definition, no extra duplicates either way. And field declaration order in the GraphQL schema shouldn't change the output at all, it needs to be stable. Oh and make sure all of this holds up across arrays, recursive types, and deeply nested complex schemas too, not just the simple flat case. The whole point is that apps validating input against these schemas stop wrongly accepting null for required fields or rejecting valid null for optional ones, so the generated schema actually reflects the nullability the original GraphQL declared.
