I'm working with the IonQ quantum computing service integration and I've hit a gap: I can create a job, grab a specific one by ID, and cancel a job, but there's no way to pull back a whole list of jobs. That's a pain when I want to audit job history, find everything matching a status, or just see all the jobs on my account. Right now I have to track job IDs externally and query them one at a time, which doesn't scale for real workloads.

I want to add a list jobs method to both the low-level client and the high-level service. It should let me filter by job status (like "completed" or "canceled"), cap the maximum total number of jobs returned, and also control the batch size per individual API call so I'm not requesting too many at once. Oh and pagination should just work: the IonQ API returns a pagination token in the response when there are more results, so the implementation needs to follow that token automatically and stitch the pages together into one merged result.

At the service level (not the raw client) the returned results should be proper job objects, not raw API response dicts, consistent with how the other job-fetching methods already behave. And error handling should match the existing patterns everywhere else, so unauthorized access surfaces an appropriate authorization error, non-retriable failures include the HTTP status code, and transient stuff like service unavailable triggers a retry.
