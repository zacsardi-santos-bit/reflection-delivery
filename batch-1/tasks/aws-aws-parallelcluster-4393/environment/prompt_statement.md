I'm working on the cluster update policy code and hit a gap around managed placement groups. Right now the update policy treats every placement group the same, but there's a real difference between ones the cluster spun up automatically versus ones a user handed us by giving an explicit name or id. The problem is if we delete a cluster-managed placement group while compute nodes are still running, that can wreck the infrastructure and leave things inconsistent.

So I want to add detection that spots when a proposed config change would delete a managed placement group, meaning one that's enabled but has no user-provided name or identifier. When that kind of deletion shows up and the cluster still has running compute capacity, I need the update blocked with a message telling the operator that all compute nodes have to be stopped first, basically shut down the whole compute fleet before the deletion can go through. If the fleet's already stopped, then the managed placement group deletion should just proceed normally, no complaints.

The tricky bit is this needs to work at both the queue level and the compute-resource level, and when both are set the compute-resource-level config wins over the queue-level one. Also placement groups that do have an explicit user-specified name or id shouldn't get caught by this stricter rule, they keep going through the standard update strategy like before. So really it's just the auto-created, enabled, no-name ones that trigger the stop-the-fleet requirement.
