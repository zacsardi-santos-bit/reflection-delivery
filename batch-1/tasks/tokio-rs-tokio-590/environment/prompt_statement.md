I'm using the line-splitting codec to read newline-delimited messages from network clients, but I've realized there's a serious problem: if a client never sends a newline, the codec just keeps buffering data forever. For a public-facing service this is a denial-of-service risk — a single bad client could exhaust all memory.

I'd like the codec to support an optional maximum line length at construction time. When a line being decoded reaches that limit without a newline, the codec should return an error instead of continuing to buffer. Importantly, after that error the codec should recover gracefully — it should discard the rest of the over-long line on its own and continue decoding subsequent lines normally, so the caller doesn't have to reinitialize everything.

Lines within the limit should still work exactly as before, including lines terminated with carriage-return/newline pairs, and bare empty lines. When data arrives in chunks and the total buffered so far hasn't hit the limit yet, the codec should keep waiting for more data rather than raising a premature error. And if the stream ends with some data left in the buffer but no final newline, whatever is there should be returned as the last line.
