I'm using the lines codec to read newline-delimited messages off network clients and just hit a nasty gap: if a client never sends a newline, the codec buffers forever. For a public-facing service that's a straight-up DoS vector, one bad (or malicious) client streaming bytes with no newline can exhaust all the memory the server has.

What I want is an optional max line length set at construction time. When a line being decoded reaches that limit without seeing a newline, it should hand back an error to the caller instead of continuing to buffer. And importantly, after that error it needs to recover on its own, discard the rest of the over-long line and keep decoding subsequent lines normally, so I don't have to tear down and reinitialize the codec.

Lines within the limit should still behave exactly like before, including ones terminated with a carriage-return/newline pair, and bare empty lines too. Also when data arrives in chunks and the total buffered so far hasn't hit the limit yet, don't raise a premature error, just keep waiting for more data. Oh and if the stream ends with leftover data in the buffer but no final newline, return whatever's there as the last line. Basically I want a built-in, easy-to-configure cap so it's simple to build safe line-oriented servers without worrying about memory exhaustion.
