I'm bumping the Container Device Interface library we use for CDI device injection to a newer major version, and the API changed on us. The old version had you grab a registry object and call methods on it, but the new release drops that entirely and hands you top-level package-level functions instead. There's one function for applying configuration options like pointing at spec directories, and a separate one for refreshing the registry, and they're meant to be called independently so you can check the error from each step on its own rather than chaining everything into one call.

Right now our device injection code still does the old registry-based thing, so it won't build against the new library at all, and the test setup that wires up CDI with the new API won't compile either. I need two things fixed: the dependency declaration itself needs pointing at the newer version, and the actual injection code needs rewriting to call the new top-level functions directly instead of obtaining a registry and invoking methods on it.

So the flow should be config first, then refresh, called in sequence, each returning its own error that I check independently. That's the whole point of the new model, it's more explicit about where device injection failures come from. Keeping current with upstream also unlocks the newer CDI features we've been wanting.
