I'm chasing a wrong-binary bug in our Cypress installer CLI. On Apple Silicon Macs (M1/M2) when someone runs installation from an Intel Node.js build under Rosetta, the installer trusts the Node process's reported arch (x64) instead of the real hardware, so it pulls the x64 Cypress binary when it should grab the native ARM64 one. On a plain native ARM64 setup we obviously want ARM64 too, that part already works, it's the emulated case that's broken.

What I want is for the installer to figure out whether the current process is being translated by Apple's Rosetta compatibility layer, and if it is, treat the system as arm64 and download the matching binary. So detection needs to look past `process.arch` and actually sniff the translation state. Also I'd like this detected value cached so we're not re-detecting on every call, and give me a way to clear that cache (handy between test runs).

The functions that build the download URLs currently do their own arch detection inline. Please refactor them to take architecture as an explicit parameter instead, so detection lives in one place and the same detected value flows through the whole download path consistently.

Oh and the test support utils that mock spawned child processes need a tweak too, the mock child process objects are missing a method stub that the spawn library expects, so add that stub alongside the existing ones. Point is the installer should always match actual hardware, not whatever arch the Node process happens to claim, otherwise Rosetta folks keep ending up with a mismatched binary that won't run right.
