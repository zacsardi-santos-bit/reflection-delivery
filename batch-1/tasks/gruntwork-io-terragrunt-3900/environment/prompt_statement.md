I'm extending Terragrunt's stack configuration system to support nested stacks. Right now a stack config file can only declare individual deployment units, but I want it to also reference entire other stacks as components so teams can build modular, layered infrastructure where one stack embeds other stacks instead of listing every unit at a single flat level.

So I need a stack block type alongside the existing unit block type in the stack config parsing, letting users reference other stacks as nested components. The bigger gap is validation. The current logic only knows about unit blocks and can't validate stack-level blocks at all, which means any nested-stack support would just bypass the checks we already do for units. I want the same rules applied to stack references: each one needs a unique, non-empty name, a non-empty source location, and a non-empty output path. If any of those fields are missing or just whitespace-only, validation should fail with a clear, descriptive message that identifies which stack had the problem and why (like which field was empty for which named stack).

Also duplicate names or duplicate paths within the same config file should get rejected too, same as units. And one thing I care about, a config file that contains only stack references with no unit references at all should still be considered valid as long as those references individually pass all the field checks (non-empty name, source, path, no dupes). Basically the validation in the stack config code should treat stacks as first-class the way units already are.
