I'm hacking on the Go SDK harness for Apache Beam, specifically the state channel that manages bidirectional state communication between pipeline workers and the runner during execution. Right now when the state comms channel hits an error, either on the read side receiving responses or the write side sending requests, the callers waiting for a response just block forever. The context never gets cancelled and there's no way for the channel manager to know it should tear down the connection and reconnect. That's bad because a transient network blip or the remote end closing the connection can silently stall the whole pipeline worker, since state reads sit there waiting on responses that'll never come.

What I want is for the channel to propagate errors back to any waiting callers immediately when something breaks, so on a read error (including end-of-stream) all pending callers get a meaningful error instead of hanging, and the same thing on a write error. In both cases it should cancel the execution context tied to the channel so dependent work can clean up promptly, and invoke a configurable callback when the channel terminates due to an error so the channel manager can delete the old channel and recreate a fresh connection.

Also after the channel has failed, any new requests submitted to it should immediately return that same error rather than blocking. Oh and the channel needs to handle concurrent request/response routing by ID, multiple callers in flight at once and each one has to receive the response matching its own request ID. One more thing, when the underlying stream returns an end-of-stream signal on a write, per the gRPC stream docs you've got to drain the receive side to get the real error, so make sure that path pulls the actual error out. The relevant code lives in the harness state channel implementation.
