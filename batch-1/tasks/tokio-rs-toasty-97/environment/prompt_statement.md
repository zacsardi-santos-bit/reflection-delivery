I'm deep in our multi-backend ORM and hit a gap in the SQL driver capability system. Right now each driver publishes a capability descriptor that the query planner reads to pick strategies, but the only relevant flag we've got is the one saying whether the database supports update statements inside common table expressions. There's nothing that tells us whether a backend can do row-level locking, and that's biting us on conditional updates. The deal is databases that support row-level locking should lock individual rows during the read, while the ones that can't need to fall back to serializable transaction isolation instead, so without a way to advertise that, we end up picking the wrong strategy and either generating invalid SQL or failing at runtime.

So I want to add a field to the SQL capability descriptor that expresses whether row-level locking is supported, alongside the existing CTE-with-update flag. Then fix the three SQL backends to declare their real capabilities. MySQL supports row-level locking but does not actually support update-within-CTE (it's currently marked as supporting that, which is wrong and generates invalid SQL for MySQL, so flip it). PostgreSQL supports both CTE-with-update and row-level locking. And SQLite supports neither, so it should be false for both. Can you wire that up?
