I'm working with encrypted Parquet and I want to write a file with a plaintext footer that carries key metadata identifiers, the idea being that a reader can later look up the actual key bytes by name through a key retriever. The read path in the crate already handles key retrievers that identify keys by metadata, but the write side is missing the matching piece. When I build the file encryption properties I can pass raw key bytes but there's no way to also attach a metadata identifier to the footer encryption key, and same problem for individual column keys. So anything integrating with a key management service basically can't produce files that a retriever-based reader can decrypt, which breaks the whole write-then-read roundtrip for that pattern.

What I need is a way, when building the encryption properties, to specify both the actual key bytes and a metadata identifier in one step, for the footer key and for each column key. So one call that sets a column's encryption key plus its metadata id together, and likewise the ability to give the footer key its own metadata identifier. Once that's in place a file written with a plaintext footer and these key metadata ids should be fully readable by a key retriever that resolves the identifiers back to the right key bytes. And if the retriever hands back the wrong bytes for an identifier, reading should fail with an informative error saying the footer signature verification failed rather than something cryptic. This all lives around the parquet encryption properties builder, roughly `@parquet/src/encryption`, matching whatever the retriever side already expects.
