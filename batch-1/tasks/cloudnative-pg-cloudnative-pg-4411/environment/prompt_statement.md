I'm building out safe promotion for replica clusters in our CloudNativePG controller and right now there's nothing stopping a promotion from firing before the replica has actually caught up, which is how you end up with data loss or split-brain. I want a token-based flow: when a cluster gets demoted from primary to replica it generates a demotion token encoding its last checkpoint state (timeline, write-ahead log position, and the system identity), and that token gets recorded in the cluster's status. To promote a replica, an operator drops that token into a promotion token field on the replica's spec.

Two layers of checking here. At admission time the webhook validation should reject tokens that aren't properly encoded or are missing required fields. At runtime we verify the replica actually reached the checkpoint the token describes before proceeding, and this needs to tell apart two failure modes: if the replica's WAL position or timeline is behind the token's value that's transient and should be retried later, but if it's already moved past the required position or the database identities don't match that's permanent and shouldn't be retried.

I also need a utility layer that parses the raw text output of the database checkpoint tool into a structured form, creates the encoded token from that structured data, and parses it back out. Oh and the cluster type needs a method that decides whether a promotion should even be triggered, comparing the current token in the spec against the last token already processed (stored in status) so we don't run the same promotion twice, and status should track that last successfully applied token to avoid re-processing.

Last thing, actually a rename: there's a field on the internal reconciler struct that's misnamed as a status client when it's really an instance client, so fix that to reflect it's an instance client.
