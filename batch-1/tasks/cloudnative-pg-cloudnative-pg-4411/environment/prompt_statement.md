I'm working on a CloudNativePG cluster controller and need to implement a safe, token-based promotion mechanism for replica clusters. Currently, when we want to promote a replica cluster to primary, there's no way to verify that the replica has actually reached the required state before allowing the promotion. This can lead to data loss or split-brain situations.

The idea is that when a cluster is demoted from primary to replica, it generates a token encoding its last checkpoint state. That token is stored in the cluster's status. To promote a replica cluster, an operator sets that token in the replica cluster's spec. The system should then validate the token format and content at admission time (rejecting tokens that are not properly encoded or are missing required fields), and at runtime it should verify that the replica has actually reached the checkpoint described by the token before proceeding.

The runtime validation needs to distinguish between two failure modes: a transient failure where the replica simply hasn't caught up yet (should be retried later), and a permanent failure where the required state can no longer be reached or the cluster identities don't match (should not be retried). Specifically, if the replica's write-ahead log position or timeline is behind the token's value, that's retryable; if it has already moved past the required position or the database identities differ, that's a permanent failure.

I also need a utility layer that can parse the raw text output of the database checkpoint tool into a structured format, create the encoded token from that structured data, and parse it back. The cluster type also needs a method to decide whether a promotion should be triggered at all — comparing the current token in the spec against the last token that was already processed (stored in status), so we don't attempt the same promotion twice.

Finally, the internal reconciler struct has a field that needs to be renamed from its current name to a more accurate name reflecting that it's an instance client rather than a status client.
