I'm building out the transaction gossip layer for an Ethereum node and right now we just blindly trust peer transaction announcements, queuing everything for fetch with zero sanity checks, which means a misbehaving peer can flood us with garbage and waste our resources chasing transactions that were announced with nonsensical metadata. I want a validation step that sits between receiving an announcement and dispatching fetch requests, inspecting each entry and deciding whether to fetch it, silently drop it, or flag the peer for bad behavior.

It needs to handle two announcement message formats: an older one that's just a list of transaction hashes, and a newer one that also carries a transaction type byte and encoded size per entry. For the newer format, entries with unrecognized transaction types get filtered out and the peer gets reported for misbehavior, but entries with a zero-byte encoded size (strictly too small to be any valid tx, below the absolute minimum) get filtered out silently without penalizing since it could be an honest mistake. Duplicate hashes in either format get deduplicated and the peer penalized when dupes show up, and an empty announcement (zero entries, either format) should immediately flag the peer for a reputation penalty too.

The output should be a map from transaction hash to optional metadata, so for the newer format the value carries the type and size, and for the older format the value's just absent. Also the filter has to return a signal telling the caller whether to apply a reputation penalty to the peer. Oh and make the filter logic pluggable so different networks can drop in their own validation rules, with a default implementation covering standard Ethereum transaction types, and that default should implement Display showing its own type name. The point here is resilience against bad actors while staying lenient toward honest peers sending benign but slightly malformed data.
