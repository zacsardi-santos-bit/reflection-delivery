I'm adding a new correctness lint rule to our JS/TS linter that finally enforces symbol-level visibility declared through documentation comment annotations. Right now devs annotate exports to say a symbol should stay within its folder or be fully private, but the linter treats all that as informational so anything can import anything, and the annotations drift out of sync with reality. I want the rule to read those doc comment annotations and raise a diagnostic whenever an import crosses the declared access level.

There are three levels I care about. A private symbol can't be imported by any other file at all, a package-scoped symbol is only importable from within the same directory, and a public symbol is importable from anywhere. I also want a config option that sets a default visibility for symbols with no annotation, so a team can opt the whole project into package-private without hand-annotating every export. An explicit annotation on a symbol always wins over that configured default, whether it's stricter or more permissive.

A few nuances to get right. When a package-scoped symbol is re-exported through a directory's index file, treat that re-export as intentionally widening scope, so importing via the index file path is allowed from the parent level. Similarly, within a folder, importing a private symbol from that same folder's own index file should be permitted. And this needs to cover default imports and combined imports, not just named ones. The diagnostic should clearly say whether the violation is private or package visibility, tell me I might need a different symbol or to relax the visibility, and point me at both the offending import specifier and the file where the symbol was actually defined.

Oh and there's an older experimental rule in the nursery category doing a much simpler version of this (it only checked whether a module lived in a subdirectory, no annotation awareness at all). Since this new correctness rule supersedes it, please remove that nursery rule as part of the same work.
