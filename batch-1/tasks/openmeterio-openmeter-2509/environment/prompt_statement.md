I'm working with our filter package and hit a gap that's making downstream code messier than it needs to be. We've got filter types for strings, ints, floats, booleans, and time values, and each one holds a bunch of optional conditions like equality checks, comparisons, pattern matching, and logical AND/OR operators. Problem is there's no clean way to tell whether a given filter actually has anything set. When one of these shows up as an optional query param it often arrives as a zero-value struct with nothing configured, and right now callers have to poke at each field by hand to figure out if it's a no-op, which is verbose and easy to get wrong.

What I want is a method on each filter type that reports whether it has any conditions configured, basically an emptiness check. The rule is a filter counts as empty only when none of its fields are set, and the moment any single field is set (a comparison, a logical operator, a pattern matcher, whatever) it's non-empty. The tricky one is the boolean filter: if it's explicitly set to false, that's still a real filter condition distinct from "no filter at all", so it has to report as non-empty even though the value is false. Don't treat false as unset.

This lets callers short-circuit and skip query-building or processing entirely when the user hasn't specified any criteria, so we stop emitting pointless clauses. Add these methods across the filter type definitions in the filter package and make sure the boolean case behaves right.
