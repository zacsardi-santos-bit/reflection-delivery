I'm hitting a couple of annoying limitations with Firestore query cursors and want to fix both. Right now when I build a cursor I can only hand it a dict of field name to value pairs, or a document snapshot. There's no way to just pass a plain ordered list or tuple when I already know the values in the right order, which is way more convenient. So I want cursors to also accept a list or a tuple, and if it's a tuple it should get converted to a list internally so everything downstream sees a list.

The other thing that's been biting me is that I can currently set a cursor before I've defined the query's sort order, and nothing complains until serialization time, if ever. That's a silent bug waiting to happen. I want the cursor validated against the ordering explicitly, and the ordering has to be established before any cursor gets applied, so if I set a cursor without a corresponding ordering it should raise a clear descriptive error. Same deal if the cursor and ordering don't line up, like the cursor has more values than there are order fields, or it references a field that isn't part of the ordering, I want a clear error for that too.

Oh and when a dict-style cursor gets normalized against the order fields, the values should be pulled out in field-order to produce an ordered list. Also the internal helper that turns a cursor into the protobuf format should get simplified so it just receives an already-normalized list of values instead of doing its own field lookup. The relevant logic lives in the query building code under the Firestore client (`@google/cloud/firestore/query.py` or wherever the cursor and order handling sits), so the changes touch how cursors are stored, how they're validated against ordering, and how they're serialized. Point is: list/tuple cursors work, tuples become lists, ordering must come first, and mismatches blow up loudly instead of silently returning wrong results.
