I'm adding multi-objective optimization support to the relational database storage backend and the current schema is blocking me. Right now a study record carries a single optimization direction field (minimize or maximize) directly on it, and each trial stores just one objective value, so there's no way to represent a study with more than one objective. I want to fix loss and runtime at the same time, that kind of thing.

What I need is to refactor the schema so optimization directions live in their own dedicated table, one row per objective per study, where each row tracks an objective index and its direction value. Same idea for trial objective values, a separate table with one row per objective per trial, each holding an objective index and the corresponding value. Both new tables need proper lookup methods, so I can find a direction by study and objective index or list all directions for a given study at once, and likewise find a value by trial and objective index or grab all values for a trial in one go.

Cascade deletion has to work too. When I delete a study it should automatically clean up all its direction rows, and when I delete a trial it should remove all its associated value records, both the final objective values and the intermediate values recorded during the trial. Oh and the existing way of constructing a study with that single direction field needs to be replaced with a relationship to the new direction records instead. This is a schema change so I also need to register a new migration version in the storage layer's version history to reflect it. Basically per-objective rows with proper cascade deletion, laying the groundwork for full multi-objective support.
