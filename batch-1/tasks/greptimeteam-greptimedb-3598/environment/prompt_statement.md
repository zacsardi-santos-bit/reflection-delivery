I'm deep in the mito2 storage engine and need parallel scan support for append-mode regions. Right now there's just one scan strategy and it's used for everything, but append-mode tables don't need dedup or strict timestamp ordering, rows just need to come back, order doesn't matter, so we're leaving a ton of throughput on the table by scanning sources one after another. What I want is for the engine to automatically pick an unordered parallel scan path for append-mode regions when parallelism is configured greater than 1, scanning multiple memtables and SST files concurrently instead of sequentially. That's a big win for time-series write-heavy workloads.

I also want a way to grab the underlying scan object directly from the engine rather than always getting a fully resolved scanner back. There are cases where I want to explicitly kick off a sequential scan from that intermediate region scan object without going through the automatic dispatch path.

Oh and there's a real bug in the region reopen utility, it always reopens with empty options which silently drops whatever config the region was created with, like append mode or compaction settings. It needs to take the original region options and pass them through to the open request so the region comes back up with the same configuration across close/reopen cycles. This bites us in tests and prod whenever a region with custom options gets restarted.

Last thing, the scanner should correctly count how many memtables it's going to scan no matter which scan strategy is actually running underneath.
