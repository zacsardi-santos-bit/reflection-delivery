I'm cleaning up our entity processing library and the way factories take the entity id is bugging me. Right now the id has to live inside the spec object itself, which mashes together two things that should be separate, the entity's identity versus its structural config. I want the factory to take the identifier as its own distinct argument instead of digging it out from inside the spec, so creating an entity type passes the id separately from the spec that describes its shape.

While I'm in there I also need a reusable way to check that a spec only uses property names we actually recognize. So I want a validation utility that takes an identifier, a spec object, and a list of allowed property names, and throws a descriptive error naming the offending key(s) when the spec has any unrecognized keys. If the spec only has allowed keys, or it's empty, it should just return without complaint.

Oh and I want a higher-level variant of that utility too, one that automatically folds in the standard set of common base modifier properties as always-allowed. That way consumers only have to list their entity-specific property names and the base modifiers get included for free, so only genuinely unexpected keys trip the error.

The point of all this is separating id from spec makes the API cleaner and more composable, and the validation helpers let factories catch config mistakes early with a helpful message instead of failing silently or blowing up with something obscure later in processing.
