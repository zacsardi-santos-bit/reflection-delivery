So I'm adding conditional rate limiting to the NGINX Kubernetes Ingress Controller and could use a hand wiring it through end to end. Right now rate limit policies apply uniformly to every request, but the real world wants different limits per user tier, like letting "gold" tier users do 100 r/s while "silver" tier gets capped at 20, based on a claim in their JWT token. There's no way to express that today.

What I want is for the rate limit policy custom resource to accept an optional condition that checks whether a specific JWT claim matches a specific value (so a claim name plus a match value). When the condition matches, that policy's limit applies, otherwise the request falls through to a different policy or goes unconstrained. So the policy type needs the new optional JWT condition field.

The config generator then has to translate those conditions into the right NGINX config structures. Oh and one gotcha, if multiple rate limit policies on the same virtual server reference the same JWT claim, I don't want the same claim variable emitted twice, so please deduplicate those generated entries.

Validation matters too. JWT-based conditions only work on the commercial (Plus) version of NGINX, so if someone specifies such a condition for the open-source build it should get rejected with a clear validation error. Also a condition block that's declared but doesn't actually include a JWT sub-condition should be rejected as well.

The point of all this is letting platform teams do tiered access control at the rate-limiting layer without touching application code, which is a common need for API gateways and multi-tenant services where subscriber entitlements live in the JWT. Please keep it working the whole way through, from the policy resource shape to config generation to the validator.
