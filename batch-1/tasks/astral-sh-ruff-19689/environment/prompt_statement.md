I'm chasing a caching bug in our language server's pull-based workspace diagnostics. The way it's supposed to work: clients send back the result identifiers from a previous response, and we use those to figure out which files haven't changed so we can skip full re-analysis and just drop into a lightweight long-polling state. Problem is some clients (VS Code is the one biting me) percent-encode special characters in the file URIs when they hand those identifiers back. So if a workspace path has a colon in it, the client sends the URI with the colon encoded as `%3A`, and since we currently match previous result IDs by exact raw URI string, we fail to see those files as unchanged and end up re-analyzing everything even though nothing actually moved.

What I want is for the server to match previous result IDs by the underlying file path instead of the raw URI string, so caching still works when the client uses different URL encoding than what we originally returned. When a client sends back previous result IDs whose URI encoding differs from ours (extra percent-encoding on colons or whatever), we should still recognize them as the same files. And when everything matches and nothing's changed, we should respond with an empty diagnostic report rather than sending full reports for every file.

This matters because any workspace with paths containing colons (URI conventions, Windows paths, that kind of thing) trips this and makes us skip caching on every single subsequent request, so we're recomputing constantly and the whole pull-diagnostics caching protocol falls apart. Fix the comparison to be path-based.
