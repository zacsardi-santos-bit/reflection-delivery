I'm hardening the security context of the containers that the Consul Kubernetes service mesh webhook injects into application pods, and there's a gap I keep hitting. The sidecar proxy container we inject already sets a non-root user and group and mounts a read-only root filesystem, but it never explicitly disables privilege escalation, so a process inside it could still gain extra privileges at runtime. I want the sidecar's security context to set allowPrivilegeEscalation to false on top of the existing restrictions.

Same story, kind of worse, on the init container that sets up network traffic redirection when CNI is active (the case where transparent proxy isn't separately enabled). It already drops all Linux capabilities, but it's missing both the read-only root filesystem setting and the privilege escalation prevention, so I want both added to its security context too, so it prevents privilege escalation and enforces readOnlyRootFilesystem alongside dropping all caps.

Oh and this needs to be consistent across both webhook injection paths, the standard one and the v2 path, so please apply the same hardening in both. It's basically about least privilege, since compliance tools flag containers that don't lock down privilege escalation, and this brings the inject behavior in line with best practices and shrinks the attack surface by default.
