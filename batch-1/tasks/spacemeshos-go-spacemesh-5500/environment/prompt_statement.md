I'm digging into our P2P networking layer and the timeout handling is way too blunt right now, we've got a single fixed timeout for every request and it treats a connection that's slowly but steadily streaming data exactly like one that's fully stalled. I want a two-tier setup instead. The idea is a stream wrapper that manages deadlines dynamically: as data flows it pushes the deadline forward proportional to how long each chunk took to transfer, so an active connection doing a big legitimate transfer over a slow link keeps breathing, but there's also a hard absolute timeout that acts as a ceiling nobody can exceed no matter what, even a pathological peer that keeps trickling tiny amounts of data to stay alive forever. So basically a per-chunk adaptive timeout that resets on activity plus a hard max deadline cap on top.

When a timeout actually fires I need the error to carry real diagnostic context so we can figure out what happened in prod, specifically how many bytes were read and how many were written (each direction separately) plus the values of both timeout parameters, the per-request one and the hard one.

Also the fetch layer's config struct needs to expose that hard timeout as a configurable field sitting alongside the existing per-request timeout. And separately, the peer discovery subsystem needs new timing knobs, I want to be able to configure the advertisement delay, the advertisement interval, the advertisement retry delay, and the peer-finding retry delay, mostly so tests are reliable but also for tuning production behavior. Make sure active connections don't get dropped prematurely while the hard cap still holds absolutely.
