I'm hitting a gap in our GraphQL schema autogen where interface types with relationship fields don't get the same treatment as concrete types. So I've got an interface that defines a relationship pointing to another node type, and when I inspect the generated schema, the relationship field on the interface is missing all its querying arguments. On a concrete type these come out fine, filtering by related node properties, traversal options, direction control, and for the connection variant of that field the usual pagination stuff (first/after), sorting, filtering, and direction. But on the interface they're just completely absent, which means I can't write the same expressive queries against the interface as I can against the concrete implementations.

There's also an extended schema mode issue. In that mode the interface's filter input type (the where input) is missing the relationship-based filter fields, so I can't filter interface instances by whether their related nodes match some condition, the all/none/single/some match variants, and there's no aggregate filter either. On top of that the aggregation input types that should exist for the relationship aren't being generated for the interface, though they are for concrete types.

I want the schema generation fixed so interface types carrying relationship fields get the full treatment, proper field arguments, aggregation inputs, and relationship filter fields in the where input, and this needs to hold whether or not the interface has extra custom directives applied to it. Right now devs using interfaces with relationships end up with an incomplete API surface that forces workarounds and kind of defeats the point of using interfaces at all.
