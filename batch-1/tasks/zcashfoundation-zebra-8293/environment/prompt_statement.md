I'm working on our scanner gRPC service and hit a gap that's been bugging me. It's got four key-management operations, retrieving scan results, registering viewing keys, clearing stored results, and deleting keys, and none of them actually check how many keys came in on the request. A client can send zero keys or hundreds and we'll happily try to process it, which either wastes downstream work or opens us up to abuse through oversized batches. A client bug that sends an empty key list should get a useful error instead of silently burning resources.

What I want is consistent input validation across all four ops. If a request shows up with no keys at all, reject it right away with an invalid-argument error before any downstream work happens. Same deal if it comes in with more keys than a sane per-request maximum, also invalid-argument. That max needs to be a documented, publicly accessible constant so callers and our tests can reference it directly, not some magic number buried in a function.

The happy path already works fine, valid requests return the right results, registered keys, cleared-results confirmation, or deleted-keys confirmation, so don't touch that. Requests that are non-empty and within the limit should behave exactly as they do today. I just need these guard clauses wired in up front on each of the four operations, checking both the empty case and the over-limit case with clear errors. Keep the validation logic uniform across them so the behavior's predictable for callers.
