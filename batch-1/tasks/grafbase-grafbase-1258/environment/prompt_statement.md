I'm hitting a weird double-error thing in my federated GraphQL gateway and could use a hand tracking it down. When one of my upstream subgraphs fails a mutation, it comes back with null data plus an errors array that explains what actually went wrong, which is fine, that's the contract. But the gateway then hands the client two errors instead of one. The first is this spurious internal "missing required field" message with a path pointing at the mutation field, and the second is the real upstream error. Only the second one means anything, the first is just noise the gateway generates itself when it tries to deserialize that null data against the expected schema and trips its own validation.

So what I want is: when an upstream subgraph returns null data alongside a non-empty errors list for a mutation, forward only those upstream errors to the client and suppress the internally generated missing-required-field one entirely. The final response data should stay absent (null), that part's correct. Basically if the upstream already told us it failed via its errors array, don't pile on a schema validation complaint on top of it.

The reason this matters is people debugging failed mutations are getting misleading responses that look like two distinct problems when really the upstream just reported a single failure. Can you fix the gateway's response handling so the null-data-with-errors case only surfaces the upstream errors and drops the internal validation artifact?
