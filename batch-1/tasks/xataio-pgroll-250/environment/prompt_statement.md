I'm hitting a nasty data integrity bug with our column-alteration migration operation. When I alter a column that already has a unique constraint, the uniqueness just silently vanishes as part of the migration. Like if I change the type of a column that was previously unique, the resulting column stops rejecting duplicates. Same thing happens if I add a check constraint to a unique column, or add a foreign key reference on it, or flip it to not null. In every one of those cases the unique constraint gets dropped somewhere in the migration process and after it completes, rows that should've been rejected as duplicates get accepted instead.

This is really bad because the whole point of the unique constraint is data integrity, and quietly losing it during a migration means duplicate data slips into the database and then you get downstream app errors and inconsistencies that are a pain to detect and repair after the fact.

What I want is for the unique constraint to be carried forward and stay in effect no matter what other alteration I'm doing to the column. So changing a column's type preserves existing unique constraints, adding a check constraint preserves them, adding a foreign key preserves them, and setting the column to not null preserves them too. And it needs to hold both during the migration transition period (when the old and new schema versions coexist) and after the migration is fully done. btw the transition window is where I suspect things are going wrong since that's when both versions are live, so double check the uniqueness holds there as well as post-completion.
