I'm hitting a gap with Apache Iceberg views in the Spark integration. Right now there's just no way to modify view properties after a view's been created, so I can't add metadata labels, update comments, or manage custom key-value annotations on views using standard SQL the way I can with tables. I want ALTER VIEW ... SET TBLPROPERTIES to add or update one or more properties on an existing view, and those changes need to persist and be retrievable when I reload the view from the catalog. Same for unsetting, I want to remove previously set properties, optionally with an IF EXISTS qualifier that suppresses the error when a property isn't there.

There's a few guardrails I need though. Certain internal reserved properties, like the format version and the internally-managed key that tracks the query column names from a view's defining query, have to be protected from user modification. Trying to set or unset one of these should fail with a clear error saying the property is reserved. And trying to unset a property that was never set (without IF EXISTS) should fail with a meaningful error naming the specific property. Oh and here's the tricky bit, if IF EXISTS is used but the target is actually a reserved property, it still needs to fail with the reserved-property error, since it's explicitly reserved not just absent.

Also there's this naming inconsistency I keep noticing in the view code (over in the Spark extensions module, `@spark/v3.x/spark-extensions/src/main/java/org/apache/iceberg/spark/`): the internal property key used to store the column names from a view's defining query reads like a generic user property key, but it's really Spark-specific internal metadata. I want it renamed with the proper Spark-scoped prefix so it's obvious it's internal and not something a user set. This makes views feel like first-class objects alongside tables, folks can annotate with comments or ownership tags, while the reserved-property protection keeps anyone from accidentally corrupting critical internal view metadata.
