I'm hitting a wall writing Cloud Custodian policies for our AWS MemoryDB clusters. The MemoryDB resource type just doesn't support the network and encryption filters I need, even though these work fine on other database resources like ElastiCache and RDS. I want to filter clusters by the security groups they're attached to (say, matching on security group tags), by the subnets they live in (like subnet name or tag), by the KMS key used for encryption including matching on key alias names, and I need the network-location filter so I can compare tags between a cluster and its associated subnets to catch mismatches.

The security-group and kms-key filters should behave like the standard ones on other resource types. The subnet one is trickier since MemoryDB clusters don't store subnet IDs directly, they reference a subnet group which in turn lists the actual subnet identifiers, so the subnet filter has to resolve the subnet group membership to figure out which subnets a cluster actually uses. To make that work (and the network-location filter too) it makes sense to also expose the MemoryDB subnet group as its own queryable resource type. The MemoryDB code lives under `@c7n/resources/memorydb.py` in the custodian tree, so that's where the four filter types and the new subnet group resource should land.

Why this matters: without these, security and compliance teams can't enforce stuff like "MemoryDB clusters must use security groups tagged for production", "clusters must sit in private-tier subnets", or "all clusters must use a customer-managed key following our naming convention". Adding these just brings MemoryDB in line with what we already have everywhere else. Oh and the network-location filter is the tag-comparison one that diffs a resource against its associated network resources, so it needs the subnet resolution working too.
