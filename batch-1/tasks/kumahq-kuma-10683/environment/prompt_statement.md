I'm adding hostname generator support for multi-zone services in Kuma and hitting a wall because the generator has no concept of them at all. Right now it can target single-zone services and external services through label selectors, but multi-zone services aren't a recognized target type, so there's just no way to point a generator at one and have it get a DNS name automatically. Operators running multi-zone deployments end up doing hostname assignment by hand or with workarounds, which is inconsistent with how everything else in the mesh works.

What I want is a new selector type on the hostname generator spec so a generator can be configured to target multi-zone services, sitting alongside the existing single-zone service and external service selector types. Then I need a new generator implementation that watches multi-zone service resources, matches them against the configured hostname generators by label, computes a hostname when there's a match, and writes that generated hostname into the matching service's status so it shows up there.

The isolation part matters a lot, so a generator configured for single-zone services shouldn't ever produce hostnames for multi-zone services, and the reverse too, and any multi-zone service that doesn't match a generator should just have no automatically assigned hostname at all. The selector type lives on the hostname generator API spec and the watching/matching logic goes in the generator implementation next to the existing single-zone and external service generators.
