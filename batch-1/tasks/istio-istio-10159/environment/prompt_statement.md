I'm adding TCP keepalive support to Istio's cluster generation and right now it's just getting dropped on the floor. When I set TCP keepalive at the global mesh level, those settings never make it into the Envoy cluster definitions we generate, and same deal for keepalive specified in a destination's traffic policy. Operators who tune this have no way to see it reflected in the upstream cluster config Envoy actually uses, so connections can go stale in certain network environments with no programmatic knob to fix it.

What I want is for the cluster builder to propagate these into the upstream connection options of each generated cluster. So if a global mesh-wide keepalive is set, it should show up on all the generated outbound clusters. If a destination traffic policy also sets keepalive for a port, that should take precedence over the global one and override it in the generated cluster. There's a subtle case too: if a policy explicitly sets an empty keepalive config with no values, the cluster should still carry a keepalive entry (just with no specific values), which tells the underlying OS to fall back to its own defaults, so it overrides the global setting rather than inheriting it. And if nothing configures keepalive anywhere, the upstream connection options on the cluster should be absent entirely, not an empty stub.

Basically it's a precedence thing, per-port policy beats mesh-wide, empty policy beats mesh-wide (OS defaults), and no config means nothing at all. Can you wire this through the cluster generation logic so all four behaviors hold?
