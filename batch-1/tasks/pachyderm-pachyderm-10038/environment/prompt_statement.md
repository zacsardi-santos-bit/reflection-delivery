So we've got clusters where pipeline version numbers in the database have drifted out of sync and multiple pipeline records end up sharing the same version number. This happens because of a bug in how versions get assigned, and the corrupt state means we can't enforce uniqueness anymore, which then breaks listing pipelines, listing the jobs tied to a pipeline, and creating new pipeline versions. I want a database migration that detects and repairs this.

The migration should find all pipelines that have duplicate version numbers, then for each affected pipeline renumber the versions sequentially starting from 1 based on creation order (oldest first). Any job records that point at the old versions need to be updated to reference the corrected version numbers so nothing dangles. Once the data's clean, apply a unique constraint on pipeline versions in the database so this can't silently come back. After the whole thing runs, listing pipelines, listing jobs, and creating new pipeline versions should all just work without error.

Oh and I need this structured for testing. Split the migration chain so there's a way to run all the steps up to but not including the dedup step, and then apply the dedup separately. That way I can stand up a test env at the pre-dedup state, artificially jam in some duplicate versions, and then run just the dedup step to confirm it resolves them correctly. Also there's an earlier migration state that's currently only reachable inside its own package, I need that exported so other packages can reference it directly as a starting point for building on or testing against the pre-dedup cluster state.
