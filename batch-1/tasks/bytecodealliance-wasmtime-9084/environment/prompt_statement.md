I've been looking at the RISC-V 64-bit floating-point code generation in Cranelift and noticed an inconsistency. When converting 32-bit integers to 64-bit double-precision floats, the generated instructions are missing the explicit rounding mode, unlike every other similar conversion in the same backend. For example, converting a 32-bit integer to a 32-bit float correctly includes the round-to-nearest rounding mode, and converting a 64-bit integer to a 64-bit double also does — but the two conversions from 32-bit integers to 64-bit doubles don't. This looks like a bug where the wrong data width is being used internally when encoding those two instructions. The fix should make those two conversion operations consistently include the rounding mode in the generated output, matching the behavior of all the other integer-to-float conversions in the backend.
