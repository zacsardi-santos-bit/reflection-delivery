I've been poking at the RISC-V 64-bit floating-point codegen in Cranelift and hit an inconsistency that looks like a real bug. When I convert 32-bit integers to 64-bit double-precision floats, the generated instructions are missing the explicit rounding mode, unlike every other similar conversion in the same backend. Converting a 32-bit int to a 32-bit float correctly emits the round-to-nearest rounding mode, and converting a 64-bit int to a 64-bit double does too, but the two conversions from 32-bit integers to 64-bit doubles don't include it at all. Both the signed and the unsigned 32-bit-to-double variants are affected.

It really looks like the wrong data width is being passed internally when these two instructions get encoded, so the rounding mode field just falls off. What I want is for converting an unsigned 32-bit integer to a 64-bit double to produce a conversion instruction that explicitly carries the round-to-nearest rounding mode, and same for the signed 32-bit-to-double case, so both line up with how all the other integer-to-float conversions in that backend already behave.

This matters for correctness, btw, since an omitted or wrong rounding mode can give subtly wrong floating-point results on hardware that applies the rounding mode field literally. So the fix should make those two conversions consistently include the rounding mode in the output, matching the rest of the backend.
