I'm working on the StackRox Kubernetes operator and I've hit a snag with how we track ownership of secrets during reconciliation. Right now when the Central custom resource gets deleted, Kubernetes garbage-collects every secret that carries an owner reference back to it. That's fine for most of them, but it's killing the central database password secret too, and when someone tries to recreate the Central instance they can't re-attach the existing database anymore, so we end up with data loss or broken recovery. Not great for disaster recovery or upgrade flows.

What I want is a flexible ownership tracking mechanism in the secret reconciliator that supports two strategies. One sets owner references on secrets (the current behavior that causes the cascading deletion), and the other only stamps a managed-by label without adding any owner reference, so those secrets survive the CR being deleted. Which strategy applies should be decided at the point where the reconciliator is created.

The "is this secret managed by us" logic needs to treat a secret as managed if it either has an owner reference pointing at the Central resource OR carries the correct managed-by label, and a secret with neither should just be left alone. Also the owner reference is the stronger signal, so if a secret has the owner ref but no label it's still managed no matter which strategy we picked. The central database password secret specifically should use the label-only strategy so it persists, while everything else (TLS certs, admin password, scanner db passwords) keeps using owner references like today.
