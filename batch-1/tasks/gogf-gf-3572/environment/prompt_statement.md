Hitting a nasty deadlock with the thread-safe map and set containers. Whenever I iterate over one of the concurrent/safe variants and call the remove method inside the iteration callback on that same container, the whole thing just hangs forever. It never finishes the traversal and never reflects the removals. My read is that iteration grabs some lock and then the remove call inside the callback tries to take the same lock, so it self-deadlocks.

What I actually want is dead simple: filter out entries in a single pass while iterating, without having to collect keys into a slice first and then delete in a second loop. That two-pass workaround is annoying and adds complexity, and this in-place delete-while-iterating pattern should just work.

So the fix needs to let me call remove from within the iteration callback for any thread-safe map or set type, and once the iteration finishes the collection should correctly show only the elements that weren't removed (removed ones gone, untouched ones still there). This has to hold across all the safe map types, the any-to-any, int-to-any, int-to-int, int-to-string, string-to-any, string-to-int, and string-to-string maps, and across the safe set types too, meaning the any set, the int set, and the string set. Basically iterating and removing on the same concurrent container should complete without hanging and end up in the right state every time.
