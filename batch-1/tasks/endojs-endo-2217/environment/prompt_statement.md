I'm deep in the peer connection layer of our distributed daemon and hitting two related bugs plus a usability annoyance. First, there's a nasty race when two peers connect to each other at the same time. If A dials B while B dials A, we end up with two open connections for the same pair, nobody arbitrates, and we get resource leaks and inconsistent state that blows up when objects get passed around. I want a new module implementing a connection manager that handles simultaneous inbound and outbound attempts for the same peer and picks exactly one winner deterministically, based on the peers' identities using lexicographic comparison of their ID strings. It also needs to entangle the connection attempts and propagate cancellation, so tearing down any one connection in a group cascades to all the related ones for that peer. And after a connection is fully torn down, a fresh connect attempt should cleanly re-establish, no lingering state getting in the way.

Second thing, object identity isn't preserved across remote round-trips. When I send a capability (a remotable object) to a remote peer and it comes back, say passed as an arg to a remote method that just returns it, my local code doesn't recognize it as the same object. I need round-trip identity preserved so a remotable sent over the network and returned is strictly identical to the original, since capability-based patterns rely on that equality check.

Oh and there's the intro thing. Right now both peers have to explicitly introduce themselves to each other before comms work, which is silly. It should be enough for only one side to do the introduction, and the other peer connects back without a separate explicit step, so the reverse connection is reachable after one side has connected. So: build out the arbitration module described above, and update the broader peer communication infrastructure so identity survives round-trips and a single introduction gives us bidirectional connectivity.
