I'm hitting a type mismatch bug in the pipeline expression evaluation code in the kubeflow/pipelines backend and it's driving me nuts. Numeric pipeline parameters get stored internally as floating-point numbers, so when a parameter holds something like 1.0 and I write a condition that compares it against a plain integer literal (say checking whether some counter equals 1 or a threshold equals 10), the evaluator blows up with a type compatibility error instead of just comparing the two values as the same number.

The thing is, the CEL language spec actually says this should work, numeric type promotion between int and double is supposed to be supported, so comparing an integer literal to a double parameter should succeed and evaluate to true. Right now it doesn't, which means pipeline authors have to know the internal storage type of their params and write explicit floating-point literals to dodge the error, which is confusing and leads to subtle mistakes. I don't want users to have to do that.

The root cause looks like the expression evaluation library is pinned at an old version that predates the cross-type numeric comparison overloads. Bumping it to a newer version should pull in the int/double comparison behavior described in the CEL spec. So the fix is upgrading that dependency so conditions using integer literals work correctly against floating-point parameter values without anyone having to write floats explicitly, bringing this in line with the spec and what people actually expect.
