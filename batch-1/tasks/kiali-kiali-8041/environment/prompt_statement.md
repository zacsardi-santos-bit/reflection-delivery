We've got a security smell in the service graph and mesh graph APIs, we're generating node and edge IDs with a cryptographically weak hashing algorithm that's considered outdated and spits out short 32-char hex strings that collide more than I'd like. I want to swap all of those identifier-generation functions over to a stronger algorithm that produces 64-character hex identifiers instead, both for security and so two different nodes or edges never end up sharing an ID.

The weak hash shows up in a few spots that all need the same treatment for consistency: the graph Cytoscape config layer that builds node and edge IDs, the equivalent config layer in the mesh graph API, and the Istio telemetry processing pipeline where we compute time series and edge traffic dedup hashes (that's both the main pipeline and the extensions appender). Update every one of those so node IDs and edge IDs in graph API responses, and the mesh graph responses too, come out as 64-character hexadecimal strings.

Then there's the golden test data. All the expected golden files under the graph and mesh API test directories need regenerating to reflect the new 64-char identifier values. Oh and while you're in there, the golden files should no longer end with a trailing newline, the last character in each file should be the closing brace of the JSON object. That's tied to a test infra cleanup: the comparison helper used to strip the last byte off the expected file before comparing against the actual API response, and we're removing that workaround so the golden files are easier to create and maintain. So make sure the helper compares the full file as-is and the goldens match without any trailing byte.
