I'm working with Cedar policies and I want the language to let me check a whole chain of nested optional attributes in one existence check, instead of writing a separate `has` check for each level. So if I want to safely touch something like a deeply nested optional path, I'd write a single existence check covering the entire path and have that count as a full guard for the chain downstream in the same condition.

The type checker needs to actually understand this. When the guarded path exactly matches the subsequent access, it should typecheck cleanly. But it still has to reject the cases that aren't actually safe, like when the access goes deeper than what I guarded, or when it accesses a different attribute at the same level than the one I checked. When it rejects, I want precise errors pointing at the unsafe access expression itself, with context about what was actually guarded, not some vague pointer at the whole expression.

Also the policy formatter needs to lay this multi-level existence syntax out right. Keep it compact and inline when it's simple, expand it with per-segment indentation when there are comments sitting between the attribute segments, and wrap it when the attribute names get long.

Oh and there's a related bug to fix while you're in here: when someone uses a reserved keyword as an attribute name in an existence check, the parse error currently points at the whole surrounding expression instead of just the reserved keyword, and the message isn't consistent with the other reserved-identifier errors. I want the error location narrowed to just that reserved keyword and the message to identify it as a reserved identifier like the rest of them do.

Without this I'm stuck writing cumbersome chains of separate existence checks just to safely reach nested optional attributes, or I'm denied a cleaner syntax the language really should support, so getting the type checker semantics right here matters for giving me accurate feedback on policies that use it.
