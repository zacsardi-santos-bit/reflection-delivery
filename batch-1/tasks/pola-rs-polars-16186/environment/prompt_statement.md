I hit a nasty silent bug with grouped rolling window ops. If I sort my DataFrame by the grouping column and then apply a rolling window grouped by that same column, the group key column in the output ends up with wrong values, the groups just get misassigned. No error, no warning, the computation runs fine and returns plausible-looking numbers that are actually attributed to the wrong groups. That's the dangerous part.

Simplest repro: I've got a tiny DataFrame with two rows, ids 1 and 2, each in its own group with a distinct timestamp. I sort by the group id column, then do a rolling window partitioned by that same id, and the group ids that come back don't match what I'd expect, they're out of order relative to the original groups.

Digging in, it looks like empty sub-windows are the culprit, that is, time windows that fall inside a group but contain no matching rows. Those empty windows seem to throw off the group key offset calculation so the key points at the wrong group. I want the fix so that even when a window within a group is empty, its group key still points to the correct group instead of getting offset.

Basically rolling aggregations with a grouping parameter should always give output where each row's group key lines up with the aggregation computed for that group and time window, and it shouldn't matter whether the input is sorted by the time index or by the group column, correctness should hold either way. Can you fix the rolling window implementation so grouping works regardless of input ordering?
