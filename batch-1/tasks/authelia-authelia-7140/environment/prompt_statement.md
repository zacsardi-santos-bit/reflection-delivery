I'm running Authelia with file-based logging and I want it to handle log rotation without me having to restart the whole service every time. On Unix the normal pattern is you send a hangup signal (SIGHUP) to the daemon and it reopens its log file so tools like logrotate can safely move or compress the old one. Right now Authelia just doesn't listen for that signal at all, so after rotation it keeps writing to the old moved file handle, which is useless, and the only fix is a full restart. That's disruptive for a long-running service.

What I want is a signal-listening service that gets registered when a log file path is actually configured. It should watch for the hangup signal and, when it fires, close and reopen the log file, creating a new timestamped log file so subsequent entries land in the fresh file. This service should be identifiable by the name "log-reload" and categorized as a "signal" type service. Important detail though: if no log file path is set, don't start this service at all, no point.

Oh and while you're in there, the error when the log file can't be opened is currently just the raw OS error, which makes it a pain to figure out what actually went wrong. I want that wrapped so it clearly says there was a problem opening the log file rather than dumping a bare OS-level error. The relevant logging and service startup wiring lives around Authelia's logging setup and the service registration code, so that's where the signal handler and the "log-reload" registration should hook in. Together the runtime reload plus the clearer message make operating this in production a lot smoother.
