I'm chasing a starvation bug in our VMM where a block device sitting on a slow drive can hog the whole processing loop and choke every other virtio device (network, entropy, vsock, all of them). Traced it back to how we handle the virtio used ring in `@src/devices/src/virtio/queue.rs`: right now every time we add a descriptor to the used ring, we immediately bump the ring's visible index and flush it out to the guest. So when a device is chewing through a batch of descriptors one at a time, the guest sees each one the instant it's added, and each of those can kick off its own interrupt or notification cycle. That per-descriptor flush is what's killing batching, the slow block device just adds descriptors one by one and ties up the loop so nothing else gets CPU.

What I want is to decouple adding a descriptor from publishing the ring index. After the change, adding a descriptor should only write the entry into the ring internally, the guest-visible index shouldn't move at all until a separate explicit publish step gets called. So devices that process descriptors in a loop should add all of them first, then call that publish step once at the end.

Oh and this'll break existing callers that assume the ring index updates right after each add, anything that adds a descriptor and then checks the ring index needs to be updated to call the new publish operation explicitly first, otherwise it'll read a stale index. Please hunt those down across the virtio device code and fix them too.
