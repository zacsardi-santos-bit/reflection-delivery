I'm working on the secret management piece that renews secrets out of a vault on a schedule, and the renewal timing logic is driving me nuts because it's non-deterministic. Right now when it figures out how long until a secret needs renewing, it measures a duration from the current wall clock time, so every call returns something different and I can't write repeatable tests against it or reason about ordering across secrets.

I want to refactor so instead of a relative duration, the method that computes when a secret should be renewed returns an absolute point in time plus a boolean saying whether that time is even known. Calling it multiple times on the same secret has to give the same answer regardless of when I call it, that's the whole point.

Also I need it to derive renewal timing from TLS certs embedded in the secret data, not just explicit TTL or lease duration values. When the secret data contains a certificate, compute the renewal time from the cert's own validity window (its start and end dates) scaled by the configured duration ratio, so cert-bearing secrets don't need a separate TTL field, the cert itself drives the schedule.

Then the function that finds which secret to update next needs updating to match. It should return an absolute renewal time rather than a duration, only consider secrets that actually have a known renewal time, and when comparing pick the one with the earliest absolute time. If no secrets have a known renewal time the "next update" result should clearly signal there's nothing to update. And wherever we schedule the next update timer, that needs to convert the absolute time back into a duration before scheduling, oh and make sure that conversion happens right at the scheduling boundary so everything upstream stays absolute.
