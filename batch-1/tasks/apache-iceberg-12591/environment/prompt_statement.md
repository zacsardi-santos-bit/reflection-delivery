I'm working on adding support for vended storage credentials in Iceberg's file I/O layer. Our catalog server can return short-lived, path-scoped credentials in its table response — for example, temporary access credentials for a specific S3 bucket or an OAuth token for a GCS bucket. Right now there's no standard way to accept those credentials and pass them into the file I/O implementation that will actually read and write the table data.

I need to introduce a new optional contract that file I/O implementations can adopt, where the caller provides a list of storage credentials (each pairing a URI prefix with a configuration map) before initialization. When credentials are provided, they should override the corresponding static credentials in the normal configuration properties. For storage systems like S3 and GCS that only make sense with a single set of credentials, providing more than one matching credential should result in a clear, descriptive error.

The utility that instantiates file I/O implementations needs to be updated to accept these credentials and forward them to implementations that support the new contract. A delegating file I/O that resolves the right backend based on path scheme must also propagate its credentials to the backends it loads.

Importantly, credentials must survive both standard Java serialization and a secondary serialization mechanism used in distributed cluster environments, so that file I/O instances continue to work correctly after being distributed across a cluster. The credential objects themselves must also be serializable via both mechanisms.
