I'm adding vended storage credential support to Iceberg's file I/O layer. Our catalog server (REST catalog) can hand back short-lived, path-scoped credentials in its table response, think temporary access creds for a specific S3 bucket or an OAuth token for a GCS bucket, and right now there's just no standard way to take those and pass them into the file I/O instance that actually reads and writes the table data. Clients are stuck relying on long-lived static creds configured cluster-wide, which is a security risk and blocks per-table credential isolation, so I want to fix that.

What I need is a new optional contract that file I/O implementations can adopt, where the caller provides a list of storage credentials before initialization, each one pairing a URI prefix with a config key-value map. When creds are provided they should take precedence over any matching static credentials in the normal properties map. For storage that only makes sense with a single credential per type like S3 and GCS, supplying more than one matching credential should fail with a clear, descriptive error rather than silently picking one.

The general file I/O loading utility needs updating to accept these credentials and forward them to any implementation supporting the new contract. Also the delegating file I/O that routes ops to scheme-specific backends based on path scheme has to propagate its own credentials down to whatever backends it loads. Oh and one big thing, the credentials have to survive both standard Java serialization and the secondary serialization mechanism (Kryo) we use in distributed cluster environments, so file I/O instances keep working after they've been shipped around a cluster. The credential objects themselves need to be serializable via both mechanisms too.
