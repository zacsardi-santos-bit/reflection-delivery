I'm working on Rally and hit a gap where custom request timeouts, custom HTTP headers, and opaque request identifiers set in my track config are just silently dropped. Even when I specify them per operation, the underlying Elasticsearch API calls never see them, which is a problem because a lot of our deployments rely on opaque IDs and headers for tracing, correlation, and routing (some plugins and middleware straight up require them). I want the main benchmark runners to forward a request timeout, custom headers, and an opaque identifier when those are present in the operation params. That's bulk indexing, searching/querying, force merge, index creation, cluster health, raw requests, and index stats.

The forwarding rules differ depending on the layer. For operations going through the low-level transport directly, the opaque identifier should get injected into the headers dict under the opaque-ID header key, and the request timeout should go into the query params dict. For operations using the higher-level client methods, the timeout and opaque identifier should be passed as dedicated keyword arguments and the headers dict passed directly. Also the search parameter source needs to surface these three fields in its output so they flow through to the query runner, and when a value isn't configured the field should still be present but set to null/absent rather than missing from the dict entirely.

Oh and one more thing, for snapshot restore when no body is specified, don't pass an explicit null body to the API, just omit it.

The key thing throughout: when a value isn't provided, don't send it at all rather than sending null.
