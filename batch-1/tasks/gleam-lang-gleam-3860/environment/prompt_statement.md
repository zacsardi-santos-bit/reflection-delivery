I'm hitting a gap in the Gleam compiler around variant inference for built-in prelude types. So the compiler already knows how to narrow pattern matches for user-defined types: if a value is always constructed with one specific constructor, it treats that value as only ever being that variant and doesn't force me to handle the others. Great feature, except it totally ignores the built-in types like booleans and results.

Concrete example, when I match on a literal `True`, I'd expect only the true branch to be required since that value can't be anything else, but right now the compiler either errors or makes me add a pointless catch-all for false. Same deal with results: if a variable is always constructed as the successful `Ok` variant, I should be able to match just the successful cases without an error branch for the failure side, but the compiler still acts like it could be any variant and throws exhaustiveness errors or demands wildcards.

It looks like the root cause is that the prelude's built-in constructors don't carry the variant info that custom constructors already carry. So the fix is to make those built-in type constructors (booleans, results, etc.) record the same variant information, so the narrowing logic can kick in and correctly reduce the required pattern match branches when a value is known to always be a specific built-in constructor.

Oh and while we're in there, the "add missing patterns" code action in the language server needs to handle this too. Right now it works on let-bound literal values but falls over on typed function parameters of built-in types. I want it to work correctly when the match subject is a typed function parameter, not just the let-bound literal case.
