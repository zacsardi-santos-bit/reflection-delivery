I'm cleaning up the CRI image service in containerd and the big problem is it's welded to the full plugin config. All the image stuff, snapshotter choice, registry mirrors and auth, pull timeout, pinned images, is buried inside a general-purpose config struct that also carries runtime, networking, and unrelated settings, so I literally can't spin up or test the image service on its own without building a whole plugin context with runtime details. I want to pull image-specific settings into their own dedicated config structure, separate from the broader plugin config. While I'm at it the old single "sandbox image" string is too limiting, I need to track multiple pinned images, so replace that concept with a named map of pinned images.

The image service constructor should take this new image config plus a simpler options struct holding just what it needs (content store, image store, filesystem paths, runtime platform info, and the client) instead of demanding the full plugin context. Couple related moves too: the gRPC-level image operations should live on a dedicated wrapper type rather than hanging directly off the core service struct, keeping transport separate from core logic, and a utility function for parsing image references should move into a shared utilities package so it's reusable.

Also the snapshotter resolution is annoying right now, when a requested runtime handler isn't found it errors out, I want it to fall back gracefully to the default snapshotter instead. Oh and the image service field the server exposes should be exported so other parts of the system can use it directly.

Last thing, the new image config needs its own validation function so I can validate it independently of the runtime plugin config, and it should reject bad combinations, for instance if registry mirrors and a registry config path are both set at the same time that's invalid and should fail. Net goal is the image service can be used and tested in isolation with clearer boundaries between image management and runtime management.
