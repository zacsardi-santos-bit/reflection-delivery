I'm extending a lint rule in the linter that flags bad suffix args passed to a path object's suffix-replacement method (the `with_suffix`-style call on path types). Right now it only catches the dotless case, where someone passes a suffix string that's missing its leading dot, and that would blow up at runtime. The rule has a decent story there since a dotless suffix has an obvious correction (just insert the missing dot), so it offers that as an automatic fix. But there's another runtime failure I keep hitting that we don't catch at all: passing a lone dot `"."` as the suffix. Python's path library rejects that too and raises at runtime, so it'd be great to flag it statically instead of letting it crash. Trouble is the current logic treats any string that starts with a dot as valid, so a bare `.` slips right through.

I want to broaden the rule to also flag the lone-dot argument across all the supported path types. The two cases should behave a little differently though. For the lone-dot case the right fix is ambiguous (maybe drop the arg, maybe extend it to a real extension, maybe rethink the call), so don't offer any automatic fix there, and the diagnostic message should say the suffix is just plain invalid rather than reusing the dotless "missing leading dot" wording, which can stay as-is for the existing case. Oh and since the rule now covers a wider category than just missing-dot suffixes, rename it to reflect that broader scope and update all references to the old name throughout.
