I'm hitting a wall trying to put a gRPC service behind our GraphQL gateway when the protobuf messages use `oneof` fields, you know, where a message can hold exactly one of several possible sub-message types. This is super common in real services (think a response that's either an error payload or a success payload, basically a discriminated union), so not supporting it means we just can't expose whole categories of gRPC backends, which is a big gap.

Right now when the gRPC backend returns a binary protobuf response that has one of these oneof fields set, things fall over. The system either crashes or hands back wrong data instead of figuring out which variant was actually populated and mapping it to the matching GraphQL union type. I want it to accept configs where proto messages contain oneof fields in both request and response message positions, and when a response comes back it should correctly deserialize the binary protobuf, identify which variant of the oneof was set, map that active variant to the right GraphQL union member, and return all the relevant fields for it.

Also the schema output needs to line up. Both the client-facing view and the fully merged config view should correctly represent all the input variants I've defined, the output union types, and their associated query fields. And inline fragments on the union members in a query should work too, returning the fields from whichever oneof variant the gRPC response actually set, so if I fragment on the success type I get the success fields and same deal for the error type.

Basically I need oneof to be a first-class thing end to end: config acceptance, binary deserialization, variant detection, union mapping, schema rendering, and inline fragment resolution all behaving correctly together.
