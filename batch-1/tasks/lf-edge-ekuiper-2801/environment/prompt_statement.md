I'm building out a stream processing pipeline where each event carries a time range, so there's a start time, an end time, and a current timestamp, and the annoying part is that multiple upstream rules keep producing overlapping ranges, meaning the same span of time gets reported more than once and my downstream sinks end up chewing on redundant data for intervals that were already handled. I want a dedup trigger node that lives in the existing node package right next to the other processing node implementations, and it should keep a running history of all the time intervals it's already processed, then for each new incoming event emit only the portions of that interval that haven't been covered before.

So concretely, when an interval shows up that's completely new, emit the whole thing as a single new range. When it partially overlaps stuff I've already seen, only emit the uncovered sub-intervals. When it's fully covered by history, emit nothing. The history should merge intervals as new ones arrive so it stays clean.

Also I need it memory-bounded, so on each invocation prune old history entries that fall outside a configurable expiration time window. If an incoming interval's entire span falls outside that window boundary, it produces no output at all, and if it's only partially expired, just consider the non-expired portion for the dedup logic.

Oh and ordering matters a lot here because events can arrive out of order. I want results emitted in ascending order of the interval's end time, not in arrival order, so use a priority queue to hold pending requests and make it orderable by the end-time value of each request. The dedup logic plus that priority queue should both go in that same node package.
