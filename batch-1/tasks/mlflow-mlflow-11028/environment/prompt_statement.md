I'm hitting a region detection bug in the MLflow S3 artifact repository over in `@mlflow/store/artifact/s3_artifact_repo.py` and it's biting us in permission-restricted environments. The way the code figures out an S3 bucket's AWS region right now, it only pulls the region out when the initial bucket-existence check (the head-bucket style call) throws an error, reading it from the error response's HTTP headers. Problem is, in our setup the IAM policy only grants limited access, so that bucket check actually returns a normal successful response instead of raising anything. The region is sitting right there in the successful response's HTTP headers, but the current logic never looks there when there's no exception, so the S3 client ends up built without the correct region and we get these annoying downstream connectivity and auth failures that are a pain to diagnose because it silently runs with the wrong region.

What I want is for the region extraction to also cover the success path. So when that bucket check comes back with a successful (non-error) response and the region is present in the response's HTTP headers, use that region to configure the S3 client, exactly the same way it would if the check had thrown an error. Keep the existing error-based path working like it does today, that behavior shouldn't change at all. And everything else about how the client gets built, the credentials, the TLS/SSL verification settings, and the endpoint URL, should stay unaffected no matter whether the bucket check succeeded or raised. Basically both branches (success and error) should end up feeding the same region into the client config when the header's there.
