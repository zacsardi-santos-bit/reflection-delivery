I'm cleaning up a Go LLM library and the core language model interface is bugging me. Right now every type that implements it has to provide a method for counting tokens in a string, which feels totally out of place. Token counting is a generic utility thing, it doesn't belong per-model, and I keep writing boilerplate for it on every new integration even when my use case never touches token counting.

What I want is to drop the token-counting method from the language model interface so that satisfying the interface only needs the methods that are actually core to invoking a model (calling it to generate text, that kind of thing). The token counting shouldn't be part of the interface contract at all anymore, so existing types that implement the interface don't have to supply it just to compile against the interface. Instead I'd rather have token counting live as a standalone utility function, decoupling it from the model abstraction entirely.

Big thing though, all the existing chain stuff has to keep working after this. Sequential chains, map-reduce, document chains, etc., anything that depends on the language model interface should behave exactly the same as before. So wherever chains currently lean on that counting method, rewire them to use the standalone utility instead. Point is to make the interface leaner and lower the barrier for anyone writing a new model integration, without breaking anything downstream.
