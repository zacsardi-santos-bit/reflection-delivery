I'm hacking on the Radius CLI and hit a gap in the run command, the one that deploys an app and streams logs for it. Right now when I run it, it only wires up port-forwarding for the application itself. Problem is we ship a Radius Dashboard, a web UI that runs inside the cluster alongside the control plane, and devs have to manually set up forwarding to reach it. I want the run command to auto-detect that dashboard and port-forward to it too, so the UI is reachable the moment someone runs their app, no extra steps.

So the behavior I'm after: when the run command fires, check the cluster for a running dashboard deployment. If it's there, stand up a port-forward session for the dashboard alongside the existing app port-forward. If it's not found, just do the app forward like before and don't blow up.

While I'm in there, the forwarding logic needs a refactor. Instead of identifying pods by plain application name strings, it should use Kubernetes label selectors as the primary way to pick which pods to forward to, and that goes for both the app and the dashboard paths so it's consistent. I want a dedicated function that builds the label selector for a named application (keying off the specific app-name label), and a separate one that builds the selector matching dashboard pods (matching on the dashboard component's name plus its group affiliation label). Keep these reusable and well-defined so both forward paths can lean on them. Basically it's about removing that manual friction, oh and making sure the not-found case degrades gracefully to app-only.
