I'm working on error diagnostics for our app update downloads from the vendor server, and the messages we produce when the server hands back garbage compressed data are basically useless. The main gap is when the response body can't even be opened as compressed content at all, decompression never starts, and right now that case looks identical to a stream that opened fine but got truncated mid-way. I want a distinct error for the can't-open-the-compressed-reader situation so operators can actually tell what happened instead of guessing it was a network interruption.

Also, vendor servers sometimes stuff a human-readable error message inside or alongside binary junk in the body, and we're throwing that away today. I want to pull those readable bits out and put them in our error output so there's something actionable to look at when an update download blows up.

To make this work I need two little utility pieces. One wraps a data stream and holds onto the most recently seen bytes efficiently, so after a failure we can inspect what came through even if we never fully buffered the stream. The other scans a byte array and grabs contiguous runs of readable text, skipping anything shorter than 5 characters (too noisy to bother with) and joining the segments it does find with " ... " between them. Weave both into the download path so the compressed-open failure and any embedded text both surface in the error we report.
