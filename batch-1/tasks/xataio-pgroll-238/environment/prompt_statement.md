I'm hitting a couple of bugs in our schema migration tool, specifically the operation that adds a foreign key constraint to an existing column as a non-breaking, dual-version migration (the kind where both old and new schema views coexist during transition).

First bug: when the column being constrained has a default value, that default gets silently dropped in the migrated view. So inserts going through the new schema version that omit the column either fail or produce wrong results, even though there's a default defined. I need the default preserved and respected the whole way through, while the migration's active and after it completes, so inserting a row without specifying that column still applies the default like you'd expect.

Second bug: if I add a foreign key constraint to a column that already has an FK constraint from an earlier migration, the old constraint vanishes once the new migration finishes. Applying an FK migration should keep any prior foreign key constraints on that column around, not clobber them. Also during the transition, the newly added FK should live on the temporary duplicate column under a temporary name, then get renamed back to the original name on completion, so watch that the rename logic doesn't drop the existing one.

Oh and as part of this I need a little test helper that can check whether a named constraint exists on a given database table, so we can actually assert these behaviors in tests. Without these fixes it's just unsafe to incrementally evolve columns that already have defaults or prior FK relationships, the schema ends up inconsistent between what the database has and what the app code thinks it has.
