I'm building out a cryptocurrency service on top of a blockchain framework, and I've got a gap that's really biting me. Right now when a transfer transaction fails, say the sender doesn't have a wallet yet, or the recipient doesn't have a wallet, or the sender just doesn't have enough funds to cover the transfer, the whole thing gets silently ignored. It still gets recorded into the blockchain and committed to a block like nothing went wrong, so from the outside a transfer that bombed on insufficient balance looks identical to one that actually went through. That's useless for clients, there's no way to give users real feedback about why their transfer didn't take.

What I want is proper execution error reporting so that after a block is created, a client can hit the blockchain explorer and query a committed transaction's status and get back a structured result telling them whether it succeeded or failed. Successful transactions should come back marked with a success status. Failed transfers need an error status carrying a numeric code that pins down the exact reason, one code for sender wallet not found, one for receiver wallet not found, and one for the sender having insufficient balance, so downstream systems can react per failure type.

Also while I'm in here the wallet API endpoints need to behave sanely, so querying a wallet with a malformed key should return an error saying the request parameter was invalid, and querying for a wallet that hasn't been committed to the blockchain yet should give back a wallet-not-found error rather than something confusing. The transaction execution logic and the wallet query handlers are the places to wire this up, threading the execution result through so it surfaces via the explorer API. It's fine to keep the actual transfer semantics the same, I just need the pass/fail plus reason to actually make it out to API consumers instead of getting swallowed.
