I'm on the Envoy Gateway xDS translation layer and hit a gap with upstream TCP keepalive. Operators can set TCP keepalive on upstream connections through backend traffic policies (probe count, idle time before probing kicks in, and the interval between probes), and the API accepts those and stores them in the intermediate representation just fine, but they never actually make it into the Envoy cluster config. So the proxy keeps making upstream connections with no keepalive at all no matter what the policy says, which is bad because long-lived upstream connections can silently drop and you end up chasing weird connectivity failures with backend services that are really just missing keepalive.

We already handle TCP keepalive on the listener side, and the IR already has a type for TCP keepalive config, it's just that when the translator builds clusters for upstream connections it ignores any keepalive settings present on the route. I want that fixed so when a route has TCP keepalive in the IR, the translator maps the probe count, idle time, and probe interval fields onto the equivalent Envoy cluster upstream connection options (the keepalive params under the cluster's upstream connection options). 

The main case to get right is a route with all three params configured, probe count plus idle time plus probe interval, producing a cluster where those values show up properly in the upstream connection options. There's a new xDS translation test case for upstream TCP keepalive that should pass, validating the full round-trip from IR input to the expected cluster YAML output, so make sure that works end to end.
