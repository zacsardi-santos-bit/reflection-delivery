I'm adding shared secrets to our service platform. Right now every secret is scoped to a specific named service, which means if two services need the same secret we end up duplicating it, and that's a pain operationally plus a consistency risk. I want a "shared secret" concept stored in a common shared service location that any service can reference, with a distinct reference format so we can tell shared secrets apart from the regular service-scoped ones.

A few things need to work. The secret reference detection and name extraction logic should recognize both the existing service-scoped format and the new shared-prefixed format as valid references, and pull the name out correctly for each. When we fetch the hash of a shared secret the lookup should read from the shared service storage location instead of the individual service directory.

On the CLI side for managing secrets, I want a new option so users can create or update a shared secret without passing a service name. A cluster list is still required for shared secrets though, so if it's missing the command should error out clearly and exit early. Also the confirmation output after adding a shared secret should print the correct shared reference format so folks know how to drop it into their service config.

For local dev runs, the code that decrypts secret env vars needs to handle the two types separately. Service-specific secrets get decrypted using the service context, shared ones using the shared service context, and then both sets get combined and returned together. Pull the single-service decryption into its own helper function so it can be reused cleanly for both paths, and keep the behavior where any decryption failure still causes an early exit.
