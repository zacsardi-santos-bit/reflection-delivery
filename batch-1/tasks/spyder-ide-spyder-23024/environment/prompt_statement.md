I'm poking at Spyder's plugin config system and hit a gap in how shortcut defaults get validated. When a plugin hands over its default keyboard shortcuts, the keys are supposed to follow a strict two-part shape: a context identifier, then a single separator, then the shortcut name. Problem is right now nothing checks that. If a plugin dev accidentally gives a key with no separator at all, or one with too many separators, the bad config just sails through and gets accepted silently. Then later when the shortcuts machinery tries to parse those keys everything falls apart with confusing, hard-to-trace errors, and people burn hours debugging what turns out to be a typo in a shortcut key.

What I want is for the configuration object to validate shortcut key names right when it's created (at initialization time), not deferred until the shortcuts are looked up or applied later. So a key that has no separator between context and name should be rejected immediately with a clear error, and a key with more than one separator should also be rejected immediately with a clear error. Basically fail fast at config load time so the mistake is obvious right away instead of quietly corrupting the shortcuts system downstream. Oh and this also makes the contract for what a valid shortcut key looks like explicit and actually enforceable, which is kind of the whole point. Both malformed cases (zero separators and more than one) need to raise on construction of the config object.
