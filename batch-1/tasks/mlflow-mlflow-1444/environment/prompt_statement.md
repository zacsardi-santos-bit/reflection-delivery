I'm adding pagination to MLflow's run search and hitting the classic problem where searching runs just dumps every matching run back in one plain list, so with big experiments there's no way to grab results in chunks or continue from where a prior search left off. What I want is for the result to still behave like a list (so runs are accessible by index and existing callers don't break) while also carrying a pagination token attribute that callers can inspect, and when more results exist that token gets passed into a follow-up search to pull the next page.

The refactor I have in mind: the public `search_runs` method on the abstract base store becomes non-abstract and does the wrapping into a special list-like object that also holds the token. Concrete backend stores stop overriding that public method and instead implement a new private internal method (think `_search_runs`) that does the actual search-and-paginate work and returns a tuple of the runs list plus the next-page token. The public method just calls the private one and wraps the pair.

For stores that don't do real pagination yet, the token comes back as None to signal no further pages, and if a caller hands in a non-empty pagination token the store should raise rather than silently ignore it, though an empty-string token needs to succeed fine. Oh and the high-level client interface should accept an optional pagination token and pass it through to the underlying store too.
