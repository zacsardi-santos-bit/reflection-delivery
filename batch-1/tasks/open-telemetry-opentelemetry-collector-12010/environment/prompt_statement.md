I'm graduating the storage extension in the OpenTelemetry Collector out of its "experimental" namespace into a stable home under the conventional cross-component "x" naming pattern that other extension packages in the project already follow. It's been stable long enough that keeping it under "experimental" is just misleading about its maturity, and I want it to read as a first-class supported API.

While I'm at it I want to clean up how storage operations are represented. Right now an operation is exposed as this opaque pointer-type alias over an unexported struct, which is awkward for anyone implementing a custom storage backend. I'd rather make the operation type a plain exported concrete struct with exported fields so implementors can work with it naturally, and then the client interface's batch method should just accept operations as straightforward plain pointer arguments to that concrete struct instead of going through the alias.

So the deliverables: a new storage module living at the correct stable path (the "x" convention, mirroring the functionality that was in the experimental namespace), the updated client interface with the simplified batch signature, and the exported concrete operation struct. Oh and everything needs to actually build, so all the module dependency manifests across the repo that referenced the old experimental storage path need to point at the new stable path, and the builder configuration files need replace directives added for the new module path. The old experimental package should stick around but be deprecated with forwarding aliases so existing users don't break, backward compatibility matters here. Can you wire all of this up throughout the repository?
