I'm working on the table function execution framework in our query engine and hit an annoying gap. Table functions have a two-phase lifecycle, a bind phase that resolves input arguments and produces a bind state (including output schema and cardinality), then an execution phase that actually processes and emits data. The problem is the execution and scanning methods, the ones that create partition states, poll for output batches, and finalize execution, don't get the bind state at all. They only receive the operator state and partition state, so if an implementation needs to reference its original config during execution it's stuck either duplicating that bind-time data into the operator state or just going without.

I want to thread the bind state through to all of these downstream methods so it's available when needed. That means updating the trait definitions for both execute-style and scan-style table functions to accept the bind state as an extra parameter in the relevant methods (partition state creation, polling, and finalization). Oh and the bind function itself needs cleanup, it's currently an instance method but there's no real reason for it to be tied to a struct instance, so make it a plain associated (static) function on both the execute and scan traits.

Once the signatures change, all the existing table function implementations scattered across the codebase need to be brought in line, otherwise nothing compiles. The series-generating table function especially should stay fully working, it should still be able to execute a generate-series call with valid start, stop, and step values through the updated interface. Passing bind state through gives implementations direct access to original configuration without copying it into downstream states, which simplifies things and opens the door for execution logic that depends on bind-time decisions.
