I've got a NATS cluster running with a bunch of gateway nodes and I have certificate stapling enforcement turned on for TLS verification (OCSP stapling basically). The problem I keep hitting is around cert rotation. When I rotate the TLS certs on one of the gateway nodes by editing its config file and triggering a reload, the cluster doesn't fully come back. Only some of the expected gateway connections re-establish, the cluster ends up partially disconnected, and cross-cluster messaging just breaks after that. It doesn't self-heal either, which makes cert rotation basically unsafe in production for anyone running stapling-enforced verification.

Digging into it, it looks like the OCSP/cert verification monitor only gets restarted during a reload when the top-level listener TLS settings change. If I only touch the gateway-specific TLS certs, that same restart path never fires, so the verification process keeps hanging onto the old certificate state and can't reconnect with the new certs. That's the root cause as far as I can tell, the restart is gated on which part of the TLS config changed.

What I want is for the cert verification process to be restarted unconditionally on every reload, regardless of whether it was listener TLS or gateway-specific TLS certs (or anything else) that changed. So after rotating a gateway node's certs via config update plus reload, the monitor should pick up the new certs, all nodes should re-establish the full expected number of outbound gateway connections, and clients on any node should be able to send and receive messages to clients on any other node once the reload finishes. The reload-handling logic is where this lives, so the fix is making that restart happen every time rather than conditionally.
