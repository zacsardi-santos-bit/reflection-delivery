I'm hitting a nasty edge case in our workflow automation engine around skipped jobs. When a job is meant to be skipped because an upstream dependency got skipped from a false condition, the engine still goes ahead and tries to expand that job's matrix strategy, which means it evaluates the dynamic template expressions sitting in the matrix values. If any of those expressions are invalid or lean on context that just isn't available at that point, the whole thing blows up with an error instead of cleanly skipping. So the run ends up in a broken state rather than propagating the skip downstream and finishing with a skipped status like it should.

What I want is for the engine to figure out a job is going to be skipped before it does any matrix expansion work at all. If a job's being skipped, either because its dependency was skipped or because its own condition evaluates to false, and it has a matrix strategy, don't expand it, just record it as a single skipped job entry with no interpolation or evaluation of the matrix expressions whatsoever. Same deal when a skipped job references an external job template, don't resolve the template, just record the one skipped entry. Oh and if a job's matrix produces zero combinations (an empty list), treat that as skipped too with a single recorded entry. In all of these cases any downstream jobs depending on the skipped one need to be skipped as well, and when every job in the run ends up skipped the overall workflow run should finalize with a "Skipped" status. Operators expect a skipped job to propagate cleanly no matter its config, without these confusing runtime errors.
