I'm deep in the Gleam compiler's JavaScript codegen for bit arrays and the endianness and signedness handling is just broken when we target JS. If I write a bit array with a little-endian or big-endian qualifier on an integer segment, or use signed/unsigned, the emitted JavaScript either drops the qualifier on the floor or spits out code that ignores the byte ordering entirely. Same story for sized floats, 32-bit floats in bit arrays aren't supported as a general feature and float endianness isn't handled at all.

What I want is for the JS target to actually support the full set of bit array options that already work elsewhere. Concretely, constructing with a little-endian integer segment should give me bytes least significant first, and big-endian should give most significant first. A 32-bit float segment needs to produce the correct 4-byte IEEE 754 single-precision bytes, and a 64-bit little-endian float should come out in the right little-endian sequence. On the pattern matching side, signed integer segments have to interpret two's complement correctly, and little-endian integer or float patterns need to read bytes in the right order. Also negative integers in sized segments should produce correct two's complement bytes. And oh, the 32-bit float support should be a standard feature across all targets, not gated as JS-specific.

The runtime helpers the compiler emits calls to (in the JS prelude) need updating to accept and correctly use these endianness and signedness parameters, both for construction and for matching. Right now they either don't take those params or don't respect them. This matters because binary protocols, file formats, and network data all lean on specific byte orderings and sign conventions, so without this Gleam-on-JS silently produces wrong bytes or fails to decode incoming data. It should behave the same as the other targets.
