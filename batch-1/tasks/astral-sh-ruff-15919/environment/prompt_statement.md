I've been leaning on the linter's auto-fix for those unnecessary native constructor calls in Python, you know the rule that spots stuff like `int(5)` and rewrites it to just `5`. Most of the time it's fine but I keep hitting cases where the fix it spits out is actually broken, and it's the signed-number ones that bite.

So when the constructor wraps a number that's got a unary plus or minus on it, and that expression lands in certain spots, the replacement either won't parse or it quietly changes what the code means. The ones I've seen: when the signed literal ends up as the left operand of an exponentiation (precedence goes wrong, so `-2 ** 2` vs the intended thing), or when it's the object of an attribute access, or the callee of a call, or the target of a subscript, and also inside an await expression the result can just be a straight syntax error. In all those the fix needs to wrap the replacement in parens to keep the original semantics and stay valid. Oh and even when the signed literal sits on the right-hand side of an operator, like inside a subscript index or a call argument, I still want the parens added there.

Separately there's the comment thing. If the constructor call has an inline comment between the parens (something like between the opening paren and the argument), the fix drops it silently but still gets applied as though it's totally safe. That's not safe, it's losing a comment, so it should be flagged unsafe in that case.

The fix logic lives around the unnecessary-literal-constructor rule, so that's where the paren-wrapping and the unsafe marking need to go. Basically I want parens added whenever they're needed to preserve meaning and valid syntax, and fixes marked unsafe whenever they'd silently remove inline comments. Auto-fixes that break syntax, shift semantics, or eat comments really undercut trust in the fixer, especially for folks applying fixes automatically through editor integration or CI where nobody's eyeballing the diff.
