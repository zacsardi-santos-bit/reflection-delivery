I'm digging into authorization check perf in OpenFGA and hit a gap around userset relationships that use set operations. We already have an optimized fast-path for tuple-to-userset (TTU) relations that combine union, intersection, and exclusion, but there's nothing equivalent for plain userset relationships. So when a model defines a group's membership as, say, a union or exclusion of sub-relations, the check falls back to the slower general evaluation path even when a faster route exists. I want to close that gap.

What I need first is a new analysis method on the type system (a "weight-2" eligibility check) that takes the object type, relation, user type, and the list of directly related userset types and returns a bool telling me whether that userset relation qualifies for fast-path evaluation. It should return true for userset patterns built from direct assignments, computed relations, union, intersection, and exclusion/difference set operations, plus conditional relations. It should return false for recursive or self-referencing usersets, anything involving wildcards or public membership, tuple-to-userset chains, or cases where the userset itself contains another nested userset as a member.

Then the actual check resolver needs to use this new fast-path when the conditions hold, correctly evaluating access through multiple parent userset types and producing the right allow/deny decisions for complex algebraic relation combos, so excluded users get denied and eligible users get granted, matching the correctness we already have on the TTU side.

Oh and while I'm in there, there's a naming inconsistency in the internal tuple mapper code in the graph resolution package. An older name for a userset mapper kind and its corresponding struct should be renamed to a cleaner, consistent name throughout, so it lines up with the rest of the codebase.
