I've been digging into a nasty block sync bug where a single malicious peer can permanently stall a node. The attack is simple: the peer first reports an absurdly high blockchain height (think max integer value), our sync pool records that as the target to reach, and then the same peer reports the real, much lower height. Problem is our maximum-height tracking only recalculates when the peer responsible for the max gets removed with an exact height match, so the pool never corrects its target and just keeps chasing an impossible number forever, never transitioning out of block sync. That's a denial-of-service vector needing no special privileges, and a stuck node can't participate in consensus, so I want it fixed.

What I need is for the block sync pool to notice when a peer reports a height (or a base) that's lower than something it claimed before. On a legit network this never happens since a blockchain only grows, so any peer doing this is malicious and should get kicked out of the active peer set and temporarily banned. Once that peer's gone the pool needs to recalculate the true maximum known height from the remaining honest peers so it can proceed and catch up normally. Oh and I also want a way to query whether a specific peer is currently banned, so other parts of the system (and tests) can confirm the malicious peer was actually identified and excluded.
