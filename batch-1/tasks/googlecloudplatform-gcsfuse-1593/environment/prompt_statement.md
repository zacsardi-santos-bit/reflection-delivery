I'm working on improving how GCS FUSE handles its metadata cache TTL configuration. Right now, when the tool starts up it immediately merges the separate stat-cache and type-cache TTL settings into a single combined value by taking the minimum, and that merged value is what gets stored and passed around. I'd like to change this so that the two TTL settings are kept separate all the way through — each stored as its own independent value — and the logic for computing the effective TTL from all the inputs is moved into a dedicated, reusable function rather than being inlined at every use site.

The resolution logic should work as follows: if the config-file TTL is set to -1, the effective TTL should be the maximum possible duration (essentially infinite); if it's 0 or a positive number of seconds, that value in seconds is the effective TTL; if the config-file TTL is not set at all, the tool should fall back to the old flag-based behavior — if either of the two old TTL flags is zero, the effective TTL is zero, otherwise it's the minimum of the two flag values rounded up to the nearest second.

I also need to add an upper-bound validation for the config-file TTL. Since the TTL is stored as a number of seconds that gets converted to a time duration internally, there is a maximum integer value that can be safely converted without overflow. If the user provides a value exceeding that maximum, the configuration should be rejected with a clear, human-readable error message rather than silently producing a bad duration value.

The default values for stat-cache capacity and the stat/type cache TTL should be extracted into named constants rather than hardcoded literals, so they can be referenced consistently from both the flag definitions and the shared TTL computation logic.
