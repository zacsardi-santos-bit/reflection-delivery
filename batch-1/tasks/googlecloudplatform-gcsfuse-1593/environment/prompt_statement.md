I'm cleaning up how GCS FUSE deals with its metadata cache TTL config and could use a hand. Right now at startup the tool immediately smashes the two separate settings, the stat-cache TTL and the type-cache TTL, into one combined value by taking the minimum, and that merged number is what gets stored and passed everywhere. Problem is the original individual values are gone before anything downstream can inspect or log them independently, and every use site that wants the effective TTL has to lean on that pre-merged value instead of the raw inputs. I want the two TTL settings kept separate all the way through, each stored as its own independent value, both still defaulting to 1 minute when nothing's explicitly set.

Also I want the resolution logic pulled into one dedicated reusable function rather than inlined at every call site. It should work like this: if the config-file TTL is -1, the effective TTL is the max possible duration (basically infinite); if it's 0 or a positive number of seconds, use that value in seconds; and if the config-file TTL isn't set at all, fall back to the old flag behavior, where if either old TTL flag is zero the effective TTL is zero, otherwise it's the minimum of the two flag values rounded up to the nearest second.

Oh and I need an upper-bound check on the config-file TTL. Since it's stored as seconds and converted to a duration internally, there's a max integer that converts safely without overflow, so if someone passes a value above that, reject the config right away with a clear human-readable error saying the value's too high and what the max supported value actually is, don't just silently produce a bad duration. And while I'm in there, the default stat-cache capacity and the stat/type cache TTL defaults should become named constants instead of hardcoded literals so the flag definitions and the shared TTL computation can reference them consistently.
