I'm working in the TiDB Operator and TiDB is the odd one out for scale-out parallelism. Right now when I scale out TiDB it only brings up one new pod per reconciliation loop no matter how many replicas I asked for, which is painful on big deployments, and meanwhile TiFlash and TiKV already let me control this. I want the TiDB component spec to accept a scale policy with a configurable parallelism setting that governs how many new TiDB pods can start at once during a scale-out.

Behavior should match what TiFlash and TiKV already do. If parallelism is set to 2, the operator tries to advance up to 2 replicas per loop, skipping any that are blocked by a pending PVC deletion (like a PVC carrying a deferred deletion annotation), and only the unblocked ones move forward while the rest get retried next round. If all the attempts are blocked, it returns an error and tries again on the next loop. Oh and this needs to work correctly whether or not the advanced scheduling feature with delete slot support is turned on, the parallelism applies consistently either way.

I also want the same pattern on scale-in for TiDB, so a configurable scale-in parallelism controls how many TiDB pods get removed in a single reconciliation round, and all the pods removed together in the same round should share the same scale-in timestamp on their PVCs so it's clear they went out as a group.
