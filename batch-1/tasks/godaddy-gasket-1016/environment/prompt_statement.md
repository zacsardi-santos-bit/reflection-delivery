I'm hitting a wall with dynamic plugins in the Gasket framework. We've got one plugin that loads additional plugins at startup, and a separate one handling CLI command registration, and the ordering is just wrong. Command registration fires too early in the startup sequence, before the dynamically loaded plugins have even been registered, so by the time my dynamic plugins exist the window to contribute commands has already slammed shut. I want that registration step moved to a later lifecycle phase, after dynamic plugins are loaded, so they actually get a chance to register their own CLI commands.

While we're in there, the configure phase should stop doing the command registration work and instead just be responsible for identifying the current command and applying command-specific config overrides, so the command-specific overrides object from config gets consumed and applied during that step.

The other half of this is that dynamically loaded plugins only run through two of the three standard setup phases, so anything a dynamic plugin sets up in that third phase just never happens, leaving it half-initialized compared to statically registered plugins. I need dynamic plugins to go through all three phases like static ones do. Oh and when a lifecycle call gets skipped for an already-initialized static plugin during the dynamic plugin setup (dedup), emit a trace message noting the skip so I can follow along in the logs.

Also, actually, I want to reference dynamic plugins by relative file path, like something starting with a dot, resolved against the application root directory, not just by package name. Without all this, dynamic plugins can't register commands and stay incomplete, which causes subtle bugs when they rely on that missing third phase.
