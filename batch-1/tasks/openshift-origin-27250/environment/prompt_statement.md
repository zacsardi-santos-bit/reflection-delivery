So we've got this annoying false-positive problem in our backend availability sampling. When the box running our disruption sampler can't resolve a hostname (DNS lookup times out on the TCP connection attempt), we're recording that as the cluster going down, and it shows up as a real availability regression even though the cluster under test is probably totally fine. It's the test runner's environment that's broken, not the service, and I want us to stop conflating "the cluster stopped responding" with "our runner couldn't do DNS."

So the change I want: in the disruption sampler, when a backend availability sample hits a DNS lookup timeout error, don't emit it as an error-level event anymore. Downgrade it to a warning-level event instead. The warning message should say something clear about DNS lookup timeouts beginning, and it still needs to carry the original error details along so whoever's reading the logs can see the actual root cause and not lose that context.

Then on top of that, I want a new automated check that scans a run for these DNS lookup timeout events happening in the disruption samplers and reports when they occurred. Since flaky DNS on our CI build clusters is a known thing (it's tracked under DPTP-2921), this check shouldn't be a hard failure, it should come back as a flake. And wire it into the existing suite of upgrade event invariants we already run after a job, so it rides along with the rest of those checks. Basically the DNS-vs-real-disruption distinction needs to show up both in how we classify the event and in the post-job diagnostics.
