I'm working on Gemini CLI and I want to configure telemetry through environment variables instead of always editing a settings file. Right now if I'm in a CI pipeline, a Docker container, or a shared machine and I want to flip telemetry on, point it at a different target backend, or change the export endpoint, I have to go touch the settings file every single time, which just isn't practical for automated setups.

What I'm after is being able to override all the major telemetry options at runtime via env vars: whether telemetry is enabled, the target backend to send data to, the OTLP endpoint and the protocol used for export, whether prompts get logged, the output file path, and whether a collector is used. And the precedence needs to be right, so env vars take priority over whatever's in the settings file when both are set, and command-line arguments take priority over env vars when both are present. When no env var is set, it should just fall back to the settings file value like today.

Couple of things I care about. If I fat-finger an env var and set it to something invalid, like an unrecognized target backend name, I want a clear error reported right away instead of it silently ignoring me or quietly picking some unexpected default. Also for the OTLP endpoint specifically, if the Gemini-specific env var isn't set, it should fall back to the standard OpenTelemetry endpoint env var, since that's the convention most tooling already follows.

Big picture this is about making Gemini CLI usable in automated and containerized environments where runtime config through env vars is the normal approach, without anyone having to modify a settings file, and it keeps the config more auditable and consistent with common tooling conventions.
