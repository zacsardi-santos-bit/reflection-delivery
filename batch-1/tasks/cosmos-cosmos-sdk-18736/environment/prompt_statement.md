I'm working on the multi-store commitment layer in our blockchain SDK and I keep hitting a wall with how proofs come back. Right now when someone queries a value with proof turned on, we only hand back a single-level proof tying the key to its store's tree root, and that's just not enough. Light clients and IBC relayers need to confirm data exists on-chain without trusting a full node, so they need a full proof chain from the individual key all the way up to the overall multi-store commit hash, and there's no way to verify that complete path with what we expose today.

What I want is for queries with proof to return two chained proof operations, one proving the key within its store's Merkle tree and a second proving that store's root hash within the overall multi-store commitment. Both levels have to be independently runnable, so feeding the output of the first into the second eventually yields the overall commit hash.

There's also a persistence gap. The commit store keeps no record of which store hashes were committed at each version, so after a restart or when I try to build a proof for a historical version, that metadata is just gone and I can't construct the proof. I need the commit store to persist commit metadata (version number and per-store hashes) to a database on every commit, so the constructor should accept a database instance for that. Commit itself should take an explicit version number, and the per-tree commit operation needs to return the committed version alongside its hash. The commit info has to be sorted lexicographically by store key so the hash computation stays deterministic. And I want a method on the commitment interface to retrieve the commit info for any specific historical version by version number. This also makes the whole thing more reliable across restarts and gives us auditable historical state.
