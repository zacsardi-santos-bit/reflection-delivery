I'm working with the go-github library and there's a gap around Dependabot alert webhooks. When GitHub fires one of these (say a vuln gets created in a repo, or an alert gets dismissed, fixed, or otherwise updated), the library has nothing to parse it into, so people consuming those webhooks can't handle them in any structured way. I want a proper typed event struct for this, something like a `DependabotAlertEvent` that carries the action string, the alert itself, plus the surrounding context, the repository, organization, enterprise, sender, and installation. Basically the same shape as the other webhook event types in the library so it feels consistent.

Couple more things while you're in there. The wiring that turns an incoming webhook into a Go type needs to recognize the new event by its string identifier (`dependabot_alert`) so `ParseWebHook` hands callers back the right type, and the hook delivery mapping needs the same entry so redelivered payloads map correctly too.

Also I noticed the existing Dependabot alert data model is dropping a field. There's no spot for when an alert was auto-dismissed, so that info silently vanishes when we pull alert data from the API. Can you add an `AutoDismissedAt` timestamp to the alert struct, and give it a nil-safe accessor (a `GetAutoDismissedAt()` getter) matching how the rest of the library does its getters. Same goes for the new event type, all the fields should have the usual nil-safe `Get*` accessors.

The upshot is folks who need to react to Dependabot security alerts over webhooks get a first-class way to do it, and the API model stops losing the auto-dismissal timestamp.
