I'm adding chunked prefill support to the vLLM scheduler and could use a hand wiring it through. Right now the scheduler has to process a request's entire input prompt in one pass before it can generate any output tokens, so a big prompt hogs the whole per-batch token budget for a round or more and everything else stalls, classic head-of-line blocking. I want a config option that turns on chunked prefill, and when it's on, prompts longer than the per-batch token budget get split into pieces that each fit the budget and get processed across successive scheduling rounds. Decode requests (the ones actively generating output) should be able to ride in the same batch as partially-processed prefill requests. Priority order matters: decoding first, then already-in-progress partial prefills, then brand-new prefills.

The budget tracker needs a rework so token and sequence counts are tracked per request-ID, making it idempotent, adding the same request twice shouldn't double-count and removing one that was never added is just a no-op. Also each sequence needs to carry an explicit stage flag saying whether it's in prompt-processing or output-generation, which matters for preemption: when a partially-processed single-sequence request gets preempted under memory pressure it should be re-queued for recomputation rather than swapped out, and its stage resets back to prompt-processing.

Oh and the output structs from the internal scheduling methods should separately list sequences in the decoding stage vs the chunked-prefill stage instead of lumping them together, and the scheduler output should report how many prefill groups are in each batch with each scheduled group carrying its token count for that batch. Requests whose prompt length exceeds the max model length get rejected and reported separately. Btw rename the internal method that schedules running sequences so it reflects that it now handles both decode and chunked-prefill, and the method that allocates resources for a running sequence should take the number of new tokens being processed as a param.
