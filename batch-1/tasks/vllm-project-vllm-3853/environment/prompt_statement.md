I'm working on adding chunked prefill support to the vLLM scheduler. Right now, the scheduler must process an entire input prompt in a single batch before any output tokens can be generated for that request. This creates a problem when a long prompt monopolizes the token budget for several rounds, causing other requests — especially ones that are already generating output tokens — to stall.

What I need is a mode where long prompts are split into smaller chunks so that each chunk fits within the per-batch token budget, and decode requests (those actively generating output) can share the same batch with partially-processed prefill requests. The key scheduling priorities should be: decoding requests first, then already-in-progress partial prefills, then brand-new prefill requests.

Along with this, the budget tracking needs to be reworked so that token and sequence counts are tracked per request-ID, making the tracking idempotent — adding the same request twice shouldn't double-count, and removing a request that was never added should be a no-op.

Each sequence also needs to carry an explicit indication of whether it is in the prompt-processing stage or the output-generation stage. This makes it possible to correctly handle preemption: when a partially-processed request is preempted due to memory pressure (and is a single-sequence request), it should be re-queued for recomputation rather than swapped out, and its stage should reset back to prompt-processing correctly.

The output structures from the internal scheduling methods need to be updated to separately list sequences in the decoding stage versus sequences in the chunked-prefill stage, rather than lumping them together. The internal method that schedules currently-running sequences should be renamed to reflect that it now handles both decode and chunked-prefill requests. The method that allocates resources for a running sequence should also accept the number of new tokens being processed as a parameter.
