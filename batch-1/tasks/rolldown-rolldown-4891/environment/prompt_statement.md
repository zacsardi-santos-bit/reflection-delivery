I'm hitting a bundling bug when I turn off entry signature preservation (the "false" mode) while using multiple entry points. In my setup some of the entry modules also get pulled in dynamically via `import()` from other modules, so they're doing double duty as both static entries and lazy-loaded chunks. The problem is that with entry signatures disabled the bundler gets too aggressive and strips the exports off those entries, so at runtime the dynamic importer can't reach the values it expects, the exports are just gone from the output chunk and the bundle breaks.

What I want is: if an entry module is a target of a dynamic import somewhere, it needs to keep its exports in the output since whoever's dynamically importing it depends on them. Only entries that are purely static, meaning nothing ever dynamically imports them, should get their exports suppressed under this mode, those can safely be merged into a shared helper chunk. So the export-suppression optimization should look at whether the entry is also a dynamic import target before deciding to drop anything.

Oh and while you're in there, when two or more entry points reference the same underlying source module, that shared content should get extracted into a single deduplicated chunk instead of being copied across each entry. This matters a lot for real code-splitting apps where a bundle is both an entry point and something that's lazily loaded elsewhere, that combo is exactly where the current behavior falls over. Can you fix it so dynamic-import-target entries retain their exports even when entry signature preservation is off?
