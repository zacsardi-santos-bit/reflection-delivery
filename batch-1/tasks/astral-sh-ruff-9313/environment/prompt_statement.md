I'm working on adding a new lint rule to the ruff linter that detects when iterator and async iterator methods in classes are annotated with overly specific return types. Specifically, when a class's iteration method only yields values without receiving sent values or having meaningful return values, it's more idiomatic to annotate the return type as an iterator rather than a generator. I'd like a rule that flags these overly specific annotations and suggests the simpler iterator equivalent.

The rule should only apply to methods inside a class — module-level functions with the same name should be ignored. It should flag bare generator return types as well as parameterized generator types where the send type and return type are trivially unused (i.e., set to placeholder values indicating no meaningful type or no value). For async iteration methods, it should flag bare async generator return types and parameterized ones where the send type is trivially unused. It should not flag cases where the generator type parameters have meaningful non-trivial types for the send or return slots.

There are also some edge cases that should not be flagged: methods defined as async, methods with extra or unusual parameters beyond the standard self parameter, and in regular Python files (as opposed to stub files), methods with non-trivial generator bodies — for example, where the method returns a meaningful value, where a yield expression is used to receive a sent value, or where the body has complex statement logic beyond simple yields.

The generator and async generator types should be recognized whether referenced from the collections.abc module or the typing module.
