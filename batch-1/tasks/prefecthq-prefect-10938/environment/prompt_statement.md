I'm working with Prefect block documents and I keep hitting a wall when I want to reference specific nested values from inside a block in my config templates. Right now when I use a block reference in a template I can only pull the entire block's content, there's no way to drill into a nested dict key or grab a specific element from a list. Say I've got a block storing a dictionary with a bunch of config keys, and I just want one key's value for a deployment template. Can't do it today, which basically forces me to make a separate block for every individual value even when they all logically belong together in one structured document, and it blocks me from using block references in deployment config files when the setting I care about is nested.

So I want to add keypath navigation to the block document reference resolver. I'd expect dot notation to navigate into nested dictionary keys at any depth, and bracket notation like `[0]` to access list elements by numeric index, and these two should combine freely for complex nested structures. For blocks that store their primary content under a standard field, the existing shorthand template syntax that omits that field name should keep resolving correctly so I don't break backwards compat. And if a block doesn't use that shorthand, accessing a named field just by naming it in the path should return that attribute's value from the block's stored data. Oh and the failure case matters: if I specify a path that doesn't exist, whether that's a key that's not in the dict, an index past the end of the list, or a field that isn't on the block, I want a clear error telling me the path couldn't be resolved rather than silently getting back something wrong. The resolution logic lives in the block document reference handling, so that's where the keypath parsing and traversal should go.
