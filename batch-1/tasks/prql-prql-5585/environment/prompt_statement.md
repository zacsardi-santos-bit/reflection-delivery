I'm hitting a nasty silent bug in the PRQL compiler. If I define a named variable that holds a table or relation (basically a full pipeline result), and then I reference that variable inside a comparison or filter expression like it's just a scalar value, the compiler happily compiles and spits out incorrect or misleading SQL instead of telling me I did something wrong. That's really easy to trip over by accident and then you're chasing a wrong result for ages.

What I want is for the compiler to actually catch this. When a table-typed variable gets used in a scalar context, say one side of a comparison inside a filter, it should return an error rather than compiling successfully. The error message needs to clearly state that a table variable can't be used as a scalar value. It also needs a help message that points me toward valid alternatives, so something like using a join or inlining the subquery directly instead of referencing the table var as a scalar.

Oh and the error has to identify the specific spot in the source query where the problematic reference shows up, so the diagnostic should carry the exact source location (a proper span) for that reference. Basically a clear, well-placed error with an actionable suggestion beats silently wrong SQL every time, it makes this kind of mistake way easier to understand and fix.
