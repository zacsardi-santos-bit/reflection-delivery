I'm adding automatic volume growth to our Postgres cluster operator and want your help wiring it up end to end. Right now when a PostgreSQL data volume fills up admins have to manually resize it, which is painful and risky for production databases that can run out of space unexpectedly. The idea is the monitor process inside each database pod periodically checks disk usage on the data directory, and when the data volume is more than 75% full it signals that it needs more space by updating a specific annotation on the pod with a suggested new size, roughly 1.5x the current volume size expressed in mebibytes.

On the operator side the pod watcher should trigger a reconciliation whenever that particular annotation changes, but not fire for unrelated annotation changes. During reconciliation the operator reads the suggested size from the cluster status, compares it against any configured storage limit, and sets the PVC request accordingly. If the suggested size equals or exceeds the limit it gets capped at the limit and an appropriate event is emitted, and if the spec's storage request already exceeds the limit then the limit value is used and a warning event fires instead. Basically I want events for actual expansions, for limit-reached conditions, and for the case where the desired size would exceed the ceiling.

The whole auto-grow behavior should only kick in when the corresponding feature gate is enabled, so clusters opt in explicitly. Oh and I want the desired size tracked in the cluster's status so it persists even when pods restart or the cluster gets shut down temporarily. That way we don't lose the target size mid-flight. Can you get the monitor-side detection, the annotation signaling, the watcher trigger, and the reconciliation-with-limit logic all working together?
