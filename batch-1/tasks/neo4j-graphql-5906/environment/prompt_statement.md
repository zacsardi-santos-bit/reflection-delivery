I'm chasing a nasty bug in the GraphQL-to-database query translation layer. When my schema has a relationship that points to an interface type (say a type with a field that can be one of several concrete node types), filtering on properties of that related interface-implementing node just doesn't work. The query comes back empty even when matching nodes clearly exist, or it returns straight up wrong results, which is a big deal because tons of schemas model polymorphic relationships as interfaces and if you can't filter by interface properties you lose a fundamental querying capability. Worst part is the queries look correct based on the schema so they silently return wrong data and it's a pain to debug.

After digging in, the issue is that the code generating database queries reuses the same internal variable name for optional match count variables across different parts of the query, and it derives that name from the relationship name (which can repeat), so when two or more optional match count patterns try to assign to the same named variable you get undefined or incorrect behavior from the collision.

What I want is for the generated queries to use unique variable names across all optional match patterns instead of that hardcoded relationship-derived name. Once that's fixed, filtering on a relationship to an interface type should correctly return nodes whose related entities match, whether the matching node is of the first concrete implementation type or the second, and return empty results when nothing satisfies the filter across any concrete type. Oh and this has gotta work for both single (non-list) interface relationships and list-type interface relationships using existence quantifiers, not just one of them.
