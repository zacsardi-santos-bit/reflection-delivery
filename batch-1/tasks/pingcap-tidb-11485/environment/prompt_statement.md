I'm cleaning up the chunk column code in our database engine and the null accounting is driving me nuts. Right now every column caches an integer null count and we have to hand-update it every single time we touch the null bitmap, on set null flag, clear, append, truncate, reconstruct, encode/decode, all of it. Problem is several code paths poke the bitmap but forget to adjust the count or adjust it wrong, so it drifts and goes stale. I want to kill the cached field entirely and instead compute the null count on demand straight from the null bitmap whenever anyone needs it. That way there's zero synchronization to maintain and the count is always correct by construction. Go through every spot in the chunk package that reads or writes that field and update them so append, truncate, reconstruct, and encode/decode still work correctly without keeping a separate count.

While I'm in there I also want bulk pre-allocation methods for the fixed-length column types, meaning the integer types of various sizes, the floating-point types, and the decimals. Each one takes a length and resets the column to exactly that many null rows, blowing away whatever was there before so the whole block starts out null and the returned null count equals the number of pre-allocated rows. After pre-alloc I need a normal append to still work and add a single non-null row at the end, leaving the pre-allocated null rows intact. Oh and there should be a way to mark an individual pre-allocated row as not-null (or flip it back to null), and the null count reported at that point has to accurately reflect the current bitmap state after each change. The point of all this is callers that want to reserve a block upfront and fill it in selectively instead of appending one value at a time, and dropping the redundant cache just makes the null bookkeeping self-consistent.
