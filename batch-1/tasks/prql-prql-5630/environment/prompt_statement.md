I'm hitting a codegen bug in the PRQL to SQL compiler when targeting Microsoft SQL Server. When I write a query that dedupes records by grouping to keep only one row per group and then caps the total number of rows, the SQL that comes out gets rejected by MSSQL at runtime. The core issue is that MSSQL is stricter than most dialects here, when DISTINCT is in play any expression in the ORDER BY has to also show up in the SELECT list. Right now the compiler drops a placeholder expression into ORDER BY when no explicit sort was given, which is fine on other backends but MSSQL flat out refuses it alongside DISTINCT.

What I want is for the compiler to notice when the compiled output for the MSSQL dialect uses DISTINCT together with FETCH-style pagination and, in that case, emit an ORDER BY that references a real column from the SELECT list instead of that placeholder. Use the first projected column as the ORDER BY expression. The row-count limit should still translate to MSSQL's OFFSET/FETCH pagination, so something like OFFSET 0 ROWS FETCH FIRST N ROWS ONLY where N is the limit. Oh and column names need to be double-quoted in both the SELECT list and the ORDER BY clause. The end result has to be valid, executable MSSQL with no hand editing needed, since producing correct dialect-specific SQL is kind of the whole point of PRQL and this is a real correctness bug for an important target.
