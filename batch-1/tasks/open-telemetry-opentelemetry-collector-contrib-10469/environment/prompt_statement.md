I'm hacking on the Datadog exporter in the OpenTelemetry Collector and hit a real correlation headache. Right now we resolve a hostname from resource attributes with one fixed strategy across all cloud providers, and the hostnames it spits out don't match what Datadog's native cloud integration agents report, so joining data from both pipelines is basically impossible. I want to add an opt-in alternative resolution mode that lines up with the native integration conventions for AWS EC2, Azure VMs, and GCP instances.

Concretely I want the hostname resolution functions for the cloud-specific packages (AWS EC2, Azure, GCP) plus the top-level resolution logic to each take an extra boolean flag that selects this alternative mode. When it's on, for Azure and EC2 use the host's unique cloud identifier (the VM's unique id for Azure, the instance id for EC2) as the primary hostname instead of the human-readable host name, and EC2 should always resolve to that instance identifier. For GCP, build the hostname from a combined format of the short host name plus the cloud account/project id. In all these cases the integration-format hostname becomes the primary hostname, and since it's already primary it must not also show up in the host aliases list, so don't append it there for Azure or GCP. Oh and container ids shouldn't be considered as hostnames at all in this mode, they're not meaningful infra-level identifiers.

When the flag isn't set, everything stays exactly as it is today, all the existing behavior preserved. This matters because without it folks collecting infra data through both the native integrations and the Collector can't reliably correlate it, the hostnames just don't line up.
