I'm adding protocol API config to the Rook Ceph object store operator and right now there's just no way to control which gateway APIs (S3, Swift, admin, and friends) the RADOS Gateway actually exposes, the operator basically assumes everything's always on. I want logic that figures out the set of enabled APIs from the object store's protocol spec, handling the case where S3 is explicitly disabled through a per-protocol option, and also the sneaky case where Swift is configured at the root URL path which implicitly conflicts with S3 so S3 should get turned off automatically. Oh and if someone hands us an explicit list of APIs that should win over any of the per-protocol enable/disable settings, and while we're at it trim whitespace on the API names so " s3 " and "s3" don't diverge.

The health probe path needs to adapt dynamically too, this is the part that bites people. If S3 is enabled, use the default S3 path like today. If S3 is off but Swift's available, switch the readiness/liveness target to the Swift health endpoint, accounting for any custom Swift URL prefix. And if neither S3 nor Swift is active (say only the admin API is up), just disable the probe entirely so we don't get false failures.

Then when the gateway config command-line flags get built, include an argument specifying the comma-separated list of enabled APIs whenever they're configured. This all lives in the object store operator code under `@pkg/operator/ceph/object`. Without it folks wanting a Swift-only store are stuck fighting the operator's assumptions and end up with broken health checks or misconfigured deployments.
