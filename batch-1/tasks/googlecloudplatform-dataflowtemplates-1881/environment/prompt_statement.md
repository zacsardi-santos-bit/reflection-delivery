I'm hacking on the CI/CD build tooling for a project where we've got these named module groups that scope builds, tests, and quality checks down to one area of the codebase. Right now the selection logic only knows about a general catch-all group and a group for the database migration modules, and there's no way to target just the Kafka data pipeline stuff as a single unit. I want to add a named Kafka group so we can run spotless, checkstyle, unit tests, and integration tests against only the Kafka pipeline code, which matters because otherwise CI either runs against everything (slow and expensive) or we hand-list each Kafka module, and neither lets us have a focused Kafka PR workflow that triggers only on relevant file changes.

So when the Kafka group gets selected the module-selection logic should return exactly the shared Kafka library module, the four Kafka-to-X pipeline modules, and the Maven plugin module, nothing more. Also there's a secondary thing I keep hitting: when we compute the "default" exclusion list, which negates all the named modules so the default build skips them, the logic currently only skips over plugin-type modules. Now that the Kafka group pulls in a shared common library module, that negation needs updating so shared/common library modules (the ones whose paths mark them as common/shared) also get omitted, otherwise default mode wrongly tries to exclude them. Net effect: only the non-common, non-plugin modules from each named group should end up negated.
