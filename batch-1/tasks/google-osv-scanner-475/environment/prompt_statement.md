I'm working on a security vulnerability scanner that runs in CI pipelines to compare scan results between commits, and I keep hitting false positives that are driving me nuts. Right now the comparison logic checks for new vulnerabilities by looking at results per source file, so when someone moves a lockfile to a different directory during a refactor, the scanner thinks all those same vulns are brand new just because the file path changed. That means PRs that only reorganize the project layout light up CI with bogus security alerts.

What I want is a smarter comparison that counts vulnerability occurrences across the whole scan by their unique ID, ignoring which source file reported them. So the idea is a new comparison function that tallies how many times each vulnerability ID shows up in the old scan vs the new one. If the total count for a given ID hasn't gone up, don't report it as new, even if the underlying files got moved around. If a vuln ID genuinely appears more times in the new scan than the old (someone actually added a vulnerable dependency), include it in the result with the excess occurrence count. If the old scan has more occurrences than the new one, the vuln was removed, so the result should be empty for that case, and same deal if the count stayed flat, nothing reported.

Oh and I don't want to rip out the existing path-based comparison. Keep that around and use it when the occurrence-based check confirms there really are new vulns, so we still get the file-level detail once we know something genuinely changed. Net effect: moving a lockfile from one dir to another produces zero false positives, but adding a new vulnerable dependency still gets caught.
