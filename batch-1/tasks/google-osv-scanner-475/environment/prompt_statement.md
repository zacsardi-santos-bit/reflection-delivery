I'm working on a security vulnerability scanner that runs in CI pipelines to compare scan results between commits. The current comparison logic checks for new vulnerabilities by looking at results per source file. The problem is that when a lockfile gets moved to a different directory as part of a refactoring, the scanner treats the same vulnerabilities as newly introduced because the file path changed. This creates false alarms in CI for pull requests that only reorganize the project structure.

I'd like to add a smarter comparison approach that counts vulnerability occurrences across the entire scan by their unique ID, regardless of which source file reported them. If the total number of times a given vulnerability ID appears hasn't increased between the old and new scans, it shouldn't be reported as new — even if the underlying files were moved around. If a vulnerability's total count genuinely went up, it should be reported. If it went down or stayed the same, nothing should be reported for that ID. This way, moving a lockfile from one directory to another would produce no false positives, but actually adding a new vulnerable dependency would still be caught.
