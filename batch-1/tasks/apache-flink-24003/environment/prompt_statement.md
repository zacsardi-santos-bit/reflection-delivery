I'm digging into Flink's job failure handling and hitting a real annoyance with cascading failures. When multiple tasks die at nearly the same time, which happens all the time when one task's failure knocks over its neighbors before the job restarts, each of those failures gets counted as its own restart event. So the restart counter gets inflated way past the actual number of failure episodes, and the exception history fills up with a separate top-level entry per failure when really it was all one event. Operators trying to set failure thresholds or diagnose instability end up with garbage numbers.

What I want is a clean distinction between a root cause failure, meaning the first failure that kicks off a new restart attempt, and concurrent failures, the ones that show up while a restart is already pending. Only root cause failures should bump the restart counter, and concurrent ones should get grouped underneath the root cause entry in the exception history instead of creating new top-level entries.

The restart strategy component feels like the right place to signal this, since failures get reported to it anyway. When a failure comes in it should say whether this is a new attempt or a concurrent one, and that info needs to flow through into the failure handling result so downstream consumers like the exception history tracker can act on it. Also I need to be able to tack concurrent failures onto an already-created exception history entry after the fact, so whatever represents those history entries has to support adding more concurrent failures later.

One edge case to get right, oh and this matters: failures that permanently suppress restarts (the non-recoverable ones) should always be treated as root cause failures no matter what the restart strategy says about new versus concurrent, since there's no restart attempt to group them under anyway. Accurate counters and a clean history are the whole point here so operators can actually understand job health.
