I'm adding path-based routing to the wasmCloud built-in HTTP server. Right now it only does address-based routing, one component per listen address, so if you want multiple components behind a single port you're stuck dedicating a port per component or hand-rolling a routing layer. I want one HTTP listener that dispatches to different components based on the URL path of incoming requests, all wired through the normal lattice link system.

The way I'm picturing it, each link carries a config key naming which path should route to the linked component. When a request comes in the server looks the path up in a routing table and forwards to the right component, and if the path isn't registered it just returns a 404. This needs to be dynamic: adding a link registers the path, removing a link deregisters it (so those requests go back to 404), and re-adding restores the 200s. When the provider gets stopped entirely, traffic to the address should fail outright, not just 404.

Please keep the path routing logic in its own module, separate from the existing address-based routing. The path routing state should track both a forward mapping from URL paths to component IDs and a reverse mapping from component-and-link-name pairs back to their registered paths. Registering a duplicate path (one already claimed by another component) should be rejected with an error, and so should registering a second path for the same component-and-link-name pair, both error cases.

Oh and I also need a test utility for provider lifecycle stuff, basically a helper that stops a provider and confirms it actually stopped, so it sends the stop command and then polls until the provider stops responding to health checks. That'll let me verify the stop-then-404-then-fail behavior in integration tests.
