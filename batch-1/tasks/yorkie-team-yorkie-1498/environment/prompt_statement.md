I'm reworking webhook retry and timeout behavior so it's configurable per project instead of globally, because right now the server has one global config for how many times auth and event webhooks retry, how long to wait between attempts, and when to time out, and every project is stuck with those same numbers. Different projects have different reliability needs and backend capabilities, so a fast reliable endpoint shouldn't get penalized by conservative settings meant for a slow one, and vice versa.

What I want is for each project to independently set its auth webhook and event webhook retry count, the minimum and maximum wait intervals between retries, and the request timeout, all editable through the normal project update API. On the webhook client side, the retry and timing options need to be passed in at the moment a webhook is actually sent rather than being fixed when the client gets created, so the right per-project settings apply dynamically per outgoing call without spinning up a separate client per project.

On the data model, the project and its updatable-fields struct both need new fields holding these per-project timing and retry values for auth and event webhooks. The project update validation should reject invalid duration strings for these new fields, and also for the client deactivation threshold field. Meanwhile the global server config should get simplified by dropping the webhook timing and retry fields that are moving to the project level, including removing the global client deactivation threshold default. And the database layer that creates and initializes projects needs updating so these settings aren't being set globally at creation time anymore.
