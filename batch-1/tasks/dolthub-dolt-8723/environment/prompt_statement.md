I'm hitting a nasty data integrity bug in Dolt's JSON column support. When I insert a JSON document with a really large string value, like several megabytes, it comes back truncated when I read it, and sometimes the operation just errors out entirely. Doesn't matter whether that big string is a value or a key in the object, either way it breaks.

Digging into it, the problem is in how Dolt stores large JSON docs internally. The indexed storage format has chunk size constraints, and when a single string is too big to fit in a chunk it can't be split across chunks without corrupting the data or breaking compatibility with older clients, and right now there's no graceful fallback so it either corrupts or fails.

What I want is for the serialization logic to detect when a JSON document contains a string that exceeds the allowed chunk size, and fall back to storing it as a plain blob instead of using the indexed format. That fallback should be automatic, no change to my query at all. After it falls back, the doc still needs to be fully readable, so I can look up keys in it and get back the complete untruncated original string value. Also inserting one of these multi-megabyte docs should just succeed cleanly, reading it back returns the full content not a shortened version, and querying the length of a large string value via a JSON path expression should return the correct full length. Basically JSON columns should faithfully store and return whatever I put in regardless of string length, since right now this is silent data corruption that can go undetected.
