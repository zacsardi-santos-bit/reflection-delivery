I'm trying to add a TTL cleanup feature to our analysis controller because right now finished analysis runs just pile up in the cluster forever and there's no built-in way to garbage collect them. Operators either delete old runs by hand or lean on rollout-level history limits which don't cover every case, and all these stale objects eat etcd storage and clutter the namespace, so I want fine-grained per-outcome retention that balances auditability with keeping things tidy.

Here's what I'm after. The TTL policy should live on the analysis run itself and support three windows: a general retention that applies to any completed run no matter the outcome, plus separate windows that only apply to successful runs or only to failed runs. When a phase-specific window is set and the run's outcome matches, that should win over the general completion window. Also important, a success window should never delete a failed run and a failure window should never delete a successful run.

For the controller logic, when a run transitions to a finished state I want it to record the completion time, and then on each reconciliation check whether elapsed time since completion has passed the configured TTL, and if so delete the run. Leave runs alone if they're still in progress, have no TTL configured, already carry a deletion marker, or have no recorded completion time. Oh and if the delete is attempted but the run's simply not found anymore, treat that as success. Any other delete error should just surface as a warning log rather than blowing up. The changes belong in the analysis controller reconcile path, so wire the completion-time recording and the TTL check into wherever it handles finished runs.
