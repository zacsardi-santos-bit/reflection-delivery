I'm working on the API reference component and I want to make the URL hash fragments customizable. Right now the slugs we generate for headings, models, tags, operations, and webhooks are hardcoded, so consumers can't plug in their own fragment schemes like internationalized slugs, sequential IDs, or patterns matching an existing routing system, and that basically blocks deep-linking against external conventions or multi-language docs.

What I'd like is to pass optional custom slug-generation functions through the reference configuration, one per section type (heading, model, tag, operation, webhook), and the navigation logic should use the supplied function instead of the default slugification whenever it's present. The config type needs to declare all five of these as optional so TypeScript consumers can actually see what's available.

There's a behavior detail on how the results get used: for headings, whatever the custom generator returns should be used as-is with no automatic prefix, but for models and tags the standard section prefix should still get prepended to the generated result.

Oh and while I'm in here, the ID generators for models and webhooks have inconsistent signatures that bug me. The model one takes a plain string right now and the webhook one takes two separate positional string args. I want both switched over to accept a single structured object instead, so the model generator takes an object with a name field, and the webhook generator takes an object carrying both the name and the HTTP method. That's more consistent and it makes it way easier to thread the custom generator support through and pass richer metadata to these hooks later.
