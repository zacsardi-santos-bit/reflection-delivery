I'm hitting a bunch of CSS scoping bugs in the Svelte compiler and they're all making styles either not apply or leak past the component boundary, so I'd love a fix to the scoping logic that covers these cases. First, when I write a style rule that reaches an element through multiple levels of ancestor context, like a descendant of a descendant, the intermediate elements in that chain are missing the scoping attribute they should get (or the wrong intermediates get scoped), so the compiled selector matches the wrong element set. Every matched intermediate element in a multi-level descendant selector should pick up the scoping attribute. Related to that, selectors that could never match because a required intermediate element just doesn't exist anywhere in the component template should be flagged as unused.

The child and sibling combinators are broken the other way, they're over-scoped. When I use a child combinator (`>`), an adjacent sibling (`+`), or a general sibling (`~`), the selector sitting before the combinator is getting an unwanted scoping modifier. Only the final target element should be scoped in those cases, the preceding context selectors shouldn't get any modifier.

Also the selector-grouping pseudo-class (`:is(...)`) doesn't work at all right now, the compiler can't tell which alternatives inside it match template elements so none of them get scoped and none get correctly marked unused. I want each alternative evaluated individually, matching ones scoped, non-matching ones commented out as unused.

Native CSS nesting is another gap, it doesn't work whatsoever. Whether I write the implicit parent-reference style or use the explicit nesting selector (`&`), the compiler doesn't understand the nesting relationship and spits out broken scoped output. I want to write modern nested CSS in my component style blocks and have it analyzed and scoped properly.

Oh and one more, attribute selectors whose values contain special characters like braces, brackets, and semicolons currently fail to parse, so those need to parse and scope correctly too.

These are all normal everyday CSS patterns and I shouldn't have to work around the scoping compiler for them. The scoping analysis lives around Svelte's CSS handling in the compiler (`@packages/svelte/src/compiler`), so that's where the selector analysis and attribute-application logic needs sorting out.
