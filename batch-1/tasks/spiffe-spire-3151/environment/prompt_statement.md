I'm building out the OIDC Discovery Provider and I need health check endpoints so it can run cleanly in containerized setups where the orchestration platform (Kubernetes and friends) wants liveness and readiness probes to decide whether to route traffic or restart an instance. Right now there's just no signal at all about whether the provider has loaded key material or is even alive, so stale or dead instances keep getting traffic.

What I want is an optional health checks config section that, when present, spins up a dedicated HTTP listener on localhost exposing two endpoints, one for readiness and one for liveness. When the section is present but empty, it should fall back to sensible defaults for the bind port and the URL paths of each endpoint, and operators should be able to override those. If the section is absent entirely, don't start the listener at all.

The readiness endpoint returns success only when key material has been fetched successfully and recently, so if keys were never loaded, or the last good fetch is too old, it reports failure. Liveness is more lenient: right after startup, before any fetch has completed, the service still counts as alive, but once key fetching is established it should fail if polling has gone stale past a threshold. Both endpoints answer HTTP 200 healthy and HTTP 500 unhealthy. Derive the staleness threshold from the configured poll interval with a minimum floor so it isn't too aggressive.

Oh and the key source interface needs to expose the time of the last successful poll so the handler can judge freshness, and both the server API and workload API source implementations need to track and expose that timestamp.
