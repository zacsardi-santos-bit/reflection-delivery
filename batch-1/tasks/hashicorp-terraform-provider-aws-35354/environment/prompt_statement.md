I'm working on the Terraform AWS provider and there's a gap in our Security Lake coverage. We've got resources for the data lake itself and for AWS-native log sources, but custom log sources have no resource at all, so anyone ingesting data from their own apps or third-party tools has to create and babysit those sources by hand in the console or CLI, which drifts from declared state and breaks the whole infra-as-code story. I want a new resource that manages the full lifecycle of a custom Security Lake log source, create, read, and delete.

The resource needs to let users declare the source name and source version, the event classes (event classifications) to ingest, a Glue crawler configuration that references an IAM role for crawling the data, and a provider identity config with an external ID and a principal for the cross-account identity setup. The source name doubles as the resource identifier. Import should work for existing custom log sources by that name, though the configuration and event class details won't be populated on import, so those computed attributes get excluded from import state verification. Oh and if someone deletes the source outside Terraform, the provider needs to detect that drift and handle it cleanly rather than erroring out.

While I'm in here, the test helpers for the existing data lake and AWS log source tests could use a little cleanup. The shared base configuration should become a constant instead of a function, and the basic, tags, and lifecycle config helpers should drop the random name parameter since it's not actually used by any of them anymore.

The end goal is teams can keep their entire Security Lake setup, data lake, AWS-native sources, and now custom sources, in one version-controlled Terraform config instead of splitting it across tools.
