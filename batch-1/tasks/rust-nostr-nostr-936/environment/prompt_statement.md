I'm working on a Nostr library and I want to untangle the NIP-05 identity stuff from HTTP. Right now the whole NIP-05 support sits behind an optional cargo feature and the library reaches out and makes network requests itself, which is annoying because I can't use the parsing in offline scenarios, unit tests with static fixtures, or when my app wants to run its own HTTP client. I'd like to split the concerns so the parsing types work by default with no feature flag at all, and I can fetch the NIP-05 JSON myself with whatever client I want then hand the raw string to the library.

Concretely I want to parse a NIP-05 address in `name@domain` format into a structured type I can pass around, and I want to give the library pre-fetched or test JSON directly and get back the resolved public key plus the relay list, with zero network calls happening inside the library. The types and parsing logic in the nip05 module (see wherever that lives, e.g. `@src/nips/nip05.rs`) should be exposed by default, not gated.

The point is decoupling the fetching from the data parsing so it's testable, composable, and usable in embedded, WASM, or async-runtime-agnostic contexts where the library making its own network access isn't acceptable or even possible. Any app should be able to use its own HTTP client, fetch the JSON, and pass it in for parsing. So basically I need an I/O-free way to parse the address and resolve a profile from a JSON string.
