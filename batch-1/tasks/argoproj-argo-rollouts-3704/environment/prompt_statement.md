I'm working on the Prometheus metric provider in Argo Rollouts and right now it can only do instant, point-in-time queries which is limiting. Lots of the meaningful evaluations I care about (error rate, latency patterns, that kind of thing) really only make sense over a window of time rather than at a single moment, so I want to add range query support to the provider.

What I'm after: I want to be able to configure a query with a start time, an end time, and a step interval so it runs as a range query instead of an instant one. The start and end boundaries shouldn't be hardcoded timestamps, they should accept flexible time expressions that can compute dynamic values, like "one hour before a specific date", so I can express relative windows. When the range query comes back, I want the result to be a flat collection of all the metric values across all the returned time series, so it can be fed straight into the existing success/failure condition evaluation without any special handling.

Error handling matters here too. If the start time, end time, or step interval expressions can't be parsed, I don't want it to silently fail or panic, I want the analysis run to fail with a clear, descriptive error that says exactly which parameter (start, end, or step) failed and why. Oh and I also need a small utility function for evaluating a time expression that either returns a proper time value or errors out if the expression is invalid or doesn't actually produce a time result, since both the start and end parsing lean on that.

So basically: extend the Prometheus provider so an instant query stays the default but a range query kicks in when the range params are present, wire up the expression evaluation for the boundaries plus the step duration, flatten all series values into one collection for condition eval, and give me the per-parameter parse errors along with that reusable time-expression helper.
