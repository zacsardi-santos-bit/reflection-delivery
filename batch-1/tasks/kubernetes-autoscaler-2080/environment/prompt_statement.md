I'm poking at the Vertical Pod Autoscaler and hit a real gap in how the admission controller applies recommendations. It honors container-level resource constraints from limit ranges just fine, but it totally ignores pod-level limit ranges. So in clusters where an admin has set pod-level resource minimums or maximums, VPA can spit out per-container recommendations that each look fine on their own but whose sum blows past (or falls under) the pod's overall policy, and then you get admission failures or policy violations that operators have to fix by hand.

What I want is this: after we compute the per-container recommendations, also check whether the aggregate resources across all containers in the pod comply with any pod-level limit range in that pod's namespace. If the total would exceed the pod-level maximum for a resource, scale every container's recommendation down proportionally so the total lands exactly at the allowed maximum. If the total falls below the pod-level minimum, scale them up proportionally so the total reaches the required minimum. And if the aggregate already fits within the pod-level constraints, leave the recommendations untouched. This needs to handle both CPU and memory.

To do this cleanly the interface we use to look up limit range info should expose a separate method for querying pod-level constraints, distinct from the existing method that handles container-level ones, so the pod-level fetching is properly separated from the container-level fetching. Oh and make sure all existing implementations of that interface get updated too, including the no-op variant, so nothing breaks.
