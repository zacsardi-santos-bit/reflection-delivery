I'm working on improving the self-signed certificate rotation logic for the Antrea controller. Right now, certificates are rotated based on a fixed maximum time duration that has elapsed since the last rotation — but this isn't really the right model. What I want instead is for the system to check how much time is left on the current certificate, and only rotate it when that remaining validity drops below a configurable threshold. I think of it as a "minimum valid duration" — if the cert has less than this much time left, rotate it; otherwise, leave it alone.

There's also a bigger issue: every time the controller restarts, it generates a brand-new self-signed certificate, which breaks any clients that already trusted the old one. I'd like the system to persist the generated certificate to a Kubernetes Secret and reuse it on startup if it's still valid enough. This way, rolling deployments don't cause certificate churn, and multiple simultaneously-running instances can converge on the same certificate instead of each generating their own.

The component responsible for providing the self-signed certificate should be refactored accordingly. The old configuration field for maximum rotation duration should be replaced with this new minimum valid duration concept. The multicluster controller's configuration should be updated to use this new field as well.

The new certificate provider should watch the Kubernetes Secret for external updates — for example, if another instance rotates the certificate and writes it to the Secret, the current instance should pick up that new certificate and start using it without requiring a restart.
