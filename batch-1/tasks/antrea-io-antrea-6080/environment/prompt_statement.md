I'm reworking how the Antrea controller handles its self-signed cert rotation and the current model bugs me. Right now rotation fires on a fixed maximum duration since the last rotation, so certs get swapped on a timer no matter how much validity is actually left, which is wasteful and imprecise. What I want instead is a "minimum valid duration" idea: check how much time remains on the current cert and only rotate when that remaining validity drops below a configurable threshold, otherwise leave it alone. So please replace the old maximum rotation duration config field on the cert config with this new minimum valid duration field, and update the trigger logic in the self-signed cert provider so rotation happens when remaining validity falls under the threshold rather than after a fixed interval.

There's a bigger annoyance too. Every time the controller restarts it generates a brand new self-signed cert, which breaks clients that already trusted the old one. I want the generated cert persisted to a Kubernetes Secret and reused on startup as long as it still has enough validity left, so rolling deployments don't cause cert churn and multiple simultaneously running instances converge on the same cert instead of each minting their own. If the cert in the Secret is missing or invalid, generate a fresh one and save it back.

Oh and the provider should watch that Secret for external updates. If another instance rotates the cert and writes it to the Secret, the running controller should pick up the new cert and start serving it without needing a restart. Refactor the self-signed cert provider component accordingly. Also update the multicluster controller configuration to use this new minimum valid duration field, set it to 90 days.
