I've been fighting with the filter directive system in the tracing subscriber and I think there's an ordering bug. When I set up two filters that end up "equally specific" under whatever comparison the code uses, one of them silently stops working. Like if I enable tracing for two different targets that happen to be the same length (say two three-character names), only one actually gets enabled, the other just gets shadowed. Same deal when I have two span filters that share a span name but each matches a different field, or two event filters that each require a single but different field to be present, or two span-plus-field directives where the span names are the same length and they both specify the same number of fields. In every one of those cases only one directive gets evaluated and events or spans that should've matched the second one just get dropped.

I'm pretty sure the culprit is the logic that decides the priority order of directives, it doesn't handle the case where two directives come out with the same structural weight (equal target string length, same field count, etc.), so instead of both applying, one overrides the other. What I want is for all matching directives to apply independently, so an event or span passes through as long as any one configured directive matches it. So both equal-length targets should fire, both same-name-different-field span directives should match their spans, both single-field event directives should pass their events, and both same-length-span same-field-count directives should create and let me observe their spans. This matters because anyone configuring multiple filters of similar specificity right now can't trust them all to be applied, and silently dropping events makes the whole filter system unreliable when different subsystems have similarly named targets or fields.
