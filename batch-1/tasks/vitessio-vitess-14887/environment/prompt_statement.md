I'm chasing down a nasty SQL error parsing bug and could use a hand. When a database op fails and the error gets wrapped up in an RPC-level error message, our parser sometimes misreads the error code and sqlstate. I traced it to bind variable data getting embedded in the error string. If a query had a bind var whose value happened to contain an error-like substring, something like "(errno 1366) (sqlstate 10000)", the parser latches onto that pattern from deeper in the message instead of the real error code that shows up near the beginning.

Concrete case: a duplicate primary key error (errno 1062, sqlstate 23000) wrapped in RPC. The outer message clearly says 1062/23000 but because the bind data has its own errno/sqlstate lurking later in the string, we extract 1366 instead and the whole thing gets misclassified. That's bad because it stops being recognized as a constraint violation, and callers that key off the parsed error type to decide retry vs. surfacing the error to the user end up doing the wrong thing (retrying something that won't succeed, or swallowing a real constraint violation).

What I want is for the parser to always grab the first, outermost occurrence of the errno/sqlstate pattern in the message and use that, so embedded error-like strings in bind variable values can't interfere. A duplicate-key constraint violation should always come back recognized as such no matter what junk shows up later in the string. Basically scan left to right and stop at the first match rather than picking up a later one. Can you fix the extraction logic so the outermost error code and state win?
