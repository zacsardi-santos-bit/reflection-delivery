We're hitting correctness problems with prefix ACL operations in Ozone's HA setup and I want you to fix the whole cluster of issues in the prefix access control path. The core bug is that when a leader processes a prefix ACL op that ends up being a no-op, like adding an access control entry that's already there or doing a "set" with the same access controls again, the in-memory prefix tree doesn't get touched and the transaction log index stays stale. Then followers replaying the log end up with divergent state from the leader, the update ID doesn't match what the leader committed, and we get silent authorization inconsistencies that are miserable to debug. So all three prefix ACL operations (add, remove, set) need to always update the in-memory prefix tree and persist the correct transaction ID whether or not the ACL content actually changed.

There's also cleanup weirdness: when the last access control entry gets removed from a prefix, the prefix entry isn't always deleted from the metadata table and the in-memory prefix tree, so a stale empty entry lingers and can mess with later operations. Removing the last ACL should delete the prefix entry entirely from both. And removing an ACL from a prefix that doesn't exist at all should consistently return a "prefix not found" response, right now that's flaky.

On top of that the path validation isn't catching malformed prefix paths early enough. A prefix path missing its trailing path delimiter should be rejected with a "prefix not found" status, and a path with invalid filesystem structure (think consecutive delimiters) should be rejected with an "invalid path" status. Currently these slip through and blow up deeper in processing.

Oh and the persistence layer needs to correctly round-trip the object ID and update ID fields so a prefix read back from storage compares equal to what was originally written, otherwise the equality checks that back all this can't be trusted. The why here is that under OM high availability, log replay on followers has to produce identical in-memory state to the leader, and stale transaction IDs plus incomplete empty-prefix cleanup cause divergent state that's hard to detect and recover from.
