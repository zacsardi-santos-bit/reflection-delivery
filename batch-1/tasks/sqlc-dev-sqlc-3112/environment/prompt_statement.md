I'm hitting a weird bug with sqlc where optional named params vanish from the generated code when they're buried inside nested SQL function calls. Like I've got a MySQL query doing optional filtering where I wrap the named param in a fallback expression (coalesce-style) and then nest that whole thing inside a pattern-matching function call, and when I run codegen the resulting params struct comes out completely empty. The params are just gone, no error, nothing. The SQL is totally valid and the intent's obvious, it just silently drops them.

Same deal on Postgres too, btw. If the named parameter sits more than one level deep inside SQL function calls it doesn't get picked up at all. It seems to happen specifically when the param shows up as an argument to a function whose return type isn't a known table type, or where the outer function's context blocks type inference from propagating inward. So the analyzer walks the outer call but never recurses far enough to find the named param sitting in there.

What I want is for the generated params struct to include every named parameter no matter how deeply it's nested inside function calls, with types inferred from whatever context is available at that point. This is such a common pattern, optional filtering where you either pass a value or skip it, and right now the only workaround is restructuring the query into something that isn't really semantically equivalent, which sucks. So the fix should make the param resolution recurse through nested function arguments properly, and it needs to work for both MySQL and PostgreSQL so codegen emits correct params structs with appropriately typed fields for these nested optional params in both engines.
