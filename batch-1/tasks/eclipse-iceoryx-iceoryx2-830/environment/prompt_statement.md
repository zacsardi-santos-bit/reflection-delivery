I'm poking at the Python bindings for our IPC library, the event-based messaging side specifically, and I've hit a wall. I can build and open an event service from Python just fine, but there's literally no way to send or receive notifications because the notifier and listener port types were never exposed to the Python API. So the whole event pattern is dead weight from Python right now.

What I need is for the event service object to hand out both a notifier factory and a listener factory so I can actually spin up port instances. On the notifier side, the factory should let me set a default event identifier upfront before I create the port, and then once I've got the notifier I want to fire off a notification either using that preconfigured default id or passing an explicit one at send time. That covers the sending half.

For receiving, the listener needs a bunch of modes: a non-blocking try-to-grab-one-event, a non-blocking grab-all-pending-events, a time-limited wait for one event (up to some duration), a time-limited wait for all pending, plus a fully blocking wait for one and a fully blocking wait for all. Whatever comes back should be in the same order the events were sent, that ordering matters. Oh and both the notifier and the listener should surface the deadline duration that got configured on the service when it was created, so an app can read it back at runtime from either port.

Basically I want to wire these missing port types into the Python bindings so the event messaging pattern reaches parity with the rest of the library and I can build real notification workflows. Can you implement them?
