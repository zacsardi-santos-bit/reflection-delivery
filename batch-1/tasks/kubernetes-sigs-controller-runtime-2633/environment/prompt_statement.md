I'm hitting two annoying bugs in the fake Kubernetes client we use for controller testing, and I need both fixed so it lines up with how a real cluster behaves.

First thing, when I fetch typed Go objects (concrete structs, not unstructured), the fake client keeps stuffing the API version and kind fields onto the returned objects after a Get or List. Real clients don't do that for typed objects because the type info is already encoded in the Go type itself, so those TypeMeta fields should just stay empty. Right now they don't, which means my tests have to add extra workarounds that wouldn't exist against a real cluster, and it makes it a pain to compare a retrieved object directly against a locally constructed reference. So after Get or List with typed objects, the apiVersion and kind should come back empty, matching real client behavior.

Second, and this one's worse, some custom resource types embed their metadata fields as pointers instead of as value fields. That's a totally valid Go struct pattern, but the fake client just falls over on it, any operation fails, whether it's Get, List, Patch, Update, or Delete. I can't write controller tests for any resource type that uses this embedding style at all right now. It should handle pointer-embedded metadata the same as any ordinary type across all of those operations.

Both fixes matter because tests on the fake client should behave consistently with tests against a real cluster, oh and custom resource authors who use pointer-style metadata embedding shouldn't hit crashes or weird errors just for defining their types that way. Fix both so the fake client is consistent with real clients and supports the full range of valid resource type definitions.
