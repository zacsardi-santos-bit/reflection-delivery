I'm adding memory pressure awareness to our Pomerium proxy so it can handle getting close to its container memory limits gracefully. Right now when we run in Docker or Kubernetes the process lives inside cgroup-constrained namespaces and if it uses too much memory the kernel just OOM-kills it with zero warning, so I want to detect pressure early and let the Envoy data plane take graduated protective steps before that happens.

What I need is a resource monitor that reads memory usage and limits straight from the Linux cgroup filesystem, and it has to auto-detect which layout we're on by inspecting the current process's mount namespace since we might be on the older cgroup v1 hierarchy, the newer unified v2 one, or a hybrid setup where both coexist. It should compute a memory saturation ratio (usage divided by limit) as a float clamped between 0.0 and 1.0, write that value out to a well-known file on disk, and configure the data plane to use that file as its resource pressure signal. When there's no memory limit set (unlimited) saturation should be 0.0, and when usage meets or exceeds the limit it caps at 1.0.

Also the polling interval should scale with pressure, so it ticks more frequently as saturation climbs. There needs to be a runtime config flag that can disable the whole resource manager, and when it's disabled the saturation reported to the data plane should reset to 0.0. Oh and if the memory limit file disappears at runtime (say a cgroup change) the monitor should stop and return an appropriate error.

For the data plane side, configure it with a set of graduated overload actions at specific saturation thresholds, starting with heap shrinking and timeout reduction at moderate pressure, then stopping the acceptance of new connections, disabling keepalive, and finally rejecting requests outright as saturation approaches 1.0. The point is progressive load shedding so we protect availability instead of dying abruptly.
