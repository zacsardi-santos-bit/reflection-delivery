I'm working on adding memory pressure awareness to our proxy service so it can gracefully handle situations where it's approaching its container memory limits. Right now, if the process uses too much memory in a containerized environment, the kernel just kills it with no warning — we'd like to detect memory pressure early and allow the proxy's data plane to take graduated protective actions.

I need a resource monitor that reads memory usage and limits from the Linux container control group filesystem — it needs to support older-style hierarchies, the newer unified hierarchy, and hybrid setups where both coexist. The monitor should compute a memory saturation ratio (usage divided by limit), write that value to a file on disk, and configure the data-plane to use that file as a resource signal. When there's no memory limit set, saturation should be zero. When usage meets or exceeds the limit, saturation should be capped at 1.0.

The polling interval should scale with memory pressure — polling more frequently as saturation increases. There also needs to be a runtime configuration flag to disable the entire resource manager, in which case the saturation reported to the data plane should drop to zero. If the memory limit file disappears at runtime, the monitor should stop and return an error.

The data plane should be configured with a set of overload actions at specific saturation thresholds: starting with heap shrinking and timeout reduction at moderate pressure, then stopping new connections, disabling keepalive, and ultimately rejecting requests as saturation approaches 1.0.
