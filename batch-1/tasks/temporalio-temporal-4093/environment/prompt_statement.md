I'm building out the streaming side of the history replication service in our distributed workflow system, and right now everything goes through polling which is slow. I want to add the infra for persistent bidirectional streams so cross-cluster replication is more responsive, and it's three pieces that need to live in the replication package and play together.

First is a generic bidirectional streaming wrapper that manages a stream connection's lifecycle. It should lazily init the connection from a provider the first time it's used, and be idempotent so calling init again after the first time is a no-op, but once it's been explicitly closed a re-init attempt has to return an error. It exposes send, receive, and close, and any send or receive error should automatically flip it to a closed state. Received messages come out through a Go channel that gets closed when the upstream connection ends or errors out.

Second is a task progress tracker keeping an ordered queue of in-flight replication tasks and computing the current low-watermark (the highest fully-processed position). Adding tasks is idempotent, so if a task's already in the queue don't add it again. For the watermark calc, advance past tasks that've been acked, and when tasks are still pending or cancelled return a position anchored to the first unfinished task using that task's ID and creation time. Empty queue returns nil, meaning no ack should go out.

Third is a stream receiver tying these together: read incoming replication messages, wrap each one into an executable task, submit to a task scheduler, and periodically send acks back to the source carrying the current watermark position and timestamp. If there's no watermark yet, don't send an ack. If the stream returns an error, propagate it up.

These are the building blocks for efficient, progress-tracked replication with proper back-pressure, so I want them clean and working together.
