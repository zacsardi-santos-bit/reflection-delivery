I'm poking at the TiDB SQL optimizer and hit something annoying: the fast single-row lookup path (the one that does direct point access when you're matching a unique/primary key) just gets skipped the moment a query slaps an alias on the table. So `select * from t where t.pk = 1` uses the optimized single-row plan, but `select * from t as x where x.pk = 1` falls back to a slower plan even though the conditions are identical. I want aliased and non-aliased forms of the same query to land on the same execution plan when everything else matches.

While I'm in there, there are a couple of related correctness things that need to line up with standard SQL semantics. When you give a table an alias, that alias should completely replace the original table name, so if I write the alias I get resolved correctly in both the SELECT list and the WHERE clause, but if I try to qualify a column with the original table name (after aliasing it) that should error out, and same deal if I use some totally unknown qualifier that isn't the alias or a real table at all. Both cases need to raise the appropriate error rather than silently doing the wrong thing.

Oh and one more, mixing a wildcard with specific named columns in the same SELECT list (like `select *, col from ...`) should work and return all the expected columns in the correct order, not drop or reorder anything.

So the fix is: get the single-row lookup optimization to kick in for aliased queries too, make sure alias-qualified references resolve properly on the fast path in both SELECT and WHERE, keep the wildcard-plus-named-columns ordering right, and make invalid references (original table name post-alias, or an unknown qualifier) produce the right errors. The whole point is that developers using aliases shouldn't get silently degraded performance or wrong results compared to the non-aliased equivalent.
