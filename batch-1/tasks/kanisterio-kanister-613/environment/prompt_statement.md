I'm cleaning up the zone selection logic we use when restoring or cloning block storage volumes across cloud regions, and the main annoyance is that the function resolving which availability zones to use in the target region spins up its own Kubernetes client internally. That makes it painful to unit test in isolation, couples zone selection to cluster connectivity, and stops the caller from reusing an existing client or handling a connection failure gracefully before we even try to resolve zones. I want to refactor so the Kubernetes client comes in as a parameter instead of being created inside. The storage provider (AWS EBS, GCP persistent disk, Azure, etc.) should be the one creating the client and passing it down, and it can log or just ignore a client creation failure before calling into zone resolution, so we can still fall back to statically known zone mappings when Kubernetes isn't reachable rather than getting all-or-nothing behavior.

Also, the helper that filters a set of candidate zones against the list of valid zone names for a provider is currently private, which forces provider packages to either duplicate that logic or reach for a higher-level function that does way more than they need. I want that filtering helper made public so a provider that already has a list of available zones can validate candidates against it directly.

Oh and one more thing on error handling in that resolution function: it needs to clearly distinguish two separate failure cases, each with its own distinct descriptive message. One is when there are no valid availability zones that can be found for a region at all, and the other is when the region itself isn't recognized by the provider's zone mapping (no zones mapped for it). Right now those aren't cleanly separated and it's confusing which situation you actually hit.
