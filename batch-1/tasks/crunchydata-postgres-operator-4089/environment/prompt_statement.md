I'm adding support for user-defined log exporters in the OpenTelemetry collector configs that the postgres-operator generates. Right now these configs only route component logs (PostgreSQL, pgBouncer, pgAdmin, pgBackRest, Patroni) to a built-in debug exporter, and there's no way to ship those logs off to an external observability system like Google Cloud Logging. Operators running in production really need a supported path to centralize logs, so I want the config generation to honor custom exporters and log routing settings from the cluster's instrumentation spec.

The behavior I want: when no instrumentation spec is configured, everything stays exactly as before, debug-only output with empty extensions, processors, and pipelines. When an instrumentation spec is provided with custom exporter definitions and log routing config, those exporters get included in the generated collector config and all the relevant log pipelines route through them instead of (or in addition to) the debug exporter.

To make this work, the functions that build collector configs need to take the instrumentation spec as a parameter so they can pull in the user-defined exporters, specifically the one that creates a base config, the pgAdmin logging one, and the one for the pgBackRest repo host pod. The other logging functions already get cluster info passed in and can read the spec from there, so those are fine.

Couple of related cleanups while I'm in here. The Patroni log pipeline should always include resource attribute enrichment and attribute grouping processors, regardless of whether custom exporters are set up (right now it's inconsistent). And the pgAdmin log transform needs improving so it preserves the original log body, sets the message as the log body, and records the logger name as the instrumentation scope name. Oh and when custom exporters are configured, the generated configs should also pull in appropriate file storage extensions so we get durable log checkpointing for persistent reading.
