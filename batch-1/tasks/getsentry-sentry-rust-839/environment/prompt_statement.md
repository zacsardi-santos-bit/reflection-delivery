I'm hitting a weird thing with the Sentry tracing integration. When I record a tracing event at warning level and attach an error to a named field, like some specific field name I picked, the error doesn't show up in the resulting breadcrumb's data under that name. It's getting collected under some generic fixed key instead, or in some cases it just vanishes from the breadcrumb data entirely. And if I had multiple error fields they'd all get merged under that one key, which is useless.

What I want is simple: if I name a field and pass an error as its value, I should be able to pull that error back out of the breadcrumb data using the exact same field name I used in the tracing event. The value stored there should be a list of human-readable strings, one per error in the chain, each formatted with the error type and its message. So the original field name gets preserved rather than discarded.

The breadcrumb level and message should keep reflecting the tracing event's severity and log text like they do now, that part's fine. It's just the error-to-data mapping that's broken. Can you fix the tracing-to-breadcrumb conversion so it keys errors by their original field names? Developers lean on field names to know what each value represents, and losing them makes it impossible to look up or tell apart specific errors by name in Sentry, so this really hurts debuggability.
