I'm chasing down a bug in the stack autoinclude feature in our infra tool. Right now both individual units and composite stacks dump their autogenerated dependency config to the same filename, and it's biting us: a stack-level autoinclude file sitting in the same directory as a plain unit config gets merged into that unit's config even though it was only ever meant for the stack component. That breaks the isolation the whole scheme is supposed to give us, stack deps bleeding into unit configs means wrong inputs get applied.

What I want is to split these into two distinct filenames keyed off the component's kind, one for units (the existing unit-level autoinclude filename) and a new separate one for stacks. There should be a lookup function that takes a component kind and hands back the right filename, and if someone passes an unknown kind it should panic with a helpful message that spells out which kinds are actually valid ("unit" or "stack"). The file generation logic then uses a component's kind to pick which filename to write, so unit autoincludes never show up under the stack filename and vice versa.

Also, and this is the important half, on the config-parsing side when we're processing a unit's own config file, the stack-level autoinclude filename has to be ignored entirely, don't merge it in at all. Only the unit-level filename should be considered during unit config parsing. That way each component type only ever processes the config that was actually intended for it.
