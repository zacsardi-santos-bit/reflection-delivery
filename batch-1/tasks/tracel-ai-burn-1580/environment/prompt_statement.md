I'm cleaning up the compute layer of our deep learning framework and the way we pass memory handles around is bugging me. Right now every read and execute call in the compute server takes handles by reference, which means the handle has to stay alive for the whole duration of the call and the lifetime gets tightly coupled to each operation. It's awkward when I want to hand ownership of a memory resource off between components, and it's hard to reason about when a handle is actually done versus still in flight.

What I want is a "binding" concept, basically a lightweight owned value you create from a handle right at the point of use. So instead of borrowing handle refs, a caller converts a handle into a binding and passes that binding by value into both read and execute. Creating the binding is the signal that the resource is being committed to that specific operation, which makes consumption intent explicit and gives us something to build memory lifecycle tracking on top of.

Concretely I'd like a new binding type living in the server module, and memory handles should convert into it through a dedicated method. The server's read op should take a single binding by value, and execute should take a collection of bindings by value. The binding needs to carry the underlying memory resource info so the server can actually get at the memory, and it should be cloneable since autotune duplicates resource refs for benchmarking, oh and it should expose that underlying resource too. The client-facing read and execute methods should mirror this same binding based interface so it's consistent across the client API and the server trait. Also the memory management layer needs updating to accept bindings by value rather than raw handle references throughout.
