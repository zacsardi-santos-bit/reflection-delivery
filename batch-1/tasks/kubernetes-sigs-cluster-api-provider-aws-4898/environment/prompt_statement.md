I'm working on the cluster-api-provider-aws stuff and hitting a wall with secondary CIDR blocks on EKS-managed VPCs. Right now the managed control plane network config only lets you specify a single secondary CIDR block, and I need it to take a whole list instead so multiple additional IP ranges can get associated with the cluster's VPC. This matters for pod networking setups where teams want a dedicated IP space alongside the primary VPC range, common with certain CNI configs, and there's just no supported path for it today.

So what I want is the network config for the managed control plane to accept a list of additional CIDR blocks (not just the one), and the provider should automatically associate all of them with the cluster's VPC at creation time. The reconcile logic needs to be smart about it though, only add the CIDR blocks that aren't already associated with the VPC and leave the existing associations alone, don't touch what's already there. And on delete, walk the list and disassociate only the ones from that list that are actually associated with the VPC at that moment, don't try to remove stuff that isn't there.

Oh and I also need a validation rule in the admission webhook. If someone uses both the old single-CIDR field and the new list field at the same time, then the single CIDR value has to be present in the list. If it's not, reject the cluster resource at admission with a clear error that names the specific missing CIDR and tells the user where it needs to be added. Basically the message should identify which entry is missing and point at the list field so it's obvious how to fix it.

Backward compat is a hard requirement, clusters that only use the old single-CIDR field should keep working exactly like before, nothing should break for them.
