I'm trying to fix how `minion.restart` behaves on systems that use a service manager. Right now the restart function over in the minion execution module just does a raw process kill regardless of platform, which is fine on bare systems but totally broken on systemd Linux or Windows services, the service manager doesn't know a restart was requested so the minion just ends up stopped and the restart silently fails.

What I want is for the function to detect whether the host uses a recognized service management layer, and if it does, delegate the restart through that layer instead of killing the process directly. On systems without a recognized service manager, keep the existing kill-and-relaunch fallback exactly as it is today.

Also I want an optional schedule-retry capability, a parameter on the restart function defaulting to off, that queues a deferred start attempt firing after a configurable number of seconds, useful when a service restart doesn't immediately bring the minion back. This retry scheduling should be skipped entirely on non-service-managed systems. If the scheduling step itself fails, capture that error in the return value and don't attempt the actual service restart at all. But if the service restart fails after the retry was scheduled successfully, then both the scheduling info and the error should show up together in the result.

Oh and the function should return a structured result with a return code, a human-readable comment, and details about the service restart plus the scheduled retry when applicable. This matters because operators on systemd and Windows can't reliably restart a minion right now, and the scheduled retry adds some resilience for environments where transient restart failures happen.
