I'm hitting a false conflict problem in the Kong Kubernetes Ingress Controller around how upstream policy conflicts get detected for services referenced by HTTP routes. Say I've got an HTTP route with two separate rules, rule 1 points to service A which has upstream policy X, and rule 2 points to service B with a different upstream policy Y. Right now the controller marks policy X as conflicted, which is wrong, because those two services live in completely different routing rules and there's no situation where Kong would ever need to apply two different upstream policies to the same upstream. Each rule independently routes traffic to a single service, so no conflict exists.

The bug is that the current logic checks all backend references across all rules of an HTTP route when deciding if a policy has a conflict. What I actually want is for the check to happen at the rule level, so a conflict is only flagged when two or more backend services with different upstream policies appear together within the same routing rule. When services with different policies show up in separate rules of the same route, that's totally fine and each policy's status should come back as "Accepted". And when a service is the only backend in its rule, it should always be treated as non-conflicting no matter what shows up in other rules.

This matters because an HTTP route can have multiple independent rules each routing to different services, and Kong can only apply a single upstream policy per upstream anyway, so the overly broad detection is rejecting perfectly valid configs and blocking operators from using per-service upstream policies across multiple rules of the same route. Please update the conflict detection so it scopes to the rule rather than across the whole route.
