I'm chasing a round-trip bug in the dynamic commitment message types in our wire protocol package. Take a valid raw binary dynamic commitment message, decode it into the struct, re-encode it, and I don't get the same bytes back, which is bad news for interop since this protocol is how two channel peers negotiate updated channel parameters without closing and reopening the channel. If the encoding drifts, the byte streams won't match what other implementations produce and upgrading channel params safely in production just breaks.

Couple things I dug up. Known TLV fields (dust limits, in-flight value caps, HTLC minimums, reserve amounts, timing delays, that kind of stuff) are getting written into the extra/opaque data portion instead of their proper dedicated TLV slots, or sometimes into both, so you get duplication in the output. I need each known field encoded exactly once in its own TLV slot, not smeared into the extra-data blob. Also unknown or future TLV records that the current code doesn't recognize need to be passed through verbatim and preserved in the extra-data field so forward compat holds.

Second thing, some satoshi-denominated fields (the dust limit and channel reserve specifically) are using fixed-width integer encoding when they should be variable-length, so the encoded bytes don't match the on-wire format. Fix those to use varint-style encoding.

Oh and there's a constant identifying the musig2 local public nonce TLV record that has the wrong type number, needs correcting to the proper value.

Might help to add a shared helper that parses the known records out of a raw TLV byte stream while collecting the leftover unrecognized records separately for storage as extra data. Net goal: decode then re-encode produces the exact same bytes, every known field appears once in its designated slot, unknowns survive round-trip, sats fields use varint, and the nonce type constant is fixed.
