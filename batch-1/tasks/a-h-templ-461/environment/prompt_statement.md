I'm hacking on a Go templ-style template parser and keep running into gaps with real-world Go expressions inside templates. First thing, if I stash a component in a slice or a map and try to call it by index inside a template element expression, the parser just chokes. I want selecting a template function out of a slice by integer index to work, and pulling a struct out of a slice by index and calling a method on it, and same deal for map-indexed component references keyed by string, plus method calls on those values. All of that should parse cleanly.

Also my template parameter lists can only live on a single line right now which gets ugly fast when a template takes a bunch of params, so I need those to span multiple lines. Same story for string expressions embedded in templates, they can't wrap across lines yet and they should be able to.

Separately I need a brand new package that pulls the Go expression portion out of control-flow statements in template source. Give me functions that take a string starting from an "if", "for", "switch", "case", or "default" keyword (with the surrounding template body content around it) and hand back the byte offsets of just the expression part within that string, oh and one for general template call expressions too. There should also be a utility that extracts argument list content and returns the argument string directly, not offsets. These feed more accurate context-aware source processing which matters for formatting and codegen down the line.

Last thing, when the parser hits an unterminated statement like an unclosed comment or a control-flow statement missing its opening brace, the error position it reports is currently pointing at the end of whatever got consumed. I want that normalized to the start of the input instead so the diagnostics don't mislead me about where things went wrong.
