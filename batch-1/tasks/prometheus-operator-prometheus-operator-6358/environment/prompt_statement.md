I'm working on the prometheus-operator and I want to extend the web server TLS config so I can point it at cert, key, and client CA files that already exist on the container filesystem, not just Kubernetes Secrets and ConfigMaps. The use case is external cert managers that write TLS materials straight to disk, right now there's no way to tell the web TLS config to use those files so I'd have to duplicate my credentials into a Secret just to serve HTTPS, which is annoying and defeats the point.

So what I'm after: the TLS config type should get optional file path fields for the certificate, the key, and the client CA, sitting alongside the existing Secret/ConfigMap reference fields. A file path field and its corresponding Kubernetes resource reference for the same material need to be mutually exclusive, so if someone sets both, that's a validation error. Also the validation has to always require both a cert and a key present, via either a file path or a Kubernetes reference, so a config that has a client CA but is missing the cert or the key isn't valid. The existing validation ordering and messages are a bit fuzzy on covering all these combos so tighten that up too.

Then on the generation side, when a file path is given for a TLS material, the server config output should reference that file path directly instead of building a path off a mounted secret or configmap. This should line up with how standard Prometheus TLS config works.
