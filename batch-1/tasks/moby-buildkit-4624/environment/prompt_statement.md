I'm adding per-mount content-based cache control to BuildKit's exec op solver and could use a hand wiring it up. The idea is that when we compute a cache key for an exec operation, some mounts can safely have their cache key derived from the actual contents of the mounted data rather than just the structural description of the build. We call this content caching and it's only reliable when a mount's content can't change during the build step, since applying it to a writable, non-root-scoped mount could produce wrong cache results. Right now there's no per-mount knob for this at all, so users can't opt a mount in or out and we can't auto-enable it where it'd be safe.

What I want is for the cache-map computation for exec ops to respect a new per-mount content-cache field with three modes. There's an "off" mode that always disables content caching regardless of any other mount properties, an "on" mode that enables it when safe but errors when unsafe, and a default mode that auto-detects safety. The safety rules: content caching is safe if the mount uses a root selector, or if the mount is read-only, or if the mount is marked as producing no output. So in default mode we should auto-enable for read-only mounts, no-output mounts, and mounts scoped to the full root of their source. In default mode we should NOT auto-enable for writable mounts scoped to a subdirectory, including mounts at the root destination path (a writable non-root-scoped mount stays unsafe). And when "on" is explicitly requested for an unsafe mount (writable and scoped to a non-root subdirectory), reject the op with a clear error saying the mount configuration is invalid rather than silently misbehaving, whereas default mode just quietly skips content caching instead of erroring.

Oh and the protobuf definition for mounts needs a new field to carry this content-cache setting with the appropriate enum values (off, on, default). Without this there's no safe way to harness content-based caching per mount and build correctness could get silently compromised if it were applied to mounts whose contents can change, so the safety check matters as much as the feature itself.
