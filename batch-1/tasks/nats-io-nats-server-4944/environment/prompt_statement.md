I'm running a NATS cluster with a bunch of gateway nodes, all set up to enforce certificate validity proofs on their gateway connections, and I keep hitting a nasty issue when I rotate TLS certs. So the scenario is: I've got TLS configured only on the gateway section, not on the main client listener, and when I rotate the certs on one server and trigger a config reload, the whole gateway mesh falls apart. Other nodes can't connect to the reloaded server anymore and cross-cluster message routing just dies.

Digging in, it looks like the certificate validity monitors aren't getting restarted during the reload when TLS is only on the gateway and not on the root/client listener. Right now they only restart if TLS is configured at that root client level, so a gateway-only cert rotation leaves the monitors stale and the server can't prove validity of its freshly rotated certs, so the TLS handshakes between gateway nodes fail.

What I want is for those validity monitors to always restart on any config reload, regardless of whether TLS is also set on the main client listener, so newly rotated gateway certs get fresh validity proofs. After a cert-rotation reload every node in the gateway mesh should re-establish full connectivity with each other, and clients connected to any node should still be able to exchange messages with clients on other nodes across the gateway mesh. Operators need to rotate gateway certs via reload without silently breaking gateway-to-gateway TLS and blowing up routing, so the fix is in the reload path that decides when to kick off the monitor restart, it just shouldn't gate that on the client listener having TLS.
