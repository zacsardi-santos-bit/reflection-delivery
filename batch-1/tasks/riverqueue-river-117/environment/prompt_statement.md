I'm building out a job queue library and hit a wall where there's just no built-in way to list or filter jobs sitting in the database. Right now you can only pick jobs up for processing, so if I want to build a dashboard or an auditing tool or anything that observes queue state, I'm stuck writing raw SQL against the jobs table by hand. I want to formalize this as part of the adapter API so it's done with proper parameter binding and pagination instead.

So first, at the low-level internal database layer, I need a function that runs a parameterized SQL query against the jobs table and returns matching jobs. It should accept filters for job state (or no state filter at all), queue name(s), arbitrary extra SQL conditions with named arguments, a sort order that allows one or more ORDER BY expressions, and a result limit that always has to be specified. This thing needs to be able to run inside a transaction too.

On top of that the higher-level database adapter layer needs two methods that wrap this. One runs directly using the adapter's own connection, and the other runs inside an externally provided transaction. Both take a params struct carrying the same stuff: state, queues, custom conditions, named args, ordering, and the limit count. When queue filtering is set it should get combined with whatever other conditions exist using AND, oh and the adapter interface itself needs both methods added so every implementation, including the test mock adapter, is forced to provide them. That last part matters because it keeps the mocks honest, they'll fail to compile until they satisfy the same contract as the real thing.
