I'm working on a job queue library and I need to add a way to list and filter jobs from the database. Right now there's no built-in mechanism to query jobs by state, queue name, or metadata — you can only pick them up for processing. I'd like to add a low-level database function (in an internal package) that runs a parameterized SQL query against the jobs table, accepting filters like job state, extra SQL conditions with named arguments, sort ordering, and a result limit. This function should work inside a transaction.

On top of that, the higher-level database adapter layer needs to expose two methods that wrap this — one that runs directly using the adapter's own connection, and one that runs inside an externally provided transaction. Both methods should accept a params struct with fields for state, queues, custom conditions, named arguments, ordering, and a limit count. When queue filtering is specified, it should be combined with any other conditions using AND. The adapter interface itself needs to be updated to include these two methods so that all implementations, including the test mock adapter, are required to provide them.
