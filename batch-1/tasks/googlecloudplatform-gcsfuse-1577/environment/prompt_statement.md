I'm working on the gcsfuse codebase and need to add a configurable maximum entry count to the directory inode's type cache. Right now the cache can grow without bound — there's no way to cap how many entries it holds, or to disable it entirely via configuration. I'd like to add a new configuration field alongside the existing TTL setting so that operators can set a maximum number of entries, disable the cache by setting the limit to zero, or allow unlimited entries by using a negative value.

At the same time, I want to move the filesystem entry type constants out of the inode package and into a dedicated metadata package so they can be shared more broadly. Two new type values should be added: one for symbolic links and one for entries that are definitively absent (enabling negative caching). The type cache implementation should live in this new metadata package and implement a clean interface with get, insert, and erase operations.

The directory inode constructor should accept the new maximum-entries parameter, and the cache should be updated consistently after every lookup, listing, creation, clone, and deletion operation — reflecting the correct entry type for each child name. When the cache is disabled (either by zero max-entries or zero TTL), all lookups into the cache should return the "unknown" type value.

The configuration parser should validate the new field and return a clear, exported error constant for invalid values. When the field is absent from the configuration file, a default value should be used. The JSON serialization of the configuration struct should include the new field.
