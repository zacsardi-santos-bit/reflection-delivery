I'm adding import support to the subaccount environment instance resource in the SAP BTP Terraform provider, over in `@internal/provider/resource_subaccount_environment_instance.go`. Right now there's no way to bring an existing environment instance into state, so if someone provisioned one through the BTP cockpit or CLI or another workspace, they're stuck destroying and recreating it to get it under Terraform management, which is obviously a non-starter for incremental adoption.

I want the import to take a composite ID: subaccount ID and environment instance ID joined by a comma. So the handler splits on the comma and needs exactly two non-empty parts. If it's malformed the error should spell out the expected format (subaccount ID, then environment instance ID, separated by a comma).

There's also a bug in the existing import logic I need fixed: it's referencing the wrong attribute name when restoring the subaccount info during import, so it'd fail even if you tried it, and the malformed-identifier error message mentions that wrong attribute name too. Both should point at the correct subaccount ID attribute.

The tricky part: after import the state has to match what a normal apply would produce, no spurious diffs on the next plan. The API returns some internally managed fields inside the parameters (like a runtime status field) that a user would never set when creating. On a normal create we keep the user-provided parameters as-is, but on import we don't have that original state, so I need to strip those internal fields out of the parameters so the imported state lines up with what Terraform would've recorded had it created the resource itself.

So: implement import, fix the attribute name bug in the handler and its error message, and make sure the post-import state is clean.
