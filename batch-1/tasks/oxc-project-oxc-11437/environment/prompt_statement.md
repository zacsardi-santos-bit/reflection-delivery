I'm hitting a false positive in the number-precision lint rule, the one that flags JS numeric literals that supposedly lose precision at runtime. When I write a big integer literal and call a method on it, like `1000000000000000128.0.toFixed()`, the linter yells that the number will lose precision, but that's just wrong for this value. It happens to land exactly on a boundary of IEEE 754 double-precision, so JS can store it with zero loss, and yet the rule still reports a diagnostic.

The issue is the precision-checking logic doesn't account for the fact that at large magnitudes the ULP (the gap between representable doubles) gets big, so plenty of large integers are still exactly representable even though they look scary. Right now the algorithm treats them as imprecise anyway.

I want the rule fixed so any number that can be stored exactly as a double is not flagged, including large integer literals whose value falls right on an exact float boundary. It should only warn when precision is genuinely lost, meaning the value JS actually stores differs from what I typed. Numbers that round-trip cleanly should pass without any warning. Devs are seeing bogus lint failures in perfectly correct code because of this, so I'd like it to reflect JS's real numeric behavior. Thanks!
