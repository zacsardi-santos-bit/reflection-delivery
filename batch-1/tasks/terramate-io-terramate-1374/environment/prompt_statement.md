So I'm poking at our code generation setup and hit an annoying gap. We've got two kinds of generation blocks, one that emits HCL and one that writes arbitrary plain file content, and the HCL one already lets you filter which stacks actually receive the generated code by matching path patterns. The plain file generation block doesn't have any of that, which is a weird inconsistency and forces people into workarounds like conditional expressions or per-directory config files just to scope file generation to, say, only stacks under some directory.

I want the file-type generation block to grow the exact same stack filtering that the HCL block already uses. So users can drop one or more filter blocks in, each holding path pattern lists, and the matching should behave like the HCL side already does: multiple patterns or conditions inside a single filter block all have to match (AND), while multiple filter blocks match if any one is satisfied (OR). Glob patterns need to work too, single-segment wildcards, multi-segment wildcards, and root-anchored paths.

Also, since filters only make sense when generating per-stack, combining a stack filter with a non-stack generation context should be a schema error. And reuse the HCL block's established parsing and validation rules, so bad path pattern formats (a bare string where a list is expected, or non-string list elements) produce the same appropriate schema errors. Keep the two block types consistent.
