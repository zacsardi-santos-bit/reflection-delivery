I'm extending the Kubernetes compliance module in the Datadog Agent, the piece that loads kubelet security config off cluster nodes. Right now it handles self-managed clusters plus AWS EKS, but it doesn't know anything about Google Kubernetes Engine or Azure Kubernetes Service, so when the compliance agent runs on a GKE or AKS worker node it fails to identify the managed environment and can't scope or classify the kubelet config it collects. That means security teams auditing two of the most popular managed platforms get incomplete or misclassified results, so I want proper detection and extraction for both.

For GKE the kubelet gets configured through a dedicated config file rather than command-line flags, so anonymous auth, the read-only port, the client CA, and the authorization mode all need to come from that file's contents, not the process args. Also any certificate file references inside that GKE config file should be resolved into objects carrying file metadata (owner, group, permissions), not left as raw string paths.

AKS is the opposite, it's driven entirely by command-line flags, so all the relevant settings get parsed straight from those flags and exposed on the kubelet config object: anonymous auth, read-only port, event QPS, max pods, certificate rotation, authorization mode, the CA file, the TLS cert and key files, the TLS cipher suites, and feature gates.

In both cases the managed environment should be identified by the right name, "gke" or "aks" respectively, and control plane components (API server, etcd, controller manager, scheduler, proxy) should be absent since managed platforms don't expose those on worker nodes, oh and the result should come back with no errors.
