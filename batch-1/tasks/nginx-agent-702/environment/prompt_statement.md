I'm working on the nginx agent and there's a gap in the config upload flow I need closed. Right now when the management plane sends a configuration upload request, the agent receives and processes it but never sends anything back, so the management plane has no idea whether the upload actually worked or blew up. I want the agent to send a data plane status response after it handles the upload request, indicating success or failure, so the control loop is actually complete. The command component needs to accept and forward these data plane response messages through the agent's internal messaging bus so they make it back out.

There's also a startup race I keep hitting: the file management component doesn't know when a connection to the management plane exists yet, so it tries to upload file overviews or update individual files before we're actually connected, and those operations fail. I want the file component to hold off on any file operations until it's been notified that a connection is established. So we need some kind of new connection notification signal that tells the file component it's safe to proceed, and it should only do overview uploads and file updates once that's fired.

Oh and one more thing on the internal messaging, when a config upload request comes in and gets forwarded across the bus, the message should carry the full management plane request structure, not just the inner upload request payload, since downstream components need all that surrounding context to do their job right.

Also the config file parser is currently ignoring the allowed directories list from the agent config. It should honor that list when parsing nginx config files instead of parsing whatever, so the restrictions in the configuration actually mean something.

Without the response mechanism the management plane is left in the dark, and without connection-gating the file ops fail silently during startup, so both of these matter for reliability.
