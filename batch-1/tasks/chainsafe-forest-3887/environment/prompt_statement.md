I'm working on Forest, a Rust Filecoin node, and I hit a gap in how we verify drand randomness beacon entries. Right now the code only knows about the traditional "chained" scheme that mainnet drand uses, where each entry's signed message comes from hashing the previous entry's signature together with the current round number. But there's a newer drand network people call "quicknet" that runs an "unchained" scheme, each entry signs just the current round on its own with no dependency on the previous entry, so it's independently verifiable. Without this, Forest can't validate chains that rely on quicknet, so I want to add it.

The annoying part is these two schemes also swap which elliptic curve groups hold the public keys vs the signatures. The chained mainnet layout puts pubkeys on one group and sigs on the other, and unchained reverses that. Our code currently just conflates them and uses whatever the BLS lib gives by default (which happens to be the chained arrangement), so there's no clean abstraction and it's easy to get a silent mismatch.

What I'd like is a dedicated beacon signatures module that cleanly expresses both. The unchained variant should get its own public key type carrying the key on its appropriate curve group, with both single-entry verification and a batch verification method. The chained variant should expose a standalone free function that takes a public key, a slice of pre-hashed messages, and a slice of signatures and verifies one or more entries. Oh and the existing beacon entry type should gain two helper methods for computing the message hash: one for the unchained scheme (just the current round) and one for the chained scheme (previous signature bytes followed by the current round).

Make sure the whole thing is actually checked against real public keys and signatures pulled from the live drand APIs for both networks, covering both that correct signatures verify and that incorrect ones get rejected.
