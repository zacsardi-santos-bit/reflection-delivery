I'm digging into the jj version control library and want to lift the file-fixing functionality out of the CLI layer and into a proper reusable library module. Right now the whole capability, applying automated content transformations to files across a range of commits, lives entirely in CLI-specific code, so anyone building plugins, integrations, or tooling on top of the jj core can't get at it without re-implementing all the commit-graph traversal and tree-rewriting logic themselves, or shelling out to the CLI, which is gross.

What I want is a library-level API that takes a set of starting commits, a file matcher, and a pluggable fixer component (the fixer receives some set of files and reports back which ones it actually changed), then walks the commit graph, calls the fixer on the relevant files, and rewrites any commits whose file trees got updated. It should let me control whether files that are identical to their parent commit's version get re-processed or skipped, defaulting to skipping unchanged ones but optionally including them. And it should hand back a structured summary: how many commits were inspected, how many were actually rewritten, and a mapping from the original commit IDs to their new rewritten equivalents.

Errors from the fixer need to bubble up cleanly through the top-level API and stop the process without leaving partial changes behind. Oh and I also want a parallel version of the fixer that can chew through many files within a commit concurrently instead of one at a time for the perf win, and if any single file fails during that parallel processing the error should propagate immediately with no partial results. This should all be testable in isolation too, that's kind of the point of pulling it into the library.
