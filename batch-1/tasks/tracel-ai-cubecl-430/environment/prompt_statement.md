I'm reworking the autotune setup in the cubecl runtime and the current API is bugging me because it forces me to bake memory bindings straight into the operation set when I construct it. The set definition (which candidate kernels to benchmark, how to build cache keys, how to clone inputs) is really a separate thing from the actual buffers I pass at a given call-site, but right now they're conflated. On top of that every individual operation stores its own copy of the bindings which is redundant boilerplate, they should only hold what they genuinely need like a kernel reference and a client, not the runtime bindings.

What I want is for the tunable set to only describe what to benchmark plus how to generate cache keys and clone inputs, while the actual input data (the memory bindings) gets supplied separately when the tuner is invoked. That way I can define a set once and reuse it with different inputs. Also I'd love to be able to pass plain closures or functions directly as tunable operations so I don't have to hand-write a full trait impl every time. And the custom checksum logic per set (used for cache invalidation) should be wired up through the builder pattern instead of mutating struct fields or overriding trait methods after construction.

One hard constraint, don't break any existing caching behavior: the same key still has to produce a cache hit, and a different key or a different checksum still has to produce a cache miss. Keep all those semantics intact while you decouple the definition from the inputs.
