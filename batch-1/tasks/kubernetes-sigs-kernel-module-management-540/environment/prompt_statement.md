I'm adding private registry support to the kernel module management system and hitting a wall because worker pods that load and unload kernel modules can only pull from public registries right now, which is a dealbreaker for production since most folks keep their module images in private registries. The core issue is we never propagate credentials into the pods or use them during the actual image pull.

First, the API types. Right now the module spec and status types each carry name, namespace, service account, and image repository secret fields scattered directly on them, and it's redundant. I want a single shared inline identity structure that groups the module name, namespace, service account name, and image repository secret reference together, and both the spec and status types should embed it inline instead of repeating those fields.

For the pod management layer, when we build loader or unloader worker pods, look up the service account configured for the module, collect all the image pull secrets off that service account plus any explicitly configured image repository secret, and mount each of those as a read-only volume into the pod so the worker can actually use them.

On the worker side I need a new function that reads Kubernetes-format pull secret files from a local directory and builds an auth keychain out of them, and it's gotta handle both the legacy dockercfg format and the newer JSON-based (`.dockerconfigjson`) format. Then the image puller needs updating to accept that authentication keychain so it can use the creds when pulling from authenticated registries.

Oh and one cleanup thing, some of the config helper methods for managing module configurations take a context parameter they don't actually use, so drop the context param from those signatures while you're in there.
