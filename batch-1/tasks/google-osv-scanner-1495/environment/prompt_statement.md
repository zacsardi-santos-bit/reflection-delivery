I'm building out a vulnerability scanner that pulls dependency metadata from Maven and npm registries, and right now it only fires off unauthenticated HTTP requests, so any private registry my org uses just fails silently and I get incomplete vuln reports for anything with internally-hosted artifacts. I need a general-purpose HTTP authentication layer that sets the Authorization header on outbound registry requests and handles multiple schemes: basic auth via username/password or a pre-encoded credential token, bearer tokens, and digest challenge-response. It should run in two modes. In always-authenticate mode the right header goes out with the very first request. Otherwise it sends an unauthenticated request first, then reacts to the server's 401 challenge by picking the first supported auth method the server advertises. When I've got multiple schemes configured, use the first applicable one in my configured preference order. Also once a request authenticates successfully, remember that so later requests to the same server include the same credentials without re-challenging. One gotcha on basic auth: it needs both a username and a password (or the pre-encoded token) present, if only one field is set don't attempt auth.

For Maven, read server credentials out of the standard Maven settings files that devs already use, expanding environment variable reference placeholders to their actual env values, and if an env var isn't set just leave the placeholder as-is. Support both global and user-level settings, with user settings winning when the same server ID shows up in both, and apply the resulting per-server auth config automatically when hitting the matching registries. For npm, rework the request flow so auth gets applied at the moment the HTTP request executes instead of being a separate construction-then-execute step.
