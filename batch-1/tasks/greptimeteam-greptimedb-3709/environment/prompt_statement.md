I'm cleaning up some rough edges in the region management layer of our storage engine and there are three related things I want to knock out together. First one is an error code issue: when a write hits a region that isn't accepting writes, either because it's a follower region opened in read-only mode or because it got gracefully set to read-only, we currently return an error that says the region is "read-only." That's misleading. The region isn't really read-only in the meaningful sense, it's just not ready to take writes yet, so I want writes to non-writable regions to come back with a "not ready" error code instead. The distinction actually matters for callers trying to figure out why a write failed and whether retrying makes any sense.

Second, accessing a region's current manifest is way more cumbersome than it should be. Right now callers have to grab a read lock on the manifest manager and then call the manifest accessor while holding that lock, which is verbose and honestly kind of error-prone with the lock management. I'd rather have the region expose a dedicated manifest context field that gives you a simple async method to get the current manifest, no explicit locking on the caller side.

Third, the manifest manager's shutdown method returns a result that everyone has to handle, but in practice that operation can't fail in any meaningful way. Make it return nothing (infallible) so all the shutdown call sites can drop the unnecessary error unwrapping/handling.

So net effect: writes to non-ready regions return the correct "not ready" error, regions carry a manifest context with a simple async manifest accessor, and shutdown is unconditionally infallible. Accurate error codes help callers understand failure causes and recovery options, and the simpler manifest interface cuts cognitive overhead and prevents subtle lock bugs. Thanks!
