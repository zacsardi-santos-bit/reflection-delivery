I'm adding Deno builder support to GoReleaser and want it to work like the Bun, Rust, and Zig builders that already exist. GoReleaser compiles and releases software for lots of runtimes, and Deno's got a strong cross-compilation story where it turns TypeScript into self-contained native binaries, so right now Deno users have no native integration and have to hack around it with the prebuilt import mechanism. I want to close that gap.

The new builder should live in its own package alongside the other non-Go builders and self-register under the name "deno", and it needs to report the Deno runtime binary as a required system dependency. It has to parse Deno-style target triple strings into a structured representation with separate fields for architecture, vendor, OS, and ABI, and translate Deno's architecture names into the conventional Go-style names used everywhere else in the codebase so templates and filters stay consistent. Also give it sensible defaults: a tool name, the compile command, working directory, entry point file, and a default set of five standard targets covering what Deno's compiler supports, which is Windows, macOS on Intel and Apple Silicon, and Linux on x86 and ARM.

Oh and the artifact filtering system needs updating so artifacts built with this builder behave like the other non-Go builders (Bun, Rust, Zig) when filtering by architecture variants. The health-check subsystem should recognize "deno" as a required binary when a project's configured to use this builder. And ship an example config file so users can easily initialize a new Deno project configuration. The point is Deno developers get the full release pipeline (archives, changelogs, publishing, all of it) without the manual workarounds.
