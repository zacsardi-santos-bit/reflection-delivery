I'm digging into the SQL parser in our database engine and I hit a real gap with pattern-matching expressions. Right now LIKE, NOT LIKE, ILIKE, NOT ILIKE, and SIMILAR TO / NOT SIMILAR TO all get parsed into the AST as generic binary operations, and that's a problem because a binary operator node has nowhere to stash the optional escape character that's part of the standard syntax for these. So if someone writes a pattern match with an escape clause, that info just evaporates when we parse it, and downstream query semantics can go wrong silently.

What I want is dedicated AST node types for each of these. The keyword-based case-sensitive match (LIKE), the case-insensitive one (ILIKE), and the regex-style similarity operator (SIMILAR TO) should each get their own node, and each one should carry the left-hand subject expression, a boolean flag for whether the match is negated, the pattern expression, and an optional escape character. When an escape clause shows up it needs to be kept in the AST and round-trip back out to SQL correctly.

There's a second thing that's related. The PostgreSQL tilde-based symbolic operators for pattern matching are getting normalized to their keyword equivalents when we format the AST back to SQL, so operator syntax doesn't round-trip, you put one form in and get a different form out. I want those tilde variants kept as distinct operators that preserve their original symbolic form during formatting. Oh and there's a spot in the SQL generator that builds binary operations from expression types, and that mapping needs updating to point at the new operator-symbol variant instead of the old keyword-based one, otherwise the two halves won't line up.
