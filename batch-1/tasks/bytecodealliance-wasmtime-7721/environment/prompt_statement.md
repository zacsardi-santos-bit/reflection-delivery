I'm filling out the memory-instruction support in the Winch baseline compiler and right now it just falls over the moment a module touches any of the bulk memory ops. I need Winch to actually handle filling a memory region with a constant byte, initializing memory from a data segment, copying one region to another, dropping a data segment, querying current memory size in pages, and dynamically growing memory. Today any wasm module that uses these can't compile or run under Winch at all, which blocks a huge chunk of real programs, so getting these in makes Winch a much more complete execution tier.

Behavior should follow the wasm spec closely. Fills, copies, and inits need to succeed when the target range fits inside the allocated memory and otherwise trap with an out-of-bounds memory access error. Init from a data segment that's already been dropped should trap too. Memory size should return the correct current page count and reflect any growth that happened. Grow should hand back the old page count on success and negative one when growth would blow past the allowed max, oh and the grow result has to be usable as a value in any expression context, so branch conditions, call args, local assignments, arithmetic, wherever.

Validation matters too: invalid operand types on any of these should get caught at module validation time with a type mismatch error, and referencing a nonexistent memory or an invalid data segment index (including modules with no declared memory) should be rejected then as well with the right unknown memory or unknown segment style errors. This all needs to work under both the standard and the pooling allocator configs. The relevant code lives in the Winch crate under `@winch/src/`, mainly the codegen and instruction-visiting paths where the other memory operations are already implemented.
