I'm building out NAT detection for the per-hop data in Trippy and could use a hand wiring it up. Quick background: when a probe goes out and some intermediate router replies with a time-exceeded error, that error echoes back part of the original probe's transport layer, including the checksum. If there's a NAT device on the path it'll rewrite that checksum, so what comes back won't match what we originally sent. Right now there's no way to detect or surface any of this, users tracing a path can't tell where NAT translation is happening and that matters for debugging connectivity or reading how probes get routed and responses interpreted.

What I want is to compare the expected checksum (the one we computed while building the probe) against the actual checksum echoed back in the router's error reply, and from that assign each hop a NAT detection status. There are three states I care about: NAT not detected, NAT detected, and not applicable when no response ever came back. For the first responding hop it's simple, matching checksums means no NAT detected, differing means NAT detected. For hops past the first, don't compare against the probe's expected checksum, compare against the checksum echoed by the previous responding hop instead, since a NATted checksum carries forward and becomes the new baseline downstream. Same rule there, differ means detected, match means not detected. Hops that got zero responses are not applicable, and the status should only ever reflect the most recently received probe for that hop.

I want this NAT status tracked as part of the hop's state and reachable through the hop data structure. Also the core logic that computes the status from an expected checksum, an actual checksum, and an optional previous-hop checksum should live in its own dedicated function so it's testable on its own.
