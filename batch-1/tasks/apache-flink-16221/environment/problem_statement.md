## Description

Flink's idle/active stream status handling has several correctness issues that cause watermarks to flow through the system incorrectly and produce spurious status change events in the output.

**Problem 1 – Watermarks flow through idle chains**

When a streaming task transitions to idle status, watermarks should be blocked from flowing downstream. Currently, both incoming watermarks from upstream *and* watermarks generated by intermediate operators within a chained pipeline are still being forwarded even when the task is idle. This can corrupt event-time processing downstream.

**Problem 2 – Spurious ACTIVE/IDLE wrapping around records**

New-style sources currently wrap every emitted record in a surrounding pair of active/idle status events (active before the record, idle after), even when the task was already idle. This produces unnecessary status noise in the output stream.

**Problem 3 – Spurious ACTIVE status on every element in the watermark assigner**

The watermark assigner operator emits a stream-active status event on every element it processes, regardless of whether the status has actually changed. Only genuine transitions from idle to active (or vice versa) should produce status events.

**Problem 4 – Watermark multiplexer doesn't go idle when all splits are removed**

When all registered outputs (splits/partitions) are removed from the shared watermark tracker, the combined output should transition to idle. Currently it does not, leaving the combined watermark status in an ambiguous state. Additionally, when zero outputs exist from the start, the combined output should correctly remain non-idle rather than accidentally flipping to idle.

## Expected Behavior

- Watermarks are blocked at every link in the operator chain while the task is idle
- Status events are only emitted on genuine state transitions
- The watermark tracker becomes idle when all its registered partitions are removed, preserving the last emitted watermark value
- No spurious ACTIVE/IDLE wrapping appears in the output around data records

## Why This Matters

These bugs can silently cause incorrect event-time semantics in streaming jobs that use idle source detection — watermarks may advance further than they should, or status signals may mislead downstream operators about the liveness of a source.
