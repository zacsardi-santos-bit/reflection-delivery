I'm poking at the vSphere Go client library's simulator and the VM hardware upgrade path is basically a no-op on validation, it just accepts whatever I throw at it. Real vSphere rejects a bunch of stuff and the simulator should too. When I try to upgrade a VM that's powered on it should fail with a power state error, and if the VM's host is in maintenance mode I want a descriptive state error, same deal (a state error) when the VM is actually a template. If I ask for a hardware version that isn't supported, either not supported in the environment at all or not supported on that VM's specific host, it needs to come back with a "not supported" error carrying an informative message. And if I request a version that's equal to or lower than the VM's current version I want an "already upgraded" error, oh and if the requested version is too old (below some minimum threshold) that's an invalid argument error. Passing an empty target version should just upgrade to the latest supported version, and when it does that it needs to update both the config version and the hardware version summary fields so they stay in sync.

To back all this I also need a small utility type in the types package for working with the "vmx-N" hardware version strings VMware uses. It should parse them case-insensitively, hand back the numeric version number, and produce a normalized lowercase canonical form, that's what the validation logic leans on for comparing and extracting versions.

Also the command-line upgrade tool currently reports success even when the VM is already sitting at the latest hardware version, which is misleading, I want it to report failure in that case instead. The whole point is making the simulator a trustworthy test double so upgrade flow tests actually catch bugs that'd blow up against real vSphere.
