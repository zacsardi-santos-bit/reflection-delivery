I'm poking at the admission webhook client in the API server and want to fix how it picks HTTP protocol versions. Right now we force HTTP/1 on every webhook connection no matter what, which was done on purpose so HTTP/2's connection multiplexing wouldn't collapse a bunch of concurrent requests onto one connection and wreck TCP-level load balancing across multiple backend webhook pods. That reasoning holds for external hostnames and cluster service addresses, but it's too broad, it also clobbers webhooks pointed at loopback where there's just no multi-backend to balance across.

So what I want: when the webhook URL targets a loopback address (localhost, 127.0.0.1, the IPv6 ::1, that kind of thing) we should let HTTP/2 through, meaning the transport config for those shouldn't explicitly exclude HTTP/2. When the URL is a non-loopback address (external hostname, cluster service, whatever) keep forcing HTTP/1 exactly like today so we don't lose the load-balancing behavior. This decision needs to happen when the client config gets built from a direct URL, during the transport configuration step where we assemble things from the webhook's URL. Loopback endpoints running on the same node or in the same process would get HTTP/2 and cut down on per-request connection setup overhead, everybody else stays on HTTP/1.

Also, and this matters, the service-reference path (the webhooks that resolve through cluster-internal service DNS names rather than a raw URL) should stay on HTTP/1 forced, don't touch that behavior. It's really just the direct-URL case that gets the loopback-vs-not differentiation. Net effect is local webhooks talk more efficiently without giving up the load-balancing properties that production externally-addressed deployments still depend on.
