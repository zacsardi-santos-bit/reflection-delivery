I'm adding a lint rule to Biome's nursery category that enforces correct usage of `parseInt`, the built-in string-to-integer parsing function. The problem is developers keep forgetting the second radix argument, and since the function's interpretation of the input depends on the string format when no base is given (a string that looks octal might parse differently across environments), you get subtle bugs that never throw at runtime. Also folks sometimes pass a bad base value, like a plain string, or something out of the valid range, or some non-standard numeric literal type, and the function just silently hands back NaN.

So I want the rule to catch three distinct situations. First, when it's called without a radix argument at all, flag it and offer an automatic but unsafe fix that inserts `10` as the radix (10 being the most commonly intended base). Second, when a radix is present but invalid (wrong type, out of the valid numeric range, or an unsupported numeric literal format), report it with no automatic fix since the intended value is ambiguous. Third, when it's called with no arguments whatsoever, raise a separate distinct warning saying the call will always produce not-a-number.

Valid calls where an in-range integer radix is supplied, including using numeric separator syntax like underscores, shouldn't produce any warning at all. Calls to similar but unrelated parsing functions should be ignored entirely. And it needs to handle both the global standalone form and the form accessed as a method on the built-in number object (Number.parseInt), not just the plain one. The whole point is surfacing these silently-misbehaving patterns at development time without needing runtime execution.
