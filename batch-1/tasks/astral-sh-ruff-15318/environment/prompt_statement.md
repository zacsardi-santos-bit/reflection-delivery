I'm hitting two linter bugs around regex patterns that have a closing parenthesis in them, and they're clearly the same root cause. First, the "unnecessary regular expression" rule is throwing a false positive: when I call a regex module function with a pattern that contains a closing paren, the linter tells me to replace the whole thing with a plain string operation. That's just wrong, a closing paren is a real regex metacharacter, so following that suggestion would silently change behavior. It shouldn't be flagging patterns with a closing paren for that plain-string swap at all.

Second, the opposite direction, a false negative in the "ambiguous test assertion pattern" rule. When a test's exception context manager uses a plain (non-raw, unescaped) string as the match pattern and that string has a closing paren, I get no warning, even though it warns fine about other metacharacters in plain strings. Since a closing paren has special regex meaning, an unescaped one in a plain match string is ambiguous and deserves the same warning.

Both come down to the shared internal list of characters treated as regex metacharacters not including the closing parenthesis. So any pattern with an unescaped closing paren should count as regex-significant, and once that char's in the list both the bad suggestion and the missed warning go away together. Please add it and confirm both rules behave right.
