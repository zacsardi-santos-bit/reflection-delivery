I'm reworking the circuit breaker in my service mesh framework and the current logic bugs me because it opens after a fixed number of consecutive failures, like 3 in a row, which ignores traffic volume entirely. If an endpoint is doing 1000 requests a minute and 3 fail, tripping the circuit is silly since the failure rate is tiny, but if only 3 requests come in and all fail, yeah it should definitely open. So I want to move to a rate-based approach where the circuit only opens once the failure rate (failures divided by total requests) meets or exceeds a configurable threshold percentage (e.g. 0.5 for 50%) AND at least a configurable minimum number of requests have been observed in the current window. The config should take that failure rate threshold and the minimum request count instead of the old raw failure count. Also I need a time window in seconds that periodically resets both the failure count and the request count so stale failure data doesn't linger forever and skew things.

There's also a gap in the half-open state I want closed. When the circuit is half-open and a test probe request gets dispatched, the endpoint should be unavailable to other requests until we know whether that probe succeeded or failed. Right now nothing blocks requests during that little window, so I want a new intermediate state covering the moment between the probe being dispatched and its result coming back, and in that state the endpoint has to be treated as unavailable to additional requests.

Last thing, the events. When the circuit opens the emitted event currently stuffs in raw internal objects and doesn't carry enough info, so I want it to include node ID as a string, action name as a string, the failure count, the total request count, and the computed failure rate, which makes it way more useful for dashboards and alerting. Oh and the half-open event should use the same cleaner format with stable string identifiers (node ID as a string, action name as a string) instead of internal object references. The whole point is the threshold approach reflects real endpoint health across different traffic volumes and stops false trips during low-traffic periods.
