I'm chasing a crash in the UPnP port mapping path that shows up whenever there's a Huawei home gateway on the network. The router answers UPnP discovery totally fine and hands back a valid device description, but every service it advertises uses proprietary or DSL Forum namespaces instead of the standard internet gateway service types we know how to talk to. So when we go to set up a port mapping against it, the code never considers the case where none of the services are usable, it just barrels ahead with an absent service reference and panics. See https://github.com/tailscale/tailscale/issues/10911 for the original report.

What I want is for this to degrade gracefully instead of taking the whole thing down. When a discovered device has no supported services, the client selection step should come back with an empty result (no usable client) rather than crash, and the actual port mapping attempt against that device should return a clean failure, so no mapping obtained and definitely no panic anywhere in the flow. Oh and importantly the network probe should still report that a UPnP-capable device exists on the network even though we can't use its services, we just skip the mapping and move on. This hits any router (Huawei being the known example, but likely other vendor-specific ones too) that responds to discovery with non-standard service types, and the rest of the app needs to keep working normally after we skip it.
