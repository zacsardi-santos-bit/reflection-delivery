So I hit a weird thing with our DDL path. When I run a CREATE TABLE, whether it comes in as SQL or through the gRPC interface, the response tells me 1 row was affected. That's just wrong, creating a table is a schema-level operation, it doesn't touch any data rows, so the affected-rows count should be 0 in both cases. Standard DB convention is 0 for DDL, and right now clients and tests can't cleanly read the outcome because of this. I want CREATE TABLE via SQL to return 0 affected rows, and the same for table creation over gRPC.

While I was digging around I found some cleanup worth doing at the same time. The function that turns an alter-table expression into a concrete alter table request currently hands back an optional and treats a missing operation kind as a valid no-op, which is annoying, I'd rather it always produce the request directly and return an error when that required field is missing, and update all the callers to match. Also the function that builds a table insert request from a gRPC insert request shouldn't need a separate schema reference passed in just to look up column types, since that type info is already embedded in the incoming insert request itself, so drop that dependency. Oh and the table alteration API would be nicer if it could carry an opaque context map alongside the fixed alter request, so callers can attach extra typed values (like the original expression that triggered the alter) and implementations can optionally read them without us changing the request struct.

Last thing, the distributed test setup needs love too. It should actually keep the temporary storage directories alive for the whole duration of the tests (they're getting dropped early) and return one unified structure that gives access to both the frontend instance and the individual datanode instances.
