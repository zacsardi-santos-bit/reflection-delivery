So I've been using gRPC Swift's code generator and the client code it spits out is way more verbose than it should be. Every RPC call, even a dumb unary one, makes me build a request wrapper object by hand, pass it into the method, then dig the response value back out of a response wrapper. Three steps for what's basically a one-liner, it's tedious.

What I want is for the generator to emit an extra extension on each service's client protocol that wraps every RPC method with a friendlier signature so I can just pass the message directly. For unary and client-streaming methods (the ones that return a single response) the convenience method should have a default response handler that just returns the response value, so I call it and get the response straight back without providing a handler. For server-streaming and bidirectional-streaming there's no single message to return, so the handler needs to be required there. And for any method that takes a stream of requests, the convenience variant should accept a producer closure instead of making me construct a streaming request object.

The new extension has to carry the same platform availability constraints as the rest of the generated code, use the same access level (public, package, or internal), and it should still show up even for services that have zero methods (an empty extension is fine). Every generated file across the codebase that the generator touches needs regenerating to include these. Oh and the code renderer needs to learn how to render dictionary literal syntax too, since the empty metadata default in the new method signatures depends on that rendering working correctly.

Point is, reducing this boilerplate makes gRPC calls from Swift much nicer and fits Swift's whole ergonomic, expressive API vibe. I should be able to do a unary call in a single expression with no intermediate request construction at all.
