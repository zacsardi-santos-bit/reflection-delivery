I'm maintaining a database MCP server that operates in read-only mode, and I'm concerned about how it currently handles query validation. Right now, every SQL query — even obviously harmful ones — gets forwarded straight to the database, which then rejects write operations using its own built-in read-only transaction settings. The problem is that this gives no application-layer protection at all. A write statement, an injection attempt, or a multi-statement sequence designed to commit around the read-only constraint all make it to the database before anything stops them.

I'd like to add a proactive SQL security layer that validates queries before the server ever opens a database connection. The idea is: detect data-modification statements (things like inserts, updates, deletes, schema changes, permission modifications, and system-level commands) and reject them immediately with a clear error. Also detect common injection patterns — tautologies, stacked queries, union-based attacks, time-based probes, file operations — and reject those too. Finally, detect multi-statement sequences that could be used to bypass the read-only transaction boundary and reject those as well.

Safe, single-statement read-only queries should pass through without any change in behavior. When a query is blocked at this validation layer, the server should not establish any database connection at all. The detection should be case-insensitive and should handle SQL with comments, varying whitespace, and mixed-case keywords correctly.
