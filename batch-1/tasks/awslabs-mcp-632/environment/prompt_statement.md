I'm working on the Aurora DSQL MCP server, the read-only one, and I've got a security gap that's bugging me. Right now the read-only query handler in the server forwards every SQL query straight to the database and just trusts the database's built-in read-only transaction mode to reject writes. That means anything harmful, a write statement, an injection payload, a multi-statement sequence crafted to commit around the read-only boundary, all get transmitted and cause a full round trip before anything stops them. There's zero application-layer defense, and if the DB read-only config is ever misconfigured or hits some edge case, harmful stuff slips through. I want defense in depth plus faster, clearer feedback for the caller.

So I'd like a proactive validation layer that runs before the server ever opens a database connection. It should detect data-modification statements (inserts, updates, deletes, schema changes like DDL, permission grants/revokes, and system-level commands) and reject them immediately with a clear error saying write operations aren't allowed. It also needs to catch common injection patterns, tautologies, stacked queries, UNION-based attacks, time-based probes, and file read/write operations, and reject those with an injection risk error. And it should flag multi-statement sequences that could bypass the read-only transaction boundary, including commit/rollback tricks, and reject those too.

Safe, single-statement read-only queries have to pass through and execute exactly like before, no behavior change. When a query does fail this validation, the important part is no database connection gets established at all, we bail before connecting. Oh and the detection has to be case-insensitive and handle SQL with comments, weird/varying whitespace, and mixed-case keywords correctly so people can't sneak stuff past by lowercasing or padding it.
