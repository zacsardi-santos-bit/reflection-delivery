I'm using the OpenLineage SQL lineage parser to pull table lineage out of our multi-statement SQL scripts, and I keep hitting a gap with context-switching. Lots of our scripts open with a statement that sets the active database or schema (you know, the usual USE-style command) before any queries run, which is super common across Snowflake, Databricks, Hive, MySQL, and the other dialects the parser already supports. Problem is the parser processes each statement in isolation so it never tracks that active context, and any bare table reference that leans on it comes out unqualified in the lineage output.

Concrete example: a script switches to db1 and then queries my_table, I want the lineage to show db1.my_table, but right now it's just my_table with no namespace at all. That makes datasets that depend on context-based resolution show up as unresolved or flat wrong in the lineage graph, which wrecks the data for governance and impact analysis.

So I want the parser to carry the active database and schema forward and apply them to later unqualified table references. It's gotta respect each dialect's conventions, because the bare context-switch form sets the schema in some dialects and the database in others, handle each correctly. Also partial updates need to preserve prior state, so switching just the database without naming a schema should keep whatever schema was already active. Partially-qualified refs (like schema.table with no database) should get merged with the active context for the missing parts, while fully-qualified references that already spell out all three name parts must never get overridden by the current context. Oh and one more, a "default" or keyword-based context switch that isn't explicitly supported for a given dialect should just be silently ignored instead of throwing an error.
