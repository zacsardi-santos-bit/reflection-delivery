We've got a bunch of storage and search sub-packages for image vulnerability data (the image CVE stuff) and image data that are currently sitting under restricted internal directories, and because Go enforces directory-level import restrictions those packages can only be imported by code within the same parent tree. That's biting me right now because I can't write proper integration tests for the background reprocessor loop that automatically unsuppresses vulnerabilities once their suppression expiry passes, the storage packages it leans on just aren't reachable from the test package.

What I want is to move these image CVE storage/search and image data storage/search packages out of the restricted dirs into locations that are importable from anywhere in the codebase, and then go fix up all the existing import paths that reference the old locations so everything still compiles. Nothing should break, all the tests that previously imported from the restricted paths need to keep passing after the paths get updated.

The real payoff is being able to stand up a full pipeline in one integration test, storage plus indexer plus searcher plus the reprocessor loop, against a real database, then insert some suppressed vulnerabilities whose suppression timestamps have already expired, run the reprocessor, and verify they actually get unsuppressed (suppressed status cleared) like they should. Oh and beyond testing this also lets other parts of the system reuse these building blocks directly instead of duplicating them, so the architecture ends up more composable.
