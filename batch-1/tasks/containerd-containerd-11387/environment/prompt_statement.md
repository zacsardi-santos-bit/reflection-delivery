I'm hitting a weird gap with our HTTP/2 stack. The version of the h2 networking library we're pinned to doesn't know about the extended connect protocol setting, you know, the one from RFC 8441 that lets you tunnel non-HTTP stuff like WebSockets over an HTTP/2 connection. So when some code asks for the string representation of that particular settings identifier at runtime, instead of getting back the proper standardized name it just falls back to an "unknown" label, which is useless for logging and debugging and generally means we can't cleanly support anything that leans on extended connect.

What I want is to bump the HTTP/2 networking dependency (the h2 crate) up to a newer version that actually recognizes this setting and names it correctly. Once that's done, when the setting's identifier gets converted to its string form it should come back with the correct standardized name (the SETTINGS_ENABLE_CONNECT_PROTOCOL type name) rather than the unknown-setting placeholder. Basically the extended connect protocol feature needs to work right in the project, and the fix is on the dependency side, so update the version in the relevant `Cargo.toml` manifest (and lockfile if needed) so the library pulls in the definition for this setting. That unblocks tunneling use cases over HTTP/2 for us.
