I'm reworking how the wallet activity feed deals with new incoming transactions during an active session. Right now when a pending tx shows up, the session update event shoves the full entry data into the notification, which is messy and doesn't play nice when a client wants to refresh and get the whole updated list with highlights. Problem is the client can't tell which entries are actually new (arrived since it last acknowledged state) versus stuff that was already there.

What I want is a two-phase thing. When new activity is detected for a session (like a new pending transaction appearing), the session update event should just carry a lightweight boolean flag saying new entries exist, not the entry payload itself. Then clients can explicitly ask to reset their session to pull the full updated activity page, and in that reset response each activity entry needs to be annotated as new or not new so the UI can highlight the fresh ones.

Also I need a helper that diffs a known list of entry identities against a freshly fetched list and tells me which entries are new (with their positions in the new list) and which got removed. It's gotta handle the empty starting state, no changes at all, adding entries on top, and entries falling out of a fixed-size window.

Oh and the test helper that generates pending transactions needs a configurable start offset so generated txs can begin at an index other than zero. Without that they collide when I generate them in multiple batches with different timestamps and addresses. The whole point here is that without the signal-plus-reset model the UI has no reliable way to highlight newly arrived transactions after a session's already loaded, and batching updates gets clean.
