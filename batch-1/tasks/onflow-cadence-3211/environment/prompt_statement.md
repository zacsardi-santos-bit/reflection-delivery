I'm working on the Cadence storage migration system and have found two bugs that need to be fixed.

The first issue is that the legacy wrapper types used during migration don't properly implement equality. When I compare two legacy-wrapped values of the same kind (for example two character wrappers, two string wrappers, two intersection type wrappers, two primitive static type wrappers, or two reference type wrappers) where both sides contain equivalent underlying values, the comparison doesn't return true as it should. Each wrapper type needs to recognize when the other operand is also the same kind of wrapper, unwrap it, and then delegate the comparison to the underlying type.

The second issue is that when the migration processes a dictionary and needs to re-key entries from their old legacy format to the new format, it's possible for two previously distinct legacy keys to collide into the same new key. For instance, two intersection types with the same members but stored in different orders in the old format might now hash to the same key. Currently this silently overwrites one entry. The migration should instead detect this situation — after removing the old key, before inserting the new key, it should check whether the new key already exists in the dictionary. If so, it must report this as an error on the migration reporter, associating the error with the correct storage address, storage domain, and storage map key. The error message should clearly indicate that a key conflict occurred. The error should also capture a stack trace for debugging. Even in the presence of such a conflict, the entries that were successfully migrated before the conflict should still be recorded in the migration report.
