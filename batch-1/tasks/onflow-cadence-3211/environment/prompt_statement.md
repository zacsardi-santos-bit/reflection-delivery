I'm deep in the Cadence storage migration code and hit two bugs that are biting me. First one is that the legacy wrapper types we use to encode values in the old format during migration don't implement equality right. When I compare two legacy-wrapped values of the same kind (two character wrappers, two string wrappers, two intersection type wrappers, two primitive static type wrappers, or two reference type wrappers) where both sides hold equivalent underlying values, the equals comparison doesn't come back true like it should. What each of these wrappers needs to do is recognize when the other operand is also the same kind of legacy wrapper, unwrap it, and then delegate the comparison down to the underlying type instead of failing or returning garbage.

Second one is nastier since it's silent data corruption. When migration processes a dictionary and re-keys entries from their old legacy format to the new format, it's possible for two previously distinct legacy keys to collide into one new key, think two intersection types with the same members stored in different orders in the old encoding that now hash to the same key. Right now one entry just silently clobbers the other. Instead, after removing the old key but before inserting the new key, it should check whether that new key already exists in the dictionary, and if it does, report that as an error on the migration reporter tied to the correct storage address, storage domain, and storage map key. The error message should clearly say a key conflict happened, and it needs to capture a stack trace for debugging. Oh and even when a conflict happens, the entries that migrated successfully before the conflict should still get recorded in the migration report, so report those separately from the conflict error. Without this, multi-step migrations can quietly corrupt stored data and the bad equality means downstream comparisons go wrong too.
