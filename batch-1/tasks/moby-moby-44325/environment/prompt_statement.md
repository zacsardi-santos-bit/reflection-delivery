I'm hardening the git cloning path in the Docker builder and hit two things I want cleaned up. First is a real security issue: when we clone a remote repo we also init its submodules, and right now those submodules can point at local file paths on the build host. So a maliciously crafted build context could sneak in a submodule referencing some sensitive directory and leak its contents during the build. I want to block the file transport entirely so submodule sources, and honestly any git remote reference, have to go over a network protocol like HTTP. Submodules should still clone fine when their sources are reachable over the network, that part can't regress.

Second thing is more of a refactor to set up future work. The git helpers in the builder live as standalone package-level functions today and they don't carry any per-operation context, which makes it a pain to thread stuff through to the actual git invocations (thinking ahead to isolating system/user git config when we build on behalf of arbitrary users). I want to convert these into methods on the repository config struct so context rides along naturally. Specifically the helper that runs git commands in a given directory should become a method, and the full clone-fetch-checkout helper should become a method on that struct too.

Oh and one detail on the run-git-in-dir method: it should actually set the directory as the working directory of the subprocess rather than passing it to git as flags, because we need it to behave correctly across the whole range of subcommands including init and config, which don't play nice with the flag approach.

The point of all this is eliminating the attack surface where a crafted submodule config reads sensitive data off the build host, plus laying groundwork for later config-isolation options.
