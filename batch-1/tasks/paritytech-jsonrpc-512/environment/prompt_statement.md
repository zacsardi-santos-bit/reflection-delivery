I'm hitting a wall with the pubsub macro in `jsonrpc-derive` and I want to loosen it up. Right now each subscription topic can only have one subscribe method attached to it, so the moment I try to add a second subscribe entry point for the same subscription (say I want two different method names with different parameter sets both feeding into the same logical subscription, sharing one unsubscribe handler), the macro blows up at compile time complaining that the subscribe method is already defined. That's too restrictive for what I'm doing.

What I want is for the macro to allow multiple subscribe methods per subscription. Each one should have its own unique RPC method name, and each should get independently registered and be callable on its own, returning a valid subscription ID when it's invoked. They all still share the single unsubscribe method for the topic.

There's one safety thing that matters here though. If I define multiple subscribe methods for the same subscription but they end up using different inner subscriber types (conflicting generic type parameters on the `Subscriber`), the macro shouldn't silently accept that, it should catch the mismatch at compile time and emit a clear error telling me which argument is inconsistent and pointing back to where the original type was defined. So it's fine to have many entry points, just not fine to have them disagree on the subscriber's generic type.

The why here is basically API ergonomics, I want to offer multiple subscription entry points for the same topic for things like versioned APIs, optional params, or different client capabilities, without having to spin up separate subscriptions or hack around the old single-subscribe limitation. Please keep the existing single-subscribe behavior working as before, just extend it to handle the multi-subscribe case and the type-consistency check.
