I want a cleaner way to make any future respect cancellation. Right now whenever I need a future to bail out on a shutdown signal I end up hand-writing select-style racing logic inline every single time, and it's repetitive and clutters everything up. What I'm after is a fluent extension method, basically the same ergonomics as the timeout adapters we already have on futures, so I can just chain a call and be done.

Concretely I want an extension trait on futures adding two methods: one that takes a borrowed cancellation token and one that takes an owned token. Both return a new future whose output is an optional value, so on normal completion you get the inner value wrapped up, and when the token fires you get the "cancelled" indicator instead (think None-style) rather than a completed result.

There's a fairness property that matters here: if the inner future finishes and the token gets cancelled at the exact same time, the inner future's result should win, it's biased toward the actual computation. Also when the token is already cancelled before the wrapper future is first polled, it needs to resolve immediately to cancelled without any spurious wakeups. And when cancellation fires while the future is still pending, the runtime waker should get notified exactly once so it re-polls, not zero times and not twice.

This is really just about reducing boilerplate and making the intent obvious at the call site, mirroring what timeout adapters already give us for cancellation tokens instead.
