I'm chasing a bug in the gossip layer's connection reading logic and I keep hitting the same broken behavior. When a peer sends us a message that can't be parsed, we do the right thing and push the error to the error channel, but then the loop just keeps on going. The reading goroutine should bail out the moment it sees an unparseable message, and it shouldn't forward anything downstream after a parse error either, right now it happily keeps reading and that leaves us in this weird inconsistent state that can leak goroutines or cause silent failures.

Related, and honestly part of the same problem, I want the server to actively close the stream when a remote peer keeps flooding us with corrupted envelope data. Today if you set up a valid connection and then just spam malformed messages, the stream never gets terminated from our side, the client can keep sending garbage forever. What I want instead is that after receiving invalid messages the server force-closes the stream so the client ends up getting a connection-closed error. Peers sending trash shouldn't be able to sit there hammering us, that's basically a resource exhaustion / disruption vector for gossip comms.

Oh and to actually test this properly I need a mock implementation of the gossip stream client interface so unit tests can simulate both well-formed and malformed message sequences without standing up a real network connection.
