I'm on the ECS agent's service connect integration and the way we talk to the proxy is too rigid right now. The URLs the agent uses to fetch stats and to drain connections from the service connect proxy are hardcoded, which breaks the moment a different proxy version exposes those APIs at different paths. I want the task runtime config to carry configurable endpoints for both the stats retrieval and the connection drain operations so the agent hits whatever's configured for a given task instead of a fixed path baked into the code. So the runtime configuration needs new fields for the stats request URL and the drain request URL, and when the service connect manager sets up a task's agent container it should store the stats and drain endpoint URLs it knows about into that task's runtime configuration, and then when we retrieve the runtime config for the task those values should come back reflecting what was set. That's the main thing since hardcoding proxy endpoints stops us from adapting when the proxy changes its API surface, and doing it through runtime config keeps us forward-compatible without a code change per endpoint variation.

While I'm in here I hit two more things that need fixing. Service connect containers should get started with an env var that explicitly disables IAM authentication for XDS, so set that on the container automatically. Also the relay socket path we put into the container's environment is being passed as a bare file path, and it should use the proper Unix socket URI format with the right scheme prefix (unix://) instead. Both of those live in the service connect manager container setup path alongside the URL storage work.
