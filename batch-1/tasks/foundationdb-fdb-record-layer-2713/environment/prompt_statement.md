I'm adding CJK support to our Lucene auto-complete search and hitting a wall with the generic text analyzer we've got. It just doesn't know how to split Chinese, Japanese, and Korean text into individual character tokens, which is exactly what those writing systems need for auto-complete to work, so right now multi-character CJK words get treated as one undivided blob and produce no meaningful suggestions. Same story with email addresses, strings with "@" symbols and domain parts aren't handled right either.

So I want a new specialized analyzer that does CJK character-level tokenization, recognizes email address patterns (the "@" and the domain components), handles mixed CJK and Latin script in the same content, and does case-insensitive matching for Latin text so queries with any capitalization still match. It also needs a configurable minimum alphanumeric token length so very short words get dropped from the stream, e.g. with a min length of 3 a word like "of" shouldn't show up as a completed token when we parse phrase queries.

The analyzer has to be wired up as a named factory so a Lucene index can select it by identifier in its index options, basically a new index config option that turns on this CJK- and email-aware analyzer. Once it's configured the index should return correct auto-complete suggestions for CJK phrases, email-like strings, and mixed-script queries. Oh and when two CJK characters are typed as a query, I want the first recognized as a completed token and the second as the prefix being completed.

Also the phrase auto-complete logic itself needs to exclude short words from the completed-token list, not include them. Concrete example: querying "United States of Ameri" should give "united" and "states" as completed tokens and "ameri" as the prefix, with "of" left out since it's below the min length threshold. Right now short common words pollute the token list and hurt match accuracy, so that filtering matters.
