I'm extending our import plugin system so plugins can hand back richer info about each resource they surface during state conversion. Right now when an import plugin converts existing infrastructure and returns its list of resources to import, each resource can only carry a type, name, ID, version, and the plugin download URL. That's too thin. Sometimes the thing being imported is actually a component resource rather than a leaf, or it's a remotely-hosted component, or it needs to come in under a logical name that differs from its declared name. Without a way to express those, the engine can't handle those cases and we're stuck limiting the kinds of infrastructure import plugins can accurately describe and migrate into Pulumi management.

So I want to add three more properties to the resource import data structure. First, a logical name, which is a name that may differ from the resource's declared name and gets used for identification. Second, a flag for whether the resource is a component resource. And third, a flag for whether it's a remote component, which only really matters when the resource is a component in the first place.

The important part is these have to flow correctly through both sides of the plugin boundary. So when we convert state, the values need to survive the trip from the server-side plugin host back through the client-side plugin wrapper, so the engine actually receives the full picture and not just the basic fields. Please make sure the new fields get properly set and passed through on both the client wrapper and the server host during that state conversion path, oh and keep them consistent with the existing type/name/id/version/download-url handling so nothing gets dropped in the round trip.
