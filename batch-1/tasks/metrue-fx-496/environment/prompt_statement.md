I'm splitting our Docker-over-SSH provisioner into two OS-specific packages because the one-size-fits-all thing is biting us. Right now macOS and Linux share a code path and macOS users get either confusing behavior or a nonsensical automated install attempt when Docker isn't set up right, so I want a separate macOS provisioner package (doesn't exist yet, build it from scratch) alongside a Linux one, both satisfying the same provisioner interface.

Here's the behavior I'm after. On macOS, when the provisioner detects Docker isn't running, it should first check whether Docker is actually installed and accessible on the system path before concluding it needs setup, and if the container runtime executable isn't on the path it should just fail with an error telling the user to install Docker manually rather than trying to auto-download and install it, since that process is totally different on macOS. But if Docker's running and it's only the required agent process that isn't active, go ahead and start the agent automatically.

For Linux the existing auto-install behavior stays, but I want that same intermediate path check added, so before deciding to install Docker it verifies whether the runtime is on the path rather than jumping straight to install when Docker just isn't responding. Otherwise error messages get confusing and we trigger install when Docker's present but simply not running.

Oh and both implementations need to handle SSH connectivity the same careful way: before sending any remote command, verify the connection is reachable and return an error immediately if the host is unreachable, don't blindly fire off commands. And in both, when the agent process isn't running on the remote host, attempt to start it automatically. The whole point here is that splitting by OS makes error handling more accurate and user-friendly, and that path check improves reliability for both platforms.
