I'm working on Kafka Connect's distributed mode and hitting a nasty recovery problem. When the broker goes offline temporarily, workers block forever trying to reconnect to the group coordinator, so tasks stay stuck in a bad state even after the broker comes back, and someone has to manually kick things to recover. Operators expect Connect to self-heal after a transient broker outage, that's the whole point here.

What I want is for a worker to detect coordinator unavailability within a bounded timeout and proactively revoke its current assignment instead of waiting indefinitely (right now workers can keep running tasks even though they're no longer active group members, which is the inconsistent state I'm trying to kill). Then when the broker comes back on the same ports, workers should rejoin the group on their own and all connector tasks should return to running without any manual intervention.

Also I want failed tasks to be restartable through the REST interface. If a task fails from a bad config (say a wrong broker address in its overrides) and then I reconfigure the connector with valid settings, posting a restart to that task's REST endpoint should bring it back to running.

Oh and the incremental cooperative rebalance assignor should fold in the current group membership identity, the generation and member info, when it computes task assignments, so each assignment can be traced back to the rebalance generation it belongs to.

There's test infra work too. The embedded Kafka cluster we use in integration tests needs to support stopping and restarting only the Kafka brokers without touching ZooKeeper, and it needs to restart brokers on the same ports they used before so existing connections can actually recover. The embedded Connect cluster also needs to support sending HTTP POST requests to the REST API endpoints so the restart flow can be exercised.
