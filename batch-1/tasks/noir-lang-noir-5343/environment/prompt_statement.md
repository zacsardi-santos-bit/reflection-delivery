I'm hitting a real gap in the Noir compiler's trait impl checking. Right now if I write a trait implementation where one of the methods carries extra where-clause constraints that the original trait method never asked for, the compiler just accepts it silently. That's wrong, the impl ends up more restrictive than the trait contract allows (basically a Liskov violation) and it makes the impl unusable in any context where that extra constraint isn't met, which then blows up as confusing type errors somewhere far away instead of at the definition.

What I want is for the compiler to catch this at the point the stricter method is defined and reject it with a clear error that names the offending constraint type and the trait involved in that extra constraint. So if the trait method has no constraints and my impl's method adds one, that should error out. It needs to work across all the kinds of constrained types too: plain generics, a generic wrapper type wrapping another type, array types, and tuple types, all of those should be detected.

Couple things it should NOT do, oh and these matter: don't fire when the method just correctly mirrors the trait's own constraints even if the generics are renamed, that's legit. And don't fire for constraints that live on the impl block itself rather than on the individual method, those are fine. When one of those impl-block-level constraints isn't satisfied at a call site, keep using the existing "no matching implementation found" error, don't reuse the new extra-constraint error for that case. The relevant logic lives in the trait implementation checking in the frontend crate under `@compiler/noirc_frontend`.
