I'm working on a lint rule that detects when code uses a for-loop to repeatedly call a file object's write method on each iteration, suggesting the user replace that pattern with a single bulk-write call instead. The rule works for the basic cases, but it's incorrectly firing in several situations where making the suggested change would actually change the program's behavior.

Specifically, if the loop variable is declared as a global or non-local variable, replacing the loop would lose the side effect of writing to that broader scope on each iteration. Similarly, if a variable with the loop's name already exists in the current scope before the loop starts, or if any of the variables introduced by the loop target (even when the loop uses tuple or list unpacking to bind multiple names) are still used in code that comes after the loop, the replacement is unsafe because it eliminates meaningful variable bindings.

I'd like the rule to be updated to safely skip all of these cases — global variables, nonlocal variables, variables with a prior assignment in the same scope, and loop variables (including those nested in complex destructuring patterns) that are referenced after the loop ends. At the same time, the rule should continue to correctly identify loops with complex loop targets like tuple unpacking, nested list/tuple patterns, and even empty tuple patterns as valid candidates when none of these safety concerns apply. The snapshot file that records the expected diagnostic output for the test fixture also needs to be updated to reflect these changes.
