I'm dealing with a bug in the lint rule that flags for-loops which just call a file object's write method on each pass and tells you to collapse them into one bulk write instead. The detection logic lives around our flake8-style pyflakes-ish write-in-loop check, and it's misfiring in a bunch of spots where actually applying the fix would quietly change what the program does, which is bad because the suggestion looks safe but isn't.

Here's what I'm hitting. If the loop variable is declared global in the enclosing scope, the loop assignment reaches that global every iteration, so tearing out the loop drops that side effect and we shouldn't fire. Same deal for nonlocal vars inside a nested function, the assignment propagates upward and can't be eliminated. Also if a variable with the same name as the loop target already got assigned earlier in the same scope, removing the loop throws away the semantics of overwriting that prior binding, so skip it. And if any variable introduced by the loop target is referenced in code after the loop, we need the final iteration value preserved, so bail there too, oh and that includes names nested inside destructuring patterns like tuple or list unpacking, not just the simple single-name case. Same thing for a global declared inside a nested destructuring pattern, still skip.

What I don't want to lose is the cases that should still fire. Complex loop targets are legit candidates when none of those safety concerns apply, so empty tuple patterns, multi-variable tuple unpacking, and arbitrarily nested list/tuple destructuring should all still get flagged. I want new coverage confirming those keep working.

So please update the rule to safely skip global vars, nonlocal vars, prior same-scope assignments, and loop targets (including complex destructured ones) that are used after the loop, while keeping the complex-target detection intact.
