I'm building out a GPU matmul library and I need a producer-consumer execution path so data loading can overlap with the actual compute. Right now everything's homogeneous, every plane loads and computes in lockstep, which means memory latency isn't hidden behind math and we're leaving perf on the table. What I want is a strategy where some planes act as producers loading matrix tiles into shared buffers while the rest act as consumers running the multiply-accumulate on already-loaded data, so we can do double- and triple-buffered pipelines.

Couple of things tied into this. The existing stage-level impl that's currently called "row accumulate" should get renamed to "multi buffer" since that describes what it actually does. Then I need a new "single buffer" stage variant for the pipelined flow, since in the pipelined approach each buffer gets filled and consumed one at a time, and the new producer-consumer global module should sit on top of that single-buffer stage. So basically a new producer-consumer global matmul module where some planes load and others compute.

Also the tiling order config needs splitting up, right now lhs and rhs share one combined setting and I want each operand to have its own independent tiling order. Oh and while you're in there, the tiling order variant names should switch to clearer row-major and column-major naming instead of whatever they're called now.

Last bit, I need a few new stage size type aliases to support the multi-stage configs, specifically for when the k-dimension of the stage has 2 or 3 tiles (double and triple buffering).

All the existing homogeneous tests need to keep passing through the renamed multi-buffer stage, and the new producer-consumer tests should pass across various matrix sizes, batch dims, and those k-stage 2 and 3 configs.
