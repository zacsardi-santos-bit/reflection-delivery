I'm hitting a nasty issue in the generic worker with how we hand off writable directory caches between sequential tasks. Right now when a cache gets mounted for a new task, the worker grants the incoming task user access to the directory, and then on unmount it revokes that access. Fine in simple setups, but it breaks badly when tasks run inside containers that use custom user ID mappings, like when containers manage sub-user ID ranges. The revoke at unmount leaves the cache in a state that's inaccessible to future tasks.

What I want instead: on mount, transfer file ownership of the cached directory contents to the new task user rather than just granting read/write perms. And log an informational message that we're updating ownership from the previous owner to the new task user, including both the source and destination usernames in that message. Then on unmount, don't revoke or deny anything at all, since the ownership transfer already handled the handoff and revocation's just unnecessary churn now.

Important bit, this only applies to multiuser builds. In non-multiuser (insecure) builds, no ownership transfer happens and nothing's logged.

Oh and the existing tests around writable directory cache scenarios currently expect log messages about granting and denying directory access, so those need updating to expect the ownership update message in multiuser mode, or no message at all in the non-multiuser case.
