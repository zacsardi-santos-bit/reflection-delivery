I'm working on the generic worker and running into issues with how writable directory caches are handed off between sequential tasks. Right now, when a cache is mounted for a new task, the worker grants the task user access to the directory, and when it's unmounted, it revokes that access. This worked in simple setups, but it's causing problems when tasks run inside containers that use custom user ID mappings — the revoke step at unmount leaves the cache in a broken state for future tasks.

I'd like to change this so that instead of granting and revoking permissions, the worker transfers file ownership of the cache directory to the incoming task user at mount time. The worker should log that it is updating the ownership from the previous owner to the new task user. The unmount step should no longer need to revoke any permissions. This change only applies to multiuser builds — in non-multiuser builds, no ownership transfer or logging is needed.

The existing tests for writable directory cache scenarios currently expect log messages about granting and denying directory access. Those tests need to be updated to instead expect an ownership update log message (in multiuser mode) or no message at all (in non-multiuser mode).
