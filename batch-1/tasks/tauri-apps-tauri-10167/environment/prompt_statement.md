I'm building a Tauri app with the isolation security pattern turned on, and I've hit a nasty bug where raw binary IPC requests get mangled on their way to the backend. The way isolation works is the sandboxed page encrypts every IPC payload before forwarding it to the backend, and each encrypted package carries metadata about the original payload including its content type (binary vs structured). Problem is the IPC request handler only reads the content type off the outer HTTP headers, and with isolation active the outer request always shows the same content type no matter what's actually inside the decrypted payload. So my raw binary stuff (typed arrays, binary blobs from the frontend) gets treated as structured data and blows up during deserialization, silently corrupting data or failing commands outright.

What I want is for the request parsing to trust the content type embedded inside the encrypted isolation payload instead of the outer headers when isolation's in play. So when the decrypted payload says binary, the resulting IPC body should come out as raw bytes, and when it says structured, it should parse as structured data, with the embedded content type taking precedence over the outer headers. It's gotta keep working for the plain non-isolation case too.

A few supporting things I need so this is actually testable, oh and these matter: the encrypted isolation payload struct should expose its embedded content type field so the decryption path can classify the body, and the encryption key type needs a method to encrypt data so I can exercise the full isolation flow end to end. Also the IPC body type needs equality comparison available in test contexts so I can assert the right deserialization happened. And btw the macro that generates the Tauri app context for tests should accept a test-mode flag that skips platform-specific code generation (like the macOS plist/config metadata embedding) since that stuff breaks unit test compilation on macOS.
