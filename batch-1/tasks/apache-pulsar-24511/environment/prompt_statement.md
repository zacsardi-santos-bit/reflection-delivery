I'm in the managed ledger module and I keep writing the same cursor replay loop over and over, every component that reads through a `ManagedCursor` from start to finish rolls its own batch-reading, callback juggling, error handling, buffer release, the works. It's repetitive and inconsistent and bugs sneak in. I want a proper reusable replay task I can drop in.

Basically it takes a cursor plus a user-supplied entry processor (something I hand each entry to), and it reads entries in configurable batch sizes using a given executor, chugging through until it hits the end of the ledger. When it's done it hands me back the position of the last entry that was successfully processed, so I can act on that (like taking a snapshot afterward).

The tricky bits are the failure modes. If my processor rejects an entry mid-replay (throws or otherwise says no), I don't want the whole thing to blow up, I want it to stop right there and return the last position that actually succeeded, so the previous good entry basically. But if some lower-level cursor read op itself throws an unexpected error, that's different, that should propagate straight to me through the returned future completing exceptionally.

Also I need a way to check how many entries got successfully processed during the replay, expose a count or something, so callers can decide what post-replay action makes sense. Oh and please release the entry buffers properly after each one is processed, otherwise we leak memory which is the kind of thing that's bitten us before.

Edge case: when the cursor has no entries at all, the result should clearly say nothing was processed, don't return some garbage position. This mostly matters because subsystems like the deduplication recovery path all need to rebuild state from a managed ledger, and right now they each babysit their own low-level replay logic, so a shared well-tested component here cuts the duplication and makes fixing this stuff once actually stick.
