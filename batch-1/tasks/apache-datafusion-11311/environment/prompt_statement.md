I'm hitting a wall with DataFusion's Substrait consumer when I try to convert certain plans into logical plans. Any Substrait plan that uses an existence-check subquery as part of a filter (basically a "does at least one matching row exist?" predicate) blows up with a not implemented error instead of translating into the right DataFusion node. The consumer already handles other subquery kinds, like the "value in a subquery result" case, but existence subqueries just aren't wired up yet, so it crashes.

This is a super common analytical pattern, think filtering a set of orders down to only those that have at least one matching line item satisfying some condition, and it blocks a bunch of standard TPC-H queries from round-tripping through Substrait. I want to add support for this missing subquery type so those plans convert cleanly.

Concretely, when I feed it a Substrait plan with an existence-check subquery in a filter, it should translate into a DataFusion logical plan where the existence check shows up as a proper subquery expression (an exists-style subquery). It needs to handle the case where the existence subquery refers to an inner relation that itself has to be recursively translated, so make sure that inner rel gets consumed too and the outer expression points at it correctly.

I want this to work end to end for TPC-H style queries. Q4 does order priority checking with a correlated existence filter over line items (orders kept only when a matching line item has a late delivery, commit date after receipt date), and the resulting plan should have the right shape: projection, sort, aggregation, a filtered table scan carrying the existence check, plus the inner subquery relation. Q5, local supplier volume with several joined tables, date range filters, and computed revenue, should translate correctly too. Substrait's whole point is being a cross-engine interchange format, so failing on something as basic as "filter by existence of related rows" really limits interop, and I'd like it fixed in the consumer.
