I'm trying to make state transitions for flow runs idempotent so clients can safely retry them. Right now if a client fires off a state transition request and the response gets lost to a network blip, retrying just makes the server apply the transition a second time like it's brand new. There's no way to say "hey I already sent this one," and that leaves us with ambiguous or inconsistent server-side state.

What I want is an optional unique identifier riding along on each state transition. When the client provides one, the server should check whether the current run state already carries that same identifier, and if it matches, reject the incoming transition as a duplicate and just return the existing state instead of applying the change again. If either state is missing the identifier, or both have identifiers but they differ, the transition should proceed normally like it always has.

On the client side I want a fresh unique identifier generated and attached automatically to every outgoing state transition request, so callers don't have to manage any of this by hand, that's the whole point of making retries detectable without manual effort.

Also, and this matters, the existing rules around invalid transitions still need to apply in the non-duplicate case. So transitioning a run to the same state type it's already in, when there's no matching duplicate identifier involved, should still get caught by the existing prevention logic and not silently accepted. Basically duplicate detection is a new short-circuit that sits in front of the normal path, it shouldn't weaken any of the checks that already run when detection doesn't kick in.
