I'm poking at namespace replication in a multi-cluster Temporal setup and hit two related bugs I want fixed together.

First one: when a global namespace gets registered on the active cluster, we don't publish any replication message, so standby clusters never hear about the new namespace and someone has to configure them by hand. Updates already publish a replication event, so registration should do the same thing on its handler path. I want registering a global namespace to send out a replication task the same way an update does.

Second one is the cluster membership list. When a namespace's cluster list changes (say we add or remove clusters), the receiving cluster sometimes just drops the incoming replication task. It's because the apply logic checks whether the local cluster is in the new cluster list before deciding to apply, so if the local cluster was just removed, that check fails and the update gets skipped, leaving a stale cluster list behind. I want that change to actually get applied on any cluster that has a local copy of the namespace, whether or not the local cluster shows up in the updated list.

Also the replication publisher needs a way to force publication when a cluster list change happened. Right now if a namespace only has a single cluster in its replication config, publication gets suppressed. So I want the publisher to accept a flag saying the cluster list was updated, and when that flag's set it publishes the replication task regardless of how many clusters are in the config. That way even single-cluster configs still propagate the membership change.

The why here: when namespace changes don't replicate right, clusters diverge and global namespaces end up unavailable or misconfigured on standbys, which breaks failover in production and forces manual cleanup. So both the registration-publishes-a-replication-event behavior and the cluster-list-change-always-applies behavior need to hold, plus the publisher flag to cover the single-cluster case.
