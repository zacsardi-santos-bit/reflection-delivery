I'm hitting a couple of bugs in the multi-stage query engine around ingest operations (INSERT and REPLACE) that produce zero rows, and I need both fixed so REPLACE queries with filtering conditions that occasionally match nothing succeed cleanly and still clean up old data properly.

First thing: empty ingest queries don't complete gracefully right now. When an INSERT or REPLACE produces no output rows, maybe a WHERE clause filtered everything out or a LIMIT left zero matches, the operation fails with an error instead of finishing. What I want is for an INSERT that produces 0 rows to just be a no-op, completes successfully without writing any segments. And a REPLACE that produces 0 rows should still delete existing data in the OVERWRITE range by creating tombstone markers, or if there's nothing existing in that range it just completes with no changes, basically a no-op. Oh and I also need a query context flag users can set so that when it's enabled, any ingest producing 0 rows gets treated as a fault and raises an appropriate error, useful when zero rows is unexpected and should signal a problem.

Second, there's a bug in how tombstone intervals get computed for REPLACE when existing segments span all of time. Currently if an existing segment covers the entire representable time range (eternity) and the replace also covers eternity, the code tries to partition the eternity end boundary by granularity and produces wrong tombstone intervals or errors instead of a single tombstone covering all of time. Fix it so a REPLACE over such a full-timeline segment generates one correct eternity-spanning tombstone. Otherwise these full-timeline datasources end up with incorrect tombstone coverage and stale segments left behind.
