I'm working on Cluster API and I want to close a gap in the cluster topology webhook. Right now nothing stops an operator (or some automation tool) from bumping the topology's Kubernetes version while a previous upgrade is still finishing, so you can end up with overlapping upgrade waves that leave the cluster in a bad, inconsistent state. I want the webhook that validates cluster topology updates to block a version change unless everything has already converged to the current version.

Concretely, before allowing a version bump it should check that the control plane is fully provisioned and sitting at the expected version, and that all topology-owned worker groups (both the regular machine deployments and the machine pools) have finished rolling out the current version. For the worker side that means comparing what version each group is targeting against what the individual nodes or machines are actually running (machine pools report the older kubelet version, deployments still have machines on an older version). If any of those components is still provisioning, mid-upgrade, or just behind, reject the update with a clear error explaining what's not ready yet.

Also I want an escape hatch: if an operator knowingly needs to override this in an emergency, like a stuck upgrade, they can put a special annotation on the cluster. When that annotation's present, let the version bump through but return a warning instead of silently allowing it.

Oh and the logic for detecting whether a group of worker machines is mid-upgrade shouldn't live only in the webhook. Please pull it out into a standalone utility function in a shared package so the same check can be reused from both the controller reconciliation loop and the webhook validation path, rather than duplicating it.
