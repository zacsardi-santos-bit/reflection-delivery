I'm hitting a nasty bug in the Postgres language server where a single edit notification with multiple changes ends up producing bogus error diagnostics. The trigger is stuff like a rename refactor or a multi-cursor edit that changes the same identifier in two or more spots at once, my editor bundles all those changes into one notification and sends them together. After the server applies them the SQL is actually valid but I still get errors, like it complains about an unknown table that definitely exists.

I'm pretty sure the root cause is that when several range-based changes arrive in the same batch, the server computes the position/offset of every change against the original document layout instead of the running state. So once the first change lands, everything after it shifts, but the second change still gets applied at its old position, which corrupts the document, and then the server reports diagnostics against that garbled content.

What I want is for each edit in a batch to be applied at the correct position relative to the document as it exists when that particular edit is processed, so earlier edits in the same batch properly influence where later ones go. After applying a batch that yields a valid SQL statement referencing tables that actually exist in the database, I should get zero diagnostics back. This matters because editors batch related edits all the time (renaming a symbol across multiple lines is the classic case) and false positives here really undermine trust in the whole tool. Can you fix the multi-change handling so the offsets account for prior edits in the batch?
