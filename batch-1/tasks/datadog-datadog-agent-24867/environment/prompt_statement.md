We've been talking to the GitLab API through a custom wrapper class that fires raw HTTP requests, and it's getting painful. We hand-rolled retry loops for 5xx server errors, we parse JSON responses ourselves, and we pass pipeline jobs around as plain dicts all over the notification and stats tooling. There's an official GitLab Python client library that does all this properly (retries, structured objects, attribute access to resources), so I want to migrate to it.

Can you add a new module under our CI provider utilities that wraps the official library and exposes a factory function for building a configured API client? The existing functions for reading GitLab CI config files and resolving their includes should live in (or be available from) this new module too. Then switch the pipeline notification functions, the ones that send failure messages and stats, plus the consistency checker, over to using the library client to list pipeline jobs and fetch job log traces instead of the raw HTTP calls.

Big thing here: everywhere we treat a job like a dict needs updating to the library's job object with proper attribute access. Heads up that the job URL field in the library's objects uses a different attribute name than the dict key we used before, so watch for that. Also the stats update code that pulls job names out of the failure list needs to move to attribute access too. Once all that's done the old wrapper class and its HTTP retry logic can just go away.
