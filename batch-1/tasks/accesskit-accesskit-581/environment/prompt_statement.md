I'm digging into our accessibility consumer library and realized the filtering logic that decides which nodes in an accessibility tree actually get exposed to assistive technologies has zero automated coverage. That's the core behavior screen readers depend on, so if something regresses here it could silently hand the wrong node set to assistive tech across every platform we support, and nobody would notice.

I want tests around the filter functions that pin down all the cases we care about. A normal node should be included, that's the baseline. A hidden node should exclude its whole subtree. But a hidden node that currently holds focus should still be included despite being hidden, that focus override matters. For generic structural container nodes, the standard filter should exclude them at the node level only (their children stay traversable, so it's a node-level skip, not a subtree hide), while a root-exception variant of the filter should include that same generic container. Then the parent-hidden case: when a parent is hidden all its children get excluded too via subtree exclusion, unless one of those children is the focused node, in which case that focused child still comes through. And oh, certain internal text representation nodes (the text run kind) should also be excluded at the node level only, same node-level-skip semantics as the generic container, not a subtree hide.

So basically I need coverage distinguishing node-level exclusion from full subtree exclusion, plus the focus-wins-over-hidden behavior, plus the root-exception vs standard filter difference. Wire these up against whatever filter entry points the library exposes for this logic so future changes can't quietly break the rules about which nodes assistive technologies see.
