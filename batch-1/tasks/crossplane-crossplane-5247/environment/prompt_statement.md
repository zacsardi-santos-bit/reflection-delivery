I'm working on adding support for composition functions to declare and receive extra Kubernetes resources during the composition pipeline. Right now, when a function runs it only receives the composite resource and its composed resources, but sometimes a function needs to read other resources that already exist in the cluster — things like shared configuration objects or referenced data sources.

I need the composition engine to support a request-fetch-retry loop: when a function returns a set of resource requirements (each keyed by a name and described by an API version, kind, and either an exact name or a label selector), the engine should look those resources up from the cluster and pass them back to the function in the next call. This should continue until the function's requirements stabilize between consecutive calls, capped at a fixed maximum number of iterations to prevent unbounded loops.

The same feature should work in the local rendering tool used for development. In that context, instead of fetching resources from a live cluster, the tool should accept an extra resources file and filter its contents against the selectors the function declares, passing the matches back on the next invocation.

I also need a concrete implementation of the resource-fetching logic that uses a Kubernetes client to look up resources: fetching a single resource by name (returning nothing — not an error — when the resource is not found) and listing resources by label selector. There should also be a way to inject a custom fetching strategy into the composition engine via a configuration option, so it can be tested and swapped out.
