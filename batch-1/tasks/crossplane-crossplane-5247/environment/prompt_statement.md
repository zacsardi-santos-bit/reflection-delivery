I'm adding support for composition functions to declare and receive extra Kubernetes resources during the composition pipeline. Right now when a function runs it only gets the composite resource and its composed resources, but sometimes a function needs to read other things that already exist in the cluster, like shared config objects, secrets, or referenced data sources, and there's no way today for a function to declare those deps or for the engine to look them up.

What I want is a request-fetch-retry loop in the composition engine. When a function returns a set of resource requirements (each keyed by a name and described by an API version, kind, and either an exact name or a label selector), the engine should look those up from the cluster and pass the matches back to the function on the next call. Keep looping until the function's declared requirements stop changing between two consecutive calls, and cap it at a fixed maximum number of iterations so we don't spin forever.

Same feature needs to work in the offline render tool we use for local dev. Instead of hitting a live cluster there, it should accept an extra resources file and filter its contents against the selectors the function declares, then pass the matches back on the next invocation, so folks can test compositions without a running cluster.

I also need a concrete implementation of the fetching logic backed by a Kubernetes client: fetch a single resource by name (and when it's not found, return nothing rather than erroring), and list resources by label selector. Oh and I want a way to inject a custom fetching strategy into the engine via a config option so it can be swapped out and tested.

The why here: without this, functions can't safely depend on external cluster state, so they end up encoding assumptions about that state directly in their logic, which makes compositions harder to write, test, and maintain. A standard way to declare and receive needed resources makes things more flexible and enables realistic local testing.
