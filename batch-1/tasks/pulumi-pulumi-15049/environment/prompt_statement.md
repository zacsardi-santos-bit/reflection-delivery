I'm hitting a few related walls with the Pulumi Automation API in Go and want to refactor how it deals with the CLI. Right now the workspace always discovers and runs whatever `pulumi` binary happens to be on the system PATH, and there's no way to swap in my own implementation, which makes unit testing genuinely painful because every test needs a real CLI installed. I want the CLI represented as an injectable interface so I can pass a lightweight test double through a dedicated workspace option, so tests can run without a live binary. So please add a workspace option that lets callers supply their own CLI implementation satisfying that interface.

Second thing, the version validation that checks whether the CLI is compatible with the SDK is buried inside workspace init, and I'd rather it be a standalone function I can call and test directly. It needs to handle at least three distinct error cases with clear messages: when the CLI version string can't be parsed at all, when the CLI's major version is ahead of what the SDK expects, and when the CLI is older than the minimum required version (and prerelease versions should count as lower than their release counterpart, so like 3.0.0-beta is below 3.0.0). Oh and there should be a way to opt out of the version check entirely through an environment variable, and when that's set it should also suppress the separate check for whether the CLI supports remote operations, they go together.

Third, when the CLI is installed in a custom directory instead of the system PATH, I want the SDK to automatically prepend that directory to the process PATH so plugins and bundled tools inside that installation get found first, rather than picking up whatever's lying around on the system PATH. This matters a lot in CI where the installed CLI may differ from what the SDK expects, and folks need to pin a version reliably. Can you help me wire this all up across the automation API (roughly `@sdk/go/auto`)?
