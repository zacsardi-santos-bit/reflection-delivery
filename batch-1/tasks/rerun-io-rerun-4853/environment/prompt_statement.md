I'm hitting a caching bug in the `re_query_cache` crate in the rerun repo. The range query cache doesn't invalidate stale entries when the underlying data store changes. So if I log some data, run a range query through the cache, then update that data or add new data at a different time, the cache just keeps handing back the old results instead of the fresh ones. It's the kind of thing that turns into subtle rendering bugs later where the viewer shows outdated component values even though I already logged new stuff.

I want this fixed so that after any insertion or update the cache correctly detects invalidation and returns results matching what an uncached query would give. This should hold no matter where the modified data lands relative to the queried range, so past, present, or future, and also timeless. The rule I'm after: timeless data updates invalidate the whole range cache for the affected archetype (since timeless affects every time-range query), while timeful updates only evict cache entries at or after the modified timepoint. Successive updates at the same timepoint should each show up too, and the cached range path always has to stay consistent with the uncached path.

"frame_122" and "frame_124" are both set to frame number 123 instead of 122 and 124, so it isn't actually checking distinct timepoints. Fix those to the right numbers while you're in there.
