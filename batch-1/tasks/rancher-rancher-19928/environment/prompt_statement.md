I'm hitting a bug in the cluster store layer where updating a cluster wipes out cloud provider credentials. Basically when someone updates a Kubernetes cluster that has a cloud provider configured (Azure, vSphere, or OpenStack), they usually leave the password and secret fields out of the update request on purpose since those are sensitive and shouldn't be round-tripped through the API. Problem is we don't restore those omitted secrets from the saved config before persisting, so the password fields just get silently cleared and the cloud provider integration breaks after any routine update that doesn't re-supply every secret. Not great.

What I want is logic that, on update, checks each relevant password or secret field in the incoming request and if it's absent or empty, fills it in from the value in the existing saved cluster config. If the user actually provided a new value, keep that new value as-is, don't touch it. So it only restores when omitted, otherwise respects the intentional change.

The vSphere case is the tricky one because those configs can have multiple named virtual center entries, each with its own password. I need the per-entry password handled independently, so restore the password for any virtual center that was carried forward from the existing config without a new password, while leaving new or explicitly-updated virtual centers alone. Right now if someone updates one vcenter without its password that password is lost, and if they add or remove a vcenter the passwords for the other untouched ones can get wiped too. Both of those need fixing.

Also important, only touch password-type fields here. Don't interfere with changes to any other config fields, those should pass through however the user set them.
