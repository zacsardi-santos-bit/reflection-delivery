I'm digging into the attribute path resolver in the workflow engine and hitting a real annoyance. When a task's output is a binary-encoded dataclass and a downstream task reaches into a specific field of that output through a promise, the resolver is handing back the leaf value still wrapped in a binary blob instead of a properly typed primitive. So if the resolved field is an int or a float or a bool, I want it coming back as a typed primitive literal the runtime understands natively, not re-encoded into binary again. Right now downstream consumers have to know the encoding and decode it manually, which totally breaks type-safe data flow, and honestly this should just match what Python dataclasses naturally produce when they carry specific integer-typed fields.

The problem is the resolver only handles a narrow slice of numeric types today. I need it extended to cover all the common integer widths, signed (the various sizes) and unsigned (the various sizes) too. For unsigned integers that are too big to fit safely in a signed 64-bit value, don't silently overflow, return a clear descriptive error instead. For every other in-range integer type, float types (both single and double precision), strings, and booleans, return the appropriate typed primitive literal. Unsupported types should also produce a clear error, not a wrong result.

Oh and I also want a new named error code for the case where a value just can't be converted to a valid primitive type. That error code string needs to actually show up in the returned error so callers can identify the failure reason (the too-large unsigned case and the unsupported-type case both fall under this). Wire it through the traversal logic so the leaf resolution path produces these typed literals when walking a binary-encoded dataclass output.
