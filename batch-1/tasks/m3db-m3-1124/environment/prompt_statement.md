I'm building out a time-series query service and I keep running into this problem where someone fires off a query with a year-long window and a one-second step, and the engine happily tries to compute millions of datapoints. It kills performance and can straight up exhaust resources, so a single badly scoped (or malicious) query can take the whole thing down. I want a configurable guard against this.

What I'm after is a config option on the query service that sets the maximum number of computed datapoints allowed per query. The datapoint count is the query time range divided by the step size, so if that works out to more than the configured max, I want the request rejected right away with an HTTP 400 and a structured error response that spells out the time range, the step size, the limit that was hit, and some actionable suggestions on how to fix it, like narrowing the time window, bumping up the step size, or raising the configured limit. Oh and if the limit is set to zero or anything negative, enforcement should just be off entirely so operators can opt out cleanly.

Also I need the query handler constructor updated to accept this limits config so it actually gets wired through. And drop a sample config file somewhere in the config directory that shows a working value for this setting, and make sure whatever example config files already live in that directory still load and validate fine without breaking anything.
