I'm on Radius's dynamic resource provider, the piece that lets folks register custom resource types with their own JSON schemas and then deploy resources of those types. Problem is the schema is basically decorative right now, we store it when someone registers a resource type but we never actually check anything against it at deploy time. So a user can submit a resource that's missing a required field or has a value of the wrong type and the platform just accepts it silently, which kind of defeats the whole point of letting people define a schema.

I want to wire schema validation into the deployment pipeline. When someone submits a dynamic resource for creation or update, we should look up the schema registered for that resource type and API version, then validate the submitted properties against it. If the properties break the schema (required field absent, wrong data type, that sort of thing) the deployment needs to fail with a clear, descriptive error that says what went wrong. If there's no schema registered for the type, just proceed normally, graceful degradation, don't block anything. And this only applies to create/update, delete operations shouldn't be touched at all.

Oh and the important bit, the validation outcome has to surface properly through the async operation result so the user actually sees a meaningful failure status, with an error code and message that identifies it as a schema validation failure rather than some generic error. Right now these schema definitions are documentation-only and devs expect registering a schema will enforce structure on what gets deployed, otherwise invalid resources sneak in and cause hard-to-debug runtime failures downstream. Closing this gap makes the extensibility story actually reliable for operators.
