I've got a Go repo with a few internal style tools and I want to move them off their homegrown test harnesses onto the standard Go test runner. Right now each tool embeds its own hand-rolled test-runner logic inside the main script, triggered by a special command-line argument, which means I can't verify the tools with the same `go test` command I use everywhere else, and it's annoying to maintain and doesn't fit the normal workflow at all. So I want each tool's core logic exposed as exported functions in its package, each tool declared as a proper standalone module with its own go.mod, and a Go workspace file (go.work) at the repo root tying all the tool modules together with the main module so one test command covers everything. Rip out the old embedded test runners and replace them with conventional test files that call the exported functions.

For the method-receiver formatter (the one that renames method receiver variables to a standard name), I want exported functions to check whether a file path is a regular non-test Go file, to process a single line of source and rename its receiver to the standard name, and to process whole file contents at once. For the unit-test formatter, exported functions to check whether a path is a Go test file, to detect whether a line is a top-level subtest invocation, and to reformat file contents so there's a blank line before each top-level subtest.

For the struct-sorting linter, make the core lint function exported and have it return a type whose string form reports each violation as a file location plus the struct name plus the expected sorted field order. Empty structs and certain exempt struct names should still produce no violations, and it needs to check both struct type definitions and composite literal instantiations. Oh and the receiver formatter and the sorter both need to keep handling the same input categories (empty structs, exempt names, already-sorted or already-formatted content) with the same outcomes as before.
