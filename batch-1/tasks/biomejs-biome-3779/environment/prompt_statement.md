I'm adding a new CSS lint rule to catch a subtle mistake that bites people all the time: you declare a CSS custom property somewhere in scope, then reference it directly as a value instead of wrapping it in the accessor function (var(...)). The browser just silently ignores it, no error, styling quietly breaks, and it's miserable to debug. I want a rule that flags a bare custom property reference only when that property is actually declared somewhere reachable from where it's used, so same block, an ancestor selector, or globally registered via a property registration. If the property was never declared anywhere in the document, leave it alone since it might be an intentional custom identifier for some specific CSS feature. Don't flag things already correctly wrapped, and don't flag bare custom names inside properties where they're semantically valid, like transition and transition-related ones, animation, grid (grid area), counter, and view transition related properties. Nesting matters too: a property declared in a parent block is accessible in child blocks and should get flagged there if unwrapped, but a property declared only in a child is not visible to the parent, so don't flag upward.

Oh and separately, the existing rule that detects dependencies imported in JS/TS source but missing from the package manifest needs to move out of the experimental/nursery category into the stable correctness group. Right now if you reference it under the correctness group in config you hit a configuration error, and I want that to just work so teams can put it in production configs. New rule lives in the CSS lint rules area alongside the other stable correctness rules, wired into the registry the same way.
