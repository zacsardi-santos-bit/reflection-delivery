We're refactoring the email analytics service in our Ghost setup and I hit a real wall with how email events get pulled from the mail provider. Right now there's one method that grabs all event types in a single batch, but opens fire way more often than delivery confirmations, failures, unsubscribes, and complaints, so bundling everything means we can't poll different types at different rates. I want to split that into two independently callable methods, one that fetches only "opened" events and another that fetches everything else (delivered, failed, unsubscribed, and complained), each passing the right event type filter down to the mail provider, and each bailing out early if the computed end timestamp lands before the begin timestamp (just skip the fetch in that case).

Also I need a status method that returns the current running state of all four analytics jobs, each entry giving the job name and whether it's currently running, names need to be correct. Oh and I want methods to schedule a fetch over a specific time range, cancel it (a scheduled fetch should support cancellation and handle empty result sets gracefully), and separately fetch events that were missed in the last run.

The batch processing logic needs to route every event type to the appropriate handler on the event processor and increment the matching counts in the result, so permanent failures, temporary failures, unsubscribes, and complaints all get handled alongside opens and deliveries. When a handler returns null the event's counted as unprocessable, and events with unknown types get counted as unhandled.

Btw there's a naming inconsistency in the queries module too, the method for retrieving the last event timestamp needs renaming so it matches what the service now expects. And the mail provider's event fetching method needs to accept an explicit list of event types as an option so callers control exactly which types come back.
