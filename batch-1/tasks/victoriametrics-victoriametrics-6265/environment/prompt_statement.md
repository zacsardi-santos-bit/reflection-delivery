I'm poking at our statsd protocol parser and there's a gap that's been biting us. Right now when we parse a statsd line, the metric type field (counter, gauge, histogram, timer, whatever) just gets dropped on the floor during parsing, so once the data's ingested there's no way to tell what kind of aggregation should apply to each metric. I want the parser to actually capture that type and stick it on each parsed metric as a special label using a reserved internal key for the metric type, and it needs to be the first label on the metric, before any of the user-defined tags. That way downstream streaming aggregation can target by type, like "last" for gauges vs "sum" for counters.

Also the type field should be required now. Currently we happily accept lines with no type at all, and I want those rejected as a parse error instead of silently passing through, since that's basically silent data corruption waiting to happen.

Oh and some statsd clients pack multiple numeric values into one line separated by colons as a batch thing. Right now we only grab the first value, so those packed lines parse wrong. I want all the colon-separated values captured and stored individually, and if any one of them isn't a valid number the whole line should fail to parse cleanly. Extended protocol fields too, stuff like container identifiers or timestamp suffixes tacked on the line, should just be recognized and silently ignored rather than tripping anything up.
