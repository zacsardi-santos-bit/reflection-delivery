I'm digging into the distributed table engine's query optimizer, specifically how it handles primary key lookups, and I keep hitting a gap around OR conditions. Right now the extractor can pull primary key values from a simple equality or an IN-list just fine, but the moment the same pk column shows up on both sides of an OR (like `pk = 10 OR pk = 20`) it just gives up and scans everything, which totally defeats the point of our zone map and bloom filter indexes.

What I want is for the primary key expression extractor to recognize OR combinations where every branch ultimately refers to the same primary key column, and collect all the candidate values into one unified set (so `pk = 10 OR pk = 20` yields {10, 20}). This has to work recursively through nested OR/AND combos, as long as every branch of an OR bottoms out in the primary key, the combined candidates come through. But if any branch of an OR touches a non-primary-key column, the whole thing should fall back to "cannot determine candidates" rather than returning something wrong.

Related, I also need a helper that takes a list of primary key expressions (a mix of scalar values and in-vector expressions) and evaluates them all into a single sorted vector of candidate values, so downstream zone map and bloom filter checks can skip irrelevant blocks.

Oh and one more thing while I'm in here: the function that iterates over blocks within a set of object statistics currently only hands block metadata to its callback. I want it to also pass the corresponding block-level object metadata so the callback can do extra filtering without having to look it up separately.
