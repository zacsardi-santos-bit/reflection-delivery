I'm building out select input widgets that can optionally show a button to remove or clear the current selection, and I need a couple of helpers to make this sane. The button type depends on the mode: multi-select needs a per-item remove button so users can deselect individual items, single-select needs a full-clear button that resets the whole selection. So I want a helper that takes an existing options dict (which a developer may have already partially filled with their own plugin and config entries) plus flags for whether the remove/clear button is requested and whether the select allows multiple values, and it returns the updated dict with the right button plugin appended to the plugin list. The catch is it can't step on anything the developer already set. If the requested plugin's already in the list, don't add a duplicate, and every other key and pre-existing plugin has to be preserved untouched. Right now there's no standardized way to do this, so anyone wanting the button behavior plus their own custom config ends up writing fragile ad-hoc logic.

Also I need a way to embed JavaScript expressions inside these nested options dicts. So there should be a wrapper type that marks a string value as an actual JS expression rather than a literal string. And then a utility that recursively walks a nested options dict and returns a flat list of dot-notation paths to every key whose value is one of those JS expressions. The config can be deeply nested, so a value two levels deep should come back as something like "parentKey.childKey". Plain string values and the intermediate sub-dicts themselves shouldn't show up in that list, only the keys whose values are genuinely JS expressions. This matters because the framework needs to know exactly which nested keys hold JavaScript so it can serialize them correctly to the browser instead of treating them as plain strings.
