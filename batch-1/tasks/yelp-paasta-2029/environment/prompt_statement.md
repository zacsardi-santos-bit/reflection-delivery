I'm working on generalizing the autoscaling boost module in PaaSTA. Right now, every function that reads or writes a boost configuration internally derives a Zookeeper storage path from a region and a pool — the caller has no control over the path. This coupling means the boost module can only be used for cluster-level autoscaling, and we can't reuse it for service-level autoscaling or any other context where the path would be different.

I'd like to refactor the module so that the core boost functions accept a pre-computed Zookeeper path directly as their first argument, instead of deriving it themselves from region and pool. There should still be a helper function to build the cluster-specific path from region and pool, but callers in other contexts should be able to pass any path they want. The module file itself should also be renamed to reflect this broader purpose.

On top of that, the cluster boost command-line tool has its business logic and argument parsing mixed together inside a single function. I'd like to split those apart: the main business logic function should accept explicit named parameters and return a boolean, while a separate entry point handles argument parsing, logging setup, and process exit codes. For the cluster context specifically, the set action should pass a flag to indicate that external metrics reporting should be triggered, since that's cluster-specific behavior that shouldn't apply to other callers of the boost API.
