I'm working on generalizing the autoscaling boost module in PaaSTA and I keep hitting the same wall. Right now every function that reads or writes a boost config internally derives its Zookeeper storage path from a region and a pool, so the caller has zero control over where things get stored. That coupling means the module only works for cluster-level autoscaling, and I can't reuse it for service-level autoscaling or any other context where the path would differ.

What I want is to refactor so the core read/write boost functions accept a pre-computed Zookeeper path directly as their first argument instead of building it themselves from region and pool. I still want a helper that constructs the cluster-specific path from a region and pool (keep that around), but callers elsewhere should be able to pass any path they like. Oh and the module file itself should be renamed to reflect this broader, general-purpose use rather than being cluster-only.

Separately, the cluster boost CLI tool mashes argument parsing and business logic into one function, which makes the core behavior hard to call programmatically or test without going through the CLI. I want those split apart: the main business logic function should take explicit named parameters and return a boolean, while a separate entry point handles the argument parsing, logging setup, and process exit codes. For the cluster context specifically, when the set action runs it should pass a flag opting into external metrics reporting, since that's cluster-specific side-effect behavior that shouldn't fire for other callers of the boost API.

The point is decoupling path construction from boost state management so the mechanism can be reused across different autoscaling targets without duplication, and making the CLI's core function independently callable, unit-testable, and composable.
