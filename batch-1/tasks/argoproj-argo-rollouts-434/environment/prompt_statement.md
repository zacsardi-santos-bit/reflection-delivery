I'm working on the argo-rollouts controller and I want to fix how failure info surfaces when an analysis run aborts a rollout. Right now if a rollout gets aborted because some analysis metric blew past its failure limit, its inconclusive limit, or its consecutive error limit, the rollout status just says it was aborted with zero detail about which metric failed or why. Operators have to go dig into the underlying analysis run objects to figure out what happened, which is painful during an incident.

What I want is for the system to build a descriptive human-readable message for each metric assessment that spells out exactly what threshold was crossed, like how many failures happened versus the allowed failure limit, or how many consecutive errors exceeded the configured limit. That message should get stored on the analysis run status when the run completes, and when a rollout gets aborted as a result, propagate that same message into the rollout's own status condition so it's visible right away without inspecting child resources.

Oh and there's a related utility I need too, a function to grab the consecutive error limit for a given metric, falling back to a default of 4 when none is configured. That default 4 shouldn't live only inside the analysis logic, please centralize it in a shared utility so other code can reference it beyond just the analysis package.

Couple edge cases: when multiple metrics fail at once, use the message from the first worst-status metric encountered, don't merge them all. And if the provider attached its own error message onto the metric result, append that to the failure reason in the rollout condition message too so we don't lose provider context.

The goal here is self-describing rollout failures so on-call can understand why a rollout was halted at a glance instead of chasing down child resources.
