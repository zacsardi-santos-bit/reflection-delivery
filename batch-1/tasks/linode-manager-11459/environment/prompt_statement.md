I'm cleaning up the Profile Settings page in the Linode Manager because right now it's one giant monolithic component that handles theme selection, email notifications, sensitive data masking, and type-to-confirm all together, which makes it a pain to maintain, test, and reason about each setting on its own. I want to split these into four separate self-contained components, each living in the Profile Settings folder and each responsible for its own data fetching and rendering.

Each one should render a heading for its setting plus a control (a checkbox or radio buttons) that reflects the current preference coming from the backend. So the mask sensitive data component reads its own preference, shows the toggle state, and displays descriptive text saying whether data is currently masked or visible. The email notifications component reads its own profile data, shows the toggle state, and shows text indicating whether email alerts are enabled or disabled. The theme component reads the stored theme preference and reflects which theme is selected (System, Light, or Dark), defaulting to System when nothing's stored. And the type-to-confirm component reads its own preference, shows the toggle state defaulting to enabled when no preference has been set yet, and displays text for the current state.

Also, the preference-fetching hook should support passing a selector so it returns just the specific value a component needs instead of always handing back the whole preferences object and making callers destructure it. So wherever the full preferences object is getting passed around just so a component can pluck one field out of it, I want those usages updated so only the specific value gets passed or selected, not the whole thing. That applies to both the sensitive data masking component and the sort order preference used in the list components. Point is to decouple each section from the full preferences data shape so changes in one setting don't accidentally break another.
