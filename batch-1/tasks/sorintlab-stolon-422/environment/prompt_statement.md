I'm working on improving the reliability of integration tests for a distributed PostgreSQL high-availability system. Right now, the tests use fixed time delays to wait for replica instances to catch up with the primary before checking synchronization — this leads to flaky failures on slower systems and unnecessarily slow tests on fast ones.

I'd like to replace this with a proper, evidence-based approach. Specifically, I need the test infrastructure to support opening a dedicated replication protocol connection to each keeper and proxy (in addition to the existing regular SQL connection), so that replication-level commands can be issued directly. Using that connection, I need a helper that can query the primary's current write-ahead log position directly. Then, the function that waits for all keepers to be synchronized should accept the actual keeper objects along with that known minimum log position, verify that each keeper has reached or exceeded it, and return an error if this doesn't happen within the timeout — rather than returning nothing.

The call sites in the tests should be updated to first fetch the current log position from the primary, then pass both the keepers and that position to the synchronization wait function, eliminating the old fixed sleeps entirely.
