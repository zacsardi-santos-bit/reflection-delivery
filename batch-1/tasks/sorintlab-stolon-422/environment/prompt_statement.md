I'm cleaning up our stolon-style Postgres HA integration tests because they lean on fixed sleeps (think a flat 5 second wait) before checking whether replicas have caught up to the primary, and it's driving me nuts, flaky on slow or loaded machines and pointlessly slow on fast ones. I want to swap all that for evidence-based polling against the actual write-ahead log position.

First thing, the test harness needs to be able to open a dedicated replication protocol connection to any keeper or proxy, alongside the regular SQL connection it already uses, so we can issue replication-level commands directly over that channel. On top of that I need a helper that queries the primary's current WAL position directly through the replication protocol, that gives us a real known lower bound to check against.

Then the function that waits for all keepers to be synchronized should change, right now it just compares whether every keeper reports the same position and returns nothing. Instead I want it to take the actual keeper objects (not just string ids) plus that known minimum log position, confirm each keeper has reached or exceeded it, and return an error if that doesn't happen inside the timeout.

Also the call sites in the tests need updating so they first read the primary's current log position, then pass both the keepers and that position into the sync-wait function, and drop the old sleeps entirely. Net effect: tests pass the moment sync is actually confirmed and fail fast with a clear error otherwise, instead of hoping an arbitrary delay was long enough.
