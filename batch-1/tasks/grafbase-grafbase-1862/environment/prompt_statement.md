I'm deep in the partial caching feature of our GraphQL gateway and I keep hitting a wall with type conditions. Whenever a schema has a union type or an interface and a query uses inline or named fragments to request different fields per concrete type, the partial caching just doesn't merge right. The core issue is the cache merging step has no idea what the concrete type of each returned object is, so it can't figure out which type-specific cached fields to apply to which items in a list. So you end up with incorrect or incomplete responses, which basically forces people to turn off partial caching any time their schema touches unions or interfaces, and those are super common patterns, so that kills a lot of the feature's value.

What I want is for the cache merge process to actually be aware of the concrete object type so it can look up the right shape to apply for each returned item. And on the other side, when the caching layer generates its own sub-queries to fetch cached fields, it needs to include type metadata in the selection sets (think a typename lookup) so it can later work out which concrete type each returned item belongs to. That metadata should get added automatically whenever a selection set contains type-condition fragments, inline or named, don't make me wire it up by hand.

This needs to hold across all the variants: union types with inline fragments, union types with named fragments, interface types with inline fragments, interface types with named fragments, and oh, all of those combined with deferred loading too since that's where things tend to fall apart. Basically any schema using unions or interfaces should be fully compatible with partial field-level caching and produce correct, complete responses.
