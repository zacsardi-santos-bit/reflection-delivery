I'm hacking on the exhaustive-dependencies lint rule (the one that checks React hooks declare all their deps correctly) and I want to add auto-fix support. Right now the rule catches two situations, a dependency array that's missing values that get used inside the hook, and a dependency array that carries extra or duplicate entries, but all it does is report, so devs have to go hand-edit every flagged array which is miserable in a big codebase.

What I want is for both cases to offer an unsafe auto-fix suggestion. When deps are missing, the fix should insert the missing entries into the array. When there are unnecessary or duplicate ones, the fix should remove them. Both are unsafe fixes since we can't fully guarantee semantics, and the diagnostics need to be marked fixable so tooling knows a fix exists. Oh and the diagnostic header for the rule should say an auto-fix is available.

There's also a related panic I keep hitting. When the rule's fix-validation logic runs against source that already has syntax errors, it blows up because it expects the modified code to be valid even though the original was already malformed, so it treats the modified output as the problem. Instead it should skip the bogus-node check and the re-parse validation whenever the original source was already invalid, rather than pointing the finger at the fix. That also stops false failures on test files that deliberately contain broken syntax.
