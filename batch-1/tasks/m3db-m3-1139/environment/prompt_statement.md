I'm poking at the M3DB commit log and hit a real gap. Right now it only rotates the underlying file automatically when we cross a configured block duration boundary, so there's no way for a caller to force a rotation at an arbitrary moment. That's a problem because operations like snapshotting or flushing need everything written up to a certain point to be sealed into a completed, rotated file, and time-based rotation alone can't guarantee that data locality relative to some external operation.

What I want is a new method on the commit log that explicitly forces a rotation of the current log file right when it's called. When it rotates it should hand back metadata about the resulting file, specifically its start time, the duration it covers, its index, and the file path. Return those so callers can precisely bound the data they need to recover later.

Couple of things it has to get right: the rotation needs to be safe to call while writes are happening concurrently in other goroutines, so no races or corruption there. Anything written before a rotation call must be preserved and stay readable after the log is closed, don't lose it. And if someone calls this on an already-closed commit log it should return an appropriate closed error instead of panicking or silently doing nothing.
