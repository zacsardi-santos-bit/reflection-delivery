I'm adding a relation loading strategy option to the Prisma query engine and could use your help wiring it up. Right now when a query pulls in nested relations there's no way to say whether those related records get fetched via SQL joins or through separate follow-up queries, and I want a new optional argument on the top-level operations so developers can pick whichever suits their database and workload.

The argument should take two values, one that loads related data using lateral joins (only valid on databases that support them like PostgreSQL and CockroachDB) and one that uses separate queries and works on every supported database. Both strategies have to return identical data, it's purely an execution choice, not a difference in the shape or content of the result.

I only want this accepted at the top level of a query or mutation, so it applies to the read operations (find many, find first, find unique, and their "or throw" variants) and the single-record writes (create, update, delete, upsert). It must not be accepted on nested relation fields, aggregation queries, group-by queries, or the bulk mutations (batch create, update, delete), and any attempt to use it in those spots should come back as a validation error.

Oh and the query validation layer needs to know about this new argument too, so that when it reports an unknown-argument error it correctly includes this one in the list of valid alternatives it suggests. The motivation here is that some databases can load related data in a single round-trip more efficiently, so exposing this lets performance-conscious folks grab join-based loading where it's supported while keeping a portable fallback everywhere else.
