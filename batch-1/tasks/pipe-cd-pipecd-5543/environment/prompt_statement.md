I'm working on our deployment platform and hitting a real limitation with how we update deploy targets for an application. Right now the update path just takes a flat list of target names, which was fine back when everything was single-plugin, but we've got multiple deployment plugins now and there's no way to say which targets belong to which plugin. It's ambiguous and it doesn't map to how real multi-plugin deployments actually work.

What I want is to change the data model so deploy targets are organized per plugin. Instead of a plain list of strings, callers should pass a map keyed by plugin name where each value is that plugin's list of deploy targets. That way each plugin manages its own set of targets independently.

This needs to be consistent everywhere the current flat list flows through. So the core datastore interface that handles updating an application's deploy targets, plus any local interface wrappers up in the API layer, and the mock implementations we use for testing all need to move to the new plugin-keyed map type. The test mock in particular needs its method signature updated to the new map type so it compiles and matches. And the gRPC API server layer has to accept the new plugin-keyed format when it processes deploy target update requests. Basically anywhere the old `[]string` (or equivalent) shape shows up for deploy targets, swap it to the map from plugin name to list of targets so the structure's expressive enough to represent what we actually deploy.
