I'm working on the Postgres operator for Kubernetes and I want to add optional owner references so Kubernetes itself can handle cascading deletion of the child resources we create for a Postgres cluster. Right now when a cluster's custom resource is deleted, cleanup depends entirely on our own delete logic, so if the operator is broken or the cluster never fully synced (initial creation failed, say), stuff gets orphaned and needs manual cleanup. Also monitoring and GitOps tools can't navigate native ownership graphs today, so they can't tell which child belongs to which cluster.

What I want is a config toggle, disabled by default, that when enabled sets native Kubernetes ownership on all the eligible children (services, endpoints, the stateful set, pod disruption budgets, secrets, and the logical backup job). When it's off, behave exactly like today. The owner reference should point from each child back to the Postgres custom resource itself, not the stateful set or any intermediate object, and it should be set as owner/controller.

It's gotta work dynamically too, so if I flip the toggle on or off the operator picks it up on the next sync, meaning during sync it needs to detect when a child's ownership metadata doesn't match desired state and update it. That means the resource comparison logic (current vs desired for services, pod disruption budgets, and the other compared resources) needs updating so a difference in owner references counts as a mismatch that triggers an update.

A few exceptions must never get owner references: persistent volume claims (the stateful set's reclaim policy handles those), Patroni's internal config service and endpoint (Patroni manages them itself), and any secrets living in a different namespace than the cluster since cross-namespace owner references aren't allowed by Kubernetes. When the toggle's disabled or toggled off, children should carry no operator-set ownership pointing at the Postgres resource.
