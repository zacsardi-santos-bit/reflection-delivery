I'm working on the Postgres operator for Kubernetes and I'd like to add support for setting ownership relationships between a Postgres custom resource and all the child resources the operator creates for it — things like services, endpoints, the stateful set, pod disruption budgets, secrets, and the logical backup job.

Right now, when a Postgres cluster is deleted, cleanup depends entirely on the operator's own delete logic. If the cluster was never fully synced (e.g. failed during creation), some resources get orphaned. I'd like to add an optional configuration toggle that, when enabled, sets native Kubernetes owner references on these child resources so that Kubernetes itself handles cascading deletion. When the setting is disabled (the default), the operator should behave as it does today.

The ownership relationship should point from the child resources back to the Postgres custom resource itself — not to the stateful set or any intermediate object. When the operator syncs, it should detect if a child resource's ownership metadata doesn't match the desired state and update it. The toggle should also work dynamically: if you flip it on or off, the operator should update existing resources on the next sync.

There are a few resources that should be excluded from owner references: persistent volume claims (handled by the stateful set's reclaim policy), Patroni's internal configuration service and endpoint, and any secrets that live in a different namespace than the cluster (cross-namespace owner references aren't allowed by Kubernetes).

The resource comparison logic also needs to be updated so that differences in owner references are treated as a mismatch requiring an update — for services, pod disruption budgets, and other resources where the operator currently compares current vs. desired state.
