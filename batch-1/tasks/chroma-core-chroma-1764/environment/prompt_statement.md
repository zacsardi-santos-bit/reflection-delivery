I'm working on the log service inside our coordinator and I keep hitting two gaps that need fixing. Right now the service can only push records into a collection's log, there's no way to read them back out, which makes the whole thing write-only. I want a pull operation so consumers can retrieve stored records incrementally, starting from a given log position and returning up to some configurable max number of records per call. The starting position should be inclusive, so pulling from a specific position returns only records at or after that position up to the batch size limit, and passing 0 should mean start from the very beginning of the log. This needs to exist both at the database access layer and as a gRPC endpoint so callers can actually hit it.

Second thing, neither push nor pull validates the collection identifier before doing anything, so when someone passes in a malformed one the error that comes back is confusing and opaque and hard to debug. I want both operations to check the identifier upfront, and if it's invalid, immediately bail out with a clear error, an appropriate status code flagging that the argument is bad (invalid argument), plus a descriptive message that identifies the collection identifier specifically as the problem so it's obvious what went wrong at the service boundary.
