I'm on an Nx monorepo that bundles libs with rollup, and after bumping rollup to a newer major the Nx rollup plugin quit auto-inferring build targets from our rollup config files. Digging in, the plugin was reaching into an internal, unstable path inside the rollup package to grab a config-loading helper, and that internal path just doesn't exist anymore in the new version. The good news is rollup now ships the same functionality through an official public API path instead, so I want the plugin switched over to use that public API for loading rollup config files.

The whole point is restoring automatic build target discovery, so once it loads configs through the supported public API, Nx should again be able to detect and configure build targets for any project using rollup. It's gotta work whether the rollup config defines a single output or multiple outputs, and it needs to handle both root-level projects and nested (non-root) project configs correctly. Right now the plugin blows up trying to import that missing internal module, which means no inferred targets and teams have to hand-configure builds as a workaround, which defeats the reason we lean on Nx in the first place.

So basically, fix the import path the rollup plugin uses to load config files (public API, not the internal one), and confirm inference comes back for single-output configs, multi-output configs, and nested projects alike.
