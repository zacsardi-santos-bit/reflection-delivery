I'm working on dispatch rate limiting observability in Apache Pulsar and hitting a real gap. When the broker throttles message delivery to a subscription there's no way to tell from the stats whether that throttle came from a broker-level policy, a topic-level one, or a per-subscription policy. Operators who notice degraded delivery rates can't tell which policy tier is the bottleneck, so tuning becomes guesswork.

I want to add separate counters that track how many times dispatch got throttled at each of the three levels, and I need them split for both message count and byte count. These should show up in the subscription statistics returned by the admin API so each subscription independently reports whether it was throttled by subscription, topic, or broker limits. The key behavior I care about: when only one level of rate limiting is actually active, only that level's counters should be non-zero and the other two stay at zero. That's what lets someone immediately point at the responsible policy tier.

Oh and they also need to surface as Prometheus metrics, with a label identifying the level (broker, topic, or subscription) so monitoring and alerting systems can distinguish the three causes across time series. Without this there's basically no insight into which tier is constraining dispatch, so let's make that source obvious per subscription.
