I'm hitting a compatibility snag in the Cloud Foundry CLI around how we pull organizations and spaces by their GUIDs. Right now the functions that fetch orgs and spaces by their unique identifiers always shove those identifiers into a server-side filter query against the Cloud Controller API, and that's fine on modern deployments but older Cloud Controller versions don't support that filter param at all, so when someone points the CLI at an older server it comes back with incorrect or unexpected results. Operators running against older deployments keep hitting these subtle bugs because we're assuming server capabilities that just aren't there.

What I want is for these functions to check the Cloud Controller API version at runtime and decide dynamically whether to filter server-side or client-side. If the server is new enough to support the identifier filter, use it, that's the efficient path. If it's too old, skip the filter entirely, fetch all the records with no filter, and then narrow things down locally so we only return the records whose identifiers match what was actually requested. Oh and one edge case, if the API version string coming back from the server is malformed or can't be parsed for whatever reason, don't blow up with an error, just safely default to the client-side filtering approach.

The important invariant across all of these paths is that the caller always gets back only the records matching the requested identifiers, doesn't matter whether the narrowing happened on the server or locally, the result set is the same. This all lives in the actions layer that wraps the Cloud Controller client, so that's where the version detection and branching logic should go.
