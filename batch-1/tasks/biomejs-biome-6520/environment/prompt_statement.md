I'm hitting a blind spot in the floating-promises lint rule over in the no-floating-promises logic. The rule's solid when a function returns a plain Promise, but it totally ignores cases where the return type is a conditional type alias. You know the TypeScript pattern where you write a type alias as a conditional, like "if some type condition holds the result is a Promise, otherwise it's something else"? When a function uses one of those aliases as its return type, calling it without awaiting, without chaining `.catch` or error handling, or without explicitly voiding it just slides through silently. No diagnostic at all, even though the thing might genuinely hand back a Promise you're floating.

The rule's treating these conditional type aliases as opaque and bailing out of Promise detection entirely, which is the bug. What I want is for it to look through the conditional and check both branches. If either the true branch or the false branch could be a Promise, treat the whole thing as potentially a Promise and flag the unhandled call. Basically handle a conditional type as a union of its two possible outcomes for detection purposes rather than giving up and calling it unresolvable.

This matters because people define helper types with conditional logic all the time, and if we don't resolve through them we miss real floating-promise bugs and hand devs false confidence that the rule caught everything. So: when the return type resolves to a conditional alias with at least one Promise branch, and the call result isn't awaited, error-handled, or discarded, it should get reported like any other floating promise.
