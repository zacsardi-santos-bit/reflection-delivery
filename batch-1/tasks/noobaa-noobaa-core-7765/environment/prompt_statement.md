I'm hitting a gap in the NooBaa NC NSFS health check around account validation. Some of our accounts are identified by an OS username instead of explicit numeric user and group IDs, and the filesystem access validation just doesn't understand that kind of identity right now. So when the health check runs it can't tell whether a username-based account actually exists on the box or whether that user has read-write access to their configured storage path, which means these accounts get silently skipped or mishandled and misconfigured setups slip through unreported. Operators lean on this check to catch bad accounts before they blow up at runtime, so that's the whole point of fixing it.

Two things I need. First, the directory accessibility check has to work for both username-based and numeric-ID-based identities, resolving the OS username to the real uid/gid when needed, then correctly evaluating standard unix permission bits (owner, group, other) to decide if the directory is both readable and writable. Second, for username-based accounts the check should surface two distinct error conditions, one where the OS user exists but can't access the configured path (an access-denied error), and a separate "invalid distinguished name" error code for when the username doesn't map to any user on the system at all.

Oh and I also want cross-platform test utility helpers to create and delete OS users so these scenarios can actually be exercised on both Linux and macOS.
