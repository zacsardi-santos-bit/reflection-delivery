I'm hitting a wall with CDI data volumes on storage classes that defer volume binding until a consumer gets scheduled, which is super common on cloud providers. When that deferred-binding mode is turned on via the feature gate, any DataVolume I create just stalls out. The PVC never binds so nothing imports, uploads, or clones, it just sits there forever. There's no escape hatch right now to say "yeah I know this storage class waits for a consumer, but bind this one immediately anyway."

What I want is a per-DataVolume annotation that signals an immediate binding request. When that annotation is present on a DataVolume, the import controller should treat it as eligible for reconciliation and go ahead and proceed even if the deferred-binding feature gate is active. When the annotation is absent and the gate is on, keep the existing skip behavior for unbound volumes, don't change that.

This needs to cover all the data volume types, so HTTP imports, blank image creation, uploads, and clones all respect the same annotation. The per-DataVolume override should win over the global feature gate setting so I can selectively force immediate binding on specific volumes without touching the global config. And the annotated ones should actually reach their terminal state, completed for imports and clones, ready-for-upload for upload volumes. Without this people are just blocked from using CDI on any storage class that defaults to deferred binding, even when they explicitly want the volume populated right away.
