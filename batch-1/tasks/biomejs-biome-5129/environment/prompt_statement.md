I'm working on Biome and want to add a new nursery lint rule that catches a really common async footgun where people await promises inside loops. The issue is each iteration ends up waiting on the previous one so you get accidental sequential execution instead of parallel work, which tanks performance when it didn't need to. So I want a rule that warns whenever an await expression shows up in a loop body or condition, and that covers while loops, for-of, for-in, plain old regular for loops, and do-while loops too. On top of that it should warn when a for-await-of statement is nested inside another synchronous loop. The diagnostic should nudge people toward concurrent promise resolution as the alternative instead of the serial version.

The tricky part is scoping, it's gotta be smart about what counts as being "in" the loop. Don't flag awaits that live inside a nested function declaration, function expression, arrow function, or class method defined within the loop body, since those spin up their own async context and the await there is fine. Also don't flag awaits sitting in the iterable position of a for-of, for-in, or for-await-of loop, nor in the initialization part of a regular for loop, and don't flag an await directly in the body of a for-await-of loop at the top level since that async iteration is the whole point. But here's the catch, if a for-await-of loop contains an inner synchronous loop, awaits inside that inner loop should still get flagged. This should land in the nursery category and slot in like the other rules there so it can catch this class of bug early before it silently degrades perf.
