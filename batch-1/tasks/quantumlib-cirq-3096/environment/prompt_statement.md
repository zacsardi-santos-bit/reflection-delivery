I'm hitting a gap in Cirq around unitary protocols on operator sum types. When I build a linear combination of gates in `@cirq/ops/linear_combinations.py` that happens to be mathematically unitary, I can't ask the library whether it's unitary or pull out the matrix. I want `cirq.has_unitary` and `cirq.unitary` to work on these, so a unitary combination reports True and hands back the right matrix, and a non-unitary one (say it's got non-unit scaling on the terms, or it's parameterized) reports False and raises the appropriate error when I try to extract the matrix anyway. Same deal for linear combinations of operations, they should behave identically under the same protocol. And sums of Pauli operators (PauliSum) should participate too, checking unitarity and returning the correct unitary when it exists, or erroring out cleanly when it doesn't.

Separately, PauliString matrix computation is too rigid. Right now it only computes over its own native qubits. I want to pass in a collection of qubits in a specific order and get the matrix over exactly those, where any qubit I list that isn't actually in the string just acts as identity on that factor. Oh and the coefficient of the Pauli string needs to be baked into the result. This makes it way easier to embed a Pauli string into a bigger multi-qubit space or line it up against other operators when the qubit ordering matters. All of this so I can uniformly use the standard unitary-checking and extraction interface across gate combos, operation combos, and Pauli sums, plus have flexibility placing Pauli strings into specific subspaces.
