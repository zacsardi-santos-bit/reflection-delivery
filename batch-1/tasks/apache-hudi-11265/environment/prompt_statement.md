I'm hitting a wall ingesting JSON into an Apache Hudi table whose schema leans on the standard Avro logical types, decimal with precision and scale, calendar date, time of day, UTC timestamp, local timestamp without a zone, fixed-size duration, and UUID. Right now the JSON-to-Avro converter either throws something unhelpful or, worse, silently writes wrong Avro data, so there's basically no reliable path to load this data, and these column types show up in real-world schemas all the time.

What I want is for the converter to properly handle all of these. Decimal fields should take human-readable string numbers or plain numeric values and produce the correct Avro bytes or fixed representation, and anything that busts the schema's precision or scale should get rejected with a clear error instead of truncated. Date fields should accept ISO date strings like "2020-09-01", epoch-day integers, or their string equivalents. Time fields at both millisecond and microsecond precision should take numeric epoch offsets or "HH:MM:SS[.fractional]" strings. Timestamp fields (UTC, both milli and micro) should accept ISO-8601 datetime strings carrying a 'Z' marker or numeric epoch values, while local-timestamp fields want ISO-8601 local datetime strings with no zone component (a timezone marker on a local field should fail) or numeric epochs. Duration fields expect a three-element list of ints for months, days, and milliseconds, and a list with the wrong count should fail cleanly. UUID just passes the string through as-is.

Oh and across all of these, inputs that don't conform, wrong format, out-of-range, schema misconfig, should raise a specific named exception type (not some generic runtime thing) so callers can catch conversion failures explicitly.
