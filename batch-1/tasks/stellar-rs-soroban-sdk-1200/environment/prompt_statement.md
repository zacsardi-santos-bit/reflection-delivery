I'm hitting a spec generation bug in the Soroban SDK and could use a hand. When I write a contract function that takes a `Duration` or `Timepoint` value as a parameter, the auto-generated contract spec doesn't classify those types right. Instead of emitting the proper built-in duration or timepoint entries in the XDR spec, the contract macro falls back to treating them as unknown user-defined (opaque) types, like it doesn't recognize them as first-class built-ins. The contract still runs fine at runtime, values pass through and everything, it's purely that the machine-readable spec that gets generated is wrong.

The problem is any tooling that reads that XDR spec (client codegen, docs, interop stuff) leans on accurate type info, so if duration and timepoint show up as opaque user types the downstream consumers can't understand the interface, which means broken integrations and bad client-side type handling.

What I want is for the contract macro system to properly recognize both the built-in duration and timepoint value types when it generates the spec. So when a function accepts a duration param, the generated spec reflects the correct built-in duration type, and same for timepoint, correct built-in timepoint type, no more falling back to the opaque user-defined case. And to be clear I still need contracts with duration or timepoint params to be executable at runtime with the values correctly passed through, so don't break the actual calling path while fixing the spec side. Basically both of those types need to land as their proper built-in type definitions in the contract's XDR specification.
