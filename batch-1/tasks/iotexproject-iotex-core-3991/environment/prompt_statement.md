I'm poking at the IoTeX account nonce logic and hit a real annoyance with legacy accounts. When an account was created under the old protocol and has only ever received funds, never sent anything, the system reports its pending nonce as 1 instead of 0. That's because legacy accounts add 1 to the stored nonce, so stored 0 becomes pending 1. But the newer zero-nonce account type starts a fresh account at pending nonce 0, so these two schemes disagree and it's hard to tell whether a "fresh" account is legacy or new, plus once the protocol upgrade kicks in these legacy fresh accounts need to send their first tx with nonce 0, not 1.

So I want to teach the account type a few new tricks. First, a way to tell if an account is "legacy fresh", meaning it's legacy type with a stored nonce of zero (received but never sent). Second, a way to read the nonce for such an account as if it were the new zero-nonce type, so it returns 0 rather than 1. Third, a method to actually convert such an account to the new zero-nonce type, which should only succeed when it's called with the adjusted nonce value of 0, and it should return whether the conversion actually happened.

Once those account-level primitives exist, the block processing path needs to use them so legacy fresh accounts get auto-upgraded to the new type when a block commits at or beyond the protocol upgrade height, and this has to apply consistently whether chain state is held in memory or persisted to disk (otherwise nodes diverge and txs get rejected). Oh and the gas price validation in the action pool needs updating too so it accounts for the new nonce semantics when the feature's active.

End goal: a legacy fresh account, after the upgrade height, behaves exactly like a brand-new account. It can send its first transaction with nonce 0 and its state stays consistent in memory and on disk.
